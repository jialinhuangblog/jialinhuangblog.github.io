我一直在說『Rust 比較快』，後來我真的坐下來量了

frontendrustbenchmarkperformancev8

我寫過一整篇，講 JavaScript 的 build 工具怎麼一層一層被 Rust 重寫。SWC 換掉 Babel，Turbopack 換掉 Webpack，整個過程我都梳理過了。但裡面有一句我只是照著講，沒有自己弄懂：Rust 比較快。

快在哪？快多少？我不知道，也從沒認真想過它到底是什麼意思。

所以我坐下來寫了一套 benchmark。我先把預期寫下來，再跑。五個預測裡，兩個當場成立，一個要換量測方法，一個我一開始讀錯，一個機制猜錯。

「Rust 比較快」不是一個數字

七種情況量下來，Rust 對 Node 從一樣快到快 37 倍都有。

一千萬個浮點數相加，Node 9.556ms、Rust 9.553ms，幾乎一樣。這種加總每一步都要用到上一步的結果（s = s + 這一筆），只能一個接一個做、沒辦法同時算，兩邊都卡在一次浮點加法的延遲上。

大量用完就丟的小物件，Node 的中位數反而比較快，因為 V8 的垃圾回收（generational GC）專門為這種情況設計。新物件都先放進一塊很快就整批清掉的區，所以配置一個物件，幾乎只是把指標往後移一個物件的大小。這個結果跟標題相反，我反而最相信它，因為我本來不希望它成立。

小陣列 Node 快，大陣列 Rust 快

同一段 code，只改陣列長度。

這迴圈對每個數字只做一個判斷：過了門檻就加進總和，沒過就跳過。

資料是亂數，所以那個 if 大約一半成立、一半不成立。而且為了讓不同長度能公平比，我把總工作量固定住：不管陣列多大，總共都讀取約兩億個元素，所以小陣列只是被重複走比較多遍而已。圖上畫的是每個元素的成本，不是總時間。

為什麼陣列變長，同一個元素就花更多時間呢？差別在 Node 跟 Rust 把那個 if 編譯成的機器碼不一樣。

Node 把它留成一個真的分支，執行到這裡有兩條路，加進去或跳過。CPU 不等比較結果出來，先猜一條往下執行（branch prediction）。猜對沒有額外成本；猜錯，剛剛先做的白做、要倒回重來。圖上 Node 每個元素從 0.9ns 升到 5ns 多，多出來的時間花在猜錯後重來。它猜的依據，是這個分支最近都往哪走。

Rust 這邊乾脆讓分支消失。 它的編譯器透過 LLVM，把「加了的」跟「沒加的」都先算出來，再用一個「二選一」的指令挑對的那個。這個指令在 ARM64 上叫 fcsel（我測的機器是 Apple M1 Pro）。代價是每次都多算一次加法、多占一個 register；沒有分支，CPU 就沒有東西要猜：

Node 那邊猜中的比例，跟陣列長度有關：

  • 小陣列：那串「加/跳」很短，被重複走很多遍 → 整串長度在分支預測器能記錄的範圍內 → 幾乎每次猜對 → 便宜。亂數不影響這件事：一串固定的短序列，就算看起來隨機，重複走幾遍，預測器就記錄到整串。
  • 大陣列：那串太長，超過分支預測器能記錄的長度 → 大約一半猜錯 → 每錯一次就要倒回重來 → 貴。

Rust 從不猜，所以不管陣列多大，每個元素的成本都一樣（圖上就是那條水平的線）。「Rust 在難猜的分支上比較快」這句話，只在陣列長到超過分支預測器能記錄的長度時成立。

那 20 到 70 倍到底哪來的

SWC 說它單執行緒比 Babel 快 20 倍、四核心快 70 倍。如果單執行緒的語言差只有三倍上下，剩下的是哪來的？

為了把「語言」跟「原生加新架構」分開，再拿 esbuild 對照。它是 Go 寫的，不是 Rust，但一樣編譯成原生執行檔、一樣是從頭設計的新工具。

esbuild 編譯要 26.3ms，SWC 要 19.6ms，同一個量級，都遠快過 Babel。所以那個大倍數用 Go 也能達成，不一定要 Rust。前面圖裡同演算法那組，一模一樣的樹走訪，JS 對原生只差 2.7 倍。這 2.7 倍來自有沒有編譯成原生，是語言本身佔的部分，只是一小部分。Babel 對 SWC 實測是 8 到 51 倍，看編譯目標是 ES2019 還是 ES5；扣掉那 2.7 倍，多出來的才是架構（Babel 的 visitor pattern、plugin pipeline、大量重建節點），跟哪個語言無關。

那個 70 倍裡的「四核心」也不是 Rust 的。同一份工作，八執行緒讓 Node 快 5.8 倍、Rust 快 6.3 倍，兩邊都能利用多核心。Node 跑的就是 JavaScript，跟 Babel 同一個語言，用內建的 worker threads 就能把工作分到每個核心。Babel 只用一個核心，是因為它沒實作這一塊。

20 到 70 倍拆開來看

  • 大概 3 倍：離開 JavaScript、換成原生執行檔。build 工具跑一次就結束，JIT 來不及暖機。
  • 最大因素，架構：Babel 每個 plugin 走訪一遍樹、一路重建節點，SWC 從頭設計。這一塊隨工作量放大：目標從 ES2019 換成 ES5，Babel 比自己原本慢了 27 倍，SWC 只慢 4.6 倍。
  • 約 3.5 倍，多核心（SWC 自己的 20 倍到 70 倍）：Babel 從來沒用，雖然 Node 有 worker threads 可以用。

原生執行檔、架構重寫、多核心，三個因子，沒有一個是 Rust 這個語言。Rust 是拿來做這些工具的好語言，只是它不是它們變快的原因。
