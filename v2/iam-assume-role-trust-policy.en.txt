14:T4d97,<p>You attach policies to IAM (Identity and Access Management) users. Policies define what actions are allowed on which resources. Simple.</p>
<p>Then <strong>assumeRole</strong> and <strong>trust policy</strong> show up, and the docs explain how to set them up before explaining why they exist.</p>
<p>A <strong>role</strong> is an IAM identity that holds permissions but has no password or permanent keys of its own. <code>sts:AssumeRole</code> is an API action in STS (Security Token Service). A service or user calls it to get temporary credentials for a role. <strong>Trust policy</strong> is the policy attached to that role that controls who is allowed to call <code>sts:AssumeRole</code> on it.</p>
<p>The examples in this article build these resources:</p>

























<table><thead><tr><th>Name</th><th>Type</th><th>Purpose</th></tr></thead><tbody><tr><td><code>s3-reader-role</code></td><td>IAM Role</td><td>the role ECS tasks and Lambda assume</td></tr><tr><td>trust policy</td><td>Policy on the role</td><td>allows <code>ecs-tasks.amazonaws.com</code> and <code>lambda.amazonaws.com</code> to call <code>sts:AssumeRole</code></td></tr><tr><td><code>s3-reader-policy.json</code></td><td>Permission policy attached to the role</td><td>grants <code>s3:GetObject</code> and <code>s3:ListBucket</code> on <code>my-app-assets</code></td></tr></tbody></table>
<h2>why not just use IAM users</h2>
<p>An IAM user has permanent credentials. Access key, secret key. They work forever until someone manually revokes them.</p>
<p>This breaks in three ways:</p>
<ul>
<li>A key leaks in a git commit. It stays valid until someone notices.</li>
<li>A partner team in another AWS account needs access. Now you're managing someone else's permanent identity.</li>
<li>An AWS service needs permissions, such as ECS (Elastic Container Service, which runs containers) or Lambda. Services don't log in. The only way to give them a permanent key is to paste it into their config, where it can leak like the first case.</li>
</ul>
<p><strong>All three cases need access that expires and covers only specific resources.</strong></p>
<p>assumeRole returns temporary credentials that expire on their own. No cleanup.</p>
<h2>the simple path: AWS services</h2>
<p>An ECS task needs to read from S3. Two steps.</p>
<h3>step 1: create the role and set who can assume it</h3>
<p>Go to <strong>IAM > Roles > Create role</strong>.</p>
<p>First thing AWS asks: <strong>"Who will use this role?"</strong> Select <strong>AWS service</strong>, pick <strong>Elastic Container Service</strong>, then the <strong>Elastic Container Service Task</strong> use case.</p>
<p>This creates the <strong>trust policy</strong>. It's not a separate thing. It's baked into the role at creation. You can see it later under the <strong>Trust relationships</strong> tab. The console writes only <code>ecs-tasks.amazonaws.com</code>. To let Lambda use the same role, add it there with <strong>Edit trust policy</strong>:</p>

<p>Done. Go to the ECS task definition, set the <strong>Task Role</strong> to <code>s3-reader-role</code>.</p>
<p>At runtime: ECS task starts → ECS calls <code>sts:AssumeRole</code> → STS checks the trust policy, finds <code>ecs-tasks.amazonaws.com</code> listed → ECS hands temporary credentials to the task → task uses those credentials to access S3.</p>
<p>No third step. AWS services handle the assume call internally. Whoever sets the Task Role does need <code>iam:PassRole</code> on <code>s3-reader-role</code>, which is what lets them hand the role to ECS; admins already have it.</p>
<h3>what if there's no assumeRole</h3>
<p>On Fargate, where AWS manages the servers and you don't run your own, a task without a role has no AWS credentials at all. Its request to S3 arrives unsigned, as an anonymous request, and the bucket rejects it.</p>
<p>Granting access to <code>ecs.amazonaws.com</code> in the bucket policy (the policy attached to the S3 bucket itself) still leaves the task unable to read the bucket, because the task's requests are not signed as that identity.</p>
<p><code>ecs.amazonaws.com</code> and <code>ecs-tasks.amazonaws.com</code> differ by a few letters, but they are two different identities, written in the trust policies of different roles:</p>
<ul>
<li><code>ecs-tasks.amazonaws.com</code> goes in the trust policy of the task role (here, <code>s3-reader-role</code>). ECS uses this identity to get <code>s3-reader-role</code> credentials for the task and hand them to the code inside it.</li>
<li><code>ecs.amazonaws.com</code> goes in the trust policy of <code>AWSServiceRoleForECS</code>. AWS creates this role automatically the first time you create an ECS cluster or service. The <a href="https://docs.aws.amazon.com/AmazonECS/latest/developerguide/using-service-linked-roles-for-clusters.html">ECS documentation</a> says ECS uses it to manage the cluster, for example to create ENIs (elastic network interfaces) for tasks and register tasks with a load balancer.</li>
</ul>
<p>Only ECS uses either identity; the code inside the task uses neither. When that code sends a request to S3, it signs with the <code>s3-reader-role</code> credentials ECS handed it. So S3 sees <code>s3-reader-role</code>, not the <code>ecs.amazonaws.com</code> written in the bucket policy, and that statement never applies to the task.</p>
<p>Naming one specific task through a service principal doesn't work either. The <a href="https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_principal.html#principal-services">AWS Principal documentation</a> defines a service principal as "an identifier for a service", in the form <code>service-name.amazonaws.com</code>. It stops at the service; there is no field for a task.</p>
<p>To grant a task access in the bucket policy, put its task role ARN in the Principal:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="json" data-theme="github-dark github-light"><code data-language="json" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">"Principal"</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">: { </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">"AWS"</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">: </span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">"arn:aws:iam::ACCOUNT-ID:role/s3-reader-role"</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> }</span></span></code></pre></figure>
<p>With that in place, every task started from a task definition that uses <code>s3-reader-role</code> matches this Principal and can read the bucket. To give different tasks different permissions, give their task definitions different roles.</p>
<p>With no role at all, what's left is the IAM user route. Create a user for each consumer, generate an access key, and paste it into the task's environment variables. Ten services reading S3 means ten permanent keys stored in ten configs. If any one of them leaks, it keeps working until someone revokes it.</p>
<p>With assumeRole, nothing permanent is stored anywhere. The role carries the permissions, and ECS fetches fresh credentials for the task. Add a new service to the trust policy, it gets the same S3 access. In the same account, the bucket policy stays untouched: the role's permission policy is enough.</p>
<h2>the full path: IAM users and cross-account</h2>
<p>A developer in another AWS account needs to read your S3 bucket. Three steps.</p>
<h3>step 1 and 2: same as above</h3>
<p>Create the role, set the trust policy to trust the other account:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="json" data-theme="github-dark github-light"><code data-language="json" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">{</span></span>
<span data-line=""><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">  "Principal"</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">: {</span></span>
<span data-line=""><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">    "AWS"</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">: </span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">"arn:aws:iam::OTHER-ACCOUNT-ID:root"</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  }</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">}</span></span></code></pre></figure>
<p><code>:root</code> here means the whole account, not its root user. The other account's admin then decides which of its users get to use the role.</p>
<p>Attach S3 read permissions. Same as before.</p>
<h3>step 3: the other side also needs permission</h3>

<h2>the mental model</h2>
<p>An IAM user with permanent keys is a house key. Works forever until the locks change.</p>
<p>assumeRole is a hotel key card. Opens one room, for one night, stops working at checkout.</p>
<p><strong>Trust policy</strong> = the hotel's guest list (who can check in)
<strong>User policy</strong> = the reservation (proof the guest is allowed to ask for a room)

You attach policies to IAM (Identity and Access Management) users. Policies define what actions are allowed on which resources. Simple.

Then **assumeRole** and **trust policy** show up, and the docs explain how to set them up before explaining why they exist.

A **role** is an IAM identity that holds permissions but has no password or permanent keys of its own. `sts:AssumeRole` is an API action in STS (Security Token Service). A service or user calls it to get temporary credentials for a role. **Trust policy** is the policy attached to that role that controls who is allowed to call `sts:AssumeRole` on it.

The examples in this article build these resources:

| Name | Type | Purpose |
|---|---|---|
| `s3-reader-role` | IAM Role | the role ECS tasks and Lambda assume |
| trust policy | Policy on the role | allows `ecs-tasks.amazonaws.com` and `lambda.amazonaws.com` to call `sts:AssumeRole` |
| `s3-reader-policy.json` | Permission policy attached to the role | grants `s3:GetObject` and `s3:ListBucket` on `my-app-assets` |

## why not just use IAM users

An IAM user has permanent credentials. Access key, secret key. They work forever until someone manually revokes them.

This breaks in three ways:

- A key leaks in a git commit. It stays valid until someone notices.
- A partner team in another AWS account needs access. Now you're managing someone else's permanent identity.
- An AWS service needs permissions, such as ECS (Elastic Container Service, which runs containers) or Lambda. Services don't log in. The only way to give them a permanent key is to paste it into their config, where it can leak like the first case.

**All three cases need access that expires and covers only specific resources.**

assumeRole returns temporary credentials that expire on their own. No cleanup.

## the simple path: AWS services

An ECS task needs to read from S3. Two steps.

### step 1: create the role and set who can assume it

Go to **IAM > Roles > Create role**.

First thing AWS asks: **"Who will use this role?"** Select **AWS service**, pick **Elastic Container Service**, then the **Elastic Container Service Task** use case.

This creates the **trust policy**. It's not a separate thing. It's baked into the role at creation. You can see it later under the **Trust relationships** tab. The console writes only `ecs-tasks.amazonaws.com`. To let Lambda use the same role, add it there with **Edit trust policy**:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": ["ecs-tasks.amazonaws.com", "lambda.amazonaws.com"]
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

One role, one trust policy. The Principal field, which names who may assume the role, accepts multiple services in an array. No need to create separate trust policies.

Name the role `s3-reader-role`.

### step 2: attach permissions to the role

Next screen. Attach a **permission policy** that defines what this role can do. Save the following as `s3-reader-policy.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::my-app-assets",
        "arn:aws:s3:::my-app-assets/*"
      ]
    }
  ]
}
```

Attach this to `s3-reader-role`:

**CLI:**

```bash
aws iam create-policy \
  --policy-name s3-reader-policy \
  --policy-document file://s3-reader-policy.json

aws iam attach-role-policy \
  --role-name s3-reader-role \
  --policy-arn arn:aws:iam::ACCOUNT-ID:policy/s3-reader-policy
```

**Console:** IAM > Roles > `s3-reader-role` > Permissions > Add permissions > Attach policies > select `s3-reader-policy`.

Done. Go to the ECS task definition, set the **Task Role** to `s3-reader-role`.

At runtime: ECS task starts → ECS calls `sts:AssumeRole` → STS checks the trust policy, finds `ecs-tasks.amazonaws.com` listed → ECS hands temporary credentials to the task → task uses those credentials to access S3.

No third step. AWS services handle the assume call internally. Whoever sets the Task Role does need `iam:PassRole` on `s3-reader-role`, which is what lets them hand the role to ECS; admins already have it.

### what if there's no assumeRole

On Fargate, where AWS manages the servers and you don't run your own, a task without a role has no AWS credentials at all. Its request to S3 arrives unsigned, as an anonymous request, and the bucket rejects it.

Granting access to `ecs.amazonaws.com` in the bucket policy (the policy attached to the S3 bucket itself) still leaves the task unable to read the bucket, because the task's requests are not signed as that identity.

`ecs.amazonaws.com` and `ecs-tasks.amazonaws.com` differ by a few letters, but they are two different identities, written in the trust policies of different roles:

- `ecs-tasks.amazonaws.com` goes in the trust policy of the task role (here, `s3-reader-role`). ECS uses this identity to get `s3-reader-role` credentials for the task and hand them to the code inside it.
- `ecs.amazonaws.com` goes in the trust policy of `AWSServiceRoleForECS`. AWS creates this role automatically the first time you create an ECS cluster or service. The [ECS documentation](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/using-service-linked-roles-for-clusters.html) says ECS uses it to manage the cluster, for example to create ENIs (elastic network interfaces) for tasks and register tasks with a load balancer.

Only ECS uses either identity; the code inside the task uses neither. When that code sends a request to S3, it signs with the `s3-reader-role` credentials ECS handed it. So S3 sees `s3-reader-role`, not the `ecs.amazonaws.com` written in the bucket policy, and that statement never applies to the task.

Naming one specific task through a service principal doesn't work either. The [AWS Principal documentation](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_principal.html#principal-services) defines a service principal as "an identifier for a service", in the form `service-name.amazonaws.com`. It stops at the service; there is no field for a task.

To grant a task access in the bucket policy, put its task role ARN in the Principal:

```json
"Principal": { "AWS": "arn:aws:iam::ACCOUNT-ID:role/s3-reader-role" }
```

With that in place, every task started from a task definition that uses `s3-reader-role` matches this Principal and can read the bucket. To give different tasks different permissions, give their task definitions different roles.

With no role at all, what's left is the IAM user route. Create a user for each consumer, generate an access key, and paste it into the task's environment variables. Ten services reading S3 means ten permanent keys stored in ten configs. If any one of them leaks, it keeps working until someone revokes it.

With assumeRole, nothing permanent is stored anywhere. The role carries the permissions, and ECS fetches fresh credentials for the task. Add a new service to the trust policy, it gets the same S3 access. In the same account, the bucket policy stays untouched: the role's permission policy is enough.

## the full path: IAM users and cross-account

A developer in another AWS account needs to read your S3 bucket. Three steps.

### step 1 and 2: same as above

Create the role, set the trust policy to trust the other account:

```json
{
  "Principal": {
    "AWS": "arn:aws:iam::OTHER-ACCOUNT-ID:root"
  }
}
```

`:root` here means the whole account, not its root user. The other account's admin then decides which of its users get to use the role.

Attach S3 read permissions. Same as before.

### step 3: the other side also needs permission

In the **other account**, go to **IAM > Users > [the user] > Permissions**, add a policy:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::YOUR-ACCOUNT-ID:role/s3-reader-role"
    }
  ]
}
```

This is the extra step that AWS services don't need. A human (or their scripts) has to prove they're allowed to ask.

**Both sides must allow it.** The role's trust policy has to list the other account, and the user's own policy has to allow `sts:AssumeRole` on this role. If either one doesn't, access denied.

Within one account the rule is looser. If the trust policy names the user's ARN (Amazon Resource Name, the full ID of an AWS resource) directly, the user needs no policy of their own. If it names the account (`:root`), the user still needs the step 3 policy.

Same runtime flow as above: the user calls `sts:AssumeRole`, STS checks both sides, and returns temporary credentials (default: one hour).

<p>接著出現了 <strong>assumeRole</strong> 跟 <strong>trust policy</strong>。文件一開始就教怎麼設定，卻沒先講為什麼需要它們。</p>

<h2>為什麼不直接用 IAM user</h2>
<p>IAM user 拿的是永久憑證，一組 access key 加 secret key。除非有人手動撤銷，不然會一直有效。</p>
<p>這在三種情況下會出問題：</p>
<ul>
<li>key 不小心被 commit 進 git。在有人發現之前，它都還能用。</li>
<li>另一個 AWS 帳號的合作團隊需要存取權限。你就得替別人管一個永久身分。</li>
<li>AWS 的 service 需要權限，例如 ECS（Elastic Container Service，用來跑 container）或 Lambda。service 不會登入，如果要給它永久 key，只能貼進它的設定裡，那就跟第一種一樣可能外洩。</li>
</ul>
<p><strong>這三種情況要的都是有期限、只涵蓋特定資源的權限。</strong></p>
<p>assumeRole 給的臨時憑證時間到了自己就失效，不用事後清理。</p>
<h2>簡單的情況：AWS service</h2>
<p>ECS task 要讀 S3，兩步就好。</p>
<h3>第一步：建 role，設定誰可以 assume</h3>
<p>到 <strong>IAM > Roles > Create role</strong>。</p>
<p>AWS 第一個問題是 <strong>「Who will use this role?」</strong>。選 <strong>AWS service</strong>，挑 <strong>Elastic Container Service</strong>，再選 <strong>Elastic Container Service Task</strong> 這個 use case。</p>
<p>這一步建出來的就是 <strong>trust policy</strong>。它在建 role 的時候就一起寫進 role 裡，事後可以在 <strong>Trust relationships</strong> 分頁看到。console 只會寫入 <code>ecs-tasks.amazonaws.com</code>，如果 Lambda 也要用同一個 role，就在那個分頁按 <strong>Edit trust policy</strong> 加上去：</p>

<p>role 取名叫 <code>s3-reader-role</code>。</p>

<p>實際跑起來的順序：ECS task 啟動 → ECS 呼叫 <code>sts:AssumeRole</code> → STS 檢查 trust policy，裡面有 <code>ecs-tasks.amazonaws.com</code> → ECS 把臨時憑證交給 task → task 用這組憑證存取 S3。</p>
<p>沒有第三步，因為 assume 這個呼叫由 AWS service 自己處理。不過設定 Task Role 的人身上要有對 <code>s3-reader-role</code> 的 <code>iam:PassRole</code>，AWS 才讓他把這個 role 交給 ECS；admin 本來就有。</p>
<h3>沒有 assumeRole 的話</h3>
<p>如果用 Fargate（機器由 AWS 管，不用自己開 server），task 沒有 role 就拿不到任何 AWS 憑證。它發給 S3 的請求沒有簽章，會被當成匿名請求，bucket 直接拒絕。</p>
<p>在 bucket policy（直接掛在 S3 bucket 上的 policy）裡把權限開給 <code>ecs.amazonaws.com</code>，task 一樣讀不到 bucket，因為 task 送出的請求不是用這個身分簽的。</p>
<p><code>ecs.amazonaws.com</code> 跟 <code>ecs-tasks.amazonaws.com</code> 只差幾個字，卻是兩個不同的身分，寫在不同 role 的 trust policy 裡：</p>
<ul>
<li><code>ecs-tasks.amazonaws.com</code> 寫在 task role（這裡是 <code>s3-reader-role</code>）的 trust policy 裡。ECS 用這個身分替 task 拿 <code>s3-reader-role</code> 的憑證，交給 task 裡的程式碼。</li>
<li><code>ecs.amazonaws.com</code> 寫在 <code>AWSServiceRoleForECS</code> 的 trust policy 裡。這個 role 是第一次建 ECS cluster 或 service 時 AWS 自動建的。<a href="https://docs.aws.amazon.com/AmazonECS/latest/developerguide/using-service-linked-roles-for-clusters.html">ECS 文件</a>說 ECS 用它管理 cluster，例如替 task 建 ENI（elastic network interface）、把 task 註冊到 load balancer。</li>
</ul>
<p>兩個身分都只有 ECS 在用，task 裡的程式碼一個也沒用到。程式碼送請求給 S3 時，簽名用的是 ECS 交給它的 <code>s3-reader-role</code> 憑證。所以 S3 看到的身分是 <code>s3-reader-role</code>，不是 bucket policy 裡寫的 <code>ecs.amazonaws.com</code>，這條 policy 就不會套用到 task 身上。</p>
<p>想改成在 service principal 裡指定某一個 task，也沒辦法。<a href="https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_principal.html#principal-services">AWS 的 Principal 文件</a>把 service principal 定義成「an identifier for a service」，格式是 <code>service-name.amazonaws.com</code>，只到 service 這一層，沒有欄位可以填 task。</p>
<p>要在 bucket policy 裡授權給 task，Principal 就填它的 task role ARN：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="json" data-theme="github-dark github-light"><code data-language="json" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">"Principal"</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">: { </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">"AWS"</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">: </span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">"arn:aws:iam::ACCOUNT-ID:role/s3-reader-role"</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> }</span></span></code></pre></figure>
<p>填了之後，只要 task definition 掛的是 <code>s3-reader-role</code>，它跑出來的 task 都符合這個 Principal，都讀得到 bucket。要讓不同的 task 有不同的權限，就讓它們的 task definition 各掛不同的 role。</p>
<p>完全不用 role 的話，剩下的辦法就是 IAM user：每個要讀 S3 的 service 各建一個 user、各產一組 access key，再貼進 task 的環境變數。十個 service 要讀 S3，就有十把永久 key 存在十份設定裡，其中任何一把外洩了，在有人撤銷之前都還能用。</p>
<p>用 assumeRole 的話，哪裡都不用存永久的東西。權限掛在 role 上，ECS 每次替 task 拿新的憑證。新的 service 加進 trust policy，就拿到一樣的 S3 權限。同一個帳號裡，bucket policy 完全不用動，role 的 permission policy 就夠了。</p>
<h2>完整的情況：IAM user 跟跨帳號</h2>
<p>另一個 AWS 帳號的開發者要讀你的 S3 bucket，這次要三步。</p>
<h3>第一、二步：跟上面一樣</h3>
<p>建 role，trust policy 改成信任對方帳號：</p>

<span data-line=""><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">    "AWS"</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">: </span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">"arn:aws:iam::OTHER-ACCOUNT-ID:root"</span></span>

<p>掛上 S3 讀取權限，跟前面一樣。</p>
<h3>第三步：對方那邊也要給權限</h3>
<p>在<strong>對方帳號</strong>到 <strong>IAM > Users > [那個 user] > Permissions</strong>，加一份 policy：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="json" data-theme="github-dark github-light"><code data-language="json" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">{</span></span>

<p>AWS service 不需要這一步，人（或人寫的 script）才需要，因為對方帳號得先允許這個 user 去 assume 這個 role。</p>
<p><strong>兩邊都要允許。</strong> role 的 trust policy 要列出對方帳號，user 自己的 policy 也要允許對這個 role 呼叫 <code>sts:AssumeRole</code>。只要有一邊沒允許，就是 access denied。</p>
<p>如果是同一個帳號，規則寬一點。trust policy 直接寫了 user 的 ARN（Amazon Resource Name，AWS 資源的完整 ID），那個 user 自己就不用掛任何 policy；trust policy 寫的是整個帳號（<code>:root</code>），user 還是要有第三步那份 policy。</p>
<p>跑起來的流程跟前面一樣：user 呼叫 <code>sts:AssumeRole</code>，STS 兩邊都檢查過，回傳臨時憑證（預設一小時）。</p>
<h2>怎麼記</h2>
<p>帶永久 key 的 IAM user 像家裡的鑰匙，換鎖之前永遠能開。</p>
<p>assumeRole 像飯店的房卡，只開一間房、只用一晚，退房就失效。</p>
<p><strong>Trust policy</strong> = 飯店的住客名單（誰可以入住）
<strong>User policy</strong> = 訂房紀錄（證明這位客人有資格來要房間）
