Five ways to reach a service in Kubernetes, and the one you should use

kubernetesnetworkingdevops

A Kubernetes service can be reached five different ways. In real code you use exactly one of them. The other four come out only when something is broken.

So why learn all five? Because walking through them is the fastest way to see what the service abstraction actually hides: a virtual IP, a node port, a DNS name, and a set of raw pods underneath. Once you've hit a service every possible way, "service down" stops being a mystery and becomes a checklist.

The setup

I'm on Kind, which runs each K8s node as a Docker container, isolated from the host. Two tiny Node.js APIs in a noah namespace:

  • joke-service → type: ClusterIP
  • number-service → type: NodePort

The YAML is identical except for one line, and that line changes everything about how you can reach it:

$ kubectl get svc -n noah
NAME             TYPE        CLUSTER-IP      PORT(S)
joke-service     ClusterIP   10.96.236.182   80/TCP
number-service   NodePort    10.96.183.131   80:30405/TCP

One detail that explains the commands below: the Alpine pods only ship wget, while Kind's Debian control-plane has curl. Same request, different tool.

Hitting a NodePort service (all five work)

A NodePort service is the permissive one. Every method is on the table.

1. Docker exec into the node (a Kind-only trick). Kind nodes are containers, so you can jump inside one and hit localhost:

30405 is the node port from kubectl get svc. This works because, inside the node, the NodePort is just a local port. On a real cluster the node isn't a container you can docker exec into, so the equivalent is to SSH in (or kubectl debug node/<name>) and hit localhost:30405 from there. The other four methods work the same everywhere.

2. Service DNS (the one you should use). Name the service, let K8s resolve it:

Two caveats worth knowing:

  • Cross-namespace needs the full name: number-service.noah.svc.cluster.local.
  • If CoreDNS is down, this is the method that stops working. The IP-based ones below still do.

3. ClusterIP direct. Skip DNS, use the service's virtual IP:

Reliable, but you have to look the IP up first (kubectl get svc).

4. NodeIP + NodePort (the painful one). Reach the node's real IP on the node port:

You need two lookups to build this: kubectl get nodes -o wide for the node IP, then kubectl get svc for the random port. Rarely worth it.

5. Direct pod IP (bypass the service entirely). Talk to one pod on its container port:

Find the pod IPs with kubectl get pods -o wide, or read them off the service's endpoints:

$ kubectl describe svc number-service -n noah
Endpoints: 10.244.1.18:3000,10.244.2.23:3000

This skips load balancing completely, which is exactly why it's useful: it lets you test one misbehaving pod in isolation.

A ClusterIP service loses two of the five

Switch joke-service to type: ClusterIP and every method that needs a node port vanishes. Here are all five, side by side:

#MethodNodePortClusterIP
1Docker exec → localhost:NodePort✅❌ no node port
2Service DNS✅✅
3ClusterIP direct✅✅
4NodeIP + NodePort✅❌ no node port
5Direct pod IP✅✅

ClusterIP keeps 2, 3, and 5, and loses 1 and 4, the two that reach in through a node port it doesn't have. Which is the point: a ClusterIP service was never meant to be reached from outside the cluster.

The takeaway

In practice, use service DNS (service-name:port). It works ~99% of the time, reads cleanly, and behaves the same on Kind, k3s, Minikube, or a real cluster.

The reason is one line: pod IPs change on every restart, service names don't. The other four methods all reach through to an IP, which makes them perfect for debugging a specific layer (is DNS the problem? is one pod the problem?) and a bad idea for anything you actually ship.
