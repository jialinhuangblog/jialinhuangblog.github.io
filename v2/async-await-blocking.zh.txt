<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">}</span></span></code></pre></figure>
<p><code>console.log(data)</code> 要等 <code>fetch</code> 回來才能跑。這就是在等，等就是 blocking。那為什麼大家還是一直說它 non-blocking？</p>
<p>因為「non-blocking」講的是執行緒，不是 <code>await</code> 後面那一行。</p>
<h2>混淆從哪裡來</h2>
<p>「blocking」這個字常常被拿來用，卻沒講清楚是誰在等。在函式裡面，<code>await</code> 下面的每一行都得等：函式暫停，剩下的程式碼停在那裡。</p>
<p>可是站到函式外面看：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="js" data-theme="github-dark github-light"><code data-language="js" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">getData</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">();</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">console.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">log</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'This runs right away'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">);</span></span></code></pre></figure>
<p><code>console.log</code> 馬上就印出來，它不等 <code>fetch</code>。</p>
<p>所以 <code>await</code> 只讓它所在的函式等。呼叫端不用等，除非呼叫端自己也寫了 <code>await</code>。</p>

<p>輸出（縮排是照呼叫的層數加上去的，實際印出來沒有縮排）：</p>
<pre><code>1. main: before await
   2. process: before await
      3. fetchData: before await
0. main thread: immediate             ← 三層都停在 await，這一行先印
      3. fetchData: after await       ← 500ms 後，最裡面那層先繼續
   2. process: after await
1. main: after await                  ← 最外面那層最後
</code></pre>
<p><code>0. main thread: immediate</code> 排在第四行，因為 <code>main</code> 呼叫 <code>process</code>，<code>process</code> 呼叫 <code>fetchData</code>，<code>fetchData</code> 跑到 <code>await delay(500)</code>，執行到這裡才暫停、把控制權交回呼叫端。在真正 await 到東西之前，async function 的執行順序跟一般函式一樣，都是同步往下跑。</p>
<p>500ms 之後，三層函式各自從 <code>await</code> 的下一行接著跑，順序由內往外，跟 call stack 回傳的順序一樣。<code>main()</code> 呼叫的時候沒有加 <code>await</code>，所以 <code>0. main thread: immediate</code> 不用等這 500ms。</p>
<p>執行順序一樣，但 async function 跟一般函式還是有兩個地方不同。<code>async function g() { return 42 }</code>，呼叫 <code>g()</code> 拿到 <code>Promise { 42 }</code>，不是 <code>42</code>。例外也不一樣：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="js" data-theme="github-dark github-light"><code data-language="js" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">async</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> function</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1"> f</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">() { </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">throw</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> new</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1"> Error</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'boom'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">); }</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">try</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> { </span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">f</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(); } </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">catch</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> (e) { console.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">log</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'caught'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">); } </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// 不會印</span></span></code></pre></figure>
<p><code>f</code> 一進去就丟例外，這時還沒碰到任何 <code>await</code>。既然 <code>f</code> 還在同步跑，呼叫端的 <code>try/catch</code> 照理抓得到。實際上抓不到，因為 async function 裡丟出的例外會變成 rejected promise，不會往外丟給呼叫端。要抓它，得寫 <code>await f()</code> 或 <code>f().catch(...)</code>。這兩個例子都在 Node 22.22.3 跑過。</p>
<h2>最外層也 await 的話呢？</h2>

我們對 async/await 都有個根深蒂固的印象：它是 non-blocking。可是看這段：

```js
async function getData() {
  const data = await fetch('/api');
  console.log(data); // 這行要等
}
```

`console.log(data)` 要等 `fetch` 回來才能跑。這就是在等，等就是 blocking。那為什麼大家還是一直說它 non-blocking？

因為「non-blocking」講的是執行緒，不是 `await` 後面那一行。

## 混淆從哪裡來

「blocking」這個字常常被拿來用，卻沒講清楚是誰在等。在函式裡面，`await` 下面的每一行都得等：函式暫停，剩下的程式碼停在那裡。

可是站到函式外面看：

```js
getData();
console.log('This runs right away');
```

`console.log` 馬上就印出來，它不等 `fetch`。

所以 `await` 只讓它所在的函式等。呼叫端不用等，除非呼叫端自己也寫了 `await`。

## 巢狀的 await

三層函式，每一層都有 `await`：

```js
const delay = (ms) => new Promise((r) => setTimeout(r, ms));

async function fetchData() {
  console.log('3. fetchData: before await');
  await delay(500);
  console.log('3. fetchData: after await');
}

async function process() {
  console.log('2. process: before await');
  await fetchData();
  console.log('2. process: after await');
}

async function main() {
  console.log('1. main: before await');
  await process();
  console.log('1. main: after await');
}

main();
console.log('0. main thread: immediate');
```

輸出（縮排是照呼叫的層數加上去的，實際印出來沒有縮排）：

```
1. main: before await
   2. process: before await
      3. fetchData: before await
0. main thread: immediate             ← 三層都停在 await，這一行先印
      3. fetchData: after await       ← 500ms 後，最裡面那層先繼續
   2. process: after await
1. main: after await                  ← 最外面那層最後
```

`0. main thread: immediate` 排在第四行，因為 `main` 呼叫 `process`，`process` 呼叫 `fetchData`，`fetchData` 跑到 `await delay(500)`，執行到這裡才暫停、把控制權交回呼叫端。在真正 await 到東西之前，async function 的執行順序跟一般函式一樣，都是同步往下跑。

500ms 之後，三層函式各自從 `await` 的下一行接著跑，順序由內往外，跟 call stack 回傳的順序一樣。`main()` 呼叫的時候沒有加 `await`，所以 `0. main thread: immediate` 不用等這 500ms。

執行順序一樣，但 async function 跟一般函式還是有兩個地方不同。`async function g() { return 42 }`，呼叫 `g()` 拿到 `Promise { 42 }`，不是 `42`。例外也不一樣：

```js
async function f() { throw new Error('boom'); }
try { f(); } catch (e) { console.log('caught'); } // 不會印
```

`f` 一進去就丟例外，這時還沒碰到任何 `await`。既然 `f` 還在同步跑，呼叫端的 `try/catch` 照理抓得到。實際上抓不到，因為 async function 裡丟出的例外會變成 rejected promise，不會往外丟給呼叫端。要抓它，得寫 `await f()` 或 `f().catch(...)`。這兩個例子都在 Node 22.22.3 跑過。

<p>Because "non-blocking" refers to the thread, not the next line.</p>
<h2>The confusion</h2>
<p>The word "blocking" gets used without saying <em>what</em> is being blocked. Inside the function, <code>await</code> absolutely blocks the lines below it. The function pauses and the remaining code waits.</p>
<p>But step outside:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="js" data-theme="github-dark github-light"><code data-language="js" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">getData</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">();</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">console.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">log</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'This runs right away'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">);</span></span></code></pre></figure>
<p><code>console.log</code> fires immediately. It does not wait for <code>fetch</code>. The caller moved on. The main thread kept going.</p>
<p>So <code>await</code> blocks the function it lives in. It does not block whoever called that function — unless the caller also uses <code>await</code>.</p>

<p>Output (indented by call depth here; the real output has no indentation):</p>
<pre><code>1. main: before await
   2. process: before await
      3. fetchData: before await
0. main thread: immediate             ← all three paused at await, this line prints first
      3. fetchData: after await       ← 500ms later, innermost resumes first
   2. process: after await
1. main: after await                  ← outermost resumes last
</code></pre>
<p><code>0. main thread: immediate</code> is the fourth line because <code>main</code> calls <code>process</code>, <code>process</code> calls <code>fetchData</code>, and <code>fetchData</code> reaches <code>await delay(500)</code>. Only there does execution suspend and return control to the caller. Until it actually awaits something, an async function runs in the same order as a regular function: synchronously, top to bottom.</p>
<p>After 500ms, each of the three functions resumes from the line after its <code>await</code>, innermost first, in the same order a call stack returns. <code>main()</code> was called without <code>await</code>, so <code>0. main thread: immediate</code> does not wait for those 500ms.</p>
<p>Same order, but an async function still differs from a regular function in two ways. With <code>async function g() { return 42 }</code>, calling <code>g()</code> gives you <code>Promise { 42 }</code>, not <code>42</code>. Exceptions differ too:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="js" data-theme="github-dark github-light"><code data-language="js" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">async</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> function</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1"> f</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">() { </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">throw</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> new</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1"> Error</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'boom'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">); }</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">try</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> { </span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">f</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(); } </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">catch</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> (e) { console.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">log</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'caught'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">); } </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// never prints</span></span></code></pre></figure>
<p><code>f</code> throws as soon as it is entered, before reaching any <code>await</code>. By the paragraph above it is running synchronously, so you would expect the caller's <code>try/catch</code> to catch it. It does not, because an exception thrown inside an async function becomes a rejected promise instead of propagating to the caller. To catch it, write <code>await f()</code> or <code>f().catch(...)</code>. Both examples were run on Node 22.22.3.</p>
<h2>What if the top level also awaits?</h2>
<p>Change <code>main()</code> to <code>await main()</code>:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="js" data-theme="github-dark github-light"><code data-language="js" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">await</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1"> main</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">();</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">console.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">log</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'0. main thread: immediate'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">);</span></span></code></pre></figure>
<pre><code>1. main: before await
   2. process: before await
      3. fetchData: before await
      3. fetchData: after await       ← 500ms later
   2. process: after await
1. main: after await
0. main thread: immediate             ← the top level awaits now, so this line waits too
</code></pre>
<p>Top-level <code>await</code> only works in an ES module (ESM). A <code>.mjs</code> file is ESM. A plain <code>.js</code> file is switched to ESM automatically from Node 22.7 when it contains this syntax. A <code>.cjs</code> file is always treated as CommonJS and throws <code>SyntaxError: await is only valid in async functions and the top level bodies of modules</code>.</p>
<h2>So which is it — blocking or not?</h2>
<p>Inside a function, every line after <code>await</code> waits. If the caller also writes <code>await</code>, it waits too. With <code>await</code> all the way to the top level, even the last <code>console.log</code> waits.</p>
<p>What non-blocking really means: during those 500ms, can the same thread handle other requests? Node runs JavaScript on one thread, and all requests take turns running on it. This server has two routes; <code>/a</code> waits 500ms and <code>/b</code> answers right away:</p>

<p>Request <code>/a</code>, then <code>/b</code> 50ms later, once with each version (Node 22.22.3). All times are counted from the <code>/a</code> request:</p>
<pre><code>version 1 await:      /a answered at 510ms, /b at 60ms
version 2 busy loop:  /a answered at 512ms, /b at 513ms
</code></pre>
<p>In version 1, <code>/a</code> suspends at <code>await</code> and the thread is free to handle <code>/b</code>, which is sent at 50ms and answered at 60ms, 10ms later. In version 2 the thread spends the whole 500ms in that <code>while</code>, so <code>/b</code> queues behind <code>/a</code> and answers only after <code>/a</code> does. <code>fs.readFileSync</code> on a large file behaves like version 2: the thread is held until the file is read.</p>
<p>At 500ms the promise from <code>wait(500)</code> settles, and <code>/a</code> resumes on the line after <code>await</code> and sends its response. If the thread is busy with another request at that moment, and that request's handler has a <code>while</code> like version 2, <code>/a</code> has to wait until it finishes.</p>
