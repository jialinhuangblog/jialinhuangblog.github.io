ReactNode、ReactElement、Component、div：哪些只在記憶體裡，哪一個會變成 DOM

2026/04/21
reactinternalstypes

寫 React 天天會碰到四個名字：ReactNode、ReactElement、Component，還有 div 這種 HTML tag 的名字。剛開始寫的時候，很容易把它們當成同一種東西，反正都是畫面上的一塊。可是回傳 <Comp /> 會 render，回傳 Comp 卻什麼都不顯示；把字串指定給 ReactElement 型別的變數，TypeScript 會報錯，指定給 ReactNode 就沒事。

這四個名字各是什麼呢？哪些只存在 JavaScript 的記憶體裡，哪一個最後會變成瀏覽器裡的 DOM 節點？

render 跟 commit

React 每次更新畫面，都分成兩步：

  1. render：React 呼叫元件的 function，算出畫面應該變成什麼樣子。這一步只處理 JavaScript 物件，頁面上的 DOM 不會變。
  2. commit：React 把 render 算出來的變更寫進頁面上的 DOM。

commit 之後瀏覽器還要算 style、排版、畫出像素，那些步驟寫在從 setState 到畫面上的像素。

四個名字各是什麼

名字是什麼存在哪裡
ReactNodeTypeScript 的型別，範圍最大，React 能 render 的值都算只在型別檢查時存在，編譯成 JavaScript 之後就沒了
ReactElementJSX 或 createElement 產生的普通物件，主要欄位是 type、props、keyJavaScript 記憶體
Component一個 function 或 class，收 props，回傳要 render 的東西JavaScript 記憶體裡的一個 function
div一個字串，HTML tag 的名字字串本身在 JavaScript 記憶體裡；React 在 render 時替它建一個 HTMLDivElement，commit 時放進頁面

這四個名字裡，只有 div 會在頁面上對應到一個 DOM 元素。不過字串跟數字也算 ReactNode，它們會變成 Text 節點。<b>{42}</b> commit 之後，頁面上的 <b> 底下有一個內容是 "42" 的 Text 節點。null 跟 false 不會產生 DOM。

Component 產生 ReactElement

寫 <Button label="OK" /> 的時候，Button 還沒被呼叫，這一行只產生一個 type: Button 的 element。等 React render 到這個 element，才會呼叫 Button。它回傳的通常是 ReactElement，也可以是字串或 null，總之是一個 ReactNode。

頁面上不會有 Button 這個東西，只有它回傳的 <span> 會在 commit 時變成頁面上的 <span> 節點。

DOM 節點什麼時候建好、什麼時候進頁面

把 document.createElement 跟 appendChild 包一層記錄，再用 React 19.3.1 的 production build mount 一個 App。App 底下有兩個元件：A render 出 <section><p>a</p></section>，B render 出 <div>b</div>。記錄下來的順序是：

  1. render App
  2. render A
  3. document.createElement('p')
  4. document.createElement('section')
  5. 把 <p> 接到 <section> 底下，<section> 還不在頁面上
  6. render B
  7. document.createElement('div')
  8. 把 <section> 接到 #root 底下，這時才進頁面
  9. 把 <div> 接到 #root 底下
  10. useLayoutEffect

<section> 跟 <p> 在 render B 之前就建好了，也就是還在 render 的時候。React 走 fiber 時，每個 fiber 會經過兩次：往下走時呼叫元件，往回走時收尾，收尾那一步叫 completeWork。host component 的 fiber 在 completeWork 裡建出 DOM 節點，再把 child 的 DOM 節點接上去，這時接好的 DOM 都還不在頁面上。對應的程式碼是 ReactFiberCompleteWork.js 的 HostComponent 分支，它呼叫 createInstance 跟 appendAllChildren。到了 commit，React 才把接好的 DOM 放進 #root。往下走、往回走的細節在 React 的 work loop 裡發生了什麼。

把整條路照順序排起來：

  1. Greeting 是原始碼裡的 function，一直都在。
  2. JSX 產生 { type: Greeting } 這個 element，下一次 render 會產生新的 element。
  3. React 替它建 fiber，hook 的值存在這個 fiber 上，會留到下一次 render。
  4. React 呼叫 Greeting，拿到 { type: 'div' } 這個 element。React 把它的 type、key、props 抄到 fiber 上之後，就沒有 fiber reference 著它。
  5. React 替它建 fiber，也會留到下一次 render。
  6. completeWork 替這個 fiber 建出 HTMLDivElement，記在 stateNode 上，這時還不在頁面上。
  7. commit 把 HTMLDivElement 放進頁面。

為什麼 fiber 有兩份

React 同時留著兩份 fiber 樹：current 是現在畫面上的版本，workInProgress 是這次 render 正在建的版本。兩邊對應同一個 <div> 的 fiber，stateNode 都指向同一個 HTMLDivElement：createWorkInProgress 建 workInProgress 的 fiber 時，會把 current 的 stateNode 抄過去。

那 React 在 workInProgress 上改東西，會不會改到畫面上的 DOM 呢？

不會。stateNode 只是指向 DOM 節點的參照，要改 DOM，得呼叫 setAttribute、appendChild、removeChild 這類 method，而 React 只在 commit 的 mutation 階段，也就是 ReactFiberCommitWork.js 裡的 commitMutationEffectsOnFiber，呼叫它們。render 時修改的都是 fiber 自己的欄位：

render 時唯一會新建的 DOM，是這次新加進來的節點，像上一節的 <section>，而它們建好的時候還沒接到頁面上。

不過 React 也不是每個 fiber 都準備兩份。mount 的時候每個 fiber 只有一份，等到第一次更新、render 走到它，React 才替它建第二份，之後兩份輪流當 current。所以「這個元件的 fiber」不是固定一個物件，每次 render 都會換成另一份。<div> 對應的 DOM 節點倒是從頭到尾都是同一個。

如果元件用 React.memo 包起來，而且 props 沒變，React 會跳過它底下整個 subtree。subtree 裡的 fiber 只要一直沒被 render 走到，就始終只有一份。因為只有一份，它的 alternate 是 null，current 跟 workInProgress 兩棵樹用的也是同一個 fiber 物件。createWorkInProgress 的註解也寫了，第二份 fiber 是等到需要才建，「to avoid allocating extra objects for things that are never updated」。元件的 type 跟 key 沒變的話，React 就一直拿這兩個物件輪流用，不會建第三個。

commit 時換掉的是什麼

commit 裡依序有三件事跟這兩份 fiber 樹有關：

  1. mutation：改真的 DOM，像 setAttribute、appendChild、removeChild。使用者會看到的變化都在這一步。
  2. 換 current：root.current = finishedWork，workInProgress 變成 current。
  3. layout：執行 useLayoutEffect、componentDidMount。

fiber 有兩份，DOM 卻只有一份，所以 mutation 沒有另一份 DOM 可以先改好再換上去，只能直接改頁面上的節點，例如改一個屬性，或加入、移除幾個節點。換 current 的時候 DOM 已經改好了，所以這一行不會讓畫面有任何變化。它影響的是下一次 render：React 會拿這次完成的版本當 current，用它上面的 props 跟新的 props 比較，而這次被換下來的舊版本，就成了下一次的 workInProgress。

情況這個 fiber 在哪邊alternate
mount只在 workInProgressnull
update，這次 render 有走到它current 跟 workInProgress 各一份兩份互指

delete只在 currentReact 不替它建 workInProgress 的 fiber

React 不是用把 alternate 設成 null 來表示刪除。要刪的節點不會有 workInProgress 的 fiber，React 把舊的 fiber 放進 parent 的 deletions 陣列，再替 parent 加上 ChildDeletion 這個 flag。commit 讀到這個陣列，就呼叫 removeChild。程式碼在 ReactChildFiber.js 的 deleteChild，它只動了 parent 的 deletions 跟 flags，被刪的 child 的 alternate 沒有人碰。

useState 的值存在哪裡

function component 只是一個 function，跑完就回傳，裡面的區域變數也跟著消失。在元件裡寫 let count = 0，每次 render 都會重新變回 0。那 useState 的值是怎麼留到下一次 render 的？

它存在元件的 fiber 上，也就是 memoizedState 欄位。這個欄位指向一個 linked list，每呼叫一次 useState、useRef、useEffect，list 上就有一個節點。例如一個元件依序呼叫 useState、useRef、useEffect，fiber.memoizedState 就指向第一個節點（useState 的），它的 next 指向 useRef 的節點，再下一個是 useEffect 的。

上一節說過，元件的 fiber 有兩份輪流用。每次 render，ReactFiberHooks.js 的 updateWorkInProgressHook 會從 current 那份 fiber 照順序把 hook 節點一個一個複製到 workInProgress 那份，所以值會一直留下來。render 時每遇到一個 useState，React 就往 list 的下一個節點走，把裡面存的值交回來。

React 怎麼知道哪個節點屬於哪個 useState 呢？它不知道變數名稱，也就不知道哪個 useState 是 name、哪個是 age，只能數：第一次呼叫拿第一個節點，第二次呼叫拿第二個，依此類推。

還有幾個問題

為什麼 <MyComponent /> 會 render，小寫的 <myComponent /> 不會？

JSX 編譯器看第一個字母決定 type 放什麼：大寫開頭是一個變數，小寫開頭是一個字串。用 esbuild 0.25.10 編譯：

<myComponent /> 看起來像元件，可是第一個字母小寫，編譯器就輸出字串 "myComponent"。React 收到 type: "myComponent"，把它當成 HTML tag，建出一個 <mycomponent>。叫做 myComponent 的 function 完全沒被呼叫。

JSX In Depth 也寫到，大小寫是 JSX 編譯器的規則，React 只會收到編譯器已經決定好的 type。

為什麼可以回傳 null，卻不能回傳一個 Component？

元件回傳的東西要是 ReactNode。null 是 ReactNode，意思是這裡什麼都不 render。Component 是一個 function，function 不是 ReactNode，要寫成 <Comp />，不能只寫 Comp。

在 React 19.3.1 裡寫 return Comp，畫面上什麼都沒有。development build 會印出「Functions are not valid as a React child. This may happen if you return Comp instead of from render. Or maybe you meant to call this function rather than return it.」，production build 什麼都不印。在 TypeScript 裡，把 function 指定給 ReactNode 型別的變數會報錯。

為什麼清單項目的 key 一換，state 就重設？

render 時，React 用 key 把新的 element 對到現有的 fiber：

  • key 跟 type 都一樣：重用這個 fiber，它的 memoizedState 跟 DOM 節點都留著。
  • key 不一樣：丟掉舊的 fiber，建一個 state 是空的新 fiber。

拿陣列的 index 當 key 就會出問題：在最前面插入一列，每一列的 index 都往後移一位，React 會把錯的 fiber 配給錯的列。下面每一列都有一個 useState('note for ' + label)，在 B、C 前面插入 A：

key 用什麼插入前在最前面插入 A 之後
indexB / note for B、C / note for CA / note for B、B / note for C、C / note for C
每列自己的 idB / note for B、C / note for CA / note for A、B / note for B、C / note for C

用 index 當 key，A 拿到了 B 原本的 state，B 拿到 C 的，C 是新建的 fiber。

整理

  1. JSX 產生 ReactElement，它的 type 是字串，或是一個 Component。
  2. render 時，React 替每個 element 建一個 fiber，或重用上一次的 fiber。type 是 Component 的話就呼叫它，拿到更多 element。
  3. React 沿著 fiber 的 child、sibling、return 一個一個走，不用遞迴呼叫。
  4. type 是字串的 fiber，在 completeWork 裡建出 DOM 節點，接好 child，這時還不在頁面上。
  5. commit 把這些 DOM 節點放進頁面，再把 root.current 換成新的版本。
