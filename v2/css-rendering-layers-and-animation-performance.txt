<h2>The rendering waterfall</h2>
<p>The browser turns CSS into pixels in stages. Each stage feeds the next. Triggering an early stage forces everything after it to re-run.</p>
<p><strong>Style → Layout → Paint → Composite</strong></p>
<ul>
<li><strong>Style</strong> works out which CSS rules apply to each element.</li>
<li><strong>Layout</strong> computes each element's size and position.</li>
<li><strong>Paint</strong> works out the pixels of each layer, a part of the page drawn as its own image.</li>
<li><strong>Composite</strong> stacks the layers into the final image.</li>
</ul>
<p>Style, Layout, and Paint run on the Main Thread, the same thread that runs JavaScript. Composite runs on a separate Compositor Thread, and the GPU draws the result. At 60fps, each frame has 16.7ms.</p>
<p>Change <code>width</code>? The browser recalculates Layout, repaints pixels, re-composites layers. Three stages, every frame, and Layout and Paint have to share the Main Thread with JavaScript.</p>
<p>Change <code>color</code>? Layout stays the same. Repaint and re-composite. Two stages.</p>
<p>Change <code>transform</code>? Layout and Paint stay the same. Only re-composite. One stage. And it runs on the Compositor Thread, so a long-running script doesn't stop Composite. Tested in November 2026 on Chrome 153: while a busy loop held the Main Thread for 600ms, the <code>transform</code> transition drew 36 frames and the <code>width</code> transition drew none.</p>

<h2>Compositor layers</h2>
<p>Each layer costs GPU memory. A 500x500 element takes roughly 1MB (4 bytes per pixel). So the browser promotes elements to independent Compositor layers only when it has a reason to.</p>
<p><strong>What creates a layer:</strong></p>
<ul>
<li><strong>3D transforms.</strong> <code>translateZ(0)</code> and <code>translate3d()</code> trigger layer promotion immediately. 2D transforms like <code>translateX(50px)</code> usually don't, unless they're inside an active animation.</li>
<li><strong><code>will-change: transform</code>.</strong> Forces the browser to create a layer in advance. Use it on elements you know will animate. Remove it after. Keeping layers alive wastes memory.</li>
<li><strong><code>position: fixed</code>.</strong> Fixed elements get their own layer.</li>
<li><strong>Active <code>transform</code> or <code>opacity</code> animations.</strong> Even 2D transforms temporarily get a layer during animation. The browser promotes them for the duration, then demotes them when it ends.</li>
</ul>
<p><strong>What doesn't create a layer:</strong></p>
<ul>
<li><strong>Hover states.</strong> Hover itself has nothing to do with layers. A <code>color</code> change on hover stays on the Main Thread. Only the animation <em>triggered by</em> hover might create one.</li>
<li><strong>Static <code>transform</code>.</strong> <code>transform: translateX(50px)</code> without animation or <code>will-change</code> is painted along with the rest of the page. No layer promotion.</li>
</ul>

<h2>Quick checklist</h2>
<ol>
<li><strong>Animate <code>transform</code> and <code>opacity</code>.</strong> These two run on the Compositor Thread.</li>
<li><strong>Use <code>will-change</code> on one or two elements, not globally.</strong> Remove it after animation ends.</li>
<li><strong>Record the animation in the DevTools Performance panel.</strong> If the Main track (the Main Thread's row) shows work in every frame, the animation is not on the Compositor Thread, even with no Layout or Paint in it.</li>
<li><strong>Test on slow hardware, or with DevTools CPU throttling.</strong> A fast laptop hides Layout cost.</li>
</ol>

## The rendering waterfall

The browser turns CSS into pixels in stages. Each stage feeds the next. Triggering an early stage forces everything after it to re-run.

**Style → Layout → Paint → Composite**

- **Style** works out which CSS rules apply to each element.
- **Layout** computes each element's size and position.
- **Paint** works out the pixels of each layer, a part of the page drawn as its own image.
- **Composite** stacks the layers into the final image.

Style, Layout, and Paint run on the Main Thread, the same thread that runs JavaScript. Composite runs on a separate Compositor Thread, and the GPU draws the result. At 60fps, each frame has 16.7ms.

Change `width`? The browser recalculates Layout, repaints pixels, re-composites layers. Three stages, every frame, and Layout and Paint have to share the Main Thread with JavaScript.

Change `color`? Layout stays the same. Repaint and re-composite. Two stages.

Change `transform`? Layout and Paint stay the same. Only re-composite. One stage. And it runs on the Compositor Thread, so a long-running script doesn't stop Composite. Tested in November 2026 on Chrome 153: while a busy loop held the Main Thread for 600ms, the `transform` transition drew 36 frames and the `width` transition drew none.

## Which properties trigger what

| Trigger | Properties | What happens |
|---|---|---|
| Layout | `width`, `height`, `margin`, `padding`, `top`, `left`, `font-size` | Recalculates positions of surrounding elements. Expensive. |
| Paint | `color`, `background`, `border-color`, `box-shadow`, `outline` | Redraws pixels. Positions stay the same. |
| Composite | `transform`, `opacity`, `filter` (except `blur()` and `drop-shadow()`) | Re-composites layers on the GPU. Cheap. |

`blur()` and `drop-shadow()` spread pixels outside the element, so Chrome animates them on the Main Thread. Chrome 153 animates `background-color` on the Compositor Thread, despite the Paint row.

For animations, always pick the Composite version:

| Instead of | Use |
|---|---|
| `left` / `top` / `margin` | `transform: translateX/Y()` |
| `width` / `height` | `transform: scale()` (stretches the content) |
| `display: none/block` | `opacity: 0/1` (still takes space and clicks) |

## Compositor layers

Each layer costs GPU memory. A 500x500 element takes roughly 1MB (4 bytes per pixel). So the browser promotes elements to independent Compositor layers only when it has a reason to.

**What creates a layer:**

- **3D transforms.** `translateZ(0)` and `translate3d()` trigger layer promotion immediately. 2D transforms like `translateX(50px)` usually don't, unless they're inside an active animation.
- **`will-change: transform`.** Forces the browser to create a layer in advance. Use it on elements you know will animate. Remove it after. Keeping layers alive wastes memory.
- **`position: fixed`.** Fixed elements get their own layer.
- **Active `transform` or `opacity` animations.** Even 2D transforms temporarily get a layer during animation. The browser promotes them for the duration, then demotes them when it ends.

**What doesn't create a layer:**

- **Hover states.** Hover itself has nothing to do with layers. A `color` change on hover stays on the Main Thread. Only the animation *triggered by* hover might create one.
- **Static `transform`.** `transform: translateX(50px)` without animation or `will-change` is painted along with the rest of the page. No layer promotion.

## What this looks like in practice

A sidebar that slides in. Two ways to build it.

```css
/* Animating width: Layout reflow every frame */
.sidebar {
  width: 0;
  transition: width 0.3s;
}
.sidebar.open {
  width: 240px;
}
```

A recording in the DevTools Performance panel shows Layout and Paint in every frame. With a data table on the page, each Layout also recalculates the table's column widths. Tested in November 2026 on Chrome 153, with a 125-row table next to the sidebar: about 2.7ms of Main Thread work per frame at full CPU speed, and about 13.1ms with DevTools CPU throttling set to 6x slower. That is 80% of a 16.7ms frame, but every run, at both speeds, still drew 61 or 62 frames a second.

```css
/* Animating transform: Compositor only */
.sidebar {
  width: 240px;
  transform: translateX(-100%);
  transition: transform 0.3s;
}
.sidebar.open {
  transform: translateX(0);
}
```

The Performance panel shows no Layout at all. The sidebar has its own layer during the transition. The Main Thread handles only the first and last few frames. The Compositor Thread draws the rest.

The sidebar is always 240px wide. It just starts off-screen and slides in. Same visual result. No reflow.

## The `will-change` trap

Developers discovered `will-change` and slapped it on everything.

```css
/* Don't do this */
* { will-change: transform, opacity; }
```

Each `will-change` creates a layer: in Chrome 153, a page with 200 divs went from 4 layers to 207. At 1MB per 500x500 element, 200 elements that size need about 200MB. web.dev warns that on devices with limited memory, that many layers can cost more than they gain.

Use `will-change` like a scalpel:

```css
/* Add it right before animation */
.card {
  transition: transform 0.1s;
}
.card:hover {
  will-change: transform;
}
.card:active {
  transform: scale(0.98);
}
```

The `transition` goes on `.card`, not `.card:active`. Otherwise the card snaps back when the mouse is released.

Most of the time you don't need `will-change` at all: the browser auto-promotes elements during a `transform` or `opacity` transition or animation. You only need `will-change` when you want the layer created *before* the animation starts, to avoid a first-frame hitch.

---

## Quick checklist

1. **Animate `transform` and `opacity`.** These two run on the Compositor Thread.
2. **Use `will-change` on one or two elements, not globally.** Remove it after animation ends.
3. **Record the animation in the DevTools Performance panel.** If the Main track (the Main Thread's row) shows work in every frame, the animation is not on the Compositor Thread, even with no Layout or Paint in it.
4. **Test on slow hardware, or with DevTools CPU throttling.** A fast laptop hides Layout cost.

<h2>渲染的流程</h2>
<p>瀏覽器把 CSS 變成畫面上的像素，要經過幾個階段，前一個階段的結果會交給下一個。所以只要觸發了前面的階段，後面的每一個都得重跑。</p>
<p><strong>Style → Layout → Paint → Composite</strong></p>
<ul>
<li><strong>Style</strong>：算出每個元素套用了哪些 CSS 規則。</li>
<li><strong>Layout</strong>：算出每個元素的大小跟位置。</li>
<li><strong>Paint</strong>：算出每個 layer 上的像素。layer 是頁面上單獨畫成一張圖的部分。</li>
<li><strong>Composite</strong>：把各個 layer 疊成最後的畫面。</li>
</ul>
<p>Style、Layout、Paint 在 Main Thread 上跑，JavaScript 也是在這條 thread 上跑。Composite 則在另一條 Compositor Thread 上跑，最後由 GPU 畫出來。如果要 60fps，每個 frame 只有 16.7ms。</p>
<p>改 <code>width</code> 的話，瀏覽器要重算 Layout、重新 paint、再重新 composite。每個 frame 都是三個階段，而且 Layout 跟 Paint 得跟 JavaScript 共用 Main Thread。</p>
<p>改 <code>color</code> 的話，Layout 不變，只要重新 paint 跟 composite，兩個階段。</p>
<p>改 <code>transform</code> 的話，Layout 跟 Paint 都不變，只要重新 composite，一個階段。而且這一步在 Compositor Thread 上跑，所以就算有一段 script 跑很久，composite 也不會停下來。2026 年 11 月在 Chrome 153 上測試時，用一個 busy loop 佔住 Main Thread 600ms，這段時間裡 <code>transform</code> 的 transition 照樣畫了 36 個 frame，<code>width</code> 的是 0 個。</p>

<h2>哪些屬性會觸發哪個階段</h2>

























<table><thead><tr><th>觸發</th><th>屬性</th><th>會發生什麼</th></tr></thead><tbody><tr><td>Layout</td><td><code>width</code>、<code>height</code>、<code>margin</code>、<code>padding</code>、<code>top</code>、<code>left</code>、<code>font-size</code></td><td>周圍元素的位置都要重算，很花時間。</td></tr><tr><td>Paint</td><td><code>color</code>、<code>background</code>、<code>border-color</code>、<code>box-shadow</code>、<code>outline</code></td><td>重新算像素，位置不變。</td></tr><tr><td>Composite</td><td><code>transform</code>、<code>opacity</code>、<code>filter</code>（<code>blur()</code> 跟 <code>drop-shadow()</code> 除外）</td><td>在 GPU 上重新疊 layer，開銷很小。</td></tr></tbody></table>
<p><code>blur()</code> 跟 <code>drop-shadow()</code> 會讓像素超出元素原本的範圍，所以 Chrome 把這兩種動畫放在 Main Thread 上跑。另外，<code>background</code> 雖然列在 Paint 那一列，Chrome 153 的 <code>background-color</code> 動畫卻是在 Compositor Thread 上跑的。</p>
<p>做動畫的時候，一律挑 Composite 的寫法：</p>





















<table><thead><tr><th>不用</th><th>改用</th></tr></thead><tbody><tr><td><code>left</code> / <code>top</code> / <code>margin</code></td><td><code>transform: translateX/Y()</code></td></tr><tr><td><code>width</code> / <code>height</code></td><td><code>transform: scale()</code>（內容會跟著拉伸）</td></tr><tr><td><code>display: none/block</code></td><td><code>opacity: 0/1</code>（還是佔著位置，也會收到點擊）</td></tr></tbody></table>

<h2>Compositor layer</h2>
<p>每個 layer 都要佔 GPU 記憶體，一個 500x500 的元素大約 1MB（每個像素 4 bytes）。所以瀏覽器要有理由，才會把元素提升成獨立的 compositor layer。</p>
<p><strong>會建立 layer 的：</strong></p>
<ul>
<li><strong>3D transform。</strong> 寫上 <code>translateZ(0)</code> 或 <code>translate3d()</code>，元素馬上就會提升成 layer。<code>translateX(50px)</code> 這種 2D transform 通常不會，除非它正在動畫裡。</li>
<li><strong><code>will-change: transform</code>。</strong> 讓瀏覽器提前建好 layer。用在確定會動的元素上，動完就拿掉，因為 layer 一直留著會浪費記憶體。</li>
<li><strong><code>position: fixed</code>。</strong> fixed 的元素會有自己的 layer。</li>
<li><strong>正在跑的 <code>transform</code> 或 <code>opacity</code> 動畫。</strong> 就算是 2D transform，動畫期間也會暫時有一個 layer，瀏覽器在動畫開始時提升它，結束後再降回來。</li>
</ul>
<p><strong>不會建立 layer 的：</strong></p>
<ul>
<li><strong>hover 狀態。</strong> hover 本身跟 layer 無關，hover 時改 <code>color</code> 還是在 Main Thread 上做。只有 hover <em>觸發的</em>動畫才可能建立 layer。</li>
<li><strong>靜態的 <code>transform</code>。</strong> 沒有動畫、也沒有 <code>will-change</code> 的 <code>transform: translateX(50px)</code>，會跟頁面其他部分一起 paint，不會提升成 layer。</li>
</ul>

<span data-line=""><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">  transform</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">: </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">translateX</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">0</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">);</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">}</span></span></code></pre></figure>
<p>Performance 分頁裡完全沒有 Layout，transition 期間側欄有自己的 layer。Main Thread 只處理開頭跟結尾那幾個 frame，中間的都由 Compositor Thread 畫。</p>
<p>側欄一直都是 240px 寬，只是一開始在畫面外，再滑進來。畫面上的結果一樣，但不用重新排版。</p>

<h2><code>will-change</code> 的 trap</h2>
<p>有人發現 <code>will-change</code> 好用，就把它加在每個元素上：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="css" data-theme="github-dark github-light"><code data-language="css" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">/* 不要這樣寫 */</span></span>
<span data-line=""><span style="--shiki-dark:#85E89D;--shiki-light:#22863A">*</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> { </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">will-change</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">: transform, opacity; }</span></span></code></pre></figure>
<p>每個 <code>will-change</code> 都會建立一個 layer。在 Chrome 153 裡，一個有 200 個 div 的頁面，layer 從 4 個變成 207 個。照 500x500 大約 1MB 來算，200 個這種大小的元素大約要 200MB。web.dev 提醒，在記憶體少的裝置上，開這麼多 layer 可能弊大於利。</p>
<p><code>will-change</code> 要用在剛好需要的地方：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="css" data-theme="github-dark github-light"><code data-language="css" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">/* 動畫開始前才加上 */</span></span>
<span data-line=""><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">.card</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> {</span></span>
<span data-line=""><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">  transition</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">: transform </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">0.1</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">s</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">;</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">}</span></span>
<span data-line=""><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">.card:hover</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> {</span></span>
<span data-line=""><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">  will-change</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">: transform;</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">}</span></span>
<span data-line=""><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">.card:active</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> {</span></span>
<span data-line=""><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">  transform</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">: </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">scale</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">0.98</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">);</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">}</span></span></code></pre></figure>
<p><code>transition</code> 要寫在 <code>.card</code> 上，不能只寫在 <code>.card:active</code> 裡，不然放開滑鼠時卡片會直接跳回原狀。</p>
<p>其實多數時候連 <code>will-change</code> 都不用寫，因為 <code>transform</code> 或 <code>opacity</code> 的 transition 跟 animation 進行時，瀏覽器會自動把元素提升成 layer。只有想在動畫<em>開始前</em>就建好 layer、避免第一個 frame 頓一下的時候，才需要 <code>will-change</code>。</p>
<hr>
<h2>檢查清單</h2>
<ol>
<li><strong>動畫用 <code>transform</code> 跟 <code>opacity</code>。</strong> 這兩個在 Compositor Thread 上跑。</li>
<li><strong><code>will-change</code> 只用在一兩個元素上，不要全域加。</strong> 動畫結束就拿掉。</li>
<li><strong>用 DevTools 的 Performance 分頁錄下動畫。</strong> 如果 Main 那條 track（Main Thread 那一列）每個 frame 都有工作，動畫就不是在 Compositor Thread 上跑，就算裡面沒有 Layout 或 Paint 也一樣。</li>
<li><strong>在慢的裝置上測，或開 DevTools 的 CPU throttling。</strong> 在快的筆電上看不太出 Layout 的開銷。</li>
</ol>
