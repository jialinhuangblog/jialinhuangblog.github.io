N+1 不是資料庫的問題，是程式碼的結構

假設一個頁面要顯示 20 篇文章的作者名字。資料模型是最常見的那種，每篇 post 存一個 author_id，名字則放在 users 表裡。也就是說，一篇文章對一個作者，一個作者可以有很多篇文章（多對一）。

這樣總共是 1 + 20 = 21 次查詢。如果一次來回要 5ms，加起來就是 105ms；同樣的資料如果用一個 JOIN，就只剩 1 次來回。

這段程式碼看起來就是個普通的迴圈，可是每跑一圈都會發一次網路請求，這就是 N+1。

教科書通常把它放在「資料庫優化」那一章。這樣分類反而把重點藏起來了，因為資料庫每一次查詢都跑得好好的，那 20 次查詢是迴圈一圈一圈發出去的。

為什麼說它不是資料庫的問題

如果把細節都拿掉，程式碼其實只剩下這兩步：

這裡的「來回」，可以是任何一種跨邊界的請求：

  • 一次 SQL 查詢（最常見的版本）
  • 一次呼叫另一個微服務的 HTTP 請求
  • 一次 Redis GET
  • 一次 gRPC 呼叫
  • 一次讀檔

只要清單裡有 N 個元素，而每個元素都各發一次跨邊界的請求，就是 N+1。當然，跨的邊界不同，花的時間也不一樣：SQL 是一次網路來回，HTTP 通常更貴，讀檔則比較便宜。但結構是完全一樣的。所以與其記「不要在迴圈裡查資料庫」，倒不如記「不要在迴圈裡跨邊界」。

同一種結構的三種寫法

換了框架之後，同一種結構會寫成不同的樣子。後面兩種比較麻煩，因為迴圈被藏起來了。

一般的 for 迴圈。 就是開頭那段。這種寫法至少把迴圈明明白白寫在程式碼裡。

ORM 的 lazy load。 迴圈還在，可是查詢不見了：

ORM 為了讓 post.author 用起來像一般物件，會在程式讀到這個屬性的當下發一次查詢。這次查詢沒有寫在程式碼裡，要等到開 profiler 或去翻 SQL log，才會發現那一行 print 其實是 20 次來回。

GraphQL resolver。 到這裡，連迴圈都不見了：

程式碼裡一個迴圈都沒寫，迴圈在 GraphQL 引擎裡。引擎拿到 20 篇文章之後，會對每篇各跑一次 author resolver，而每次都去查一次 user 表。結果一樣是 1+N，寫的人手上卻只有一段乾淨的宣告式查詢，code review 的時候也就更難發現。

Promise.all 看起來像解法，其實不是

這時候第一個反應通常是：那全部用 Promise.all 一起送出去不就好了？

這樣寫，頁面會變快。那 20 次作者查詢一個一個跑要 20 × 5ms = 100ms（開頭的 105ms 還包含拿文章清單的那 1 次）；如果 connection pool 有 20 條以上的連線，20 個同時送出去，延遲就只剩最慢的那一個，大約 5ms。如果 pool 只有 10 條，就得分兩批，大約 10ms。

可是資料庫還是收到 20 次查詢，次數一次都沒少。連線也一樣，原本是 1 條連線佔 100ms，現在變成 20 條連線各佔 5ms，加起來佔用的連線時間其實差不多。JOIN 卻只要 1 條連線、1 次來回就拿到全部的資料。

要消掉 N+1，得把 N 次請求合併成 1 次。

三種真正的解法

下面三種合併的位置不同。

JOIN（在資料庫層合併）：

一個查詢就搞定。不過它只能在同一個資料庫、同一個查詢裡完成，所以沒辦法跨服務。

IN 批次查詢（在應用層手動合併）：

這樣就從 21 次降到 2 次。雖然比 JOIN 多一次來回，但邏輯很清楚，而且資料就算分散在不同的服務、cache 或資料庫裡也沒關係。中間那行 posts.map(p => p.author_id) 一次收齊了所有 id，下一行才能把它們塞進同一個 IN。

DataLoader（在應用層自動合併）： 如果程式裡沒有那個一次收齊 id 的地方，就輪到它了。GraphQL resolver 剛好就是這種情況，因為每個 resolver 手上只有自己那篇文章，根本不知道另外 19 篇的存在。

誰呼叫誰

由上到下依序是：

DataLoader 只負責收集 key、抓準時間點，查詢要寫在批次函式裡。ORM 跟資料庫照常執行收到的查詢，跟沒用 DataLoader 的時候一樣。每個角色的細節可以點開來看。

DataLoader：收集 key、抓時間點，不碰資料庫

.load(id) 只把 id 收進批次，回傳一個還沒完成的 promise，這時候還沒有任何查詢。DataLoader 本身不處理 SQL、ORM 或資料表，只管 key 跟 promise。

你的批次函式：查詢寫在這裡

DataLoader 會交給你 [id1, id2, …]，而要跑什麼查詢由你決定，所以那一個 IN 查詢就寫在這裡：

findMany({ in: ids }) 是寫在批次函式裡的，並不是 DataLoader 產生的。另外，回傳的資料也要照 ids 的順序排好，不然每個呼叫 .load() 的地方會拿到錯的那一筆。

ORM：把 findMany 轉成 SQL

prisma.user.findMany({ where: { id: { in: ids } } }) 會變成 SELECT * FROM users WHERE id IN ($1, $2, …)，這就是一般的 ORM 轉換，跟其他查詢沒兩樣。就算把 Prisma 換成 TypeORM（In(ids)）或 Drizzle（inArray(users.id, ids)），產出的 SQL 也還是一樣。這一層跟有沒有用 DataLoader 無關。

DataLoader 怎麼「自動收集」

既然 resolver 是一個一個呼叫 .load() 的，那 DataLoader 怎麼知道什麼時候該一起送出去呢？

.load(key) 不會碰資料庫，它只把 key 推進一個批次，然後馬上回傳一個 pending promise。同一輪 event loop 裡所有的 .load()，都會進到同一個批次。等這一輪結束，DataLoader 才送出一次，也就是呼叫批次函式（那個 IN 查詢），等資料庫回來之後，再依照 index 把每個 promise 填上結果。

那「一輪」到底什麼時候結束呢？拿 await Promise.all(ids.map(id => loader.load(id))) 來說，依序會發生這些事：

第 4 步在 GraphQL 裡很常見。因為上一層 resolver 的 promise 一 resolve，下一層 resolver 才開始跑，所以下一層的 .load() 就是在這種回呼裡呼叫的。

第 1 步預約的寫法是 Promise.resolve().then(() => process.nextTick(dispatch))。這裡包了兩層，.then 負責等第 2 步，process.nextTick 負責等第 4 步：

  • .then：它的回呼要等第 3 步結束才會跑，所以第 2 步的 key 都收得進來。
  • process.nextTick：它是在 .then 的回呼裡才呼叫的，而 Node 會等目前排隊的 promise 回呼全部跑完，才執行它排進去的 dispatch，所以第 4 步的 key 也收得進來。

如果第 1 步直接呼叫 process.nextTick(dispatch)，dispatch 反而會比第 4 步那些 promise 回呼先跑，GraphQL 下一層的 key 就會錯過這一批。

什麼寫法會讓批次失效

只要在兩次 .load() 中間放一個真的 await（真的去等 I/O），批次就會在那裡提早送出。如果迴圈每一圈都 await，100 次 load 就會被切成 100 批：

第二種是很常見的錯誤。每次 await loader.load(id) 都要等這次 load 完才進下一圈，所以每一圈都自成一個批次，用了 DataLoader 還是回到 N+1。

不過 GraphQL resolver 雖然每個欄位也各自 await load()，卻是安全的。因為 GraphQL 引擎會平行呼叫同一層的 resolver，所以這些 .load() 發生在同一輪，也就進到同一個批次。只有自己手寫的依序迴圈會出問題，因為它在兩次 .load() 中間夾了一個 await。

別跟 p-limit 搞混

DataLoader 跟 p-limit 看起來都在「控制一堆非同步」，可是 DataLoader 減少的是查詢次數，p-limit 限制的是同時跑的數量。

DataLoaderp-limit
解決N+1（查詢太多次）pool 用光（同時太多連線）
做法收集 .load()，合併成一次批次查詢限制同時跑的非同步數量
查詢次數同一個 loader 的 5 個 .load()，合併成 1 次查詢100 個任務照樣跑 100 次，同時最多 10 條連線
適合可以合併成 WHERE IN (...) 的資料每個任務做的事都不一樣（讀 → 判斷 → 更新）

這兩個通常不會用在同一段程式碼上。DataLoader 把同一批 key 合併起來查，查詢數已經夠少，用不到 p-limit 的限流。像 API key 那個例子，不管這次查了幾個 key，都只查 links 一次、roles 一次。p-limit 處理的則是沒辦法合併的任務，因為每個任務做的事都不一樣，DataLoader 幫不上忙。

不過用了 DataLoader，connection pool 還是可能不夠用。如果同一層有三個欄位各用一個 loader，這三個 loader 會在同一輪各自送出一批，一個 request 就同時要用到三條連線；同時有 10 個 request 進來，就是 30 條。這時候可以調大 pool，或用 p-limit 限制同時處理的 request 數。連線用光以後，Prisma 預設讓查詢等 10 秒（pool_timeout），等超過就失敗；pg driver 的 connectionTimeoutMillis 預設是 0，會一直等下去（Prisma 文件）。

回到開頭 Promise.all 的那個問題。如果真的沒辦法批次，一定要送 N 次獨立的請求，這時候才需要 p-limit。只是它並不會讓請求變少，它的用途是讓這些請求不要同時把 connection pool 的連線用光。

整理一下。N+1 是程式碼的寫法造成的，所以不只發生在 SQL，HTTP、Redis、讀檔也會，只是 SQL 最常見。ORM 的 lazy load 跟 GraphQL resolver 會把迴圈藏起來。Promise.all 雖然讓頁面變快，請求數卻沒變。要把 N 次合併成 1 次，可以用 JOIN、手動 IN，或 DataLoader。DataLoader 靠 Promise.then 加上 process.nextTick 抓送出的時機，所以每個 resolver 照樣各自呼叫 .load()，同一個 loader 在同一輪收到的 key，卻只合併成一次查詢。
