N+1 不是資料庫的問題，是程式碼的結構

2026/06/28
n-plus-1dataloadergraphqlevent-loopnodejsperformance

一個管理頁要列出所有 API key，每個 key 旁邊顯示它有哪些 role。資料模型是多對多：一個 key 可以有好幾個 role，一個 role 也可以給好幾個 key 用，所以兩邊的對應關係存在中間表 links。

要拿到一個 key 的 role，得先到 links 找出它的 role id，再到 roles 把這些 role 讀出來。下面的程式碼都用 Prisma 接 PostgreSQL，假設資料庫一次來回 5ms，總共有 5 個 key。

最直覺的寫法：11 次

數一下查詢次數：

如果 key 變成 100 個，就是 1 + 2 × 100 = 201 次。查詢次數跟著 key 的數量一起長，這就是 N+1。這個例子每個 key 要跨兩張表，所以算起來是 1 + 2N。

資料庫每一次查詢都跑得好好的，那 11 次是迴圈一圈一圈發出去的。假如每一圈呼叫的是另一個服務的 HTTP API、一次 Redis GET，或讀一次檔，一樣是 N+1，只是每次來回花的時間不同。所以與其記「不要在迴圈裡查資料庫」，倒不如記「不要在迴圈裡跨邊界」。

頁面變快了，可是資料庫收到的還是 11 次查詢。如果 key 有 100 個，就會有 100 次 links 查詢同時要連線，pool 不夠大的話，剩下的就得排隊。

換成 GraphQL resolver：又變回 11 次

前面每一步都有個前提：有一個變數同時裝著全部的 key。換成 GraphQL，這個變數就不在我們寫的程式碼裡了。

adminRoles 是一個 field resolver，每個 key 各跑一次：

GraphQL 引擎拿到 5 個 key 之後，會對每個 key 各呼叫一次 adminRoles，而且同一層的 resolver 是同時呼叫的。程式碼裡一個迴圈都沒寫，跑起來卻等於第一步的迴圈加上第二步的 Promise.all，查詢又回到 11 次。

每次呼叫 resolver，傳進來的 apiKey 只有一個，所以沒辦法自己收齊 key 去查 IN。

用 DataLoader 把 resolver 的呼叫收齊：回到 3 次

dataloader 是 Facebook 開源的 npm 套件。resolver 改成各自呼叫 .load(key)。GraphQL 是同時呼叫這 5 個 resolver 的，所以 5 次 .load() 會落在同一輪 event loop 裡。DataLoader 等這一輪結束，才把 5 個 key 一次交給批次函式，而批次函式裡寫的就是前面那段 IN。

DataLoader 怎麼「自動收集」

既然 resolver 是一個一個呼叫 .load() 的，那 DataLoader 怎麼知道什麼時候該一起送出去呢？

.load(key) 只把 key 加進一個批次，然後馬上回傳一個 pending promise。等這一輪 event loop 結束，DataLoader 才呼叫一次批次函式，查詢結果回來之後，再依照 index 把每個 promise 填上結果。

那「一輪」到底什麼時候結束呢？拿 await Promise.all(ids.map(id => loader.load(id))) 來說，依序會發生這些事：

第 4 步在 GraphQL 裡很常見。因為上一層 resolver 的 promise 一 resolve，下一層 resolver 才開始跑，所以下一層的 .load() 就是在這種 callback 裡呼叫的。

第 1 步預約的寫法是 Promise.resolve().then(() => process.nextTick(dispatch))。這裡包了兩層，.then 負責等第 2 步，process.nextTick 負責等第 4 步：

  • .then：第 3 步的同步程式碼跑完之前，這個 callback 不會執行，所以第 2 步的 key 這時都已經在批次裡了。
  • process.nextTick：Promise.resolve().then().then().then(() => loader.load(x)) 隔了三層才呼叫 .load()，x 照樣跟第 2 步的 key 在同一批。因為 V8 開始跑 promise callback 之後，會一路跑到 microtask queue 清空才把控制權交回 Node，途中新排進來的 callback 也照跑。DataLoader 是在其中一個 .then callback 裡呼叫 process.nextTick，所以 Node 要等 queue 清空、拿回控制權之後，才執行 nextTick 排的 dispatch。

如果第 1 步直接呼叫 process.nextTick(dispatch)，dispatch 反而會比第 4 步那些 promise callback 先跑，GraphQL 下一層的 key 就會錯過這一批。

什麼寫法會讓批次失效

只要在兩次 .load() 中間放一個真的 await（真的去等 I/O），批次就會在那裡提早送出。如果迴圈每一圈都 await，100 次 load 就會被切成 100 批：

第二種寫法裡，每次 await loader.load(id) 都要等這次查完才進下一圈。所以第一個 key 會自己成一批送出去。等它查完，迴圈才呼叫第二次 .load()，這時候 DataLoader 又開了一個新的批次。100 個 key 就是 100 批，用了 DataLoader 還是回到 N+1。

GraphQL resolver 雖然也各自 await load()，卻不會這樣。GraphQL 引擎會同時呼叫同一層的 resolver，5 次 .load() 都在任何一個 await 結束之前就呼叫完了，所以落在同一輪。

p-limit 限制的是同時跑幾個

p-limit 是一個 npm 套件，用來限制同時跑幾個非同步任務。把 100 次查詢交給 pLimit(10)，100 次一樣全部會送出去，只是同一時間最多 10 個在跑，其他的排隊等。

用了 DataLoader，pool 還是可能不夠用。如果同一層有三個欄位各用一個 loader，一個 request 就同時要用到三條連線；同時有 10 個 request 進來，就是 30 條。這時候可以調大 pool，或用 p-limit 限制同時處理的 request 數。至於等連線最多等多久，Prisma 文件寫到，Prisma v6 的 pool_timeout 預設是 10 秒；v7 接 Postgres 改用 pg adapter，它的 connectionTimeoutMillis 預設是 0，也就是不設上限。

回到 Promise.all 那一步。如果每個任務做的事都不一樣，沒辦法合併成一個 IN，就只能送 N 次查詢，這時候用 p-limit 讓這些查詢不要同時把 pool 的連線用光。

Promise.all 只讓時間變短，查詢次數要靠合併才會變少。從 IN 開始，每一步都把 N 次查詢合成一次，只是合併發生在不同的地方，依序是自己寫的程式碼、Prisma、資料庫和 DataLoader。GraphQL resolver 每次只拿到一個 key，所以 DataLoader 靠 Promise.then 加上 process.nextTick 抓送出的時機，把同一輪的 .load() 收齊。
