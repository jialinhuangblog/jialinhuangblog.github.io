14:T75e3,<p>Once <code>sales</code> is partitioned by year with <code>PARTITION BY RANGE (sale_date)</code>, a common next step is dealing with old data: splitting the 2022 partition out into its own table to archive, or moving it to cheaper disk. In Postgres, one <code>DETACH PARTITION</code> takes the partition out from under <code>sales</code> and leaves it as a standalone table. MySQL and Oracle have no such command; you create an empty table first and swap it with the partition using <code>EXCHANGE PARTITION</code>. The <code>PARTITION BY</code> that creates the partitions reads the same in all three databases, yet the steps to split one out differ, because whether a partition is a table, and where its data is stored, differ across the three.</p>

<p>The design lets the database tell which partition a row is in from its value alone. Querying 2023 in the two examples above, MySQL's <code>EXPLAIN</code> lists only <code>p2023</code>, and Postgres's query plan scans only <code>sales_2023</code>; no other partition is read. If rows could stay in the parent, every query would have to scan the parent too, just to be sure nothing matching was there.</p>
<h2>The two questions</h2>
<p><strong>Q1. Does a partition become its own table?</strong> Can you <code>SELECT * FROM &#x3C;partition></code> as you would any table, or is there still just one table that the partitions are only reachable through? This is a question about <em>identity</em>.</p>
<p><strong>Q2. Where does a partition's data physically live?</strong> One file, many files, a specific disk? This is a question about <em>location</em>. All three databases use a <em>tablespace</em> to say where data goes. A tablespace is a name you write in SQL; behind it are files or a directory on disk, and one tablespace can hold many tables.</p>

























<table><thead><tr><th>Database</th><th>Q1: its own table?</th><th>Q2: where the data lives</th></tr></thead><tbody><tr><td>MySQL</td><td>no</td><td>each partition has its own <code>.ibd</code> file, but can't be assigned a tablespace</td></tr><tr><td>Oracle</td><td>no</td><td>a partition has no file of its own; it shares data files with the other tables in its tablespace, and can be assigned a tablespace</td></tr><tr><td>PostgreSQL</td><td>yes, a real child table</td><td>each partition has its own file, and can be assigned a tablespace</td></tr></tbody></table>
<p>The two answers can differ. A MySQL partition has its own file, yet it is not a table of its own.</p>
<p>A MySQL tablespace can't hold a partition together with another table; Oracle and Postgres can:</p>
<ul>
<li><strong>MySQL</strong>: each partition is its own tablespace, one <code>.ibd</code> file holding only that partition. Several plain tables can share a tablespace made with <code>CREATE TABLESPACE</code>, but a partition can't go in; you get <code>ERROR 1478 (HY000): InnoDB : A partitioned table is not allowed in a shared tablespace.</code>.</li>
<li><strong>Oracle</strong>: each partition can be put in any tablespace alongside other tables, and one data file mixes data from several tables.</li>
<li><strong>PostgreSQL</strong>: each partition can also be put in any tablespace, in the same directory as other tables, but every table and every partition gets its own file.</li>
</ul>
<p>The next three sections use the same example: two tables, <code>orders</code> and <code>sales</code>, with <code>sales</code> split into 2022 and 2023 partitions. Each section's diagram switches between before and after partitioning; hover a table or partition to light up the files that hold its data. Every file location in the diagrams was queried in docker; the versions are in the last section.</p>
<h2>MySQL</h2>
<p>In MySQL (InnoDB), each table gets its own <code>.ibd</code> file by default, and that file is its tablespace. After partitioning, <code>sales.ibd</code> is gone and each partition has its own <code>.ibd</code>, yet there is still only one table, <code>sales</code>:</p>

<p>To query only the 2022 partition, you go through <code>sales</code>:</p>

<p>Putting <code>p2022</code> on a cheap disk can't be done with a tablespace. <a href="https://dev.mysql.com/doc/refman/8.4/en/general-tablespaces.html">MySQL's tablespace documentation</a> states that partitions can't go into a shared tablespace made with <code>CREATE TABLESPACE</code>, so you give that partition a <a href="https://dev.mysql.com/doc/refman/8.4/en/innodb-create-table-external.html"><code>DATA DIRECTORY</code></a> when you create it.</p>
<h2>Oracle</h2>
<p>Like MySQL, Oracle still has only one <code>sales</code> after partitioning. The difference is location: in <a href="https://docs.oracle.com/en/database/oracle/oracle-database/19/cncpt/logical-storage-structures.html">Oracle</a>, every table and partition lives in some tablespace. Under a tablespace are data files, shared by the tables in that tablespace.</p>
<p>The existing <code>sales</code> can be turned into a partitioned table with <code>ALTER TABLE</code>, assigning each partition a tablespace in the same statement, for example 2022 to <code>ts_cold</code> on a cheap disk and 2023 staying in <code>ts_fast</code>:</p>

<h2>Does splitting one out move the data?</h2>
<p>When a partition is split out, none of the three copies any data, but each does it differently:</p>
<ul>
<li><strong>Postgres</strong>: a partition is already a table with its own file. After <code>DETACH</code>, <code>sales_2022</code> is still the same file, <code>base/5/16387</code>; it just no longer hangs under <code>sales</code>.</li>
<li><strong>MySQL</strong>: the swap renames the two <code>.ibd</code> files. Looking at inodes (the file system's number for each file) with <code>ls -i</code>: before the swap, p2022's data is in <code>sales#p#p2022.ibd</code> (inode 168717) and the empty <code>sales_2022.ibd</code> is inode 168721; after it, file 168717 is named <code>sales_2022.ibd</code> and 168721 is named <code>sales#p#p2022.ibd</code>.</li>
<li><strong>Oracle</strong>: <a href="https://docs.oracle.com/en/database/oracle/oracle-database/19/vldbg/maintenance-partition-tables-indexes.html">Oracle's documentation</a> says the exchange swaps the two data segments. A data segment is the space a table or partition occupies in the data files. In the test, before the swap, partition <code>sales_2022</code> had segment 73291, starting at block 778 of <code>cold01.dbf</code> in <code>ts_cold</code> (Oracle's file number 26); after it, <code>sales_2022_arc</code> had the same segment 73291 at the same place.</li>
</ul>
<p>These operations aren't always instant, though. Postgres's <code>DETACH</code> waits for queries running on <code>sales</code> to finish. The MySQL and Oracle swaps check by default that every row falls inside the partition's range, so more data means a longer check.</p>

Once `sales` is partitioned by year with `PARTITION BY RANGE (sale_date)`, a common next step is dealing with old data: splitting the 2022 partition out into its own table to archive, or moving it to cheaper disk. In Postgres, one `DETACH PARTITION` takes the partition out from under `sales` and leaves it as a standalone table. MySQL and Oracle have no such command; you create an empty table first and swap it with the partition using `EXCHANGE PARTITION`. The `PARTITION BY` that creates the partitions reads the same in all three databases, yet the steps to split one out differ, because whether a partition is a table, and where its data is stored, differ across the three.

## To split out 2023, the other years need partitions too

Say `sales` has one row each for 2021 through 2024. To split out only 2023, you might write a single partition in MySQL 8.0:

```sql
ALTER TABLE sales PARTITION BY RANGE (YEAR(sale_date)) (
  PARTITION p2023 VALUES LESS THAN (2024)
);
-- ERROR 1526 (HY000): Table has no partition for value 2024
```

The whole statement fails. `p2023` is only a name; its range is "less than 2024", so 2021, 2022 and 2023 would all go into it, and 2024 has nowhere to go. Once a table is partitioned, no whole table is left behind; the remaining years have to be assigned too:

```sql
ALTER TABLE sales PARTITION BY RANGE (YEAR(sale_date)) (
  PARTITION p_before VALUES LESS THAN (2023),      -- 2021, 2022
  PARTITION p2023    VALUES LESS THAN (2024),      -- 2023 only
  PARTITION p_after  VALUES LESS THAN MAXVALUE     -- 2024 onward
);
```

Postgres can use a `DEFAULT` partition to take every row that matches no range:

```sql
CREATE TABLE sales_2023  PARTITION OF sales FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');
CREATE TABLE sales_other PARTITION OF sales DEFAULT;   -- 2021, 2022, 2024 all go here
```

The design lets the database tell which partition a row is in from its value alone. Querying 2023 in the two examples above, MySQL's `EXPLAIN` lists only `p2023`, and Postgres's query plan scans only `sales_2023`; no other partition is read. If rows could stay in the parent, every query would have to scan the parent too, just to be sure nothing matching was there.

## The two questions

**Q1. Does a partition become its own table?** Can you `SELECT * FROM <partition>` as you would any table, or is there still just one table that the partitions are only reachable through? This is a question about *identity*.

**Q2. Where does a partition's data physically live?** One file, many files, a specific disk? This is a question about *location*. All three databases use a *tablespace* to say where data goes. A tablespace is a name you write in SQL; behind it are files or a directory on disk, and one tablespace can hold many tables.

| Database | Q1: its own table? | Q2: where the data lives |
|---|---|---|
| MySQL | no | each partition has its own `.ibd` file, but can't be assigned a tablespace |
| Oracle | no | a partition has no file of its own; it shares data files with the other tables in its tablespace, and can be assigned a tablespace |
| PostgreSQL | yes, a real child table | each partition has its own file, and can be assigned a tablespace |

The two answers can differ. A MySQL partition has its own file, yet it is not a table of its own.

A MySQL tablespace can't hold a partition together with another table; Oracle and Postgres can:

- **MySQL**: each partition is its own tablespace, one `.ibd` file holding only that partition. Several plain tables can share a tablespace made with `CREATE TABLESPACE`, but a partition can't go in; you get `ERROR 1478 (HY000): InnoDB : A partitioned table is not allowed in a shared tablespace.`.
- **Oracle**: each partition can be put in any tablespace alongside other tables, and one data file mixes data from several tables.
- **PostgreSQL**: each partition can also be put in any tablespace, in the same directory as other tables, but every table and every partition gets its own file.

The next three sections use the same example: two tables, `orders` and `sales`, with `sales` split into 2022 and 2023 partitions. Each section's diagram switches between before and after partitioning; hover a table or partition to light up the files that hold its data. Every file location in the diagrams was queried in docker; the versions are in the last section.

## MySQL

In MySQL (InnoDB), each table gets its own `.ibd` file by default, and that file is its tablespace. After partitioning, `sales.ibd` is gone and each partition has its own `.ibd`, yet there is still only one table, `sales`:

<iframe src="/embeds/partition-storage?db=mysql" width="100%" height="320" style="border:0;display:block;margin:1.5rem 0 2.5rem" loading="lazy" title="MySQL files before and after partitioning"></iframe>

To query only the 2022 partition, you go through `sales`:

```sql
SELECT * FROM sales PARTITION (p2022);
SELECT * FROM `sales#p#p2022`;   -- ERROR 1146: Table 'shop.sales#p#p2022' doesn't exist
```

To turn `p2022` into a plain table, create an empty table with the same columns and indexes as `sales`, remove its partitioning, then swap it with `p2022`:

```sql
CREATE TABLE sales_2022 LIKE sales;
ALTER TABLE sales_2022 REMOVE PARTITIONING;
ALTER TABLE sales EXCHANGE PARTITION p2022 WITH TABLE sales_2022;
-- sales_2022 now holds the 2022 rows; partition p2022 of sales is empty
```

[MySQL's exchange documentation](https://dev.mysql.com/doc/refman/8.4/en/partitioning-management-exchange.html) lists the conditions for the swap, such as neither table having foreign keys.

Putting `p2022` on a cheap disk can't be done with a tablespace. [MySQL's tablespace documentation](https://dev.mysql.com/doc/refman/8.4/en/general-tablespaces.html) states that partitions can't go into a shared tablespace made with `CREATE TABLESPACE`, so you give that partition a [`DATA DIRECTORY`](https://dev.mysql.com/doc/refman/8.4/en/innodb-create-table-external.html) when you create it.

## Oracle

Like MySQL, Oracle still has only one `sales` after partitioning. The difference is location: in [Oracle](https://docs.oracle.com/en/database/oracle/oracle-database/19/cncpt/logical-storage-structures.html), every table and partition lives in some tablespace. Under a tablespace are data files, shared by the tables in that tablespace.

The existing `sales` can be turned into a partitioned table with `ALTER TABLE`, assigning each partition a tablespace in the same statement, for example 2022 to `ts_cold` on a cheap disk and 2023 staying in `ts_fast`:

```sql
ALTER TABLE sales MODIFY PARTITION BY RANGE (sale_date) (
  PARTITION sales_2022 VALUES LESS THAN (DATE '2023-01-01') TABLESPACE ts_cold,
  PARTITION sales_2023 VALUES LESS THAN (DATE '2024-01-01') TABLESPACE ts_fast
);
```

<iframe src="/embeds/partition-storage?db=oracle" width="100%" height="360" style="border:0;display:block;margin:1.5rem 0 2.5rem" loading="lazy" title="Oracle data files before and after partitioning"></iframe>

`ts_fast` has a single data file, `fast01.dbf`, and the data of both `orders` and `sales_2023` is written into it.

A partition is not a table, so queries go through `sales`:

```sql
SELECT * FROM sales PARTITION (sales_2022);
SELECT * FROM sales_2022;   -- ORA-00942: table or view "SHOP"."SALES_2022" does not exist
```

To turn partition `sales_2022` into a plain table, create an empty `sales_2022_arc` and swap it with the partition:

```sql
CREATE TABLE sales_2022_arc TABLESPACE ts_fast FOR EXCHANGE WITH TABLE sales;
ALTER TABLE sales EXCHANGE PARTITION sales_2022 WITH TABLE sales_2022_arc;
```

## PostgreSQL

A Postgres tablespace maps to a directory; without one, data goes into the default `pg_default`. Each table has its own data file in that directory, named by an internal number. After partitioning, `sales` has no file of its own; its data lives in the partitions' files:

<iframe src="/embeds/partition-storage?db=postgres" width="100%" height="340" style="border:0;display:block;margin:1.5rem 0 2.5rem" loading="lazy" title="Postgres files before and after partitioning"></iframe>

A Postgres partition is itself a table, so you can query it directly:

```sql
SELECT * FROM sales_2022;
SELECT * FROM sales PARTITION (sales_2022);   -- no error, but it reads all of sales
```

If you copy the MySQL syntax, Postgres takes `PARTITION` as an alias for `sales`, so the query covers every year. In the test, `sales` had 3 rows, 2 of them from 2022, and this line returned 3.

Unlike MySQL and Oracle, Postgres also can't turn an existing table into a partitioned one with `ALTER TABLE`; you create a new table:

```sql
CREATE TABLE sales (id int, sale_date date) PARTITION BY RANGE (sale_date);
CREATE TABLE sales_2022 PARTITION OF sales FOR VALUES FROM ('2022-01-01') TO ('2023-01-01');
CREATE TABLE sales_2023 PARTITION OF sales FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');
```

To turn a partition into a plain table, Postgres needs no swap. `sales_2022` is already a table that hangs under `sales`; `DETACH` takes it off:

```sql
ALTER TABLE sales DETACH PARTITION sales_2022;
-- sales_2022 is now a plain standalone table: archive it, drop it, move it
```

A tablespace's directory can sit on any disk. Create a tablespace on the cheap disk, then move `sales_2022` into it, and its file moves into that directory:

```sql
CREATE TABLESPACE cold_hdd LOCATION '/mnt/hdd/pg';
ALTER TABLE sales_2022 SET TABLESPACE cold_hdd;
```

## Does splitting one out move the data?

When a partition is split out, none of the three copies any data, but each does it differently:

- **Postgres**: a partition is already a table with its own file. After `DETACH`, `sales_2022` is still the same file, `base/5/16387`; it just no longer hangs under `sales`.
- **MySQL**: the swap renames the two `.ibd` files. Looking at inodes (the file system's number for each file) with `ls -i`: before the swap, p2022's data is in `sales#p#p2022.ibd` (inode 168717) and the empty `sales_2022.ibd` is inode 168721; after it, file 168717 is named `sales_2022.ibd` and 168721 is named `sales#p#p2022.ibd`.
- **Oracle**: [Oracle's documentation](https://docs.oracle.com/en/database/oracle/oracle-database/19/vldbg/maintenance-partition-tables-indexes.html) says the exchange swaps the two data segments. A data segment is the space a table or partition occupies in the data files. In the test, before the swap, partition `sales_2022` had segment 73291, starting at block 778 of `cold01.dbf` in `ts_cold` (Oracle's file number 26); after it, `sales_2022_arc` had the same segment 73291 at the same place.

These operations aren't always instant, though. Postgres's `DETACH` waits for queries running on `sales` to finish. The MySQL and Oracle swaps check by default that every row falls inside the partition's range, so more data means a longer check.

<p>資料庫這樣設計，是為了能從一列的值直接判斷它在哪個 partition。上面兩個例子查 2023 年的資料時，MySQL 的 <code>EXPLAIN</code> 只列出 <code>p2023</code>，Postgres 的 query plan 只掃 <code>sales_2023</code>，其他 partition 都不讀。如果允許資料留在母表，每次查詢都得多掃母表一次，才能確定裡面沒有符合的資料。</p>
<h2>兩個問題</h2>
<p><strong>Q1：partition 會變成一張獨立的 table 嗎？</strong> 能不能像對一般 table 那樣下 <code>SELECT * FROM &#x3C;partition></code>？還是說仍然只有一張 table，partition 只能透過它存取？這是 <em>identity</em>（身分）的問題。</p>
<p><strong>Q2：partition 的資料實際存在哪裡？</strong> 一個檔案、很多個檔案，還是某顆指定的硬碟？這是 <em>location</em>（位置）的問題。三個資料庫都用 <em>tablespace</em> 來指定資料放在哪。tablespace 是 SQL 裡寫的一個名字，背後對應到磁碟上的檔案或目錄，一個 tablespace 底下可以放很多張 table。</p>

























<table><thead><tr><th>資料庫</th><th>Q1：是獨立的 table 嗎？</th><th>Q2：資料存在哪</th></tr></thead><tbody><tr><td>MySQL</td><td>不是</td><td>每個 partition 有自己的 <code>.ibd</code> 檔，但不能指定 tablespace</td></tr><tr><td>Oracle</td><td>不是</td><td>partition 沒有自己的檔案，跟同一個 tablespace 裡的其他 table 共用 data file；可以指定放在哪個 tablespace</td></tr><tr><td>PostgreSQL</td><td>是，一張真的 child table</td><td>每個 partition 有自己的檔案，也可以指定放在哪個 tablespace</td></tr></tbody></table>
<p>兩題的答案可以不一樣。MySQL 的 partition 有自己的檔案，卻不是獨立的 table。</p>
<p>MySQL 的 tablespace 不能同時放 partition 跟別的 table，Oracle 跟 Postgres 可以：</p>
<ul>
<li><strong>MySQL</strong>：每個 partition 自己一個 tablespace，也就是一個 <code>.ibd</code> 檔，裡面只有它。好幾張一般的 table 可以一起放進 <code>CREATE TABLESPACE</code> 建的 tablespace，但 partition 放不進去，會報 <code>ERROR 1478 (HY000): InnoDB : A partitioned table is not allowed in a shared tablespace.</code>。</li>
<li><strong>Oracle</strong>：每個 partition 可以指定放進任何 tablespace，跟別的 table 放在一起，而且同一個 data file 裡會混著好幾張 table 的資料。</li>
<li><strong>PostgreSQL</strong>：每個 partition 也可以指定放進任何 tablespace，跟別的 table 放在同一個目錄，但每張 table、每個 partition 各自一個檔案。</li>
</ul>
<p>下面三節用同一組例子：<code>orders</code> 跟 <code>sales</code> 兩張 table，<code>sales</code> 按年切成 2022、2023 兩個 partition。每節的圖可以切換切 partition 之前跟之後，滑鼠移到 table 或 partition 上，存它資料的檔案會亮起來。圖裡的檔案位置都是用 docker 實際查出來的，版本寫在最後一節。</p>

<h2>Oracle</h2>
<p>Oracle 跟 MySQL 一樣，切完還是只有一張 <code>sales</code>。不同的是位置：<a href="https://docs.oracle.com/en/database/oracle/oracle-database/19/cncpt/logical-storage-structures.html">Oracle</a> 的每張 table、每個 partition 都一定放在某個 tablespace 裡。tablespace 底下是 data file，放在同一個 tablespace 的 table 共用這些 data file。</p>

<p>如果照抄 MySQL 的寫法，Postgres 會把 <code>PARTITION</code> 當成 <code>sales</code> 的別名，查的就是全部年份。實測時 <code>sales</code> 有 3 筆，其中 2022 年 2 筆，這行回傳的是 3 筆。</p>
<p>Postgres 也沒辦法像 MySQL、Oracle 那樣用 <code>ALTER TABLE</code> 把一張現有的 table 改成 partitioned table，要另外建一張新的：</p>

<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">CREATE</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> TABLE</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1"> sales_2023</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> PARTITION</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> OF sales </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">FOR</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> VALUES</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> FROM</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> (</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'2023-01-01'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">) </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">TO</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> (</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'2024-01-01'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">);</span></span></code></pre></figure>
<p>如果想讓 partition 轉成單純的 table，Postgres 不用交換。<code>sales_2022</code> 本來就是 table，只是掛在 <code>sales</code> 底下，用 <code>DETACH</code> 拿掉就好：</p>

<span data-line=""><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">-- sales_2022 現在是一張普通的獨立 table，要封存、刪除或搬走都可以</span></span></code></pre></figure>

<h2>拆出來的時候，資料會搬嗎</h2>
<p>把 partition 拆出來時，三個資料庫都不會複製資料，但做法不一樣：</p>
<ul>
<li><strong>Postgres</strong>：partition 本來就是一張有自己檔案的 table。<code>DETACH</code> 之後，<code>sales_2022</code> 還是同一個檔案 <code>base/5/16387</code>，只是不再掛在 <code>sales</code> 底下。</li>
<li><strong>MySQL</strong>：交換是把兩個 <code>.ibd</code> 檔互換名字。用 <code>ls -i</code> 看檔案的 inode（檔案系統給每個檔案的編號），交換前，p2022 的資料在 <code>sales#p#p2022.ibd</code>（inode 168717），空的 <code>sales_2022.ibd</code> 是 inode 168721；交換後，inode 168717 這個檔案改叫 <code>sales_2022.ibd</code>，168721 改叫 <code>sales#p#p2022.ibd</code>。</li>
<li><strong>Oracle</strong>：<a href="https://docs.oracle.com/en/database/oracle/oracle-database/19/vldbg/maintenance-partition-tables-indexes.html">Oracle 的文件</a>寫，交換是把兩邊的 data segment 對調。data segment 是一張 table 或一個 partition 在 data file 裡佔用的那塊空間。實測交換前，partition <code>sales_2022</code> 的 segment 編號是 73291，起點在 <code>ts_cold</code> 的 <code>cold01.dbf</code>（Oracle 給它的檔案編號是 26）第 778 個 block；交換後，<code>sales_2022_arc</code> 的 segment 是同一個 73291、同一個位置。</li>
</ul>
<p>不過這些操作不一定馬上做完。Postgres 的 <code>DETACH</code> 要等 <code>sales</code> 上正在跑的 query 結束。MySQL 跟 Oracle 的交換預設會逐列檢查資料有沒有落在 partition 的範圍內，資料越多，檢查越久。</p>
