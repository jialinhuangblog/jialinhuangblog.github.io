The home page of this site is 14 KB of HTML. With its scripts, styles and fonts it is about 300 KB on the wire. A cold start took 1128 ms. Which stage took the time?

This object follows the W3C spec Navigation Timing Level 2 (Working Draft, this revision dated 2026-09-01); the API is PerformanceNavigationTiming. The Navigation Timing diagram redrawn in the iframe below comes from the first version, Level 1 (W3C Recommendation, 2012-12-17), in its Processing Model section; its API is performance.timing, now marked deprecated on MDN. Each stage's blocking issue

  • unload, redirect, App cache: always 0 on this site. unload is set only when the previous page was on the same origin, 0 otherwise. redirect is 0 because since Chrome 115 the browser upgrades http:// to https:// before sending the request, so the server's 301 for http:// is never followed.
  • DNS: the first lookup took 73 ms. After that the answer stays in the operating system's resolver cache, which a fresh browser profile does not clear, so only the first of five cold starts was not 0.
  • TCP: a handshake needs at least one round trip, and ping from this machine to the server is 42 to 54 ms. No code removes that; only a CDN moves the endpoint closer. The 152 ms in the table is an exception: halfway through TLS on that load, Chrome swapped its certificate verifier and reopened the connection, so it measured two connections. In a Chrome netlog recorded separately (a log of the connection steps), each single handshake took 46 to 68 ms. Only starting a new Chrome for every measurement runs into this.
  • TLS: a TLS 1.2 handshake takes two round trips and TLS 1.3 takes one; a connection that is not reused is also slow. HTTP/1.1 keeps connections open by default and HTTP/2 and HTTP/3 multiplex one connection, so TLS usually happens once per origin.
  • Request: the server handling the request. For a static file, a long TTFB usually means the CDN had no cached copy; for server rendering, the time mostly goes to the render function. Rendering strategy mainly affects this stage.
  • Response: the HTML is large, or not compressed. Compare encodedBodySize with decodedBodySize (transferSize includes headers, so it does not work for this). Here encodedBodySize is 3772 and it decodes to 14187, so compression is on.
  • Parse: the same HTML takes 5 to 10 ms on reload and 198 to 424 ms on a cold start; the difference is all waiting for stylesheets. <body> has inline <script> elements, and the HTML spec makes them wait for stylesheets in <head> that are still loading, so the parser stops too. Five more cold starts with a script that also records each resource's timing put domInteractive 1 to 29 ms after the last stylesheet finished, every time. One of the three stylesheets is cross-site, fonts.googleapis.com, and it alone costs an extra DNS lookup plus a new connection, 57 to 138 ms. So a faster Parse on this site means inlining the stylesheets, preloading them, or dropping the cross-site origin.
  • Deferred scripts: <script defer> runs after parsing and before DOMContentLoaded, and DOMContentLoaded waits for it. This site loads its chunks with async, which does not delay DOMContentLoaded, so this is 0 here. If a page loads <script defer src="app.js"> and app.js takes 300 ms to run, those 300 ms show up in Deferred scripts.
  • Subresources: load waits for images, scripts and iframes. MDN does not list fonts, but they count: on a test page whose only slow resource is a 2 s font, load came 2 s later. The article page from-setstate-to-pixels embeds a cross-site iframe. Across five runs of the script that records resource timing this stage took 487 to 596 ms, nearly all of it waiting for that iframe: domComplete came 0.2 to 1.7 ms after the iframe finished.

The measurement script

Node 22, macOS, Chrome installed at the default path. The script reads the entry after load. The reload column uses the same script plus one step: after the first load, send Page.reload and read the entry again. The stylesheet timings come from a sibling script that also dumps performance.getEntriesByType('resource'). The font test is a local page whose only slow resource is a font file delayed by 2 s.

Which Level 1 timestamps did Level 2 drop

  • navigationStart: Level 2 changed clocks. Level 1's values are absolute milliseconds since 1970; Level 2 uses DOMHighResTimeStamp counted from the time origin, so the start is always 0. The reasons are that an absolute clock can go backwards when the system clock is adjusted and only resolves to a millisecond. navigationStart became the 0 of startTime.
  • domLoading: browsers create the Document at different moments, Chrome before the response begins, IE when it starts, Firefox after buffering some of it, so the value measured an implementation detail. Issue #13 proposed removing it in 2015 and the spec added a deprecation note. The closest value is responseEnd.
  • Prompt for unload: happens before navigationStart, since Level 1 defines the start as the moment right after prompting to unload the previous document, so neither version has a timestamp for it; the diagram draws the box only to show what precedes the start.

The gap between startTime and fetchStart has no name. unload and redirect would fall in that span if they happened, and both were 0 here; a redirectStart of 0 means there was no redirect, not that a redirect took 0 ms.
