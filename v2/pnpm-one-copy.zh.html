pnpm 怎麼把十份 react 塞進一份的空間

pnpmpackage-managerfilesystemhardlinkcopy-on-write

機器上有十個專案都用 react 的話，npm 會在每個專案各放一份完整的 react，pnpm 讓這十個專案都連到同一份。這是怎麼辦到的呢？

node_modules/react 是一條 symlink

打開一個 pnpm 專案的 node_modules/react：

node_modules/react -> .pnpm/react@19.2.4/node_modules/react

所以真正的套件檔案在 .pnpm/ 底下，還在專案裡。但 .pnpm/ 那份也不是完整複製，它的檔案連到一個整台機器共用的 store，每個檔案在 store 只存一份。

從 node_modules/react 到 store，中間有兩種連結。滑鼠移到下面的套件上，它的連結會亮起來。

import 'react' 的時候，Node 在 node_modules/react 讀到 symlink，照著它找到 .pnpm/ 底下的檔案。這條 symlink 只連到專案內的 .pnpm/，不會連到 store。

連到 store 的是 .pnpm/ 底下的檔案，唯一那份實體放在 store。

store 只存一份，用內容定址

store 在 macOS 是 ~/Library/pnpm/store，Linux 是 ~/.local/share/pnpm/store。機器上裝過的每個套件檔案，在那裡只存一份。

store 裡的檔案用內容的 hash 當檔名。兩個專案都裝了同一個 react/index.js，內容一樣、hash 就一樣，store 裡只有一個檔案，兩邊都指向它。

git 的 .git/objects/ 也是這樣，裡面的檔案用 SHA 當檔名。

連到 store：Linux 是 hardlink，macOS 是 clone

「pnpm 用 hardlink」這個說法，只在 Linux 上成立。store 的檔案跟專案的檔案是同一個 inode。一個 inode，兩個名字指著它：

inode #100  <- react/index.js，真的 bytes
  ├─ ~/.local/share/pnpm/store/.../index.js   (1)
  └─ my-app/.../.pnpm/react@.../index.js       (2)
                                     link count = 2

在第二個專案裝同一個套件，它又 hardlink 到同一個 inode，count 變 3。

在 macOS 的 APFS（Apple 的檔案系統）上，pnpm 改用 copy-on-write clone，底層呼叫 clonefile。專案的檔案拿到自己的新 inode。它的磁碟區塊跟 store 共用，但只到有人寫入為止。第一次寫入，檔案系統只複製改動的區塊，兩個檔案就分開了。因為 inode 是自己的，link count 讀出來是 1。

ls -li 兩邊都能用。第一欄是 inode，第三欄是 link count。

為什麼 macOS 選 clone

hardlink 代表 store 的檔案跟專案的檔案根本是同一個檔。要是有工具寫進 node_modules，它就直接寫進 store，機器上每個專案的那個套件都跟著壞。在 Linux 上，pnpm 用 verifyStoreIntegrity 處理這件事：連結到專案之前，先檢查 store 裡的檔案有沒有被改過。

clone 沒有這個風險。寫入專案裡的檔案時，檔案系統只複製被改的區塊，store 那份不變。檔案系統支援 copy-on-write 時，pnpm 就用 clone，pnpm 文件也說 clone 是最快、最安全的方式。

讀 link count

link count 就是有幾個名字指向同一個 inode。

在 Linux，它同時是個共用計數器。count 2 代表 store 加一個專案。count 5 代表四個專案共用這一份。

在 macOS，count 永遠是 1。clone 出來的檔案有自己的 inode，沒有第二個名字指向它。空間還是共用的，但共用發生在磁碟區塊，link count 不會計算這一層。

自己驗證看看

Linux 跟 macOS 查詢共用的指令不同，因為 hardlink 共用 inode，clone 共用磁碟區塊。

install 也比較快

pnpm 官方的 benchmark 裡，alotta-packages 這個專案在有快取、有 lockfile 的情況下重裝，npm 要 16.4 秒，pnpm 12 要 2.23 秒，約 7.4 倍。這個情境下套件都已經在 store 裡，pnpm 只需要建立連結，不用再下載跟複製。

什麼快取都沒有的 clean install，store 是空的，pnpm 還是快 7.4 倍：npm 要 1 分 40 秒，pnpm 12 要 13.6 秒。這時沒有檔案可以連結，pnpm 官方的解釋是步驟的順序不同。npm 先解析完全部相依，再全部下載，最後全部寫進 node_modules。pnpm 在解析相依的同時，就開始把套件下載進 store，剩下的套件在連結階段一邊下載一邊連結。
