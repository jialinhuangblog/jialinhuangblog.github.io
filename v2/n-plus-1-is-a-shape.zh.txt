14:Tdc15,<p>假設一個頁面要顯示 20 篇文章的作者名字。資料模型是最常見的那種，每篇 <code>post</code> 存一個 <code>author_id</code>，名字則放在 <code>users</code> 表裡。也就是說，一篇文章對一個作者，一個作者可以有很多篇文章（多對一）。</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>posts(id, title, author_id)   author_id → users.id</span></span>
<span data-line=""><span>users(id, name)</span></span></code></pre></figure>
<p>最直覺的寫法，大概就是一個 for 迴圈：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> posts</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> await</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> db.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">query</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'SELECT * FROM posts LIMIT 20'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">);  </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// 1 次查詢</span></span>
<span data-line=""> </span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">for</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> (</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> post</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> of</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> posts) {</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  post.author </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">=</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> await</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> db.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">query</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span></span>
<span data-line=""><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">    'SELECT * FROM users WHERE id = ?'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, [post.author_id]</span></span>

<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">}</span></span></code></pre></figure>
<p>這樣總共是 1 + 20 = 21 次查詢。如果一次來回要 5ms，加起來就是 105ms；同樣的資料如果用一個 JOIN，就只剩 1 次來回。</p>
<p>這段程式碼看起來就是個普通的迴圈，可是每跑一圈都會發一次網路請求，這就是 N+1。</p>
<p>教科書通常把它放在「資料庫優化」那一章。這樣分類反而把重點藏起來了，因為資料庫每一次查詢都跑得好好的，那 20 次查詢是迴圈一圈一圈發出去的。</p>
<h2>為什麼說它不是資料庫的問題</h2>
<p>如果把細節都拿掉，程式碼其實只剩下這兩步：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>拿到一份清單（1 次查詢）</span></span>
<span data-line=""><span>清單裡每個元素各跑一次來回（N 次查詢）</span></span></code></pre></figure>
<p>這裡的「來回」，可以是任何一種跨邊界的請求：</p>
<ul>
<li>一次 SQL 查詢（最常見的版本）</li>
<li>一次呼叫另一個微服務的 HTTP 請求</li>
<li>一次 Redis <code>GET</code></li>
<li>一次 gRPC 呼叫</li>
<li>一次讀檔</li>
</ul>
<p>只要清單裡有 N 個元素，而每個元素都各發一次跨邊界的請求，就是 N+1。當然，跨的邊界不同，花的時間也不一樣：SQL 是一次網路來回，HTTP 通常更貴，讀檔則比較便宜。但結構是完全一樣的。所以與其記「不要在迴圈裡查資料庫」，倒不如記「<strong>不要在迴圈裡跨邊界</strong>」。</p>
<h2>同一種結構的三種寫法</h2>
<p>換了框架之後，同一種結構會寫成不同的樣子。後面兩種比較麻煩，因為迴圈被藏起來了。</p>
<p><strong>一般的 for 迴圈。</strong> 就是開頭那段。這種寫法至少把迴圈明明白白寫在程式碼裡。</p>
<p><strong>ORM 的 lazy load。</strong> 迴圈還在，可是查詢不見了：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="python" data-theme="github-dark github-light"><code data-language="python" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D"># Django</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">posts </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">=</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> Post.objects.all()       </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D"># 1 次查詢</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">for</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> post </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">in</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> posts:</span></span>
<span data-line=""><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">    print</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(post.author.name)      </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D"># ← 讀屬性的時候發一次查詢</span></span></code></pre></figure>
<p>ORM 為了讓 <code>post.author</code> 用起來像一般物件，會在程式讀到這個屬性的當下發一次查詢。這次查詢沒有寫在程式碼裡，要等到開 profiler 或去翻 SQL log，才會發現那一行 <code>print</code> 其實是 20 次來回。</p>
<p><strong>GraphQL resolver。</strong> 到這裡，連迴圈都不見了：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="graphql" data-theme="github-dark github-light"><code data-language="graphql" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">{</span></span>
<span data-line=""><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">  posts</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> {</span></span>
<span data-line=""><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">    title</span></span>
<span data-line=""><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">    author</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> { </span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">name</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> }</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  }</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">}</span></span></code></pre></figure>
<p>程式碼裡一個迴圈都沒寫，迴圈在 GraphQL 引擎裡。引擎拿到 20 篇文章之後，會對每篇各跑一次 <code>author</code> resolver，而每次都去查一次 user 表。結果一樣是 1+N，寫的人手上卻只有一段乾淨的宣告式查詢，code review 的時候也就更難發現。</p>
<h2>Promise.all 看起來像解法，其實不是</h2>
<p>這時候第一個反應通常是：那全部用 Promise.all 一起送出去不就好了？</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> posts</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> await</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> db.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">query</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'SELECT * FROM posts LIMIT 20'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">);</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">await</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> Promise</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">all</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  posts.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">map</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">post</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =></span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">    db.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">query</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'SELECT * FROM users WHERE id = ?'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, [post.author_id])</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  )</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">);</span></span></code></pre></figure>
<p>這樣寫，頁面會變快。那 20 次作者查詢一個一個跑要 20 × 5ms = 100ms（開頭的 105ms 還包含拿文章清單的那 1 次）；如果 connection pool 有 20 條以上的連線，20 個同時送出去，延遲就只剩最慢的那一個，大約 5ms。如果 pool 只有 10 條，就得分兩批，大約 10ms。</p>
<p>可是資料庫還是收到 20 次查詢，次數一次都沒少。連線也一樣，原本是 1 條連線佔 100ms，現在變成 20 條連線各佔 5ms，加起來佔用的連線時間其實差不多。JOIN 卻只要 1 條連線、1 次來回就拿到全部的資料。</p>
<p>要消掉 N+1，得把 N 次請求合併成 1 次。</p>
<h2>三種真正的解法</h2>
<p>下面三種合併的位置不同。</p>
<p><strong>JOIN（在資料庫層合併）：</strong></p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="sql" data-theme="github-dark github-light"><code data-language="sql" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">SELECT</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> p.</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">*</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">u</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">name</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> AS</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> author_name</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">FROM</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> posts p </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">JOIN</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> users u </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">ON</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> p</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">author_id</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> u</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">id</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">LIMIT</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> 20</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">;</span></span></code></pre></figure>
<p>一個查詢就搞定。不過它只能在同一個資料庫、同一個查詢裡完成，所以沒辦法跨服務。</p>
<p><strong>IN 批次查詢（在應用層手動合併）：</strong></p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> posts</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> await</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> db.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">query</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'SELECT * FROM posts LIMIT 20'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">);</span></span>

<p>這樣就從 21 次降到 2 次。雖然比 JOIN 多一次來回，但邏輯很清楚，而且資料就算分散在不同的服務、cache 或資料庫裡也沒關係。中間那行 <code>posts.map(p => p.author_id)</code> <strong>一次收齊了所有 id</strong>，下一行才能把它們塞進同一個 IN。</p>
<p><strong>DataLoader（在應用層自動合併）：</strong> 如果程式裡沒有那個一次收齊 id 的地方，就輪到它了。GraphQL resolver 剛好就是這種情況，因為每個 resolver 手上只有自己那篇文章，根本不知道另外 19 篇的存在。</p>
<h2>要跨兩張表的時候</h2>
<p>前面的例子只跨一張表（post → user），但實際遇到的 N+1 常常要跨兩層。例如一個 production 上的 GraphQL 查詢，要拉出一串 API key，而每個 key 都帶著它的 <code>adminRoles</code>：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="graphql" data-theme="github-dark github-light"><code data-language="graphql" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">query</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> {</span></span>
<span data-line=""><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">  apiKeys</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> {</span></span>
<span data-line=""><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">    name</span></span>
<span data-line=""><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">    adminRoles</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> { </span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">id</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, </span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">name</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> }</span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">   # ← 每個 key 都會觸發一次查詢</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  }</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">}</span></span></code></pre></figure>
<p><code>adminRoles</code> 沒辦法從單一張表拿到，因為資料模型是多對多：一個 API key 可以有很多 role，一個 role 也可以屬於很多 key。所以兩邊的對應關係存在中間表 <code>links</code>，role 本身的資料則存在 <code>roles</code>。</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>api_keys(api_key, name)</span></span>
<span data-line=""><span>links(api_key, admin_role_id)      ← 中間表，多對多</span></span>
<span data-line=""><span>roles(id, name, description)</span></span>
<span data-line=""> </span>
<span data-line=""><span>api_keys ──&#x3C; links >── roles</span></span></code></pre></figure>
<p>因此查一個 key 的 <code>adminRoles</code> 要跨兩層，先從 <code>api_keys</code> 到 <code>links</code> 找出它的 role id，再到 <code>roles</code> 載入這些 role。最直覺的 field resolver 大概長這樣：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">@</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">ResolveField</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(() </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">=></span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> [ApiKeyAdminRoleDto], { name: </span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'adminRoles'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> })</span></span>

<p>假設有 5 個 API key，數一下查詢次數：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>1 × SELECT api_keys</span></span>
<span data-line=""><span>5 × SELECT links  WHERE api_key = ?    ← 每個 key 一次</span></span>
<span data-line=""><span>5 × SELECT roles  WHERE id IN (...)    ← 每個 key 一次</span></span>

<p>這裡用的 DataLoader 是 Facebook 開源的 npm 套件 <a href="https://github.com/graphql/dataloader"><code>dataloader</code></a>，GraphQL 後端幾乎都在用。<code>new DataLoader(batchFn)</code> 會包住一個批次函式，收集、合併、依序 resolve 都由它處理，寫的人只要負責那個 IN 查詢。</p>

<h2>誰呼叫誰</h2>
<p>由上到下依序是：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>你的 resolver  →  .load(id)          （每個 parent 一次）</span></span>
<span data-line=""><span>DataLoader     →  收集 id，呼叫一次你的 batchFn</span></span>
<span data-line=""><span>你的 batchFn   →  一次查詢：findMany({ id: { in: ids } })</span></span>
<span data-line=""><span>ORM            →  SELECT ... WHERE id IN (...)</span></span>
<span data-line=""><span>資料庫         →  執行 SQL</span></span></code></pre></figure>
<p>DataLoader 只負責收集 key、抓準時間點，查詢要寫在批次函式裡。ORM 跟資料庫照常執行收到的查詢，跟沒用 DataLoader 的時候一樣。每個角色的細節可以點開來看。</p>
<details>
<summary><strong>DataLoader</strong>：收集 key、抓時間點，不碰資料庫</summary>
<p><code>.load(id)</code> 只把 id 收進批次，回傳一個還沒完成的 promise，這時候還沒有任何查詢。DataLoader 本身不處理 SQL、ORM 或資料表，只管 key 跟 promise。</p>
</details>
<details>
<summary><strong>你的批次函式</strong>：查詢寫在這裡</summary>
<p>DataLoader 會交給你 <code>[id1, id2, …]</code>，而要跑什麼查詢由你決定，所以那一個 <code>IN</code> 查詢就寫在這裡：</p>

</details>
<details>
<summary><strong>ORM</strong>：把 findMany 轉成 SQL</summary>
<p><code>prisma.user.findMany({ where: { id: { in: ids } } })</code> 會變成 <code>SELECT * FROM users WHERE id IN ($1, $2, …)</code>，這就是一般的 ORM 轉換，跟其他查詢沒兩樣。就算把 Prisma 換成 TypeORM（<code>In(ids)</code>）或 Drizzle（<code>inArray(users.id, ids)</code>），產出的 SQL 也還是一樣。這一層跟有沒有用 DataLoader 無關。</p>
</details>
<h2>DataLoader 怎麼「自動收集」</h2>
<p>既然 resolver 是一個一個呼叫 <code>.load()</code> 的，那 DataLoader 怎麼知道什麼時候該一起送出去呢？</p>
<p><code>.load(key)</code> 不會碰資料庫，它只把 key 推進一個批次，然後馬上回傳一個 <strong>pending promise</strong>。同一輪 event loop 裡所有的 <code>.load()</code>，都會進到同一個批次。等這一輪結束，DataLoader 才送出一次，也就是呼叫批次函式（那個 IN 查詢），等資料庫回來之後，再依照 index 把每個 promise 填上結果。</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>load(key1) load(key2) … load(key5)   ← 同一輪，全部推進同一個批次</span></span>
<span data-line=""><span>        ↓ 這一輪結束</span></span>
<span data-line=""><span>batchFn([key1..key5]) → 1 × SELECT ... IN (...)</span></span>
<span data-line=""><span>        ↓ 資料庫回傳</span></span>
<span data-line=""><span>依 index 把每個 .load() 的 promise resolve 掉</span></span></code></pre></figure>
<p>那「一輪」到底什麼時候結束呢？拿 <code>await Promise.all(ids.map(id => loader.load(id)))</code> 來說，依序會發生這些事：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>1. map 跑第 1 次 load(id1)：key 進批次，DataLoader 預約一次 dispatch（送出批次）</span></span>
<span data-line=""><span>2. map 繼續跑 load(id2) … load(id100)：key 都進同一個批次</span></span>
<span data-line=""><span>3. map 跑完，同步程式碼結束</span></span>
<span data-line=""><span>4. 其他已經排隊的 promise 回呼先跑，裡面如果又呼叫 .load()，key 也進這個批次</span></span>
<span data-line=""><span>5. 輪到 dispatch：用整批 key 呼叫一次批次函式</span></span></code></pre></figure>
<p>第 4 步在 GraphQL 裡很常見。因為上一層 resolver 的 promise 一 resolve，下一層 resolver 才開始跑，所以下一層的 <code>.load()</code> 就是在這種回呼裡呼叫的。</p>
<p>第 1 步預約的寫法是 <a href="https://github.com/graphql/dataloader/blob/main/src/index.js"><code>Promise.resolve().then(() => process.nextTick(dispatch))</code></a>。這裡包了兩層，<code>.then</code> 負責等第 2 步，<code>process.nextTick</code> 負責等第 4 步：</p>
<ul>
<li><strong><code>.then</code></strong>：它的回呼要等第 3 步結束才會跑，所以第 2 步的 key 都收得進來。</li>
<li><strong><code>process.nextTick</code></strong>：它是在 <code>.then</code> 的回呼裡才呼叫的，而 Node 會等目前排隊的 promise 回呼全部跑完，才執行它排進去的 dispatch，所以第 4 步的 key 也收得進來。</li>
</ul>
<p>如果第 1 步直接呼叫 <code>process.nextTick(dispatch)</code>，dispatch 反而會比第 4 步那些 promise 回呼先跑，GraphQL 下一層的 key 就會錯過這一批。</p>
<h2>什麼寫法會讓批次失效</h2>
<p>只要在兩次 <code>.load()</code> 中間放一個真的 <code>await</code>（真的去等 I/O），批次就會在那裡提早送出。如果迴圈每一圈都 await，100 次 load 就會被切成 100 批：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// ✓ 同一輪：100 個 load 進同一個批次 → 1 次查詢</span></span>

<p>第二種是很常見的錯誤。每次 <code>await loader.load(id)</code> 都要等這次 load 完才進下一圈，所以每一圈都自成一個批次，用了 DataLoader 還是回到 N+1。</p>
<p>不過 GraphQL resolver 雖然每個欄位也各自 <code>await load()</code>，卻是安全的。因為 GraphQL 引擎會<strong>平行</strong>呼叫同一層的 resolver，所以這些 <code>.load()</code> 發生在同一輪，也就進到同一個批次。只有<strong>自己手寫的依序迴圈</strong>會出問題，因為它在兩次 <code>.load()</code> 中間夾了一個 <code>await</code>。</p>
<h2>別跟 p-limit 搞混</h2>
<p>DataLoader 跟 <code>p-limit</code> 看起來都在「控制一堆非同步」，可是 DataLoader 減少的是查詢次數，p-limit 限制的是同時跑的數量。</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>DataLoader：很多呼叫要的是同一種資料 → 合併成一次查詢</span></span>
<span data-line=""><span>p-limit：   很多請求同時發出 → 排隊，一次只放 10 個過去</span></span></code></pre></figure>

<p>這兩個通常不會用在同一段程式碼上。DataLoader 把同一批 key 合併起來查，查詢數已經夠少，用不到 p-limit 的限流。像 API key 那個例子，不管這次查了幾個 key，都只查 links 一次、roles 一次。p-limit 處理的則是沒辦法合併的任務，因為每個任務做的事都不一樣，DataLoader 幫不上忙。</p>
<p>不過用了 DataLoader，connection pool 還是可能不夠用。如果同一層有三個欄位各用一個 loader，這三個 loader 會在同一輪各自送出一批，一個 request 就同時要用到三條連線；同時有 10 個 request 進來，就是 30 條。這時候可以調大 pool，或用 p-limit 限制同時處理的 request 數。連線用光以後，Prisma 預設讓查詢等 10 秒（<code>pool_timeout</code>），等超過就失敗；pg driver 的 <code>connectionTimeoutMillis</code> 預設是 0，會一直等下去（<a href="https://www.prisma.io/docs/orm/prisma-client/setup-and-configuration/databases-connections/connection-pool">Prisma 文件</a>）。</p>
<p>回到開頭 Promise.all 的那個問題。如果真的沒辦法批次，一定要送 N 次獨立的請求，這時候才需要 p-limit。只是它並不會讓請求變少，它的用途是讓這些請求不要同時把 connection pool 的連線用光。</p>
<hr>
<p>整理一下。N+1 是程式碼的寫法造成的，所以不只發生在 SQL，HTTP、Redis、讀檔也會，只是 SQL 最常見。ORM 的 lazy load 跟 GraphQL resolver 會把迴圈藏起來。Promise.all 雖然讓頁面變快，請求數卻沒變。要把 N 次合併成 1 次，可以用 JOIN、手動 IN，或 DataLoader。DataLoader 靠 <code>Promise.then</code> 加上 <code>process.nextTick</code> 抓送出的時機，所以每個 resolver 照樣各自呼叫 <code>.load()</code>，同一個 loader 在同一輪收到的 key，卻只合併成一次查詢。</p>15:T43b3,
假設一個頁面要顯示 20 篇文章的作者名字。資料模型是最常見的那種，每篇 `post` 存一個 `author_id`，名字則放在 `users` 表裡。也就是說，一篇文章對一個作者，一個作者可以有很多篇文章（多對一）。

```text
posts(id, title, author_id)   author_id → users.id
users(id, name)
```

最直覺的寫法，大概就是一個 for 迴圈：

```ts
const posts = await db.query('SELECT * FROM posts LIMIT 20');  // 1 次查詢

for (const post of posts) {
  post.author = await db.query(
    'SELECT * FROM users WHERE id = ?', [post.author_id]
  );  // ← 每篇文章查一次，總共跑 20 次
}
```

這樣總共是 1 + 20 = 21 次查詢。如果一次來回要 5ms，加起來就是 105ms；同樣的資料如果用一個 JOIN，就只剩 1 次來回。

這段程式碼看起來就是個普通的迴圈，可是每跑一圈都會發一次網路請求，這就是 N+1。

教科書通常把它放在「資料庫優化」那一章。這樣分類反而把重點藏起來了，因為資料庫每一次查詢都跑得好好的，那 20 次查詢是迴圈一圈一圈發出去的。

## 為什麼說它不是資料庫的問題

如果把細節都拿掉，程式碼其實只剩下這兩步：

```text
拿到一份清單（1 次查詢）
清單裡每個元素各跑一次來回（N 次查詢）
```

這裡的「來回」，可以是任何一種跨邊界的請求：

- 一次 SQL 查詢（最常見的版本）
- 一次呼叫另一個微服務的 HTTP 請求
- 一次 Redis `GET`
- 一次 gRPC 呼叫
- 一次讀檔

只要清單裡有 N 個元素，而每個元素都各發一次跨邊界的請求，就是 N+1。當然，跨的邊界不同，花的時間也不一樣：SQL 是一次網路來回，HTTP 通常更貴，讀檔則比較便宜。但結構是完全一樣的。所以與其記「不要在迴圈裡查資料庫」，倒不如記「**不要在迴圈裡跨邊界**」。

## 同一種結構的三種寫法

換了框架之後，同一種結構會寫成不同的樣子。後面兩種比較麻煩，因為迴圈被藏起來了。

**一般的 for 迴圈。** 就是開頭那段。這種寫法至少把迴圈明明白白寫在程式碼裡。

**ORM 的 lazy load。** 迴圈還在，可是查詢不見了：

```python
# Django
posts = Post.objects.all()       # 1 次查詢
for post in posts:
    print(post.author.name)      # ← 讀屬性的時候發一次查詢
```

ORM 為了讓 `post.author` 用起來像一般物件，會在程式讀到這個屬性的當下發一次查詢。這次查詢沒有寫在程式碼裡，要等到開 profiler 或去翻 SQL log，才會發現那一行 `print` 其實是 20 次來回。

**GraphQL resolver。** 到這裡，連迴圈都不見了：

```graphql
{
  posts {
    title
    author { name }
  }
}
```

程式碼裡一個迴圈都沒寫，迴圈在 GraphQL 引擎裡。引擎拿到 20 篇文章之後，會對每篇各跑一次 `author` resolver，而每次都去查一次 user 表。結果一樣是 1+N，寫的人手上卻只有一段乾淨的宣告式查詢，code review 的時候也就更難發現。

## Promise.all 看起來像解法，其實不是

這時候第一個反應通常是：那全部用 Promise.all 一起送出去不就好了？

```ts
const posts = await db.query('SELECT * FROM posts LIMIT 20');
await Promise.all(
  posts.map(post =>
    db.query('SELECT * FROM users WHERE id = ?', [post.author_id])
  )
);
```

這樣寫，頁面會變快。那 20 次作者查詢一個一個跑要 20 × 5ms = 100ms（開頭的 105ms 還包含拿文章清單的那 1 次）；如果 connection pool 有 20 條以上的連線，20 個同時送出去，延遲就只剩最慢的那一個，大約 5ms。如果 pool 只有 10 條，就得分兩批，大約 10ms。

可是資料庫還是收到 20 次查詢，次數一次都沒少。連線也一樣，原本是 1 條連線佔 100ms，現在變成 20 條連線各佔 5ms，加起來佔用的連線時間其實差不多。JOIN 卻只要 1 條連線、1 次來回就拿到全部的資料。

要消掉 N+1，得把 N 次請求合併成 1 次。

## 三種真正的解法

下面三種合併的位置不同。

**JOIN（在資料庫層合併）：**

```sql
SELECT p.*, u.name AS author_name
FROM posts p JOIN users u ON p.author_id = u.id
LIMIT 20;
```

一個查詢就搞定。不過它只能在同一個資料庫、同一個查詢裡完成，所以沒辦法跨服務。

**IN 批次查詢（在應用層手動合併）：**

```ts
const posts = await db.query('SELECT * FROM posts LIMIT 20');
const authorIds = posts.map(p => p.author_id);
const users = await db.query('SELECT * FROM users WHERE id IN (?)', [authorIds]);
const userMap = new Map(users.map(u => [u.id, u]));
posts.forEach(p => p.author = userMap.get(p.author_id));
```

這樣就從 21 次降到 2 次。雖然比 JOIN 多一次來回，但邏輯很清楚，而且資料就算分散在不同的服務、cache 或資料庫裡也沒關係。中間那行 `posts.map(p => p.author_id)` **一次收齊了所有 id**，下一行才能把它們塞進同一個 IN。

**DataLoader（在應用層自動合併）：** 如果程式裡沒有那個一次收齊 id 的地方，就輪到它了。GraphQL resolver 剛好就是這種情況，因為每個 resolver 手上只有自己那篇文章，根本不知道另外 19 篇的存在。

## 要跨兩張表的時候

前面的例子只跨一張表（post → user），但實際遇到的 N+1 常常要跨兩層。例如一個 production 上的 GraphQL 查詢，要拉出一串 API key，而每個 key 都帶著它的 `adminRoles`：

```graphql
query {
  apiKeys {
    name
    adminRoles { id, name }   # ← 每個 key 都會觸發一次查詢
  }
}
```

`adminRoles` 沒辦法從單一張表拿到，因為資料模型是多對多：一個 API key 可以有很多 role，一個 role 也可以屬於很多 key。所以兩邊的對應關係存在中間表 `links`，role 本身的資料則存在 `roles`。

```text
api_keys(api_key, name)
links(api_key, admin_role_id)      ← 中間表，多對多
roles(id, name, description)

api_keys ──< links >── roles
```

因此查一個 key 的 `adminRoles` 要跨兩層，先從 `api_keys` 到 `links` 找出它的 role id，再到 `roles` 載入這些 role。最直覺的 field resolver 大概長這樣：

```ts
@ResolveField(() => [ApiKeyAdminRoleDto], { name: 'adminRoles' })
async adminRoles(@Parent() apiKey: ApiKeyDto) {
  const links = await this.queryService.findAdminRolesByApiKey(apiKey.apiKey);  // 第 1 層
  const roleIds = links.map(l => l.adminRoleId);
  const roles = await this.roleRepository.listByIds(roleIds);                    // 第 2 層
  return roles.map(/* ... */);
}
```

假設有 5 個 API key，數一下查詢次數：

```text
1 × SELECT api_keys
5 × SELECT links  WHERE api_key = ?    ← 每個 key 一次
5 × SELECT roles  WHERE id IN (...)    ← 每個 key 一次
= 11 次查詢
```

這裡用的 DataLoader 是 Facebook 開源的 npm 套件 [`dataloader`](https://github.com/graphql/dataloader)，GraphQL 後端幾乎都在用。`new DataLoader(batchFn)` 會包住一個批次函式，收集、合併、依序 resolve 都由它處理，寫的人只要負責那個 IN 查詢。

做法是新寫一個 loader，把兩層查詢都搬進它的批次函式裡。resolver 還是一次處理一個 key，只是改成呼叫 `.load()`：

```ts
import DataLoader from 'dataloader';

@Injectable({ scope: Scope.REQUEST })   // 每個 request 一個獨立的 instance
export class ApiKeyAdminRoleLoaderService {
  // 型別：load(string) → 回傳 ApiKeyAdminRole[]
  private readonly loader: DataLoader<string, ApiKeyAdminRole[]> =
    new DataLoader(this.#batchLoad.bind(this));

  // DataLoader 收齊同一輪所有 .load() 的 key，只呼叫這裡一次
  async #batchLoad(apiKeyIds: string[]): Promise<ApiKeyAdminRole[][]> {
    // 第 1 層：一次查完所有 links
    const allLinks = await this.linkRepository.findLinksByApiKeys(apiKeyIds);

    // 第 2 層：一次查完所有 roles
    const roleIds = [...new Set(allLinks.map(l => l.adminRoleId))];
    const roles = await this.roleRepository.listByIds(roleIds);
    const roleMap = new Map(roles.map(r => [r.id, r]));

    // 依 apiKey 分組；回傳順序必須跟輸入一樣
    const grouped = new Map<string, ApiKeyAdminRole[]>();
    for (const link of allLinks) {
      const role = roleMap.get(link.adminRoleId);
      if (role) {
        if (!grouped.has(link.apiKey)) grouped.set(link.apiKey, []);
        grouped.get(link.apiKey)!.push(role);
      }
    }
    return apiKeyIds.map(id => grouped.get(id) || []);
  }

  load(apiKeyId: string) { return this.loader.load(apiKeyId); }
}
```

resolver 則變成一行：

```ts
@ResolveField(() => [ApiKeyAdminRoleDto], { name: 'adminRoles' })
async adminRoles(@Parent() apiKey: ApiKeyDto) {
  const roles = await this.loader.load(apiKey.apiKey);
  return roles.map(/* ... */);
}
```

結果：

```text
1 × SELECT api_keys
1 × SELECT links  WHERE api_key IN (5 個 key)
1 × SELECT roles  WHERE id      IN (3 個 role)
= 3 次查詢   （11 → 3，少了 73%）
```

每一層都合併成一個 IN，而第二層還順便用 `new Set` 把重複的 id 拿掉了。因為 5 個 key 裡有好幾個共用同一個 role，拿掉重複的之後，只要查 3 個 role 就夠了。**兩層查詢的合併全寫在批次函式裡，resolver 只剩一行 `.load()`。**

## 誰呼叫誰

由上到下依序是：

```text
你的 resolver  →  .load(id)          （每個 parent 一次）
DataLoader     →  收集 id，呼叫一次你的 batchFn
你的 batchFn   →  一次查詢：findMany({ id: { in: ids } })
ORM            →  SELECT ... WHERE id IN (...)
資料庫         →  執行 SQL
```

DataLoader 只負責收集 key、抓準時間點，查詢要寫在批次函式裡。ORM 跟資料庫照常執行收到的查詢，跟沒用 DataLoader 的時候一樣。每個角色的細節可以點開來看。

<details>
<summary><strong>DataLoader</strong>：收集 key、抓時間點，不碰資料庫</summary>

`.load(id)` 只把 id 收進批次，回傳一個還沒完成的 promise，這時候還沒有任何查詢。DataLoader 本身不處理 SQL、ORM 或資料表，只管 key 跟 promise。

</details>

<details>
<summary><strong>你的批次函式</strong>：查詢寫在這裡</summary>

DataLoader 會交給你 `[id1, id2, …]`，而要跑什麼查詢由你決定，所以那一個 `IN` 查詢就寫在這裡：

```ts
new DataLoader(async (ids) => {
  const rows = await prisma.user.findMany({ where: { id: { in: [...ids] } } });
  const map = new Map(rows.map(r => [r.id, r]));
  return ids.map(id => map.get(id) ?? null);   // 順序要跟 ids 一樣
});
```

`findMany({ in: ids })` 是寫在批次函式裡的，並不是 DataLoader 產生的。另外，回傳的資料也要照 ids 的順序排好，不然每個呼叫 `.load()` 的地方會拿到錯的那一筆。

</details>

<details>
<summary><strong>ORM</strong>：把 findMany 轉成 SQL</summary>

`prisma.user.findMany({ where: { id: { in: ids } } })` 會變成 `SELECT * FROM users WHERE id IN ($1, $2, …)`，這就是一般的 ORM 轉換，跟其他查詢沒兩樣。就算把 Prisma 換成 TypeORM（`In(ids)`）或 Drizzle（`inArray(users.id, ids)`），產出的 SQL 也還是一樣。這一層跟有沒有用 DataLoader 無關。

</details>

## DataLoader 怎麼「自動收集」

既然 resolver 是一個一個呼叫 `.load()` 的，那 DataLoader 怎麼知道什麼時候該一起送出去呢？

`.load(key)` 不會碰資料庫，它只把 key 推進一個批次，然後馬上回傳一個 **pending promise**。同一輪 event loop 裡所有的 `.load()`，都會進到同一個批次。等這一輪結束，DataLoader 才送出一次，也就是呼叫批次函式（那個 IN 查詢），等資料庫回來之後，再依照 index 把每個 promise 填上結果。

```text
load(key1) load(key2) … load(key5)   ← 同一輪，全部推進同一個批次
        ↓ 這一輪結束
batchFn([key1..key5]) → 1 × SELECT ... IN (...)
        ↓ 資料庫回傳
依 index 把每個 .load() 的 promise resolve 掉
```

那「一輪」到底什麼時候結束呢？拿 `await Promise.all(ids.map(id => loader.load(id)))` 來說，依序會發生這些事：

```text
1. map 跑第 1 次 load(id1)：key 進批次，DataLoader 預約一次 dispatch（送出批次）
2. map 繼續跑 load(id2) … load(id100)：key 都進同一個批次
3. map 跑完，同步程式碼結束
4. 其他已經排隊的 promise 回呼先跑，裡面如果又呼叫 .load()，key 也進這個批次
5. 輪到 dispatch：用整批 key 呼叫一次批次函式
```

第 4 步在 GraphQL 裡很常見。因為上一層 resolver 的 promise 一 resolve，下一層 resolver 才開始跑，所以下一層的 `.load()` 就是在這種回呼裡呼叫的。

第 1 步預約的寫法是 [`Promise.resolve().then(() => process.nextTick(dispatch))`](https://github.com/graphql/dataloader/blob/main/src/index.js)。這裡包了兩層，`.then` 負責等第 2 步，`process.nextTick` 負責等第 4 步：

- **`.then`**：它的回呼要等第 3 步結束才會跑，所以第 2 步的 key 都收得進來。
- **`process.nextTick`**：它是在 `.then` 的回呼裡才呼叫的，而 Node 會等目前排隊的 promise 回呼全部跑完，才執行它排進去的 dispatch，所以第 4 步的 key 也收得進來。

如果第 1 步直接呼叫 `process.nextTick(dispatch)`，dispatch 反而會比第 4 步那些 promise 回呼先跑，GraphQL 下一層的 key 就會錯過這一批。

## 什麼寫法會讓批次失效

只要在兩次 `.load()` 中間放一個真的 `await`（真的去等 I/O），批次就會在那裡提早送出。如果迴圈每一圈都 await，100 次 load 就會被切成 100 批：

```ts
// ✓ 同一輪：100 個 load 進同一個批次 → 1 次查詢
await Promise.all(ids.map(id => loader.load(id)));

// ✗ 依序跑的迴圈：每次 await 都讓出執行權，批次提早送出，每次各自一批 → 100 次查詢
for (const id of ids) await loader.load(id);
```

第二種是很常見的錯誤。每次 `await loader.load(id)` 都要等這次 load 完才進下一圈，所以每一圈都自成一個批次，用了 DataLoader 還是回到 N+1。

不過 GraphQL resolver 雖然每個欄位也各自 `await load()`，卻是安全的。因為 GraphQL 引擎會**平行**呼叫同一層的 resolver，所以這些 `.load()` 發生在同一輪，也就進到同一個批次。只有**自己手寫的依序迴圈**會出問題，因為它在兩次 `.load()` 中間夾了一個 `await`。

## 別跟 p-limit 搞混

DataLoader 跟 `p-limit` 看起來都在「控制一堆非同步」，可是 DataLoader 減少的是查詢次數，p-limit 限制的是同時跑的數量。

```text
DataLoader：很多呼叫要的是同一種資料 → 合併成一次查詢
p-limit：   很多請求同時發出 → 排隊，一次只放 10 個過去
```

|  | DataLoader | p-limit |
|---|---|---|
| 解決 | N+1（查詢太多次） | pool 用光（同時太多連線） |
| 做法 | 收集 `.load()`，合併成一次批次查詢 | 限制同時跑的非同步數量 |
| 查詢次數 | 同一個 loader 的 5 個 `.load()`，合併成 1 次查詢 | 100 個任務照樣跑 100 次，同時最多 10 條連線 |
| 適合 | 可以合併成 `WHERE IN (...)` 的資料 | 每個任務做的事都不一樣（讀 → 判斷 → 更新） |

這兩個通常不會用在同一段程式碼上。DataLoader 把同一批 key 合併起來查，查詢數已經夠少，用不到 p-limit 的限流。像 API key 那個例子，不管這次查了幾個 key，都只查 links 一次、roles 一次。p-limit 處理的則是沒辦法合併的任務，因為每個任務做的事都不一樣，DataLoader 幫不上忙。

不過用了 DataLoader，connection pool 還是可能不夠用。如果同一層有三個欄位各用一個 loader，這三個 loader 會在同一輪各自送出一批，一個 request 就同時要用到三條連線；同時有 10 個 request 進來，就是 30 條。這時候可以調大 pool，或用 p-limit 限制同時處理的 request 數。連線用光以後，Prisma 預設讓查詢等 10 秒（`pool_timeout`），等超過就失敗；pg driver 的 `connectionTimeoutMillis` 預設是 0，會一直等下去（[Prisma 文件](https://www.prisma.io/docs/orm/prisma-client/setup-and-configuration/databases-connections/connection-pool)）。

回到開頭 Promise.all 的那個問題。如果真的沒辦法批次，一定要送 N 次獨立的請求，這時候才需要 p-limit。只是它並不會讓請求變少，它的用途是讓這些請求不要同時把 connection pool 的連線用光。

<p>1 + 20 = 21 queries. If each round-trip is 5ms, that's 105ms total. A single JOIN would be one round-trip.</p>
<p>It reads like an ordinary loop. But every iteration sends a network request. That's N+1.</p>
<p>Textbooks put it under "database optimization." I think that placement hides the truth: N+1 has nothing essential to do with databases. It's a <strong>shape</strong>.</p>
<h2>A shape, not SQL</h2>
<p>Strip the code down and the skeleton is this:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>take a list (1 query)</span></span>
<span data-line=""><span>for each element, make one round-trip (N queries)</span></span></code></pre></figure>
<p>What the round-trip <em>is</em> doesn't change whether the shape holds. It can be:</p>
<ul>
<li>a SQL query (the most common version)</li>
<li>an HTTP call to another microservice</li>
<li>a Redis <code>GET</code></li>
<li>a gRPC call</li>
<li>a file read</li>
</ul>
<p>The moment you send one cross-boundary request per item across N items, you have N+1. The only difference is the cost of that boundary. SQL is a network round-trip, HTTP is more expensive, a file read is cheaper. The shape is identical. So instead of memorizing "don't query inside a loop," remember: <strong>don't cross a boundary inside a loop</strong>.</p>
<h2>Three forms of the same shape</h2>
<p>Same shape, different forms across frameworks. The hard part is the last two, where the loop is invisible.</p>
<p><strong>The plain for loop.</strong> The opening snippet. At least it's honest: the loop is visible in the code.</p>
<p><strong>ORM lazy load.</strong> The loop is still there, but the query disappeared:</p>

<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">for</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> post </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">in</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> posts:</span></span>

<p>To make <code>post.author</code> feel like a plain object, the ORM sends a query the instant you read that attribute. The person writing it feels nothing. Only a profiler or the SQL log shows that one <code>print</code> line is 20 round-trips.</p>

<span data-line=""><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">    author</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> { </span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">name</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> }</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  }</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">}</span></span></code></pre></figure>
<p>You wrote no loop. The GraphQL engine wrote one for you: it takes 20 posts and runs the <code>author</code> resolver once per post, each one querying the user table. Same 1+N. The framework hid the loop, and you only see a clean declarative query.</p>
<p>Three forms, one shape. The further down you go, the more invisible the loop, the harder to notice in code review.</p>
<h2>Promise.all looks like a fix, but it isn't</h2>
<p>The first instinct: just send them all with Promise.all.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> posts</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> await</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> db.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">query</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'SELECT * FROM posts LIMIT 20'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">);</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">await</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> Promise</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">all</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  posts.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">map</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">post</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =></span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">    db.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">query</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'SELECT * FROM users WHERE id = ?'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, [post.author_id])</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  )</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">);</span></span></code></pre></figure>
<p>Written this way, the page gets faster. One by one, the 20 author queries take 20 × 5ms = 100ms (the 105ms at the start also counts the 1 query for the post list). With 20 or more connections in the pool, all 20 go out at once and the latency drops to the slowest one, around 5ms. With only 10 connections, they go in two waves, around 10ms.</p>
<p>But the DB still receives 20 queries, not one fewer. Connection time is about the same too: one connection held for 100ms becomes 20 connections held for 5ms each. A JOIN gets all the data with 1 connection and 1 round-trip.</p>
<p>To actually remove N+1, turn N requests into 1.</p>
<h2>Three real fixes</h2>
<p>All doing the same thing: combine N requests into 1. They differ in which layer they combine at.</p>
<p><strong>JOIN (combine at the DB layer):</strong></p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="sql" data-theme="github-dark github-light"><code data-language="sql" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">SELECT</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> p.</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">*</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">u</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">name</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> AS</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> author_name</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">FROM</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> posts p </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">JOIN</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> users u </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">ON</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> p</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">author_id</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> u</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">id</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">LIMIT</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> 20</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">;</span></span></code></pre></figure>
<p>One statement covers it. The catch: it is tied to a single DB and a single query, and can't reach across services.</p>
<p><strong>IN batch (combine manually at the application layer):</strong></p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> posts</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> await</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> db.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">query</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'SELECT * FROM posts LIMIT 20'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">);</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> authorIds</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> posts.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">map</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">p</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =></span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> p.author_id);</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> users</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> await</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> db.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">query</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'SELECT * FROM users WHERE id IN (?)'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, [authorIds]);</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> userMap</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> new</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1"> Map</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(users.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">map</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">u</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =></span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> [u.id, u]));</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">posts.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">forEach</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">p</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =></span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> p.author </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">=</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> userMap.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">get</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(p.author_id));</span></span></code></pre></figure>
<p>21 down to 2. One more round-trip than JOIN, but the logic is clear, and the data can live across different services / caches / DBs. The key step is that middle line <code>posts.map(p => p.author_id)</code>: <strong>you have one place to collect every id at once</strong>.</p>
<p><strong>DataLoader (combine automatically at the application layer):</strong> for when you don't have that one place to collect ids. GraphQL resolvers are exactly that case. Each resolver sees only its own post and has no idea the other 19 exist. The rest of this article is about this.</p>
<h2>The clean fix: when two tables need joining</h2>
<p>The earlier example crosses one table (post → user). Real-world N+1 is often two hops. Here's a production case.</p>
<p>A GraphQL query pulls a list of API keys, each carrying its <code>adminRoles</code>:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="graphql" data-theme="github-dark github-light"><code data-language="graphql" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">query</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> {</span></span>
<span data-line=""><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">  apiKeys</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> {</span></span>
<span data-line=""><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">    name</span></span>
<span data-line=""><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">    adminRoles</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> { </span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">id</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, </span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">name</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> }</span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">   # ← triggers a lookup per key</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  }</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">}</span></span></code></pre></figure>
<p><code>adminRoles</code> can't come from one table. The data model is a many-to-many: one API key holds many roles, one role attaches to many keys. A junction table <code>links</code> holds the pairing, and the role bodies live in <code>roles</code>.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>api_keys(api_key, name)</span></span>
<span data-line=""><span>links(api_key, admin_role_id)      ← junction, many-to-many</span></span>
<span data-line=""><span>roles(id, name, description)</span></span>
<span data-line=""> </span>
<span data-line=""><span>api_keys ──&#x3C; links >── roles</span></span></code></pre></figure>
<p>So fetching <code>adminRoles</code> for one key is two hops: <code>api_keys</code> → <code>links</code> (find its role ids) → <code>roles</code> (load those roles). The naive field resolver:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">@</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">ResolveField</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(() </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">=></span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> [ApiKeyAdminRoleDto], { name: </span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'adminRoles'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> })</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">async </span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">adminRoles</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(@</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">Parent</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">() apiKey: ApiKeyDto) {</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">  const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> links</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> await</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> this</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.queryService.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">findAdminRolesByApiKey</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(apiKey.apiKey);  </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// hop 1</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">  const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> roleIds</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> links.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">map</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">l</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =></span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> l.adminRoleId);</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">  const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> roles</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> await</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> this</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.roleRepository.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">listByIds</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(roleIds);                    </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// hop 2</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">  return</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> roles.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">map</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">/* ... */</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">);</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">}</span></span></code></pre></figure>
<p>5 API keys, count the queries:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>1 × SELECT api_keys</span></span>
<span data-line=""><span>5 × SELECT links  WHERE api_key = ?    ← once per key</span></span>
<span data-line=""><span>5 × SELECT roles  WHERE id IN (...)    ← once per key</span></span>
<span data-line=""><span>= 11 queries</span></span></code></pre></figure>
<p>The DataLoader here isn't a concept I wrote by hand. It's Facebook's open-source npm package <a href="https://github.com/graphql/dataloader"><code>dataloader</code></a>, the standard choice for GraphQL backends. <code>new DataLoader(batchFn)</code> wraps a batch function, and it handles collect + merge + resolve-in-order. You only write the IN query.</p>
<p>The fix is a new loader whose batch function holds both hops. The resolver still handles one key at a time; it just calls <code>.load()</code> now:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">import</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> DataLoader </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">from</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62"> 'dataloader'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">;</span></span>
<span data-line=""> </span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">@</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">Injectable</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">({ scope: Scope.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">REQUEST</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> })   </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// one independent instance per request</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">export</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> class</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1"> ApiKeyAdminRoleLoaderService</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> {</span></span>

<h2>Who calls whom</h2>
<p>Top to bottom:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>your resolver  →  .load(id)          (once per parent)</span></span>
<span data-line=""><span>DataLoader     →  collects the ids, calls your batch function once</span></span>
<span data-line=""><span>your batchFn   →  one query: findMany({ id: { in: ids } })</span></span>
<span data-line=""><span>ORM            →  SELECT ... WHERE id IN (...)</span></span>
<span data-line=""><span>database       →  runs the SQL</span></span></code></pre></figure>
<p>The common misread: DataLoader does <strong>not</strong> turn <code>.load()</code> into a query. It only collects keys and gets the timing right. <em>You</em> write the query, inside the batch function. The ORM and the database do their normal jobs, unaware DataLoader exists. Open each player for the detail.</p>
<details>
<summary><strong>DataLoader</strong> — collects and times, never touches the DB</summary>
<p><code>.load(id)</code> pushes the id into an array and returns a pending promise. No query yet. DataLoader waits out the round (the event-loop timing from the next section), then calls your batch function once with the full array of ids, and when the results come back, resolves each promise by index. It knows nothing about SQL, ORMs, or tables. It holds keys and promises, nothing more.</p>
</details>
<details>
<summary><strong>Your batch function</strong> — the one place the query is decided</summary>
<p>DataLoader hands you <code>[id1, id2, …]</code>. What query to run is your decision. You write the single <code>IN</code> lookup here:</p>

</details>
<details>
<summary><strong>The ORM</strong> — turns findMany into SQL</summary>
<p><code>prisma.user.findMany({ where: { id: { in: ids } } })</code> becomes <code>SELECT * FROM users WHERE id IN ($1, $2, …)</code>. Normal ORM translation, the same as any other query. Swap Prisma for TypeORM (<code>In(ids)</code>) or Drizzle (<code>inArray(users.id, ids)</code>) and the SQL is the same. None of this knows DataLoader is involved.</p>
</details>
<h2>Under the hood: how DataLoader "auto-collects"</h2>
<p>Resolvers call <code>.load()</code> one by one. How does DataLoader know when to send them together? The JavaScript event loop.</p>
<p>The plain version first. DataLoader puts a short pause between the moment you call <code>.load()</code> and the moment the DB is actually queried. In that pause it collects every key from the round. Without the pause, the call and the query are stuck together, so you query the DB once for every call. With it, each loader sends one query per round. Everything below is just <em>how</em> it places that pause.</p>
<p>Now the mechanics. <code>.load(key)</code> doesn't touch the DB. It pushes the key into a batch and returns a <strong>pending promise</strong> right away. Every <code>.load()</code> made in the same round of the event loop lands in that one batch. At the end of the round, DataLoader dispatches once: it calls your batch function (the IN query), and after the DB returns, it fills each promise in order.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>load(key1) load(key2) … load(key5)   ← same round, all pushed into one batch</span></span>
<span data-line=""><span>        ↓ end of the round</span></span>
<span data-line=""><span>batchFn([key1..key5]) → 1 × SELECT ... IN (...)</span></span>
<span data-line=""><span>        ↓ DB returns</span></span>
<span data-line=""><span>resolve each .load() promise by index</span></span></code></pre></figure>
<p>So when does a "round" end? Take <code>await Promise.all(ids.map(id => loader.load(id)))</code>. In order:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>1. map runs load(id1): the key joins the batch, DataLoader schedules a dispatch (sending the batch)</span></span>
<span data-line=""><span>2. map keeps going, load(id2) … load(id100): every key joins the same batch</span></span>
<span data-line=""><span>3. map finishes, the synchronous code ends</span></span>
<span data-line=""><span>4. promise callbacks already queued run first; any .load() inside them also joins this batch</span></span>
<span data-line=""><span>5. the dispatch runs: the batch function is called once with every key</span></span></code></pre></figure>
<p>Step 4 is common in GraphQL. A child resolver only starts after its parent resolver's promise resolves, so the child's <code>.load()</code> calls happen inside exactly this kind of callback.</p>
<p>The dispatch scheduled in step 1 is <a href="https://github.com/graphql/dataloader/blob/main/src/index.js"><code>Promise.resolve().then(() => process.nextTick(dispatch))</code></a>. It is wrapped twice because each layer covers one step:</p>
<ul>
<li><strong><code>.then</code></strong>: its callback can't run until step 3 is over, so every key from step 2 makes it in.</li>
<li><strong><code>process.nextTick</code></strong>: it is only called inside that <code>.then</code> callback, and Node runs the dispatch it queues after the currently queued promise callbacks finish, so the keys from step 4 make it in too.</li>
</ul>
<p>Call <code>process.nextTick(dispatch)</code> directly in step 1 instead, and the dispatch runs before those step 4 promise callbacks. The next GraphQL level's keys would miss this batch.</p>
<h2>The way to break batching</h2>
<p>Put a real <code>await</code> (yielding to real I/O) between two <code>.load()</code> calls and the batch is sent early at that point. If a loop awaits on every iteration, 100 loads become 100 batches:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// ✓ same round: 100 loads in one batch → 1 query</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">await</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> Promise</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">all</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(ids.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">map</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">id</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =></span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> loader.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">load</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(id)));</span></span>
<span data-line=""> </span>
<span data-line=""><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// ✗ sequential loop: each await yields, dispatch runs early, each its own batch → 100 queries</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">for</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> (</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> id</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> of</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> ids) </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">await</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> loader.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">load</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(id);</span></span></code></pre></figure>
<p>The second one is the common mistake. Each <code>await loader.load(id)</code> waits for this load to finish before the next iteration, so each iteration becomes its own batch. You think DataLoader keeps you safe, and you end up back at N+1.</p>
<p>But GraphQL resolvers, where each field does its own <code>await load()</code>, are safe. Don't confuse the two. The engine calls sibling resolvers <strong>in parallel</strong>, so those <code>.load()</code> calls happen in the same round and the same batch. What to watch for is a <strong>sequential loop you wrote by hand</strong>, because it puts an <code>await</code> between two <code>.load()</code> calls.</p>
<h2>Don't confuse it with p-limit: different problems</h2>
<p>One last common mix-up. DataLoader and <code>p-limit</code> both "control a pile of async," but they solve opposite problems.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>DataLoader:  many asking the same question → merge into one, ask once</span></span>
<span data-line=""><span>p-limit:     many requests at the same time → queue up, let 10 through at a time</span></span></code></pre></figure>






























<table><thead><tr><th></th><th>DataLoader</th><th>p-limit</th></tr></thead><tbody><tr><td>Solves</td><td>N+1 (too many queries)</td><td>pool exhaustion (too many connections at once)</td></tr><tr><td>How</td><td>collects <code>.load()</code>, merges into one batch query</td><td>caps how many async run at the same time</td></tr><tr><td>Query count</td><td>5 <code>.load()</code> on the same loader become 1 query</td><td>100 tasks still run 100 times, at most 10 connections at once</td></tr><tr><td>Fits</td><td>rows that merge into <code>WHERE IN (...)</code></td><td>tasks that each do something different (read → decide → update)</td></tr></tbody></table>
<p>They're usually not used on the same code. DataLoader merges a batch of keys into one query, so the query count is already low and p-limit's throttling has nothing to do. In the API key example, however many keys come in, it queries links once and roles once. p-limit is for tasks that can't merge, because each one does something different, and there DataLoader can't help.</p>
<p>DataLoader can still run the connection pool short, though. If one level has three fields, each with its own loader, those three loaders dispatch in the same round and one request needs three connections at once; ten concurrent requests need thirty. Then you can enlarge the pool, or use p-limit to cap how many requests are handled at once. Once connections run out, Prisma lets a query wait 10 seconds by default (<code>pool_timeout</code>) and then fails it; the pg driver's <code>connectionTimeoutMillis</code> defaults to 0, so it waits indefinitely (<a href="https://www.prisma.io/docs/orm/prisma-client/setup-and-configuration/databases-connections/connection-pool">Prisma docs</a>).</p>
<p>Back to that Promise.all problem from the start: if your case genuinely can't batch and you must send N separate requests, that's when p-limit is used. Not to remove requests, but to keep them from overloading the connection pool all at once.</p>
