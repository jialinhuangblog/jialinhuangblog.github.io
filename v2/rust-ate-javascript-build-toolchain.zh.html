Rust ate.

frontendbuild-toolsbundlertransformerrustvitenextjs

我學前端是 2018 那年。那時候還在吵 React、Vue、Angular，各有各的擁護者。

框架本身其實還好，因為怎麼寫怎麼組裝 HTML，官方文件裡都有；麻煩的是它們底下那一坨 build 設定：webpack 的 config、一個接一個的 loader、babel 要配哪些 preset。那時候學前端真的是狂看官方文件，而且特殊 loader 一來又整個重來，超煩的。對，還有 plugin，看情況裝。

然後 Next.js 出現了。它把那一整層包起來。我不用再寫 webpack config，不用再排 loader 順序，create-next-app 完直接就會動。好爽啊。從那之後 build 對我來說就是個黑盒子，能不碰就不碰。

直到 Next.js 生態系的技術文章開始冒出 SWC、Turbopack，我才想說好像應該把整個進化過程梳理一下。總不能 Next.js 讓你無後顧之憂，你還真的無後顧之憂地生存下去。

build（不管是 next build 還是別的 build）分成三個角色

而且剛好就是我當年手動在配的那三個：

  • parse + transform：把我寫的 TS、JSX 轉成瀏覽器能執行的 JS。當年是 Babel。
  • bundle：把一堆 import 拼成幾個檔。當年是 Webpack。
  • minify：把輸出壓小。當年是 Terser。

沒在關注黑盒子這幾年，這三個都變成 Rust 了 LOL。

從 Button.tsx 到 app.382f3f.js

Button.tsx 到上線的檔案，中間會經過：

Button.tsx
  │  parse + transform     (SWC / esbuild / Oxc / Babel)
  │  TS → JS、JSX → JS、降新語法
  ▼
Button.js   (純 JS，沒有型別)
  │  bundle                (Turbopack / Vite / Rolldown)
  │  跟著 import 走依賴圖，拼在一起
  ▼
一大張 module graph
  │  minify                (SWC / esbuild / oxc / terser)
  │  砍空白、改短變數名、丟掉沒用到的 code
  ▼
app.382f3f.js    ← 382f3f 是內容 hash，拿來破快取

（在旁邊，不在這條線上）
tsc --noEmit  →  檢查型別，什麼都不輸出

382f3f 是用檔案內容算出來的 hash。code 一改，hash 就變，檔名跟著變，瀏覽器就會重新下載，不會用到舊的快取。

parse + transform：SWC

SWC 的作者是韓國人 DongYoon Kang，網路上叫 kdy1，大家喊他 Donny。他早在 2017 年就開始用 Rust 寫這個 Babel 的替代品，一樣做 parse + transform，只是預設會開多執行緒。官方的說法是單執行緒比 Babel 快 20 倍，四個核心快 70 倍，20 倍跟 70 倍的不同來自核心數。

2021 年 8 月，Next.js 11.1 的公告裡提到 Kang 加入了 Vercel；才過兩個月，Next.js 12 就把預設的 Babel 換成 SWC 了。

bundle：Turbopack

Turbopack 是 Webpack 的作者 Tobias Koppers 寫的，他現在也在 Vercel。等於是原作者自己用 Rust 寫了 webpack 的後繼者，而且底層直接用 SWC。Turbopack 的 next dev 在 Next.js 15（2024 年 10 月）正式穩定，到 Next.js 16（2025 年 10 月）連 next build 都變預設了。要繼續用 webpack，就加 --webpack。

minify：也是 SWC

Next.js 從 v13 起連壓縮都預設走 SWC。我以前為了省幾 KB 在調的那些 minify 設定，現在框架自己決定了。

還有 Vite 好像滿紅的

Vite 2020 年出來，開發時用 esbuild（Go 寫的，作者是 Figma 的 Evan Wallace），正式打包時用 Rollup。後來 Rollup 也被 Rust 重寫成 Rolldown，2026 年 3 月 Vite 8 直接拿它當預設，連開發時用的 esbuild 也一起換掉了：

dev server 啟動時，先把 node_modules 打包好esbuildRolldown
正式打包RollupRolldown

各框架預設用什麼：除了 Next.js，幾乎都是 Vite

幾乎每個框架預設都用 Vite，只有 Next.js 自己用 Turbopack。

Angular 比較特別，打包用 esbuild，dev server 用 Vite。前面說 Vite 8 以前開發時用 esbuild，那是 esbuild 包在 Vite 裡面；Angular 只拿 Vite 的 dev server，打包直接呼叫 esbuild，不走 Vite 的 Rollup。所以在 Angular 裡，Vite 只管 dev server，打包是 esbuild 自己來。Next.js + Vite 從來不是一回事，Next 只出自己的 bundler。Turbopack 跟 Parcel 也從沒兜過，兩個不相干的專案。

大家都接 Vite，大概是因為它不綁特定框架。

Benchmark 呢

到 2026 年，這些工具都夠快了，速度已經不是選工具的主要考量，比較看生態、相容性跟維護狀況。而且這些 benchmark 大多是某個工具的團隊自己出的，看數字前先看是誰出的。想自己查數字，可以看：

  • rstackjs/build-tools-performance：最全、還在持續更新的比較（Rspack、Vite、Rolldown、esbuild、webpack、Rollup、Parcel、Farm）。由 Rspack 團隊維護。
  • esbuild 自己的 benchmark：esbuild vs webpack / Rollup / Parcel。立場偏 esbuild，測試方式寫在 FAQ 裡，可以對照（three.js ×10：esbuild 0.39s、Parcel 14.9s、Rollup+Terser 34.1s、webpack 41.2s）。

Vite 本身很少被單獨拿來測，因為轉換跟打包都交給前面表格裡那些工具做。

Babel 會處理 TypeScript，為什麼還要跑 tsc

當年看專案設定總覺得哪裡怪怪的，又說不上來：Babel 都會處理 TypeScript 了，旁邊怎麼還掛著一個 tsc？

說穿了，轉換型別跟檢查型別是兩件事：

  • 轉換型別（TS→JS）：把 TS 轉成能跑的 JS，型別直接拿掉。Babel、SWC、esbuild、Oxc 都會。
  • 檢查型別：確認型別有沒有寫錯。很長一段時間只有 tsc 會，直到 2026 年 10 月 Bun 也內建了型別檢查器 bun check，不過預設不會自動跑。

所以只要設定沒把型別檢查包進去，就得另外手動跑 tsc：

設定轉換型別（TS→JS）型別檢查你要跑
Next.jsSWC，內建next build 幫你跑 tsc不用
Vite內建；原本是 esbuild，Vite 8（2026-03）起換成 Oxc沒包tsc --noEmit（Vue 專案常見 vue-tsc -b && vite build）
Bun內建原本沒包；v1.4.3（2026-10）起有 bun check，run、build、test 也可以加 --check，但預設不跑原本是 tsc --noEmit，現在可以改用 bun check
Babel + Webpack（當年的我）@babel/preset-typescript沒包另外跑 tsc --noEmit
只用 tsc（小 lib）tsctsc，同一次tsc，兩件一起，但不打包

tsc 單獨跑會做兩件事，檢查型別加吐出 .js。tsc --noEmit 是同一個檢查，只是把輸出關掉。現代設定用 --noEmit，是因為 .js 已經有更快的工具生好了，只需要 tsc 的檢查，不需要它比較慢的輸出。

Next.js 就是最寵你的那個：它把全部包起來，你只看到 next build :)

then Bun

Bun 是另一個跟 Node 打對台的 runtime，一開始用一個叫 Zig 的語言寫，2023 年就 1.0 了。而它自己現在也在從 Zig 換成 Rust，2026 年 5 月剛把核心重寫進 main。

then

有個叫 Oxc 的專案，Boshen 在做，想法更進一步：與其每個工具各自 parse 一遍，不如 parse 一次、大家共用同一棵 AST。目前 parser、linter（oxlint）、transformer 都出來了，Rolldown 底層的 parser 也已經用 Oxc。要是成了，現在 SWC、Oxc 各有一套 parser 的狀況，可能哪天又可以面臨大一統。

所以呢

那個黑盒子裡到底發生了什麼？整層工具從 JavaScript 換成原生執行檔、架構重新設計，也開始用多核心，所以快很多。

至於『Rust 比較快』到底是不是真的，我跑了 benchmark 量量看。結果有時打平，也有兩次 Node 反而比較快，不過多數時候是 Rust 快三倍上下。SWC 官網說的 20 到 70 倍，量下來大半來自四核心跟兩個程式的架構差，不是 Rust 這個語言。完整的過程跟每一張圖，我寫成另一篇了：Rust 比 Node 快多少？我量了七種情境。每個原因單獨的數字在這：Rust vs V8。
