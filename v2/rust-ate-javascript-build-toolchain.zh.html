Rust ate.

frontendbuild-toolsbundlertransformerrustvitenextjs

我學前端是 2018 那年。那時候還在吵 React、Vue、Angular，三邊各有各的人，選一個框架等於選一個陣營。

框架本身其實還好，因為怎麼寫怎麼組裝 HTML，官方文件裡都有；麻煩的是它們底下那一坨 build 設定：webpack 的 config、一個接一個的 loader、babel 要配哪些 preset。那時候學前端真的是狂看官方文件，而且特殊 loader 一來又整個重來，超煩的。對，還有 plugin，看情況裝。

然後 Next.js 出現了。它把那一整層包起來。我不用再寫 webpack config，不用再排 loader 順序，create-next-app 完直接就會動。好爽啊。從那之後我就不太碰 build 設定了，能不碰就不碰。接下來幾年我就停在這裡：框架把底下顧好，我在上面寫 component，build 對我來說是個黑盒子，能動就好。我沒去追它，也不覺得需要追。

直到 Next.js 生態系的技術文章開始冒出 SWC、Turbopack，我才想說，好像應該把整個進化過程梳理一下。總不能 Next.js 讓你無後顧之憂，你還真的無後顧之憂地生存下去。

build（不管是 next build 還是別的 build）分成三個角色

而且剛好就是我當年手動在配的那三個：

  • parse + transform：把我寫的 TS、JSX 轉成瀏覽器能執行的 JS。當年是 Babel。
  • bundle：把一堆 import 拼成幾個檔。當年是 Webpack。
  • minify：把輸出壓小。當年是 Terser。

沒在關注黑盒子這幾年，這三個都變成 Rust 了 LOL。

從 Button.tsx 到 app.382f3f.js

Button.tsx 到上線的檔案，中間會經過：

Button.tsx
  │  parse + transform     (SWC / esbuild / Babel)
  │  拔掉 TS 型別、JSX → JS、降新語法
  ▼
Button.js   (純 JS，沒有型別)
  │  bundle                (Turbopack / Vite / Rolldown)
  │  跟著 import 走依賴圖，拼在一起
  ▼
一大張 module graph
  │  minify                (SWC / esbuild / oxc / terser)
  │  砍空白、改短變數名、丟掉沒用到的 code
  ▼
app.382f3f.js    ← 382f3f 是內容 hash，拿來破快取

（在旁邊，不在這條線上）
tsc --noEmit  →  檢查型別，什麼都不輸出

382f3f 是用檔案內容算出來的 hash。code 一改，hash 就變，檔名跟著變，瀏覽器就會重新下載，不會用到舊的快取。

SWC 把 Babel 換掉

寫 SWC 的是一個韓國人，DongYoon Kang，網路上叫 kdy1，大家喊他 Donny。他 2017 年就開始寫，一個 Babel 的替代品，一樣做 parse + transform，但用 Rust、預設多執行緒。20 倍跟 70 倍差在核心數：官方的說法是單執行緒比 Babel 快 20 倍，四個核心快 70 倍。

Next.js 12 在 2021 年 10 月把預設的 Babel 換成 SWC。SWC 這個名字冒出來我才注意到，但它一點都不新。Kang 本人 2021 年 8 月就進 Vercel 了，我只是一直沒看。

Turbopack 把 Webpack 換掉

寫它的是 Webpack 的作者本人，Tobias Koppers，現在也在 Vercel。同一個作者用 Rust 寫了 webpack 的後繼者，底層還用了 SWC。Turbopack 的 next dev 在 Next.js 15（2024 年 10 月）正式穩定，到 Next.js 16（2025 年 10 月）連 next build 都變預設了。要繼續用 webpack，就加 --webpack。

SWC 連 Terser 也換掉

Next.js 從 v13 起連壓縮都預設走 SWC。我以前為了省幾 KB 在調的那些 minify 設定，現在框架自己決定了。

還有 Vite 好像滿紅的

Vite 2020 年出來，開發時用 esbuild（Go 寫的，作者是 Figma 的 Evan Wallace），正式打包時用 Rollup。後來 Rollup 也被 Rust 重寫成 Rolldown，2026 年 Vite 8 直接拿它當預設。

各框架預設用什麼：除了 Next.js，幾乎都是 Vite

現行狀況查了一下，幾乎每個框架預設都用 Vite，只有 Next.js 自己用 Turbopack。

框架預設 build 工具
Next.jsTurbopack（v16 起 dev 跟 build 都預設，要用 webpack 加 --webpack）

Vue（create-vue）Vite（Evan You 兩個都做的）
NuxtVite（webpack / rspack 可選）

Angular 比較特別，打包用 esbuild，dev server 用 Vite。前面說 Vite 開發時用 esbuild，那是 esbuild 包在 Vite 裡面；Angular 只拿 Vite 的 dev server，打包直接呼叫 esbuild，不走 Vite 的 Rollup，所以這裡兩個是並排的零件。Next.js + Vite 從來不是一回事，Next 只出自己的 bundler。Turbopack 跟 Parcel 也從沒兜過，兩個不相干的專案。

這也很合理，因為 Vite 不綁任何框架、誰都能接，所以大家就都接了。Next.js 則是因為夠大、Vercel 錢也夠多，所以自己養一套。

Benchmark 呢

到 2026 年，這些工具都夠快了，速度已經不是選工具的主要考量，比較看生態、相容性跟維護狀況。而且這些 benchmark 大多是某個工具的團隊自己出的，看數字前先看是誰出的。想自己查數字，可以看：

  • rstackjs/build-tools-performance：最全、還在持續更新的比較（Rspack、Vite、Rolldown、esbuild、webpack、Rollup、Parcel、Farm）。由 Rspack 團隊維護。
  • esbuild 自己的 benchmark：esbuild vs webpack / Rollup / Parcel。立場偏 esbuild，測試方式寫在 FAQ 裡，可以對照（three.js ×10：esbuild 0.39s、Parcel 14.9s、Rollup+Terser 34.1s、webpack 41.2s）。

Vite 本身很少是被測的對象。它 dev 用 esbuild、prod 用 Rollup/Rolldown，所以「Vite 很快」的數字，量到的多半是底下的 esbuild 跟 Rollup／Rolldown。

我一直搞不清楚的那件事：為什麼要跑兩次

當年有個地方我一直卡：明明 Babel 就會處理 TypeScript，為什麼專案裡還要另外跑一次 tsc？

問題是我把拔型別跟檢查型別當成同一件事：

  • 拔型別（TS→JS）：把型別拿掉好讓它能跑。Babel、SWC、esbuild 都會。
  • 檢查型別：確認型別有沒有寫錯。只有 tsc 會。

Babel、SWC、esbuild 只拔型別，不做型別檢查。要不要另外手動跑 tsc，取決於設定有沒有把型別檢查包進去：

設定拔型別（TS→JS）型別檢查你要跑
Next.jsSWC，內建next build 幫你跑 tsc不用
Viteesbuild，內建沒包tsc --noEmit（所以常見 vue-tsc && vite build）
Bun內建沒包tsc --noEmit
Babel + Webpack（當年的我）@babel/preset-typescript沒包另外跑 tsc --noEmit
只用 tsc（小 lib）tsctsc，同一次tsc，兩件一起，但不打包

tsc 單獨跑會做兩件事，檢查型別加吐出 .js。tsc --noEmit 是同一個檢查，只是把輸出關掉。現代設定用 --noEmit，是因為 .js 已經有更快的工具生好了，只需要 tsc 的檢查，不需要它比較慢的輸出。

Next.js 就是最寵你的那個：它把全部包起來，你只看到 next build :)

then Bun

Bun 是另一個跟 Node 打對台的 runtime，一開始用一個叫 Zig 的語言寫，2023 年就 1.0 了。結果我這次去看，它自己也在從 Zig 換成 Rust，2026 年 5 月剛把核心重寫進 main。一篇在講「Rust 吃掉整條工具鏈」的東西，連 Bun 這個例子都在中途被 Rust 吃掉了。

then

有個叫 Oxc 的專案，Boshen 在做，想法更進一步：與其每個工具各自 parse 一遍，不如 parse 一次、大家共用同一棵 AST。目前 parser、linter（oxlint）、transformer 都出來了，Rolldown 底層的 parser 也已經用 Oxc。要是成了，現在 SWC、Oxc 各有一套 parser 的狀況，可能又被收回成一套。

所以呢

那個黑盒子裡到底發生了什麼？整層工具從 JavaScript 換成原生執行檔、架構重新設計，也開始用多核心，所以快很多。快在哪、各佔多少，測量是寫在另一篇。

『Rust 比較快』這個想法逐漸成熟，反正就心血來潮做 benchmark。結果有時打平，也有兩次 Node 反而比較快，不過多數時候是 Rust 快三倍上下。SWC 官網說的 20 到 70 倍，量下來大半來自四核心跟兩個程式的架構差，不是 Rust 這個語言。完整的過程跟每一張圖，我寫成另一篇了：我一直在說『Rust 比較快』，後來我真的坐下來量了。每個原因單獨的數字在這：Rust vs V8。

而我從頭到尾沒感覺，因為 Next.js 一直幫我蓋著。到現在我還是不用碰它。只是這次我至少知道底下是什麼了。
