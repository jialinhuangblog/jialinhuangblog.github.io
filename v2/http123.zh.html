HTTP/1.1、2、3：同一頁 12 張圖，每一版怎麼載

2025/04/30
networkhttpquictls

一個商品頁有 12 張圖，每張圖 server 要花 300 ms 才送出來。用 Chrome 156 載這個頁面，server 跟瀏覽器在同一台機器上，網路的 RTT 幾乎是 0：走 HTTP/1.1 要 630 ms 左右，走 HTTP/2 只要 320 ms 左右。同樣 12 張圖、同一台 server，為什麼差了一倍？

再換到訊號不好的手機網路，路上只要掉了一個 packet，HTTP/2 的 12 張圖就會一起停下來等。HTTP/3 的規格在開頭就提到這個問題，而 HTTP/3 的做法是把底下的 TCP 換成 QUIC（RFC 9114 §1.1）。

連線、RTT、handshake 是什麼

瀏覽器要跟 server 說話，得先建立一條 TCP 連線。TCP 保證送出去的資料完整、照順序到達，HTTP 的請求跟回應都在這條連線上傳。HTTPS 則是在 TCP 上面再加一層 TLS 加密。

資料在網路上是切成一個一個 packet 傳的，一張圖可能要好幾十個 packet 才送得完。

RTT（round trip time）是一個 packet 從瀏覽器送到 server，再有一個 packet 回來，總共花的時間。它量的是瀏覽器乾等了多久，不是送了幾個 packet。

client → server    去程
server → client    回程
合起來 = 1 RTT

handshake 是開始傳資料之前，雙方先來回確認的幾個步驟。TCP 的三向 handshake 有三個 packet，可是只花 1 RTT：

client → server:  SYN
server → client:  SYN-ACK       ← 等了 1 RTT，到這裡結束
client → server:  ACK + 資料     ← 跟下一筆資料一起送，不用再等

第三個 packet 不必等任何回覆，client 送出它的同時就開始傳資料。所以三個 packet，乾等的時間只有一個來回。

如果是 HTTPS，TCP handshake 完成之後還有 TLS handshake，TLS 1.3 要再等 1 RTT，TLS 1.2 要 2 RTT。

HTTP/1.0：每張圖開一條新連線

HTTP/1.0 預設每個請求用完就關掉連線，下一個請求要重新建一條（MDN）。12 張圖就是 12 次 TCP handshake，每次都要先等 1 RTT 才能送出請求。

當時有些瀏覽器跟 server 支援 Connection: keep-alive 讓連線留著，不過這是 HTTP/1.0 規格以外的擴充，各家實作不一樣（RFC 9112 附錄 C.2.2）。

HTTP/1.1：連線留著，但一次只處理一個請求

HTTP/1.1 把連線預設改成留著：沒有寫 Connection: close，回應送完之後連線就不關（RFC 9112 §9.3）。12 張圖可以用同一條連線，不用每張都重新 handshake。

可是同一條連線上，請求還是一個接一個。第 1 張圖的回應沒送完，第 2 張的請求就只能等。

head-of-line blocking

HTTP/1.1 有一個叫 pipelining 的功能：不等回應，連續送出好幾個請求。可是 server 必須照請求的順序回應（RFC 9112 §9.3.2）。如果第 1 張圖剛好很大，或是 server 處理得很慢，排在後面的第 2、第 3 張就算早就準備好了，也得等它送完：

請求：  [圖1] [圖2] [圖3] →
回應：  [圖1......] [圖2] [圖3]
             ↑
     圖2、圖3 在等圖1

排在隊伍最前面的請求卡住了後面所有請求，這種情況叫 head-of-line blocking。

主流瀏覽器預設都沒有開 pipelining。MDN 的說法是很多 proxy 處理 pipelining 有 bug，出問題時開發者很難查出原因（MDN）。所以實際上，HTTP/1.1 的每條連線一次只跑一組請求跟回應。

瀏覽器的解法：同一個 host 同時開 6 條連線

一條連線一次只能載一張圖，瀏覽器就同時開好幾條。Chrome 對同一個 host 同時最多 6 條連線在用（Chromium 原始碼 client_socket_pool_manager.cc 的 g_max_sockets_per_group），Firefox 的預設也是 6（network.http.max-persistent-connections-per-server）。

開頭的商品頁用 HTTP/1.1 載的時候，server 收到請求的時間大約是這樣：

0 ms      圖1–圖6 的請求同時到（6 條連線）
300 ms    圖1–圖6 送完
300 ms    圖7–圖12 的請求才到
600 ms    圖7–圖12 送完
協定同時在跑的圖頁面載完（5 次裡的第 2 到第 5 次）
HTTP/1.16626–634 ms
HTTP/212319–325 ms

12 張圖分成兩批，所以 HTTP/1.1 花了大約兩倍時間。

第 2 到第 5 次，Chrome 沒有拿前 6 條連線載圖 7 到圖 12，而是另外開了 6 條新的，所以每次載這一頁，server 都看到 12 條連線，只是同一時間最多 6 條在跑。這裡沒有查 Chrome 為什麼開新的、不重複用舊的。

6 條的上限是每個 host 分開算的。所以有些網站把圖片分散到 img1.example.com、img2.example.com 好幾個 subdomain，讓瀏覽器多開幾組連線，這叫 domain sharding。

HTTP/2：一條連線同時載 12 張圖

Google 在 2009 年發表 SPDY（Chromium Blog），想證明 HTTP 的語意不變，也能傳得更快。IETF 在 2015 年以 SPDY 為基礎訂出 HTTP/2（RFC 7540），2022 年改版成 RFC 9113。

stream 跟 frame

HTTP/2 的主要改變是 multiplexing：一條 TCP 連線裡同時跑很多個 stream，一個 stream 就是一組請求跟回應。12 張圖就是同一條連線上的 12 個 stream，不用排隊。

HTTP/1.1:  [圖1][圖1][圖1][圖2][圖2][圖3][圖3]   ← 一張送完才送下一張
HTTP/2:    [圖1][圖2][圖3][圖1][圖2][圖3][圖1]   ← 交錯送

為了交錯送，HTTP/2 把每個訊息切成更小的 frame。每個 frame 標著自己屬於哪個 stream（stream ID），接收端照 stream ID 把 frame 拼回原本的訊息。TCP 送出去的一個 packet（TCP 叫它 segment）裡，可能同時裝著三個 stream 的 frame：

TCP segment 1: [圖1 frame 1] [圖2 frame 1] [圖3 frame 1]
TCP segment 2: [圖2 frame 2] [圖2 frame 3]
TCP segment 3: [圖1 frame 2] [圖2 frame 4] [圖3 frame 2]

同一個 stream 裡的 frame 照順序；不同 stream 之間不排順序，所以圖 2 不必等圖 1 送完。

開頭的商品頁換成 HTTP/2，server 只看到 1 條連線，12 個請求到達的時間前後相差不到 5 ms，300 ms 後全部送完，就是上面表格裡的 320 ms。

一條連線就夠了

RFC 9113 寫明 client 對同一個 host 跟 port 不應該開超過一條 HTTP/2 連線（§9.1）。HTTP/1.1 時代的 domain sharding 到了 HTTP/2 反而有害：每多一個 subdomain，瀏覽器就要多做一次 TCP 跟 TLS handshake，而且下面講的 header 壓縮表是每條連線各記各的，連線一拆開，同一個 cookie 在每條連線上都要整串送一次。

header 壓縮（HPACK）

HTTP/1.1 會壓縮 body（Content-Encoding: gzip），header 卻是純文字。12 張圖的請求，每一個都帶著同樣的 User-Agent 跟 Cookie。

HTTP/2 用 HPACK 壓縮 header（RFC 7541）。它有兩張表：

  • static table：規格裡寫死的 61 筆常見 header，例如 2 號是 :method GET，4 號是 :path /。
  • dynamic table：這條連線上送過的 header。編號從 62 開始，最新加進去的是 62，舊的往後推（§2.3.3）。

下一個請求要送同樣的 header，就只送它的編號。用 Go 的 x/net/http2/hpack 實際編碼兩個請求，header 裡有一個 2008 bytes 的 cookie：

bytes
同樣的 header 用 HTTP/1.1 純文字送每個請求 2173
HPACK，第 1 個請求（/img/1.jpg）1702
HPACK，第 2 個請求（/img/2.jpg）15

第 2 個請求裡，2008 bytes 的 cookie 只花了 1 byte。第 1 個請求送完之後，兩張表的內容如下（static table 只列其中兩筆，dynamic table 全列）：

static table（規格寫死）：
  2  →  :method GET
  4  →  :path /

dynamic table（每條連線各一份，最後加進去的是 62）：
  62 →  cookie session=...
  63 →  user-agent Mozilla/5.0 ...
  64 →  :path /img/1.jpg
  65 →  :authority shop.example

第 1 個請求的 header 照 :authority、:path、user-agent、cookie 的順序加進表，cookie 最後加，所以拿到最小的 62。:method GET 跟 :scheme https 在 static table 裡已經有，不用加。第 2 個請求的 :authority 用 65 號送。:path 是 /img/2.jpg，跟 64 號的 /img/1.jpg 不同，所以 /img/2.jpg 整串送，同時加進表當新的 62，原本的編號全部往後推一號。輪到 cookie 的時候它已經是 63 號，還是只花 1 byte。

Server Push：已經停用

HTTP/2 允許 server 在瀏覽器開口之前就把資源推過去。瀏覽器要 index.html，server 順便把 style.css 跟 app.js 一起推過來。

照理說這能省掉幾個來回。可是 server 不知道瀏覽器的 cache 裡已經有哪些檔案，常常把瀏覽器早就有的東西又推一次（Jake Archibald）。Chrome 的統計是只有 1.25% 的 HTTP/2 網站用過 push，後來重算降到 0.7%，各方的分析也沒有看到明確的效能提升，很多情況反而變慢（Chrome 部落格）。

  • Chrome 106（2022 年）起預設停用 push，其他 Chromium 瀏覽器跟進。
  • Firefox 132（2024 年）也預設停用（MDN）。
  • HTTP/3 的規格雖然有 push，很多 HTTP/3 的 server 跟 client 都沒有實作。

取代它的是 103 Early Hints（RFC 8297）。server 不直接推檔案，只先回一個 103，告訴瀏覽器接下來大概會用到哪些檔案，要不要抓由瀏覽器決定，cache 裡已經有的就不抓（Chrome 文件）。用 curl 連 www.cloudflare.com，在 200 之前就先收到一個 HTTP/2 103。

ALPN：在 TLS handshake 裡順便選好協定

TLS 有一個擴充叫 ALPN（Application-Layer Protocol Negotiation，RFC 7301），瀏覽器用它告訴 server 自己要講 HTTP/2。TLS handshake 時，client 列出自己支援的協定，server 挑一個回覆，不用多一個來回。用 curl 連 www.cloudflare.com：

$ curl -v --http2 https://www.cloudflare.com/
* ALPN: curl offers h2,http/1.1
* ALPN: server accepted h2
> GET / HTTP/2

ALPN 取代了 SPDY 時代的 NPN（Next Protocol Negotiation）。

瀏覽器只在 TLS 上跑 HTTP/2（h2）。不加密的 HTTP/2（h2c）規格允許，但用 HTTP/1.1 Upgrade header 升級成 h2c 的做法，RFC 9113 已經宣告廢止（§3.1），剩下的做法是 client 事先知道 server 講 HTTP/2，一開始就直接用。在本機開一個 Node.js 的 h2c server：curl --http2-prior-knowledge 拿到 2 200，Chrome 156 則回 ERR_INVALID_HTTP_RESPONSE。所以瀏覽器上的 HTTP/2 一定走 HTTPS。

HTTP/2 碰到掉封包：12 張圖一起等

手機或 Wi-Fi 訊號不好時，有些 packet 會在路上不見，TCP 發現之後會重送。

TCP 保證資料照順序交給上層（RFC 9293）。所以只要有一個 packet 沒到，後面已經到的 packet 都得先放著，等掉的 packet 重送成功，才能一起交給 HTTP/2。

回到 12 張圖。假設裝著圖 1 第 3 個 frame 的 packet 掉了：

圖1: [frame 1] [frame 2] [frame 3 掉了] [frame 4]
圖2: [frame 1] [frame 2] ← 已經到了，但在等圖1 的 frame 3 重送
圖3: [frame 1]           ← 也在等

圖 2 跟圖 3 的資料其實早就到了，卻因為 TCP 要照順序交出去，只能跟著等。HTTP/2 解決了 HTTP 這一層的 head-of-line blocking，但 TCP 自己這一層還有一個。

HTTP/1.1 開 6 條連線的話，掉一個 packet 只影響掉了 packet 的連線，另外 5 條照常進行。HTTP/2 只有一條連線，所以 12 張圖全部跟著停。整個頁面在掉封包的網路上會不會因此比 HTTP/1.1 慢，各家研究結果不一致，這裡沒有量。

HTTP/3：把 TCP 換成 QUIC

TCP 的 head-of-line blocking 來自 TCP 本身照順序交資料的設計，要去掉它就得換掉 TCP。QUIC 是一個跑在 UDP 上的傳輸協定，最早是 Google 做的，後來交給 IETF 標準化，在 2021 年訂成 RFC 9000。HTTP/3 就是跑在 QUIC 上的 HTTP（RFC 9114，2022 年）。

UDP 本身不保證送達也不保證順序，QUIC 自己補上重送、排序，還有 congestion control（依照網路壅塞的程度調整送多快）。跟 TCP 不同的是，QUIC 的排序是每個 stream 各排各的：掉了一個 packet，只有這個 packet 裡有資料的 stream 要等重送，其他 stream 照常往下走（RFC 9000 §13）。

同樣是圖 1 的 frame 3 掉了，換成 HTTP/3：

圖1: [frame 1] [frame 2] [frame 3 掉了] [frame 4]  ← 圖1 等重送
圖2: [frame 1] [frame 2]                        ← 照常交出去
圖3: [frame 1]                                  ← 照常交出去

有幾件事 QUIC 沒有改成每個 stream 各自處理：

  • 一個 QUIC packet 可以同時裝好幾個 stream 的資料，這個 packet 掉了，裡面的 stream 全部要等（RFC 9000 §13）。
  • congestion control 還是整條連線共用一份（RFC 9002）。
  • 實際載網頁時，瀏覽器常常讓少數幾個 stream 先送完，同時在跑的 stream 不多，所以去掉 head-of-line blocking 的效果比理論上小（Smashing Magazine）。

header 壓縮也跟著換掉。在 HPACK 裡，圖 2 的請求用一個編號代表 cookie，而這個編號是圖 1 的請求把 cookie 加進 dynamic table 時拿到的。TCP 保證圖 1 的 header 先到，所以沒有問題。可是在 QUIC 上，如果裝著圖 1 header 的 packet 掉了，圖 2 的 header 會先到，server 查不到 cookie 的編號代表什麼，只能等圖 1 的 packet 重送，又變回 head-of-line blocking（RFC 9204 §1）。

所以 HTTP/3 改用 QPACK。QPACK 把「往 dynamic table 加一筆 cookie」這種指令放在一個專門的 stream 上送，跟圖 1、圖 2 的請求分開。server 收到之後，再從另一個專門的 stream 回覆確認（RFC 9204 §4.4）。

client 編碼圖 2 的 header 時有兩種做法：

  • 只用 server 已經確認過的編號。server 還沒確認收到 cookie 的話，cookie 就整串照送，不過圖 2 不用等任何 packet 重送。整串照送的時候，QPACK 跟 HPACK 一樣會用 Huffman 編碼，讓常見的字元用比較少的 bit 表示。同一個 2008 bytes 的 cookie 交給 quic-go 的 QPACK encoder，送出去是 1627 bytes。反過來，如果 server 已經確認收到 cookie，client 就只送編號，照 RFC 9204 §4.5.2 的格式只要 1 byte（這個沒有量）。
  • 照樣用 cookie 的編號。如果加入 cookie 的指令還沒到 server，server 就要等這個指令到了才能讀圖 2 的 header。連線一開始，server 會用 SETTINGS_QPACK_BLOCKED_STREAMS 告訴 client 最多容許幾個 stream 這樣等。假設 server 寫的是 0，client 就只能用第一種做法（RFC 9204 §2.1.2）。

瀏覽器怎麼知道 server 有 HTTP/3

第一次連一個網站，瀏覽器還不知道它有沒有 HTTP/3，通常先走 TCP。server 在回應裡帶一個 Alt-Svc header，瀏覽器下次才改用 QUIC（RFC 9114 §3.1.1）。curl 連 www.cloudflare.com 收到的是：

alt-svc: h3=":443"; ma=86400

UDP 被網路封鎖、QUIC 連不上的時候，瀏覽器會退回 TCP 上的 HTTP/2 或 HTTP/1.1。

0-RTT 是什麼

0-RTT 不是完全不用來回。client 之前連過這個 server，留著上次給的 session ticket，下次連線時用它算出金鑰，第一個 packet 就帶著加密過的請求出發。TLS handshake 沒有多花任何 RTT，從送出請求到拿到回應，整個過程只要 1 RTT。

HTTP/2 搭 TLS 1.3 也能做 0-RTT，可是在這之前還是得先做 TCP handshake，多 1 RTT。QUIC 把連線的 handshake 跟 TLS 的 handshake 合在一起，所以省下這一趟。

0-RTT 有兩個限制：

  • 0-RTT 的資料可能被攻擊者錄下來重送，所以只適合重送也沒關係的請求，例如 GET（RFC 9001 §9.2）。quic-go 要把 method 寫成 http3.MethodGet0RTT，請求才會放進 0-RTT 送出。
  • server 可以不接受。同一支程式連 www.google.com，20 次都用了 0-RTT；連 www.cloudflare.com，5 次都沒有。

之前連過，恢復 session1 RTT1 RTT；另外可以用 0-RTT 在第一個 packet 就帶請求，server 可以拒絕
ClientHello 裡就帶 key share沒有，要多一個來回交換金鑰有

TLS 1.3 的 client 在 ClientHello 裡就附上 key share，server 收到後手上已經有算金鑰需要的東西，一次就能回完。TLS 1.2 要多一個來回才能交換金鑰。

整條演進

HTTP/1.0  →  每個請求開一條新的 TCP 連線，每次都要 handshake
    ↓ 連線留著重複用
HTTP/1.1  →  一條連線一次一個請求，前面的慢，後面的就等（head-of-line blocking）
    ↓ 一條連線裡同時跑很多個 stream
HTTP/2    →  TCP 掉一個 packet，所有 stream 一起等
    ↓ 把 TCP 換成 QUIC（UDP 加上每個 stream 各自排序）
HTTP/3    →  第一次連 2 RTT，之前連過可以 1 RTT
