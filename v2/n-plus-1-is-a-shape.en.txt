14:Tca4f,<p>An admin page lists every API key, and next to each key, the roles it has. The data model is many-to-many: one key can hold several roles, and one role can belong to several keys, so the pairing lives in a junction table <code>links</code>.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>api_keys(api_key, name)</span></span>
<span data-line=""><span>links(api_key, admin_role_id)      ← junction, many-to-many</span></span>
<span data-line=""><span>roles(id, name, description)</span></span>
<span data-line=""> </span>
<span data-line=""><span>api_keys ──&#x3C; links >── roles</span></span></code></pre></figure>
<p>To get one key's roles, you go to <code>links</code> for its role ids, then to <code>roles</code> to read those roles. All code below uses Prisma with PostgreSQL. Assume one database round-trip takes 5ms and there are 5 keys.</p>

<p>Count the queries:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>1 × SELECT api_keys</span></span>
<span data-line=""><span>5 × SELECT links  WHERE api_key = ?    ← once per key</span></span>
<span data-line=""><span>5 × SELECT roles  WHERE id IN (...)    ← once per key</span></span>
<span data-line=""><span>= 11 queries, one after another, about 55ms</span></span></code></pre></figure>
<p>With 100 keys, it's 1 + 2 × 100 = 201. The query count grows with the number of keys. That's N+1. Each key here crosses two tables, so it works out to 1 + 2N.</p>
<p>Every single query runs fine on the database. The loop sends those 11 queries one iteration at a time. If each iteration called another service's HTTP API, did a Redis <code>GET</code>, or read a file, it would still be N+1. Only the cost of each round-trip changes. So instead of "don't query the database inside a loop," remember: <strong>don't cross a boundary inside a loop</strong>.</p>
<h2>Send them at once with Promise.all: still 11</h2>
<p>In the loop, each key waits for the previous key to finish. Send them all at once instead:</p>

<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  });</span></span>

<p>The 5 keys query <code>links</code> at the same time, and each then queries <code>roles</code>. With 5 or more connections in the pool, the total wait is three round-trips (api_keys, links, roles), about 15ms.</p>
<p>The page is faster, but the database still receives 11 queries. With 100 keys, 100 <code>links</code> queries want a connection at the same time, and if the pool is smaller than that, the rest wait in line.</p>

<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> keyMap</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> new</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1"> Map</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(keys.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">map</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">k</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =></span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> [k.apiKey, { </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">...</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">k, roles: [] }]));</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">for</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> (</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> l</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> of</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> links) keyMap.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">get</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(l.apiKey).roles.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">push</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(roleMap.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">get</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(l.adminRoleId));</span></span></code></pre></figure>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>1 × SELECT api_keys</span></span>
<span data-line=""><span>1 × SELECT links  WHERE api_key IN (5 keys)</span></span>
<span data-line=""><span>1 × SELECT roles  WHERE id      IN (3 roles)</span></span>
<span data-line=""><span>= 3 queries</span></span></code></pre></figure>
<p>Like Promise.all, it's three round-trips, about 15ms. But the database receives only 3 queries, and it stays 3 whether there are 5 keys or 100. The <code>new Set</code> on the second hop removes duplicate role ids: several of the 5 keys share a role, so only 3 roles need querying.</p>
<p>This works because when <code>keys.map(k => k.apiKey)</code> runs, <strong><code>keys</code> already holds all 5 keys</strong>.</p>
<h2>Hand it to Prisma's include: still 3</h2>
<p>Collecting keys, querying with IN, and putting results back: Prisma's <code>include</code> does all three. As long as the schema defines the relations (<code>ApiKey</code> has <code>links</code>, <code>Link</code> has <code>role</code>), it's one call:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> keys</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> await</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> prisma.apiKey.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">findMany</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">({</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  include: { links: { include: { role: </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">true</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> } } },</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">});</span></span></code></pre></figure>
<p>Without the <code>relationJoins</code> preview feature, Prisma queries each table once and joins the results in the application, so it's still 3 queries. You just don't write the IN and the Map yourself (<a href="https://www.prisma.io/docs/orm/v7/prisma-client/queries/relation-queries">Prisma docs</a>).</p>
<h2>Let the database JOIN: 1</h2>
<p>When all three tables live in the same database, the database can connect them itself:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="sql" data-theme="github-dark github-light"><code data-language="sql" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">SELECT</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> k</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">api_key</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">k</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">name</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">r</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">id</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> AS</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> role_id, </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">r</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">name</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> AS</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> role_name</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">FROM</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> api_keys k</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">LEFT JOIN</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> links l </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">ON</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> l</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">api_key</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> k</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">api_key</span></span>

<p>On PostgreSQL, Prisma then uses a LATERAL JOIN to fetch everything in one query, and the result is still grouped objects.</p>
<p>A JOIN only works inside one database. If roles live in another service, you're back to IN: query each side and combine.</p>
<h2>Switch to GraphQL resolvers: back to 11</h2>
<p>Every step so far relied on one thing: a variable holding all the keys at once. In GraphQL, that variable is no longer in the code you write.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="graphql" data-theme="github-dark github-light"><code data-language="graphql" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">query</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> {</span></span>
<span data-line=""><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">  apiKeys</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> {</span></span>
<span data-line=""><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">    name</span></span>
<span data-line=""><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">    adminRoles</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> { </span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">id</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, </span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">name</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> }</span></span>

<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">}</span></span></code></pre></figure>

<p>After the GraphQL engine gets 5 keys, it calls <code>adminRoles</code> once for each, and it calls resolvers on the same level at the same time. There's no loop in the code, yet it runs like the first step's loop plus the second step's Promise.all. Back to 11 queries.</p>
<p>Each resolver call receives a single <code>apiKey</code>, so it can't collect the keys for an IN query by itself.</p>
<h2>Collect the resolver calls with DataLoader: back to 3</h2>
<p><a href="https://github.com/graphql/dataloader"><code>dataloader</code></a> is an npm package Facebook open-sourced. Each resolver now calls <code>.load(key)</code>. GraphQL calls the 5 resolvers at the same time, so the 5 <code>.load()</code> calls land in the same round of the event loop. DataLoader waits for that round to end, then hands all 5 keys to the batch function at once. The batch function holds the same IN queries as before.</p>

<h2>How DataLoader "collects automatically"</h2>
<p>Resolvers call <code>.load()</code> one at a time. How does DataLoader know when to send them together?</p>
<p><code>.load(key)</code> only adds the key to a batch and immediately returns a <strong>pending promise</strong>. When the current round of the event loop ends, DataLoader calls the batch function once. When the query results come back, it fills each promise by index.</p>
<p>So when does a "round" end? Take <code>await Promise.all(ids.map(id => loader.load(id)))</code>. In order:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>1. map runs load(id1): the key joins the batch, DataLoader schedules a dispatch (sending the batch)</span></span>
<span data-line=""><span>2. map keeps going, load(id2) … load(id100): every key joins the same batch</span></span>
<span data-line=""><span>3. map finishes, the synchronous code ends</span></span>
<span data-line=""><span>4. promise callbacks run until the microtask queue is empty, including ones queued along the way; any .load() inside them also joins this batch</span></span>
<span data-line=""><span>5. the dispatch runs: the batch function is called once with every key</span></span></code></pre></figure>
<p>Step 4 is common in GraphQL. A child resolver only starts after its parent resolver's promise resolves, so the child's <code>.load()</code> calls happen inside exactly this kind of callback.</p>
<p>The dispatch scheduled in step 1 is <a href="https://github.com/graphql/dataloader/blob/main/src/index.js"><code>Promise.resolve().then(() => process.nextTick(dispatch))</code></a>. It is wrapped twice: <code>.then</code> waits out step 2, and <code>process.nextTick</code> waits out step 4.</p>
<ul>
<li><strong><code>.then</code></strong>: its callback can't run until step 3 is over, so every key from step 2 makes it in.</li>
<li><strong><code>process.nextTick</code></strong>: <code>Promise.resolve().then().then().then(() => loader.load(x))</code> calls <code>.load()</code> three hops later, and x still lands in the same batch as the keys from step 2. Once V8 starts running promise callbacks, it keeps going until the microtask queue is empty, including callbacks queued along the way, before handing control back to Node. DataLoader calls <code>process.nextTick</code> inside one of those <code>.then</code> callbacks, so Node runs the dispatch only after the queue is empty and control is back.
Call <code>process.nextTick(dispatch)</code> directly in step 1 instead, and the dispatch runs before those step 4 promise callbacks. The next GraphQL level's keys would miss this batch.</li>
</ul>
<h2>What breaks batching</h2>
<p>Put a real <code>await</code> (waiting on real I/O) between two <code>.load()</code> calls and the batch is sent early at that point. If a loop awaits on every iteration, 100 loads become 100 batches:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// ✓ same round: 100 loads in one batch → 1 query</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">await</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> Promise</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">all</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(ids.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">map</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">id</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =></span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> loader.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">load</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(id)));</span></span>
<span data-line=""> </span>
<span data-line=""><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// ✗ sequential loop: each await yields, dispatch runs early, each its own batch → 100 queries</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">for</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> (</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> id</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> of</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> ids) </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">await</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> loader.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">load</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(id);</span></span></code></pre></figure>
<p>In the second version, each <code>await loader.load(id)</code> waits for its query to finish before the next iteration. So the first key goes out as a batch of one. Only after it returns does the loop call <code>.load()</code> a second time, and DataLoader opens a new batch. 100 keys means 100 batches, and with DataLoader in place the code is back at N+1.</p>
<p>GraphQL resolvers also each <code>await load()</code>, but they don't hit this. The engine calls resolvers on the same level <strong>at the same time</strong>, so all 5 <code>.load()</code> calls are made before any <code>await</code> finishes, and they land in the same round.</p>
<h2>p-limit caps how many run at once</h2>
<p><code>p-limit</code> is an npm package that caps how many async tasks run at the same time. Hand 100 queries to <code>pLimit(10)</code> and all 100 still go out, but at most 10 run at once while the rest wait in a queue.</p>

























<table><thead><tr><th></th><th>DataLoader</th><th>p-limit</th></tr></thead><tbody><tr><td>Solves</td><td>N+1 (too many queries)</td><td>pool exhaustion (too many connections at once)</td></tr><tr><td>100 calls</td><td>merged into 1 query</td><td>still 100 runs, at most 10 at once</td></tr><tr><td>Fits</td><td>rows that merge into <code>WHERE IN (...)</code></td><td>tasks that each do something different (read → decide → update)</td></tr></tbody></table>
<p>DataLoader can still run the pool short. If one level has three fields, each with its own loader, one request needs three connections at once; ten concurrent requests need thirty. Then you can enlarge the pool, or use p-limit to cap how many requests are handled at once. As for how long a query waits for a connection: in Prisma v6, <code>pool_timeout</code> defaults to 10 seconds; in v7, Postgres goes through the pg adapter, whose <code>connectionTimeoutMillis</code> defaults to 0, meaning no limit (<a href="https://www.prisma.io/docs/orm/prisma-client/setup-and-configuration/databases-connections/connection-pool">Prisma docs</a>).</p>
<p>Back to the Promise.all step. If each task does something different and can't merge into one IN, you have to send N queries, and that's where p-limit keeps them from using up every connection in the pool at once.</p>

<p>To recap, with the same 5 keys:</p>

<p>Promise.all only shortens the wait. The query count drops only when queries are merged. From IN onward, every step merges N queries into one; the merge just happens in a different place each time: your own code, Prisma, the database, and DataLoader. A GraphQL resolver only ever receives one key, so DataLoader uses <code>Promise.then</code> plus <code>process.nextTick</code> to time the dispatch and collect every <code>.load()</code> from the same round.</p>15:T37a9,
An admin page lists every API key, and next to each key, the roles it has. The data model is many-to-many: one key can hold several roles, and one role can belong to several keys, so the pairing lives in a junction table `links`.

```text
api_keys(api_key, name)
links(api_key, admin_role_id)      ← junction, many-to-many
roles(id, name, description)

api_keys ──< links >── roles
```

To get one key's roles, you go to `links` for its role ids, then to `roles` to read those roles. All code below uses Prisma with PostgreSQL. Assume one database round-trip takes 5ms and there are 5 keys.

## The obvious version: 11 queries

```ts
const keys = await prisma.apiKey.findMany();                  // 1 query

for (const key of keys) {
  const links = await prisma.link.findMany({
    where: { apiKey: key.apiKey },
  });                                                          // 1 per key
  key.roles = await prisma.role.findMany({
    where: { id: { in: links.map(l => l.adminRoleId) } },
  });                                                          // 1 more per key
}
```

Count the queries:

```text
1 × SELECT api_keys
5 × SELECT links  WHERE api_key = ?    ← once per key
5 × SELECT roles  WHERE id IN (...)    ← once per key
= 11 queries, one after another, about 55ms
```

With 100 keys, it's 1 + 2 × 100 = 201. The query count grows with the number of keys. That's N+1. Each key here crosses two tables, so it works out to 1 + 2N.

Every single query runs fine on the database. The loop sends those 11 queries one iteration at a time. If each iteration called another service's HTTP API, did a Redis `GET`, or read a file, it would still be N+1. Only the cost of each round-trip changes. So instead of "don't query the database inside a loop," remember: **don't cross a boundary inside a loop**.

## Send them at once with Promise.all: still 11

In the loop, each key waits for the previous key to finish. Send them all at once instead:

```ts
const keys = await prisma.apiKey.findMany();

await Promise.all(keys.map(async key => {
  const links = await prisma.link.findMany({ where: { apiKey: key.apiKey } });
  key.roles = await prisma.role.findMany({
    where: { id: { in: links.map(l => l.adminRoleId) } },
  });
}));
```

The 5 keys query `links` at the same time, and each then queries `roles`. With 5 or more connections in the pool, the total wait is three round-trips (api_keys, links, roles), about 15ms.

The page is faster, but the database still receives 11 queries. With 100 keys, 100 `links` queries want a connection at the same time, and if the pool is smaller than that, the rest wait in line.

## Collect the keys, query once with IN: 3

Each loop iteration queries with a single key. Collect all the keys first, and each table needs only one query:

```ts
const keys = await prisma.apiKey.findMany();                        // 1 query

const links = await prisma.link.findMany({
  where: { apiKey: { in: keys.map(k => k.apiKey) } },
});                                                                  // 1 query

const roleIds = [...new Set(links.map(l => l.adminRoleId))];
const roles = await prisma.role.findMany({
  where: { id: { in: roleIds } },
});                                                                  // 1 query

// put each role back under its key
const roleMap = new Map(roles.map(r => [r.id, r]));
const keyMap = new Map(keys.map(k => [k.apiKey, { ...k, roles: [] }]));
for (const l of links) keyMap.get(l.apiKey).roles.push(roleMap.get(l.adminRoleId));
```

```text
1 × SELECT api_keys
1 × SELECT links  WHERE api_key IN (5 keys)
1 × SELECT roles  WHERE id      IN (3 roles)
= 3 queries
```

Like Promise.all, it's three round-trips, about 15ms. But the database receives only 3 queries, and it stays 3 whether there are 5 keys or 100. The `new Set` on the second hop removes duplicate role ids: several of the 5 keys share a role, so only 3 roles need querying.

This works because when `keys.map(k => k.apiKey)` runs, **`keys` already holds all 5 keys**.

## Hand it to Prisma's include: still 3

Collecting keys, querying with IN, and putting results back: Prisma's `include` does all three. As long as the schema defines the relations (`ApiKey` has `links`, `Link` has `role`), it's one call:

```ts
const keys = await prisma.apiKey.findMany({
  include: { links: { include: { role: true } } },
});
```

Without the `relationJoins` preview feature, Prisma queries each table once and joins the results in the application, so it's still 3 queries. You just don't write the IN and the Map yourself ([Prisma docs](https://www.prisma.io/docs/orm/v7/prisma-client/queries/relation-queries)).

## Let the database JOIN: 1

When all three tables live in the same database, the database can connect them itself:

```sql
SELECT k.api_key, k.name, r.id AS role_id, r.name AS role_name
FROM api_keys k
LEFT JOIN links l ON l.api_key = k.api_key
LEFT JOIN roles r ON r.id = l.admin_role_id;
```

1 query, 1 round-trip, about 5ms. If you run this SQL with `$queryRaw`, a key with 3 roles comes back as 3 rows, and you group by `api_key` yourself. The other option is to enable `relationJoins` in `schema.prisma` and add `relationLoadStrategy` next to `include`:

```ts
// schema.prisma: generator client { previewFeatures = ["relationJoins"] }
const keys = await prisma.apiKey.findMany({
  relationLoadStrategy: 'join',
  include: { links: { include: { role: true } } },
});
```

On PostgreSQL, Prisma then uses a LATERAL JOIN to fetch everything in one query, and the result is still grouped objects.

A JOIN only works inside one database. If roles live in another service, you're back to IN: query each side and combine.

## Switch to GraphQL resolvers: back to 11

Every step so far relied on one thing: a variable holding all the keys at once. In GraphQL, that variable is no longer in the code you write.

```graphql
query {
  apiKeys {
    name
    adminRoles { id, name }
  }
}
```

`adminRoles` is a field resolver that runs once per key:

```ts
@ResolveField(() => [RoleDto], { name: 'adminRoles' })
async adminRoles(@Parent() apiKey: ApiKeyDto) {
  const links = await this.prisma.link.findMany({
    where: { apiKey: apiKey.apiKey },
  });                                                   // hop 1
  return this.prisma.role.findMany({
    where: { id: { in: links.map(l => l.adminRoleId) } },
  });                                                   // hop 2
}
```

After the GraphQL engine gets 5 keys, it calls `adminRoles` once for each, and it calls resolvers on the same level at the same time. There's no loop in the code, yet it runs like the first step's loop plus the second step's Promise.all. Back to 11 queries.

Each resolver call receives a single `apiKey`, so it can't collect the keys for an IN query by itself.

## Collect the resolver calls with DataLoader: back to 3

[`dataloader`](https://github.com/graphql/dataloader) is an npm package Facebook open-sourced. Each resolver now calls `.load(key)`. GraphQL calls the 5 resolvers at the same time, so the 5 `.load()` calls land in the same round of the event loop. DataLoader waits for that round to end, then hands all 5 keys to the batch function at once. The batch function holds the same IN queries as before.

```ts
import DataLoader from 'dataloader';

@Injectable({ scope: Scope.REQUEST })   // one independent instance per request
export class ApiKeyRoleLoader {
  constructor(private readonly prisma: PrismaService) {}

  // called once, after every .load() key from the same round is collected
  private readonly loader = new DataLoader<string, Role[]>(async (apiKeys) => {
    const links = await this.prisma.link.findMany({ where: { apiKey: { in: [...apiKeys] } } });
    const roleIds = [...new Set(links.map(l => l.adminRoleId))];
    const roles = await this.prisma.role.findMany({ where: { id: { in: roleIds } } });

    const roleMap = new Map(roles.map(r => [r.id, r]));
    const grouped = new Map(apiKeys.map(k => [k, [] as Role[]]));
    for (const l of links) grouped.get(l.apiKey)!.push(roleMap.get(l.adminRoleId)!);
    return apiKeys.map(k => grouped.get(k)!);   // same order as the incoming keys
  });

  load(apiKey: string) { return this.loader.load(apiKey); }
}
```

The resolver becomes one line:

```ts
@ResolveField(() => [RoleDto], { name: 'adminRoles' })
adminRoles(@Parent() apiKey: ApiKeyDto) {
  return this.loader.load(apiKey.apiKey);
}
```

```text
1 × SELECT api_keys
1 × SELECT links  WHERE api_key IN (5 keys)
1 × SELECT roles  WHERE id      IN (3 roles)
= 3 queries   (11 → 3)
```

The queries are identical to the hand-written IN step. There, the keys were collected on the `keys.map(...)` line. Here, DataLoader collects them from 5 `.load()` calls. The batch function must return its array in the same order as the incoming keys, or each resolver gets another key's roles.

## How DataLoader "collects automatically"

Resolvers call `.load()` one at a time. How does DataLoader know when to send them together?

`.load(key)` only adds the key to a batch and immediately returns a **pending promise**. When the current round of the event loop ends, DataLoader calls the batch function once. When the query results come back, it fills each promise by index.

So when does a "round" end? Take `await Promise.all(ids.map(id => loader.load(id)))`. In order:

```text
1. map runs load(id1): the key joins the batch, DataLoader schedules a dispatch (sending the batch)
2. map keeps going, load(id2) … load(id100): every key joins the same batch
3. map finishes, the synchronous code ends
4. promise callbacks run until the microtask queue is empty, including ones queued along the way; any .load() inside them also joins this batch
5. the dispatch runs: the batch function is called once with every key
```

Step 4 is common in GraphQL. A child resolver only starts after its parent resolver's promise resolves, so the child's `.load()` calls happen inside exactly this kind of callback.

The dispatch scheduled in step 1 is [`Promise.resolve().then(() => process.nextTick(dispatch))`](https://github.com/graphql/dataloader/blob/main/src/index.js). It is wrapped twice: `.then` waits out step 2, and `process.nextTick` waits out step 4.

- **`.then`**: its callback can't run until step 3 is over, so every key from step 2 makes it in.
- **`process.nextTick`**: `Promise.resolve().then().then().then(() => loader.load(x))` calls `.load()` three hops later, and x still lands in the same batch as the keys from step 2. Once V8 starts running promise callbacks, it keeps going until the microtask queue is empty, including callbacks queued along the way, before handing control back to Node. DataLoader calls `process.nextTick` inside one of those `.then` callbacks, so Node runs the dispatch only after the queue is empty and control is back.
Call `process.nextTick(dispatch)` directly in step 1 instead, and the dispatch runs before those step 4 promise callbacks. The next GraphQL level's keys would miss this batch.

## What breaks batching

Put a real `await` (waiting on real I/O) between two `.load()` calls and the batch is sent early at that point. If a loop awaits on every iteration, 100 loads become 100 batches:

```ts
// ✓ same round: 100 loads in one batch → 1 query
await Promise.all(ids.map(id => loader.load(id)));

// ✗ sequential loop: each await yields, dispatch runs early, each its own batch → 100 queries
for (const id of ids) await loader.load(id);
```

In the second version, each `await loader.load(id)` waits for its query to finish before the next iteration. So the first key goes out as a batch of one. Only after it returns does the loop call `.load()` a second time, and DataLoader opens a new batch. 100 keys means 100 batches, and with DataLoader in place the code is back at N+1.

GraphQL resolvers also each `await load()`, but they don't hit this. The engine calls resolvers on the same level **at the same time**, so all 5 `.load()` calls are made before any `await` finishes, and they land in the same round.

## p-limit caps how many run at once

`p-limit` is an npm package that caps how many async tasks run at the same time. Hand 100 queries to `pLimit(10)` and all 100 still go out, but at most 10 run at once while the rest wait in a queue.

|  | DataLoader | p-limit |
|---|---|---|
| Solves | N+1 (too many queries) | pool exhaustion (too many connections at once) |
| 100 calls | merged into 1 query | still 100 runs, at most 10 at once |
| Fits | rows that merge into `WHERE IN (...)` | tasks that each do something different (read → decide → update) |

DataLoader can still run the pool short. If one level has three fields, each with its own loader, one request needs three connections at once; ten concurrent requests need thirty. Then you can enlarge the pool, or use p-limit to cap how many requests are handled at once. As for how long a query waits for a connection: in Prisma v6, `pool_timeout` defaults to 10 seconds; in v7, Postgres goes through the pg adapter, whose `connectionTimeoutMillis` defaults to 0, meaning no limit ([Prisma docs](https://www.prisma.io/docs/orm/prisma-client/setup-and-configuration/databases-connections/connection-pool)).

Back to the Promise.all step. If each task does something different and can't merge into one IN, you have to send N queries, and that's where p-limit keeps them from using up every connection in the pool at once.

---

To recap, with the same 5 keys:

```text
for loop                    11 queries   ~55ms
→ Promise.all               11 queries   ~15ms
→ collect keys, IN           3 queries   ~15ms
→ Prisma include             3 queries   ~15ms
→ JOIN                       1 query     ~5ms

GraphQL resolver            11 queries   ~15ms
→ DataLoader                 3 queries   ~15ms
```

Promise.all only shortens the wait. The query count drops only when queries are merged. From IN onward, every step merges N queries into one; the merge just happens in a different place each time: your own code, Prisma, the database, and DataLoader. A GraphQL resolver only ever receives one key, so DataLoader uses `Promise.then` plus `process.nextTick` to time the dispatch and collect every `.load()` from the same round.

<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">    where: { id: { in: links.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">map</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">l</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =></span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> l.adminRoleId) } },</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  });                                                          </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// 每個 key 再 1 次</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">}</span></span></code></pre></figure>
<p>數一下查詢次數：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>1 × SELECT api_keys</span></span>
<span data-line=""><span>5 × SELECT links  WHERE api_key = ?    ← 每個 key 一次</span></span>
<span data-line=""><span>5 × SELECT roles  WHERE id IN (...)    ← 每個 key 一次</span></span>
<span data-line=""><span>= 11 次查詢，一次接一次跑，大約 55ms</span></span></code></pre></figure>
<p>如果 key 變成 100 個，就是 1 + 2 × 100 = 201 次。查詢次數跟著 key 的數量一起長，這就是 N+1。這個例子每個 key 要跨兩張表，所以算起來是 1 + 2N。</p>
<p>資料庫每一次查詢都跑得好好的，那 11 次是迴圈一圈一圈發出去的。假如每一圈呼叫的是另一個服務的 HTTP API、一次 Redis <code>GET</code>，或讀一次檔，一樣是 N+1，只是每次來回花的時間不同。所以與其記「不要在迴圈裡查資料庫」，倒不如記「<strong>不要在迴圈裡跨邊界</strong>」。</p>
<h2>用 Promise.all 同時送出去：還是 11 次</h2>
<p>迴圈裡每個 key 都在等上一個 key 查完。改成同時送出去：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> keys</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> await</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> prisma.apiKey.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">findMany</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">();</span></span>
<span data-line=""> </span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">await</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> Promise</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">all</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(keys.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">map</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">async</span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209"> key</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =></span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> {</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">  const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> links</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> await</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> prisma.link.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">findMany</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">({ where: { apiKey: key.apiKey } });</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  key.roles </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">=</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> await</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> prisma.role.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">findMany</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">({</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">    where: { id: { in: links.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">map</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">l</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =></span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> l.adminRoleId) } },</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  });</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">}));</span></span></code></pre></figure>
<p>5 個 key 同時查 <code>links</code>，各自查完再查 <code>roles</code>。如果 connection pool 有 5 條以上的連線，總共只要等三次來回（api_keys、links、roles），大約 15ms。</p>
<p>頁面變快了，可是資料庫收到的還是 11 次查詢。如果 key 有 100 個，就會有 100 次 <code>links</code> 查詢同時要連線，pool 不夠大的話，剩下的就得排隊。</p>
<h2>先收齊 key，用 IN 一次查：3 次</h2>

<p>跟 Promise.all 一樣是三次來回、大約 15ms，可是資料庫只收到 3 次查詢，而且 key 從 5 個變成 100 個，也還是 3 次。第二層的 <code>new Set</code> 順便把重複的 role id 拿掉了，因為 5 個 key 裡有幾個共用同一個 role，拿掉重複的之後只要查 3 個 role。</p>
<p>能這樣寫，是因為執行到 <code>keys.map(k => k.apiKey)</code> 的時候，<strong><code>keys</code> 裡已經有全部 5 個 key</strong>。</p>
<h2>交給 Prisma 的 include：一樣 3 次</h2>
<p>收 key、查 IN、再分回去，這三件事 Prisma 的 <code>include</code> 會自己做。只要 schema 裡定義了 relation（<code>ApiKey</code> 有 <code>links</code>、<code>Link</code> 有 <code>role</code>），就能寫成一句：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> keys</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> await</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> prisma.apiKey.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">findMany</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">({</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  include: { links: { include: { role: </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">true</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> } } },</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">});</span></span></code></pre></figure>
<p>沒有開 <code>relationJoins</code> 這個 preview 功能的時候，Prisma 會每張表各查一次，再在應用層組起來，所以還是 3 次查詢，只是不用自己寫 IN 和 Map（<a href="https://www.prisma.io/docs/orm/v7/prisma-client/queries/relation-queries">Prisma 文件</a>）。</p>
<h2>讓資料庫 JOIN：1 次</h2>
<p>三張表都在同一個資料庫裡的話，可以讓資料庫自己串起來：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="sql" data-theme="github-dark github-light"><code data-language="sql" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">SELECT</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> k</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">api_key</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">k</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">name</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">r</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">id</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> AS</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> role_id, </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">r</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">name</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> AS</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> role_name</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">FROM</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> api_keys k</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">LEFT JOIN</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> links l </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">ON</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> l</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">api_key</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> k</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">api_key</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">LEFT JOIN</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> roles r </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">ON</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> r</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">id</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> l</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">admin_role_id</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">;</span></span></code></pre></figure>
<p>1 次查詢、1 次來回，大約 5ms。用 <code>$queryRaw</code> 跑這段 SQL 的話，一個 key 有 3 個 role 就會回來 3 列，得自己依 <code>api_key</code> 分組。另一個做法是在 <code>schema.prisma</code> 打開 <code>relationJoins</code>，再在 <code>include</code> 旁邊加上 <code>relationLoadStrategy</code>：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// schema.prisma：generator client { previewFeatures = ["relationJoins"] }</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> keys</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> await</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> prisma.apiKey.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">findMany</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">({</span></span>

<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">  include: { links: { include: { role: </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">true</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> } } },</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">});</span></span></code></pre></figure>
<p>這樣 Prisma 在 PostgreSQL 上就會改用 LATERAL JOIN 一次查回來，而且回傳的還是分好組的物件。</p>
<p>JOIN 只能在同一個資料庫裡做。如果 role 存在另一個服務，就只能回到 IN，各查各的再組起來。</p>
<h2>換成 GraphQL resolver：又變回 11 次</h2>
<p>前面每一步都有個前提：有一個變數同時裝著全部的 key。換成 GraphQL，這個變數就不在我們寫的程式碼裡了。</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="graphql" data-theme="github-dark github-light"><code data-language="graphql" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">query</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> {</span></span>

<p>每次呼叫 resolver，傳進來的 <code>apiKey</code> 只有一個，所以沒辦法自己收齊 key 去查 IN。</p>
<h2>用 DataLoader 把 resolver 的呼叫收齊：回到 3 次</h2>

<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">@</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">ResolveField</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(() </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">=></span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> [RoleDto], { name: </span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'adminRoles'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> })</span></span>

<p>查詢跟手寫 IN 那一步一模一樣。手寫版是在 <code>keys.map(...)</code> 那一行收齊 key，這裡則是 DataLoader 從 5 次 <code>.load()</code> 收過來。批次函式回傳的陣列要照傳進來的 key 排好，不然每個 resolver 會拿到別的 key 的 role。</p>
<h2>DataLoader 怎麼「自動收集」</h2>
<p>既然 resolver 是一個一個呼叫 <code>.load()</code> 的，那 DataLoader 怎麼知道什麼時候該一起送出去呢？</p>
<p><code>.load(key)</code> 只把 key 加進一個批次，然後馬上回傳一個 <strong>pending promise</strong>。等這一輪 event loop 結束，DataLoader 才呼叫一次批次函式，查詢結果回來之後，再依照 index 把每個 promise 填上結果。</p>
<p>那「一輪」到底什麼時候結束呢？拿 <code>await Promise.all(ids.map(id => loader.load(id)))</code> 來說，依序會發生這些事：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-dark github-light"><code data-language="text" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span>1. map 跑第 1 次 load(id1)：key 進批次，DataLoader 預約一次 dispatch（送出批次）</span></span>
<span data-line=""><span>2. map 繼續跑 load(id2) … load(id100)：key 都進同一個批次</span></span>
<span data-line=""><span>3. map 跑完，同步程式碼結束</span></span>
<span data-line=""><span>4. promise callback 一個接一個跑到 microtask queue 清空為止，途中新排進來的也算；裡面如果又呼叫 .load()，key 也進這個批次</span></span>
<span data-line=""><span>5. 輪到 dispatch：用整批 key 呼叫一次批次函式</span></span></code></pre></figure>
<p>第 4 步在 GraphQL 裡很常見。因為上一層 resolver 的 promise 一 resolve，下一層 resolver 才開始跑，所以下一層的 <code>.load()</code> 就是在這種 callback 裡呼叫的。</p>
<p>第 1 步預約的寫法是 <a href="https://github.com/graphql/dataloader/blob/main/src/index.js"><code>Promise.resolve().then(() => process.nextTick(dispatch))</code></a>。這裡包了兩層，<code>.then</code> 負責等第 2 步，<code>process.nextTick</code> 負責等第 4 步：</p>
<ul>
<li><strong><code>.then</code></strong>：第 3 步的同步程式碼跑完之前，這個 callback 不會執行，所以第 2 步的 key 這時都已經在批次裡了。</li>
<li><strong><code>process.nextTick</code></strong>：<code>Promise.resolve().then().then().then(() => loader.load(x))</code> 隔了三層才呼叫 <code>.load()</code>，x 照樣跟第 2 步的 key 在同一批。因為 V8 開始跑 promise callback 之後，會一路跑到 microtask queue 清空才把控制權交回 Node，途中新排進來的 callback 也照跑。DataLoader 是在其中一個 <code>.then</code> callback 裡呼叫 <code>process.nextTick</code>，所以 Node 要等 queue 清空、拿回控制權之後，才執行 nextTick 排的 dispatch。</li>
</ul>
<p>如果第 1 步直接呼叫 <code>process.nextTick(dispatch)</code>，dispatch 反而會比第 4 步那些 promise callback 先跑，GraphQL 下一層的 key 就會錯過這一批。</p>
<h2>什麼寫法會讓批次失效</h2>
<p>只要在兩次 <code>.load()</code> 中間放一個真的 <code>await</code>（真的去等 I/O），批次就會在那裡提早送出。如果迴圈每一圈都 await，100 次 load 就會被切成 100 批：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="ts" data-theme="github-dark github-light"><code data-language="ts" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// ✓ 同一輪：100 個 load 進同一個批次 → 1 次查詢</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">await</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> Promise</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">all</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(ids.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">map</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">id</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =></span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> loader.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">load</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(id)));</span></span>
<span data-line=""> </span>
<span data-line=""><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// ✗ 依序跑的迴圈：每次 await 都讓出執行權，批次提早送出，每次各自一批 → 100 次查詢</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">for</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> (</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">const</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5"> id</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> of</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> ids) </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">await</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> loader.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">load</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(id);</span></span></code></pre></figure>
<p>第二種寫法裡，每次 <code>await loader.load(id)</code> 都要等這次查完才進下一圈。所以第一個 key 會自己成一批送出去。等它查完，迴圈才呼叫第二次 <code>.load()</code>，這時候 DataLoader 又開了一個新的批次。100 個 key 就是 100 批，用了 DataLoader 還是回到 N+1。</p>
<p>GraphQL resolver 雖然也各自 <code>await load()</code>，卻不會這樣。GraphQL 引擎會<strong>同時</strong>呼叫同一層的 resolver，5 次 <code>.load()</code> 都在任何一個 <code>await</code> 結束之前就呼叫完了，所以落在同一輪。</p>
<h2>p-limit 限制的是同時跑幾個</h2>
<p><code>p-limit</code> 是一個 npm 套件，用來限制同時跑幾個非同步任務。把 100 次查詢交給 <code>pLimit(10)</code>，100 次一樣全部會送出去，只是同一時間最多 10 個在跑，其他的排隊等。</p>

























<table><thead><tr><th></th><th>DataLoader</th><th>p-limit</th></tr></thead><tbody><tr><td>解決</td><td>N+1（查詢太多次）</td><td>pool 用光（同時太多連線）</td></tr><tr><td>100 次呼叫</td><td>合併成 1 次查詢</td><td>照樣跑 100 次，同時最多 10 個</td></tr><tr><td>適合</td><td>可以合併成 <code>WHERE IN (...)</code> 的資料</td><td>每個任務做的事都不一樣（讀 → 判斷 → 更新）</td></tr></tbody></table>
<p>用了 DataLoader，pool 還是可能不夠用。如果同一層有三個欄位各用一個 loader，一個 request 就同時要用到三條連線；同時有 10 個 request 進來，就是 30 條。這時候可以調大 pool，或用 p-limit 限制同時處理的 request 數。至於等連線最多等多久，Prisma v6 的 <code>pool_timeout</code> 預設是 10 秒；v7 接 Postgres 改用 pg adapter，它的 <code>connectionTimeoutMillis</code> 預設是 0，也就是不設上限（<a href="https://www.prisma.io/docs/orm/prisma-client/setup-and-configuration/databases-connections/connection-pool">Prisma 文件</a>）。</p>
<p>回到 Promise.all 那一步。如果每個任務做的事都不一樣，沒辦法合併成一個 IN，就只能送 N 次查詢，這時候用 p-limit 讓這些查詢不要同時把 pool 的連線用光。</p>
