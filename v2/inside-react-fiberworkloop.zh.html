setState 之後，React 的 reconciler 依序呼叫了哪些 function

2026/04/20
reactinternalsfiber

呼叫 setState 之後，React 不會當場重新 render。它先記下這次更新，等到某個時間點才 render，最後再把結果寫進 DOM。從 setState 到畫面上的像素把 React 做的事縮成 render 跟 commit 兩步。那這兩步裡面，React 依序呼叫了哪些 function？哪些 render 可以做到一半先停下來，讓瀏覽器去處理別的事？

這些 function 都在 react-reconciler 裡。reconciler 是 React 裡負責算出畫面要怎麼變的部分。下面照 7km.top 這張流程圖的編號走：

reconciler 的流程，分四步。圖片來源：7km.top reconciler 运作流程。

7km.top 這個系列是照 React 17.0.2 的原始碼寫的。圖上大部分 function 到 React 19.3.1 都還在，有兩個改了名字，第三步會講到。

fiber、lane、Scheduler 是什麼

  • fiber：React 替每個元件、每個 DOM 節點各建一個記錄物件，叫 fiber，上面記著 props、state、child，還有對應的 DOM 節點。fiber 之間用 child、sibling、return 三個指標接成一棵 tree。元件更新過之後，它的 fiber 會有兩份，一份對應畫面上現在的樣子，一份是這次 render 正在建的，兩份用 alternate 這個欄位互相指著。fiber 怎麼來的、為什麼有兩份，寫在 ReactNode、ReactElement、Component、div。
  • lane：一次更新的 priority。React 用一個整數裡不同的 bit 代表不同的 priority，例如 SyncLane、DefaultLane，transition 用的是另外幾個 bit。
  • Scheduler：scheduler 這個 npm package，負責決定一件工作什麼時候跑。它不屬於 React 本身。

一、輸入：scheduleUpdateOnFiber

在 event handler 裡呼叫 setState，React 依序做三件事（ReactFiberHooks.js 的 dispatchSetState）：

  1. 用 requestUpdateLane 決定這次更新的 lane。在 click 這類離散事件裡呼叫的是 SyncLane，包在 startTransition 裡的是 transition 的 lane，在 setTimeout 或 fetch 回來之後呼叫的是 DefaultLane。
  2. 把這次更新放進 hook 的 queue，並在這個元件的 fiber 上記下：有一個這個 lane 的更新還沒處理。
  3. 呼叫 scheduleUpdateOnFiber(root, fiber, lane)。它在 root 上也記下有這個 lane 的工作，再呼叫下一步的 ensureRootIsScheduled。

function component 的 setState、useReducer 的 dispatch、class component 的 this.setState，還有 root.render()，最後都會呼叫 scheduleUpdateOnFiber。到這裡，React 還沒 render 任何東西。

二、登記：ensureRootIsScheduled

React 19.3.1 的 ensureRootIsScheduled 只做兩件事：把這個 root 加進待處理的清單，再確認已經排了一個 microtask（ReactFiberRootScheduler.js）。同一個 event handler 裡呼叫十次 setState，也只會排一個 microtask。

等 microtask 跑起來，React 才在 scheduleTaskForRootDuringMicrotask 裡決定怎麼處理：

  • 如果是 SyncLane，就不交給 Scheduler，在同一個 microtask 的最後直接 render 跟 commit。
  • 如果是其他 lane，就呼叫 Scheduler 的 scheduleCallback 排一個 task，什麼時候跑由 Scheduler 決定。

React 18.3.1 的做法不一樣，ensureRootIsScheduled 在 setState 裡就當場決定 priority，當場呼叫 scheduleCallback。7km.top 的圖畫的是這種做法。

在 Chrome 156 上可以比較兩種做法。在 click 的 handler 或 setTimeout 的 callback 裡，呼叫 setState 之後馬上加一個測試用的 microtask，再用 MessageChannel 加一個測試用的 task，然後記下三件事發生的先後順序：測試用的 microtask 執行、測試用的 task 執行、元件 render。每種情況跑三次，三次的順序都一樣：

click 是 SyncLane，所以 React 不經過 Scheduler，render 在 React 的 microtask 裡做。React 在 setState 裡就把這個 microtask 放進 queue，比測試用的 microtask 早，所以 render 最先發生。

setTimeout 的更新是 DefaultLane，startTransition 裡的更新是 transition 的 lane，兩種都不是 SyncLane。所以 React 要呼叫 scheduleCallback 排一個 Scheduler 的 task，render 在那個 task 裡做。Scheduler 在瀏覽器裡也是用 MessageChannel 排 task，所以它的 task 跟測試用的 task 排在同一個 queue，誰先放進去誰先執行。

在 19.3.1，React 要等自己的 microtask 跑起來，才呼叫 scheduleCallback，這時測試用的 task 已經在 queue 裡了，所以 render 最後才發生。

在 18.3.1，setState 當場就呼叫 scheduleCallback，Scheduler 的 task 比測試用的 task 早放進 queue，所以 render 比測試用的 task 先執行。不過 task 要等目前所有的 microtask 都跑完才會開始，所以 render 還是在測試用的 microtask 之後。

Scheduler 自己也有一個 work loop，就是圖右下角的「workLoop 任务调度」，這個迴圈只負責依序執行排進來的 task，不會建 fiber。

三、建 fiber 樹

Scheduler 執行到 React 排的 task，或者 SyncLane 的 microtask 跑到最後，React 就開始 render，也就是圖上那條藍色箭頭「执行 task 回调 / fiber 树构造」。

圖上的兩個入口 performSyncWorkOnRoot 跟 performConcurrentWorkOnRoot 是 React 17 的名字。在 React 19.3.1 裡，microtask 走 performSyncWorkOnRoot，Scheduler 的 task 走 performWorkOnRootViaSchedulerTask，兩個都會呼叫 performWorkOnRoot，由它決定這次 render 能不能中途停下來（ReactFiberWorkLoop.js）：

includesBlockingLane 列出的 lane 有 SyncLane、InputContinuousLane、DefaultLane，另外還有它們在 hydration 時用的版本跟 GestureLane。只要這次要處理的 lane 裡有其中一個，render 就走 renderRootSync，一口氣做完。

所以交給 Scheduler 排時間，不代表 render 能中途停下來。setTimeout 裡的 setState 是 DefaultLane，它雖然排成 Scheduler 的 task，render 的時候照樣走 renderRootSync。只有 transition、Suspense 的 retry 跟 idle 這幾種 lane，render 會分成好幾小塊做。transition 要是等超過 5 秒都還沒做完，includesExpiredLane 會變成 true，接下來也改成一口氣做完。

在 Chrome 156 上，讓一個元件底下有 300 個子元件，每個在 render 時空轉 1 ms。旁邊另外跑一個用 MessageChannel 一直排新 task 的 counter，每個子元件 render 時記下 counter 的值。如果 300 個記到的值都一樣，代表整個 render 在同一個 task 裡做完，中間瀏覽器沒有機會做別的事。每種情況跑三次：

workLoopConcurrentByScheduler 每處理完一個 fiber，就呼叫一次 shouldYield()，問 Scheduler 這 5 ms 用完了沒，用完了就先離開迴圈，把 main thread 還給瀏覽器。workLoopSync 不問，一路做到 workInProgress 變成 null。

每個 fiber 經過兩次

迴圈每一圈處理一個 fiber，走的順序是 depth-first。假設元件 tree 是 App 底下一個 div，div 底下有 h1 跟 p，React 走過的順序是：

  1. beginWork(App)
  2. beginWork(div)
  3. beginWork(h1)，h1 沒有 child
  4. completeWork(h1)，接著走到 sibling
  5. beginWork(p)，p 沒有 child
  6. completeWork(p)，沒有 sibling 了，往上回到 parent
  7. completeWork(div)
  8. completeWork(App)

往下走時呼叫 beginWork：如果是 function component 就執行它，拿回傳的 element 跟上一次比，建出或更新 child 的 fiber，再往第一個 child 走。

往上走時呼叫 completeWork：如果是 div、span 這種 host component，就在記憶體裡建出 DOM 節點，或記下哪些屬性要改，再把 child 的 flag 往上合併到自己身上，commit 時才知道整棵 tree 裡哪裡有東西要改。parent 的 DOM 節點要等 child 的 DOM 都建好才能接起來，所以這一步放在往上走的時候做。

performUnitOfWork 本身只呼叫 beginWork。beginWork 回傳 null 的時候，代表這個 fiber 沒有 child，performUnitOfWork 就改呼叫 completeUnitOfWork，由它執行 completeWork，再決定接下來走 sibling，還是繼續往上。

為什麼不用遞迴

這個走法是一個 while 迴圈，沒有遞迴呼叫。每個 fiber 上都有 child、sibling、return 三個指標，迴圈照著指標一步一步走，目前走到哪裡，記在 workInProgress 這個變數裡，不在 JavaScript 的 call stack 上。所以 React 可以在任何兩個 fiber 之間停下來，把 main thread 還給瀏覽器，下一個 task 再從 workInProgress 指的那個 fiber 接著做。

React 16 以前的 reconciler 用遞迴走元件 tree，目前的位置存在 call stack 上。call stack 沒辦法先存起來、之後再接著跑，所以只能一口氣跑到底。React 團隊描述 Fiber 時，說它是「reimplementation of the stack」，每個 fiber 就像一個可以留在記憶體裡、隨時再執行的 stack frame（React Fiber Architecture）。

迴圈結束時，workInProgress 這棵 tree 就建好了，每個要改的地方都已經用 flag 標起來。

四、輸出：commitRoot

fiber tree 建好之後，React 呼叫 commitRoot。

commitRoot 依序做 before mutation、mutation、layout 三步，把標起來的變更寫進真正的 DOM，useEffect 則排到之後再跑。圖上那條綠色箭頭「输出」從 commitRoot 指向 react-dom。

這三步通常在同一次呼叫裡做完，中間瀏覽器沒有機會跑別的 task。在 React 19.3.1，下面兩個條件同時成立時，這三步會拆成兩段，中間讓瀏覽器跑別的 task：

  • 這次 commit 的 lane 只有 transition、retry、idle 這幾種。
  • 這次更新動到某個 <ViewTransition> 元件。哪些寫法算動到，下面的表列了量過的幾種。

兩個條件都成立時，commitRoot 做完 before mutation，就呼叫瀏覽器的 document.startViewTransition，把 mutation 跟 layout 放進它的 update callback，什麼時候跑由瀏覽器決定（ReactFiberWorkLoop.js 的 commitRoot，ReactFiberConfigDOM.js 的 startViewTransition）。沒用到 <ViewTransition> 的 app，commit 一律在同一次呼叫裡做完。

「拿掉一個 <div>，<ViewTransition> 在這個 <div> 裡面」不會拆。<div> 被拿掉時整塊一起消失，React 把 DOM 元素當成一整塊處理，不替它裡面的 <ViewTransition> 另外跑離場動畫（ReactFiberCompleteWork.js 的註解：「Host Components act as their own View Transitions」）。做法是每個 fiber 上有一個 ViewTransitionStatic flag，記「底下有沒有 <ViewTransition>」，DOM 元素的 fiber 一律把它清掉。React 從被拿掉的 <div> 開始往下找，讀到的是「沒有」，就不往裡面走，也就不會呼叫 document.startViewTransition。新加進一個 <div> 也照這個規則，<div> 裡面就算有 <ViewTransition>，這次更新也不算動到它。

下一列換成有 name 的，就又會拆。同一次更新拿掉舊的 <ViewTransition name="x">，又在畫面別處加進新的 <ViewTransition name="x">。名字一樣，React 要讓舊的那塊畫面用動畫移到新的位置，所以也呼叫 document.startViewTransition。React 在被拿掉的 <div> 底下找有 name 的 <ViewTransition>，好跟新加進的那個配成一對。這一步讀另一個 flag ViewTransitionNamedStatic，DOM 元素不會清掉它，所以 <div> 裡面的也找得到。

reconciler 本身不直接碰 DOM。它呼叫的 appendChild、insertBefore、removeChild、commitUpdate 這些 function，是 react-dom 實作的（ReactFiberConfigDOM.js），裡面才真的呼叫 DOM API。這一步做完，DOM 就變了，接下來輪到瀏覽器做 Style Recalc、Layout、Paint 跟 Composite。

四步整理

步驟React 19.3.1 的 function做什麼能中途停下來嗎
一、輸入scheduleUpdateOnFiber決定 lane，在 fiber 跟 root 上記下這次更新這一步還沒開始 render，當場做完
二、登記ensureRootIsScheduled，microtask 裡的 scheduleTaskForRootDuringMicrotaskSyncLane 留在 microtask 處理，其他 lane 交給 Scheduler這一步還沒開始 render，當場做完
三、建 fiber 樹performUnitOfWork（beginWork、completeWork）建 workInProgress、跟上一次比、建 DOM 節點只有 transition、retry、idle 的 lane 可以
四、輸出commitRoot把變更寫進 DOM通常不行；transition 碰到 <ViewTransition> 時，before mutation 跟 mutation 之間會跑別的 task

大部分的元件不會重跑

每次更新都從 root 開始走，被中斷之後又從 root 重來，聽起來很花時間。不過大部分的 fiber 會直接 bail out，也就是不重跑這個元件。

beginWork 碰到一個 fiber，如果 props 跟上一次是同一個物件、context 沒變，這個 fiber 自己也沒有待處理的更新，React 就不重跑這個元件，接著看它底下：

  • 底下也沒有任何待處理的更新：整個 subtree 都跳過，裡面一個元件都不跑。
  • 底下某個子孫有更新：這個元件不跑，但繼續往下走，走到有更新的那個子孫。

每個 fiber 的 childLanes 記著底下有沒有待處理的更新，所以 React 雖然從 root 出發，只會走進有變化的路徑。

寫程式的人也能讓更多 fiber 跳過。React.memo 讓子元件在 parent 重跑時，只要 props 每一個欄位都跟上次一樣，就跳過；useMemo 跟 useCallback 讓傳下去的物件跟 function 每次都是同一個，這個比較才會過。

為什麼第 2 次點擊還會 render：兩份 fiber 上的 lanes

App 第一次 mount 的時候，React 只建了一份 fiber，alternate 是 null，第二份要等第一次更新才建。所以第 1 次點擊時，setState 只在這一份身上記下 SyncLane。render 的時候，React 從它複製出第二份 fiber，執行 App 之前把第二份的 lanes 清成 0。commit 之後，第二份變成畫面上那份，第一份變成 alternate。這次 render 只清了第二份的 lanes，第一份身上的 SyncLane 還在。

三個 package 各管一件事

流程圖把三件常被混在一起的事分開：

  • Scheduler 決定什麼時候跑。
  • reconciler（圖上的 ReactFiberWorkLoop）決定怎麼建 fiber 樹、哪些地方要改。
  • react-dom 把要改的地方寫進 DOM。

scheduler 是 react-dom 的 dependency，安裝 react-dom 時會一起裝。reconciler 的程式碼則直接編譯進 react-dom：react-dom 19.3.1 的 react-dom-client.production.js 裡自己定義了 beginWork、performUnitOfWork，require 的只有 react、react-dom 跟 scheduler。

react-reconciler 另外也發布成一個 npm package，給要自己寫 renderer 的人用。ink 8.0.0 把它列成 dependency，react-three-fiber 9.8.2 則把一份 react-reconciler 的 build 直接打包在自己的 package 裡。React Native 的 renderer 也是拿同一份 reconciler 原始碼編譯出來的。換掉 react-dom，同一套 reconciler 就能把元件畫到 3D 場景（react-three-fiber）或 terminal（ink）上。

react-dom、react-reconciler、scheduler 三個核心 package 之間怎麼互相呼叫（React 17.0.2）。圖片來源：7km.top 宏观包结构。

平常用的 API 怎麼接到這四步

這四步大多發生在平常不會 import 的地方。對照平常會碰到的 package：

package平常會 import 嗎負責什麼
react每天都會寫元件用的 API：useState、useMemo、startTransition
react-dom會進入點跟 DOM 輸出：createRoot、flushSync；reconciler 也編譯在這裡面
react-reconciler不會自己寫 renderer 時才用的 reconciler
scheduler不會決定那些工作什麼時候跑、一次跑多久

startTransition 讓 render 走 renderRootConcurrent，每 5 ms 停下來一次，所以一個很長的 transition render 不會讓分頁卡住；可是 click 或 setTimeout 觸發的長 render 走的是 renderRootSync，照樣會卡住分頁。React.memo 讓第三步的 beginWork 可以跳過那個元件。
