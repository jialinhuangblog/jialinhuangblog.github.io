GCP 的三種 credential：這個請求用誰的身分？

2025/09/08
cloudgcpauthoauth

很多網站都有「用 Google 登入」的按鈕，那是 OAuth 2.0。後來我要讓 server 每天定時讀一份 Google Calendar，執行時沒有使用者在登入。OAuth 的每個請求都代表一個按過「允許」的使用者，所以 server 要用 OAuth，就得先找一個人授權，之後一直借用他的身分。這樣做得到，可是那個人一撤銷授權，或 token 失效，server 就讀不到了。要讀的 calendar 不屬於哪個使用者的時候，用 app 自己的身分比較合適，也就是 Service Account。

GCP 有三種 credential，各自用不同的身分發請求。

Credential用誰的身分用途
OAuth 2.0 Client ID真人使用者讓人登入你的 app，代他存取他的資料
Service Account你的 app 自己機器對機器，沒有使用者參與
API Key誰的都不用，前端後端都一樣呼叫 Maps 這類公開的 Google API

選的時候依序問：

  • 要一個真人按下「允許」→ OAuth 2.0 Client ID。
  • 像 Maps 這種公開 API，不需要任何人的身分 → API Key，後端呼叫也一樣。
  • 你的 app 用自己的身分去做事 → Service Account。

OAuth 2.0 Client ID：代表使用者發請求

我是在做 Google 登入的時候碰到它的。那是 One Tap 的彈出視窗，Medium 也有，正式名稱叫 Google Identity Services。它要我填一個 OAuth 2.0 Client ID，我就搞糊塗了，因為我已經透過 Firebase Auth 在做 Google 登入，這兩個是不同的系統嗎？

其實不是。兩邊底下都是 OAuth 2.0 Client ID，差別只在串接方式，而且都要使用者自己走完登入流程。兩個還可以接在一起用：讓 One Tap 拿到 credential，再交給 Firebase Auth 管理。

OAuth 的每個請求都代表一個使用者。 使用者登入時，如果 app 申請了 offline access，後端會拿到一個 refresh token。之後使用者不在線上，後端也能用它換新的 access token。所以只要有人同意過一次，定時跑的後端其實可以一直用 OAuth 讀他的 calendar。

只是 server 的權限從此綁在這個人身上。Google 的 OAuth 文件列了 refresh token 會失效的情況，例如使用者撤銷授權、token 六個月沒用過。app 的 consent screen 還在 Testing 狀態的話，refresh token 七天就過期。碰到任何一種，server 就讀不到 calendar，得再請那個人登入一次。

建立的路徑：GCP Console → APIs & Services → Credentials → Create Credentials → OAuth 2.0 Client ID → 選 application type → 設定 authorized redirect URIs。

Service Account：一個虛擬員工

機器對機器、中間沒有人的工作，就用這種 credential。Service Account（SA）像一個虛擬員工，有自己的身分（一個 email 地址），再替它設定權限。

我要讓後端用自己的身分讀某一份特定的 calendar，不借用任何使用者的授權，所以用 Service Account。

最後成功的流程：

  1. 在 GCP 啟用 Calendar API。
  2. 建一個 Service Account，也就是之後要拿來呼叫這個 API 的身分。
  3. 把這個 SA 的 email 加進那份 calendar 的共用名單。
  4. 下載 SA 的 JSON key，把裡面的值放進環境變數，建立 auth client。

第一次我漏了第 3 步，其他設定看起來都對，API 卻一直失敗。我用這個 SA 實測過兩種情況。第一種，calendar 存在，只是沒有共用給 SA；第二種，calendar 根本不存在。API 兩種都回 404 Not Found，回應內容一模一樣。這跟 Google 的 Calendar API 文件寫的一致。所以如果 API 回了 404，先去看共用名單裡有沒有這個 SA。

SA 在 GCP 裡的權限再大，也讀不到沒共用給它的 calendar。就算在 GCP IAM（Identity and Access Management）給 SA 整個 project 的 Owner，結果也一樣。Calendar 是 Google Workspace 的 API（Gmail、Calendar、Drive 這一系列），讀取權限只看 calendar 自己的共用設定，GCP IAM 的角色涵蓋不到它。公司如果用 Workspace，還有另一個辦法：由 Workspace 的 super admin 開 domain-wide delegation，讓 SA 以組織裡的使用者身分存取資料。這個設定在 Workspace 的 Admin console，同樣不在 GCP IAM。

API Key：公開服務的通行證

最後一種最單純。API Key 用在不碰任何人私人資料的公開 Google 服務，例如 Maps。

這把 key 跟身分沒什麼關係，它是拿來防濫用的：rate limit、追蹤用量、計費、限制哪些網站或 app 能用。AWS API Gateway 的 API key 也是同一個用途，讓服務方計算用量跟費用。

合起來看

一般的全端流程三種都會用到：

  1. 前端用 OAuth 2.0 讓使用者登入。
  2. 前端把使用者的 token 傳給後端驗證身分。
  3. 後端用 Service Account 呼叫 Google 的服務。
  4. 要用 Maps 這種公開服務，再加一把 API Key。

要選哪一種，照這個順序問：

SA 一定要下載 key 嗎？

上面的流程第 4 步下載了 SA 的 JSON key。這把 key 預設不會過期，萬一外洩，在有人撤銷之前都能用。

部署在 GCP 上（Cloud Run、GCE、GKE）：建 client 時不傳 credential，Google 的 SDK 會用 ADC（Application Default Credentials）依序去三個地方找，用第一個找到的：

  1. 環境變數 GOOGLE_APPLICATION_CREDENTIALS 指到的 JSON 檔。
  2. 在這台機器上跑過 gcloud auth application-default login 留下的檔案，裡面是登入那個人自己的 credential，不是 SA。
  3. 程式執行環境上掛的 SA。GCP 的機器內建一個 metadata server，程式可以向它要這個 SA 的短期 token。

在 Cloud Run 上，前兩個通常不存在，ADC 會用到第三個，所以不需要 key 檔。部署時沒指定 SA 的話，Cloud Run 會掛上 Compute Engine 的預設 SA。2024-05-03 以前建立的 organization，或不屬於任何 organization 的 project，GCP 可能已經自動給這個預設 SA 整個 project 的 Editor 角色。這樣一來，有人只要攻破這個服務，就能拿它的身分改動 project 裡大部分的資源。所以最好自己建一個 SA，只給它需要的權限，再掛到服務上。

在自己的電腦上開發時，ADC 通常停在第 2 個，用的是開發者本人的身分。如果開發者本人就是 calendar 的擁有者，本機用他的身分一定讀得到。所以共用名單就算漏了 SA，本機也不會出錯。要等上線改用 SA 的身分，API 回了 404，才會發現 SA 漏加了。要在本機用 SA 的身分測試，可以改用 gcloud auth application-default login --impersonate-service-account SA的email 登入。Google 的 impersonation 文件寫明，開發者的帳號要在這個 SA 上有 roles/iam.serviceAccountTokenCreator 才能這樣登入。

部署在 Vercel 這類平台：機器不在 GCP 上，沒有 metadata server，ADC 的三個地方都是空的。這時有兩個選擇：像上面的程式碼一樣把 key 放進環境變數，或用 Vercel 的 OIDC（OpenID Connect）federation。走 OIDC 的話，程式在 Vercel 上會拿到一個 Vercel 簽發的 token，再拿它向 GCP 換一個 SA 的短期 token，整個過程不需要 key。

GCP 換發之前會檢查兩件事，所以要先設定好：

  1. 這個 token 是不是 GCP 信任的來源簽的。在 GCP 建一個 Workload Identity Federation，指定信任 Vercel。
  2. 這個 Vercel 專案能不能用這個 SA。federation 會把 token 裡寫的團隊、專案、環境，變成一個 GCP 認得的身分（principal），例如 principal://iam.googleapis.com/projects/123456/locations/global/workloadIdentityPools/vercel/subject/owner:my-team:project:my-app:environment:production。在 SA 上把 roles/iam.serviceAccountUser 授予這個 principal。

完整的設定步驟在 Vercel 的文件。

跟 AWS 比較

AWS 跟 GCP 給服務權限的預設方向剛好相反。

AWS 上什麼都要先授權才能用。在 console 建一個 Lambda，預設會幫它建一個新的 execution role，只有基本的寫 log 權限，像 CreateLogStream 跟 PutLogEvents。再建第二個 Lambda，預設也會另外建一個 role，就算權限一模一樣。「這個 function 可以碰哪個服務」永遠要自己寫。

GCP 則是預設就先給了權限。部署 Cloud Run 時沒指定 service account 的話，每個服務都共用同一個 Compute Engine 預設 SA，而這個 SA 可能有整個 project 的 Editor 權限。有了 Editor，服務讀寫 project 裡大部分的 GCP 資源都不用另外授權。不過 Editor 是 GCP IAM 的角色，SA 要讀 calendar，還是得被加進那份 calendar 的共用名單。
