Archiving an old year's partition: MySQL, Postgres, Oracle

2024/10/16
databasesqlpostgresqlmysqloraclepartitioning

Once sales is partitioned by year with PARTITION BY RANGE (sale_date), a common next step is dealing with old data: splitting the 2022 partition out into its own table to archive, or moving it to cheaper disk. In Postgres, one DETACH PARTITION takes the partition out from under sales and leaves it as a standalone table. MySQL and Oracle have no such command; you create an empty table first and swap it with the partition using EXCHANGE PARTITION. The PARTITION BY that creates the partitions reads the same in all three databases, yet the steps to split one out differ, because whether a partition is a table, and where its data is stored, differ across the three.

The two questions

Q1. Does a partition become its own table? Can you SELECT * FROM <partition> as you would any table, or is there still just one table that the partitions are only reachable through? This is a question about identity.

Q2. Where does a partition's data physically live? One file, many files, a specific disk? This is a question about location. All three databases use a tablespace to say where data goes. A tablespace is a name you write in SQL; behind it are files or a directory on disk, and one tablespace can hold many tables.

DatabaseQ1: its own table?Q2: where the data lives
MySQLnoeach partition has its own .ibd file, but can't be assigned a tablespace
Oraclenoa partition has no file of its own; it shares data files with the other tables in its tablespace, and can be assigned a tablespace
PostgreSQLyes, a real child tableeach partition has its own file, and can be assigned a tablespace

The two answers can differ. A MySQL partition has its own file, yet it is not a table of its own.

A MySQL tablespace can't hold a partition together with another table; Oracle and Postgres can:

  • MySQL: each partition is its own tablespace, one .ibd file holding only that partition. Several plain tables can share a tablespace made with CREATE TABLESPACE, but a partition can't go in; you get ERROR 1478 (HY000): InnoDB : A partitioned table is not allowed in a shared tablespace..
  • Oracle: each partition can be put in any tablespace alongside other tables, and one data file mixes data from several tables.
  • PostgreSQL: each partition can also be put in any tablespace, in the same directory as other tables, but every table and every partition gets its own file.

Does splitting one out move the data?

When a partition is split out, none of the three copies any data, but each does it differently:

  • Postgres: a partition is already a table with its own file. After DETACH, sales_2022 is still the same file, base/5/16387; it just no longer hangs under sales.
  • MySQL: the swap renames the two .ibd files. Looking at inodes (the file system's number for each file) with ls -i: before the swap, p2022's data is in sales#p#p2022.ibd (inode 168717) and the empty sales_2022.ibd is inode 168721; after it, file 168717 is named sales_2022.ibd and 168721 is named sales#p#p2022.ibd.
  • Oracle: Oracle's documentation says the exchange swaps the two data segments. A data segment is the space a table or partition occupies in the data files. In the test, before the swap, partition sales_2022 had segment 73291, starting at block 778 of cold01.dbf in ts_cold (Oracle's file number 26); after it, sales_2022_arc had the same segment 73291 at the same place.

These operations aren't always instant, though. Postgres's DETACH waits for queries running on sales to finish. The MySQL and Oracle swaps check by default that every row falls inside the partition's range, so more data means a longer check.
