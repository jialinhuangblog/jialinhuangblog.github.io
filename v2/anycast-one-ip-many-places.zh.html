位址一樣，回應的卻是三個城市的機器。很多地方的機器共用同一個 IP，這種做法叫 anycast。

如果只學過 unicast，也就是一個 IP 對一台機器，這件事很難想像。封包上只寫了 1.1.1.1，沒寫要去台北還是巴黎，它是怎麼被送到其中一台的呢？

路上每一台 router 都會查自己的 routing table，照上面寫的方向把封包往下送。unicast 跟 anycast 都是這樣查表。

unicast 的封包怎麼找到路

封包從電腦出發，一路上每一站都在查表：

1. 自己的電腦。 在 macOS 上跑 route -n get 1.1.1.1：

   route to: 1.1.1.1
destination: default
    gateway: 192.168.0.1

電腦不知道 1.1.1.1 在哪裡，只好套用 default 那一筆：不認得的位址，一律交給 192.168.0.1，也就是家裡的 router。

2. 家裡的 router。 一樣只有一筆 default，交給 ISP。

3. ISP 對外的 router。 這裡才有完整的 routing table，internet 上每一段位址（prefix）該交給哪個鄰居（next hop）都列在裡面：

位址段（prefix）交給誰（next hop）
1.1.1.0/24隔壁某個網路的 router
8.8.8.0/24另一個鄰居網路的 router

router 拿封包的目的地去比對，好幾筆都符合時選範圍最小的那筆，再照它寫的方向轉出去。下一台 router 再查一次，一跳一跳接下去。

就算是 unicast，也沒有任何一台 router 知道 1.1.1.1 在哪個城市。 router 的職責就是把封包丟給下一位，接下來去哪，讓下一位去煩惱就好。

routing table 裡的每一筆從哪來：BGP

internet 是很多個各自管理的網路接起來的。每個網路叫一個 AS（Autonomous System），有自己的編號，例如 Cloudflare 是 AS13335。

從台灣連 1.1.1.1，會碰到的 AS 照離使用者多近排，大致是這三種：

角色位置做什麼例子
ISP離使用者最近接家裡、手機的網路，線路主要在一個國家裡台灣的電信業者
transit中間幫別的網路轉送流量，線路跨國跨洲，ISP 沒接到的地方就付錢請它代送NTT（AS2914）
Cloudflare另一端1.1.1.1 就在它的網路裡，很多城市都有機房，跟很多 ISP 直連，也接了 transitAS13335

從台灣連 1.1.1.1，封包出了 ISP 就直接進 Cloudflare，後面的 traceroute 可以看到。ISP 跟目的地沒有直連的時候，中間才會多一段 transit。

兩個網路「直連」，是指雙方的 router 可以直接互傳封包、直接跑 BGP，中間不經過第三個網路。線路通常有兩種拉法：在同一棟資料中心裡拉一條線把兩台 router 接起來，或兩邊都接到同一個 Internet Exchange（IX）的 switch 上。IX 是很多網路集中交換流量的地方。IX 的 switch 只負責把線路接通，本身不算一個網路，所以路徑上的 AS 編號不會多出一個。

相鄰的 AS 之間用 BGP（Border Gateway Protocol）互相告知「要去這段位址，交給我」，這叫宣告。每個網路收到宣告，就把這段位址跟「交給誰」寫進自己的 routing table，但不一定會再轉告出去。

線路接好之後，兩個網路還要約定誰的流量可以走這條線。最常見的約定是 peering：雙方只交換往自己網路的流量，以及往「付錢給自己的網路」的流量，不替對方把流量轉給第三方。Cloudflare 在 peering policy 裡寫明採用 open peering，跟它在同一個地點有機房的網路，想 peering 就能接上。假設台北 ISP 跟 Cloudflare 的直連是 peering，台北 ISP 從 Cloudflare 收到的路由，只會轉告給付錢給它的客戶網路，不會轉告給它自己的 transit。Cloudflare 另外接了 transit，其他國家的網路是從 transit 那裡收到 1.1.1.0/24 的宣告：

  1. Cloudflare（AS13335）把 1.1.1.0/24 宣告給直連的 ISP，也宣告給它接的 transit，路徑是 13335。
  2. 台北的 ISP 收到，記下「1.1.1.0/24 交給 Cloudflare」，再轉告給它的客戶網路。
  3. transit 收到，記下「1.1.1.0/24 交給 Cloudflare」，再轉告給付錢給它的 ISP。路徑變成兩個編號，transit 自己的 AS 編號在左、13335 在右。
  4. 那些 ISP 記下「1.1.1.0/24 交給這個 transit」。

宣告每經過一個網路，路徑上就多一個 AS 編號，收到的網路因此知道這條路要經過幾個網路。

如果台北 ISP 把從 peering 收到的 Cloudflare 路由轉告給自己的 transit，這家 transit 手上就有兩條路。Cloudflare 直接給的路徑是 13335，台北 ISP 轉來的路徑有兩個編號，台北 ISP 的編號在左、13335 在右。transit 選路時通常先選客戶給的路由，因為客戶付錢給它，而台北 ISP 正是它的客戶。所以就算台北 ISP 那條比較長，transit 也可能選它。

transit 選了這條之後，會再轉告給付錢給 transit 的其他客戶。那些客戶往 1.1.1.1 的流量於是先進這家 transit，再交給台北 ISP。台北 ISP 等於花錢買 transit 的線路，替 Cloudflare 送別人的流量，線路也可能塞爆。

這種轉告在 RFC 7908 §3.4 裡叫 route leak。2015 年，印度的 ISP Hathway 把從 Google 收到的 336 個 prefix 轉告給它的 transit Airtel，Google 在歐洲、亞洲的服務因此大範圍中斷。

RIPE（歐洲的 IP 註冊機構）在世界各地放了一種叫 collector 的機器，用來觀察各地的網路收到了什麼宣告。collector 跟當地的網路接上 BGP 之後，每個網路會把自己目前使用的路由告訴 collector，collector 再把這些路由記下來給人查詢。collector 收到路由只做記錄，不拿來轉送封包。

collector 記下的路徑要從右往左讀，最右邊是發出宣告的網路，往左每多一個編號，就是宣告多經過一個網路。以東京 collector 收到的 4777 13335 為例：

  1. 13335（Cloudflare）宣告：1.1.1.0/24 交給我。
  2. 4777（APNIC，亞太區 IP 註冊機構在東京的網路）收到，轉告東京的 collector。
  3. collector 記下的路徑就是 4777 13335。

2026-10-27 在 RIPEstat looking glass 查 1.1.1.0/24 的結果：

collector 所在收到的路徑轉告 collector 的網路
東京4777 13335AS4777，APNIC
倫敦15692 13335AS15692，英國的 Razorblue
23 個 collector 合計路徑全部以 13335 結尾351 個 peer，屬於 254 個 AS

兩條路徑都只有兩個編號，表示 4777、15692 跟 Cloudflare 之間沒有隔著別的 AS。peer 是跟 collector 接上 BGP 的 router，同一個網路可以接好幾個，所以 peer 比 AS 多。東京跟倫敦收到的路徑都以 13335 結尾，但路徑上只有 AS 編號，所以分不出這兩條最後是接到同一個城市的機房，還是不同城市的。

阿姆斯特丹 collector 收到的路徑是 20514 1299 13335，從右往左讀：Cloudflare 宣告，1299（transit 業者 Arelion）收到後轉告 20514（瑞典的 Axians），Axians 再告訴 collector。1299 跟 13335 之間沒有別的編號，所以 Arelion 是直接從 Cloudflare 收到 1.1.1.0/24 的宣告。同一天的資料裡，NTT、Cogent 等其他 transit 業者也出現在 13335 左邊第一個位置。

同一段位址從很多城市宣告

Cloudflare 從不同城市的機房宣告同一段 1.1.1.0/24，台北的機房對台北一帶的網路宣告，巴黎的機房對巴黎一帶的網路宣告。開頭那張表的 TPE、NRT、CDG 三個回應，就是三個城市各自宣告的結果。

這時巴黎 ISP 會同時收到兩則 1.1.1.0/24 的宣告。巴黎機房直接告訴它「交給我」，路徑只有 13335。台北機房也把宣告交給亞洲的 transit，再經過歐洲 transit 傳到巴黎 ISP。照這則走的話，封包要交給歐洲 transit，路徑上多了兩個 AS。

unicast 也常常這樣。例如一家公司同時接了 ISP 甲跟 ISP 乙，甲跟乙都會往外宣告這家公司的位址。如果遠方有一家 transit 業者跟甲、乙都直連，它就會從甲、乙各收到一則宣告，兩則都指向同一家公司。router 的做法一直都是從收到的幾條裡挑一條最好的寫進 routing table，其他的留著備用。router 分辨不出兩條路的盡頭是不是同一台機器，選路時也用不到這個資訊。

把出發地跟「1.1.1.1 放在哪裡」兩兩配對，結果是這樣：

出發地只有台北有 1.1.1.1（unicast）台北、巴黎都有 1.1.1.1（anycast）
台北台北 ISP → Cloudflare 台北台北 ISP → Cloudflare 台北（一樣）
巴黎巴黎 ISP → 歐洲 transit → 亞洲 transit → Cloudflare 台北巴黎 ISP → Cloudflare 巴黎

四種組合裡，只有從巴黎出發、兩邊都有 1.1.1.1 的時候結果變了。巴黎 ISP 照 BGP 的規則，挑了 AS 比較少的巴黎機房那則宣告，所以封包交給了巴黎的機房。

「近」是怎麼算的

BGP 的選路步驟（RFC 4271 §9.1）依序比：

  1. 每個網路替路由打的偏好分數，怎麼打由各網路自己決定，RFC 沒規定
  2. 路徑上的 AS 數量
  3. 在自己網路裡走到交接點有多遠

這裡只列了三項，RFC 在第 2、3 項之間還有 Origin、MED 等幾項比較細的比法。全部比下來，沒有一項是地理距離。

多數時候，近的機房剛好也是路徑短、交接點近的那個，所以看起來像是送到最近的機房。

2026 年 10 月借了 Globalping 放在世界各地的 40 台量測機器（probe），各連一次 1.1.1.1。如果照地理距離走，每台都該連到離自己最近的 Cloudflare 機房。40 台裡有 22 台連到自己所在城市的機房。另外 18 台連到別的城市。其中有些所在城市可能沒有 Cloudflare 機房，不過這次沒有逐一確認。下面兩組，同一個地區的 probe 連到了不同的機房：

probe 所在所在網路連到的機房距離
紐倫堡（德國）netcup法蘭克福（FRA）紐倫堡到法蘭克福約 190 km
紐倫堡（德國）Hetzner巴黎（CDG）紐倫堡到巴黎約 640 km
蒙特婁（加拿大）OVH多倫多（YYZ）兩城相距約 500 km
多倫多（加拿大）HostPapa蒙特婁（YUL）兩城相距約 500 km

距離是兩個城市之間的直線距離。

  • 紐倫堡：兩台 probe 在同一個城市，所在網路不同。netcup 那台連到比較近的法蘭克福，Hetzner 那台卻連到 640 km 外的巴黎。
  • 蒙特婁、多倫多：兩個城市都有 Cloudflare 機房，照距離應該各自連到本地，實際上兩台剛好連到對方的城市。

紐倫堡的 Hetzner 那一筆，七分鐘後又指定同一個網路重跑一輪，分到的三個 probe 都連到巴黎。同時跑的 traceroute 顯示，封包在 Hetzner 自己的線路上從紐倫堡走到巴黎，到了巴黎才交給 Cloudflare。量測資料裡沒有 probe 編號，所以不確定這三個裡有沒有第一輪那一個。

Cloudflare 在法蘭克福也有機房，Hetzner 為什麼不在那裡交出去，從外面沒辦法確定。traceroute 只會顯示 Hetzner 最後選中的路；網路之間交換路由時也只傳選中的那條，所以公開的路由資料一樣查不到它手上有沒有法蘭克福那條。

一個 IP 不是應該唯一嗎

  • 只登記一次。 1.1.1.0/24 登記在 APNIC（亞太區的 IP 註冊機構）名下，whois 紀錄寫著「Routed globally by AS13335/Cloudflare」。
  • 只有 AS13335 能宣告。 RPKI（Resource Public Key Infrastructure）是一套給路由用的簽章紀錄，其中一筆 ROA（Route Origin Authorization）寫著 1.1.1.0/24 只能由 AS13335 宣告。別的 AS 用自己的編號宣告，有開 RPKI 驗證的網路會把那條判成無效，接著要丟掉還是只調低優先順序，由各網路自己決定（RFC 6811 §5）。
  • RPKI 驗證只比對兩樣東西：位址段（prefix），跟路徑最右邊、發出宣告的那個 AS 編號。 所以別的網路要是想冒充 Cloudflare，把自己宣告的路徑最右邊寫成 13335，RPKI 驗證一樣會通過，原本該送到 1.1.1.1 的一部分流量，就可能被送到這個網路去（RFC 6811 §6）。RPKI 驗證也不看宣告是從哪個城市發出來的，所以 Cloudflare 每個城市發出的宣告都會通過驗證。

常見應用

  • CDN：同一個 IP 到處宣告，多數使用者會被自己網路的 router 送到附近的機房。
  • 分散 DDoS：botnet 的機器散在世界各地，每台送出的流量由它所在的網路送到對應的機房，攻擊流量因此分散到很多機房，不會全部擠到同一個。RFC 4786（講怎麼營運 anycast 服務）把這點列為使用 anycast 的理由之一。
  • 雲端的全球入口：AWS Global Accelerator、Google Cloud 的 global external Application Load Balancer 都用 anycast 把使用者帶到附近的 edge。這個 edge 是業者私有網路的入口。以 Global Accelerator 來說，使用者的 TCP 連線在 edge 就結束了，它再另外開一條連線到 endpoint，中間走 AWS 自己的網路。Google 的 Premium 網路層級也一樣，走 Google 自己的 backbone。
