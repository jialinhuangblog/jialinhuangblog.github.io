Inside React's work loop: what the reconciler calls after setState

2026/04/20
reactinternalsfiber

After you call setState, React does not re-render on the spot. It records the update, renders at some later point, and only then writes the result into the DOM. From setState to pixels collapses what React does into two steps, render and commit. So inside those two steps, which functions does React call, in what order? And which renders can stop halfway to let the browser handle something else?

These functions all live in react-reconciler. The reconciler is the part of React that works out how the screen should change. The walk below follows the numbers on this diagram from 7km.top:

The reconciler's flow in four steps. Credit: 7km.top reconciler workflow.

The 7km.top series is written against the React 17.0.2 source. Most functions in the diagram still exist in React 19.3.1; two were renamed, covered in step 3.

What fiber, lane, and Scheduler are

  • fiber: React creates one record object for every component and every DOM node, called a fiber. It holds props, state, children, and the matching DOM node. Fibers link into a tree through three pointers: child, sibling, return. Once a component has updated, its fiber has two copies, one matching what is on screen now and one this render is building, and the two point at each other through the alternate field. Where fibers come from and why there are two copies is in ReactNode, ReactElement, Component, div.
  • lane: the priority of an update. React uses different bits of one integer for different priorities, such as SyncLane and DefaultLane; transitions use a few other bits.
  • Scheduler: the scheduler npm package, which decides when a piece of work runs. It is not part of React itself.

1. Input: scheduleUpdateOnFiber

When an event handler calls setState, React does three things in order (dispatchSetState in ReactFiberHooks.js):

  1. requestUpdateLane picks this update's lane. Called inside a discrete event such as a click, it is SyncLane; inside startTransition, a transition lane; inside setTimeout or after a fetch resolves, DefaultLane.
  2. It puts the update into the hook's queue, and records on this component's fiber that an update with this lane is pending.
  3. It calls scheduleUpdateOnFiber(root, fiber, lane), which records the lane's work on the root as well, then calls the next step, ensureRootIsScheduled.

A function component's setState, a useReducer dispatch, a class component's this.setState, and root.render() all end up calling scheduleUpdateOnFiber. At this point React has not rendered anything.

2. Register: ensureRootIsScheduled

In React 19.3.1, ensureRootIsScheduled does only two things: it adds the root to a list of roots with pending work, and it makes sure a microtask is scheduled (ReactFiberRootScheduler.js). Ten setState calls in one event handler still schedule just one microtask.

When the microtask runs, React decides what to do in scheduleTaskForRootDuringMicrotask:

  • If it is SyncLane, React does not hand it to Scheduler; it renders and commits right at the end of the same microtask.
  • If it is any other lane, React calls Scheduler's scheduleCallback to queue a task, and Scheduler decides when it runs.

React 18.3.1 works differently: ensureRootIsScheduled decides the priority right inside setState and calls scheduleCallback on the spot. The 7km.top diagram shows this approach.

The two approaches can be compared in Chrome 156. Inside a click handler or a setTimeout callback, right after calling setState, queue a test microtask, then queue a test task with MessageChannel, and record the order of three events: the test microtask runs, the test task runs, the component renders. Three runs per case, all three in the same order:

A click is SyncLane, so React skips Scheduler and renders inside React's microtask. React puts that microtask into the queue during setState, ahead of the test microtask, so the render happens first.

An update in setTimeout is DefaultLane, and an update inside startTransition is a transition lane; neither is SyncLane. So React calls scheduleCallback to queue a Scheduler task, and the render happens inside that task. In the browser, Scheduler also queues its tasks with MessageChannel, so its task and the test task sit in the same queue, and whichever went in first runs first.

In 19.3.1, React waits until its own microtask runs before calling scheduleCallback. By then the test task is already in the queue, so the render comes last.

In 18.3.1, setState calls scheduleCallback on the spot, so the Scheduler task enters the queue before the test task and the render runs before the test task. But a task only starts after every pending microtask has run, so the render still comes after the test microtask.

Scheduler also has its own work loop, the "workLoop 任务调度" box in the bottom right of the diagram. That loop only runs queued tasks in order; it does not build fibers.

3. Build the fiber tree

When Scheduler runs the task React queued, or the SyncLane microtask reaches its end, React starts rendering. This is the blue arrow in the diagram labeled "执行 task 回调 / fiber 树构造" (run the task callback / build the fiber tree).

The two entry points in the diagram, performSyncWorkOnRoot and performConcurrentWorkOnRoot, are React 17 names. In React 19.3.1, the microtask goes through performSyncWorkOnRoot and a Scheduler task goes through performWorkOnRootViaSchedulerTask. Both call performWorkOnRoot, which decides whether this render can stop halfway (ReactFiberWorkLoop.js):

includesBlockingLane lists SyncLane, InputContinuousLane, DefaultLane, plus their hydration variants and GestureLane. If the lanes being rendered include any of them, the render goes through renderRootSync and finishes in one go.

So being scheduled by Scheduler does not mean a render can stop halfway. A setState inside setTimeout is DefaultLane; even though it becomes a Scheduler task, its render still goes through renderRootSync. Only transition, Suspense retry, and idle lanes get their render split into small pieces. If a transition is still unfinished 5 seconds after it was scheduled, includesExpiredLane becomes true and from then on it also renders in one go.

Measured in Chrome 156: a component has 300 children, and each busy-waits 1 ms while rendering. Alongside, a counter keeps queueing new tasks with MessageChannel, and each child records the counter's value when it renders. If all 300 record the same value, the whole render ran inside one task and the browser had no chance to do anything else in between. Three runs per case:

Either path ends up in the same kind of loop. The two versions in React 19.3.1:

workLoopConcurrentByScheduler calls shouldYield() after every fiber, asking Scheduler whether the 5 ms are used up. If they are, it leaves the loop and gives the main thread back to the browser. workLoopSync does not ask; it keeps going until workInProgress becomes null.

Each fiber is visited twice

Each turn of the loop handles one fiber, in depth-first order. Suppose the component tree is an App with a div under it, and an h1 and a p under the div. React visits them in this order:

  1. beginWork(App)
  2. beginWork(div)
  3. beginWork(h1); h1 has no child
  4. completeWork(h1), then move to the sibling
  5. beginWork(p); p has no child
  6. completeWork(p); no more siblings, go back up to the parent
  7. completeWork(div)
  8. completeWork(App)

On the way down, React calls beginWork: for a function component it runs the function, compares the returned elements with last time, creates or updates the child fibers, and moves to the first child.

On the way up, React calls completeWork: for a host component such as div or span, it creates the DOM node in memory, or records which attributes need to change, then merges its children's flags into its own, so commit knows where in the whole tree something needs to change. A parent's DOM node can only have its children attached once their DOM nodes exist, which is why this happens on the way up.

performUnitOfWork itself only calls beginWork. When beginWork returns null, the fiber has no child, so performUnitOfWork calls completeUnitOfWork instead, which runs completeWork and then decides whether to move to the sibling or keep going up.

Why not recursion

This walk is a while loop with no recursive calls. Every fiber has the three pointers child, sibling, return, and the loop follows them one step at a time. The current position is kept in the workInProgress variable, not on the JavaScript call stack. So React can stop between any two fibers, give the main thread back to the browser, and continue in the next task from the fiber workInProgress points to.

The reconciler before React 16 walked the component tree recursively, so the current position lived on the call stack. A call stack cannot be saved and resumed later, so the walk had to run to the end in one go. When the React team described Fiber, they called it a "reimplementation of the stack", where each fiber is like a stack frame that can be kept in memory and run again at any time (React Fiber Architecture).

When the loop ends, the workInProgress tree is built, and every place that needs to change has been marked with a flag.

4. Output: commitRoot

Once the fiber tree is built, React calls commitRoot.

commitRoot runs before mutation, mutation, and layout, in that order, writing the marked changes into the real DOM; useEffect is queued to run later. The green arrow labeled "输出" (output) in the diagram points from commitRoot to react-dom.

These three steps usually finish within one call, and the browser gets no chance to run another task in between. In React 19.3.1, when both of the following hold, the three steps are split into two parts, and the browser runs other tasks between them:

  • The lanes in this commit are only transition, retry, or idle lanes.
  • This update touches some <ViewTransition> component. The table below lists the cases that were measured.

When both conditions hold, commitRoot finishes before mutation and then calls the browser's document.startViewTransition, putting mutation and layout into its update callback; the browser decides when that runs (commitRoot in ReactFiberWorkLoop.js, startViewTransition in ReactFiberConfigDOM.js). An app that uses no <ViewTransition> always finishes commit within one call.

"A <div> is removed, and the <ViewTransition> is inside that <div>" does not split. When the <div> is removed, the whole block disappears with it; React treats a DOM element as one block and does not run a separate exit animation for a <ViewTransition> inside it (comment in ReactFiberCompleteWork.js: "Host Components act as their own View Transitions"). The way it does this: every fiber has a ViewTransitionStatic flag recording "is there a <ViewTransition> below", and the fiber of a DOM element always clears it. React starts from the removed <div> and looks down, reads "no", does not go inside, and so does not call document.startViewTransition. Adding a new <div> follows the same rule: even with a <ViewTransition> inside the <div>, the update does not count as touching it.

The next row, with a name, splits again. The same update removes the old <ViewTransition name="x"> and adds a new <ViewTransition name="x"> elsewhere on the page. The names match, so React animates the old part of the page into the new position, and it calls document.startViewTransition for that too. React looks under the removed <div> for a <ViewTransition> with a name, to pair it with the newly added one. This step reads a different flag, ViewTransitionNamedStatic, which DOM elements do not clear, so a <ViewTransition> inside the <div> is still found.

React calls a class component's getSnapshotBeforeUpdate during before mutation and its componentDidUpdate during layout. The reconciler itself never touches the DOM. Functions it calls, such as appendChild, insertBefore, removeChild, commitUpdate, are implemented by react-dom (ReactFiberConfigDOM.js), and those are what call the DOM APIs. After this step the DOM has changed, and it is the browser's turn to run Style Recalc, Layout, Paint, and Composite.

Most components do not run again

Every update walks from the root, and after an interruption it starts again from the root, which sounds expensive. But most fibers bail out, meaning React does not run that component again.

When beginWork reaches a fiber whose props are the same object as last time, with no context change and no pending update of its own, React does not run that component again, and then looks below it:

  • Nothing below has a pending update either: the whole subtree is skipped, and no component inside it runs.
  • Some descendant has an update: this component does not run, but React keeps walking down until it reaches that descendant.

Each fiber's childLanes records whether anything below it has a pending update, so even though React starts from the root, it only walks into the paths that changed.

You can make more fibers skip. React.memo lets a child skip when its parent runs again, as long as every prop is the same as last time; useMemo and useCallback keep the objects and functions you pass down the same between renders, so that comparison passes.

Why click 2 still renders: lanes on the two fibers

When App first mounts, React creates only one fiber; its alternate is null, and the second copy is not created until the first update. So on click 1, setState records SyncLane on that one fiber only. During the render, React copies a second fiber from it and clears the second fiber's lanes to 0 before running App. After commit, the second fiber becomes the one on screen and the first becomes the alternate. This render cleared only the second fiber's lanes; the first still carries SyncLane.

So on click 2, dispatchSetState did not compare the values; it recorded SyncLane on both fibers and scheduled a render. This render uses the alternate, and React clears its lanes to 0 before running App. App computes the same state as last time, so React calls bailoutHooks (ReactFiberHooks.js), which removes SyncLane from the fiber on screen too, and then skips Child. Only at this point are both fibers' lanes 0. On click 3 both are 0, so dispatchSetState compares the values, finds them equal, and drops the update.

Three packages, one job each

The diagram separates three things that often get mixed together:

  • Scheduler decides when to run.
  • The reconciler (ReactFiberWorkLoop in the diagram) decides how to build the fiber tree and what needs to change.
  • react-dom writes those changes into the DOM.

scheduler is a dependency of react-dom and is installed along with it. The reconciler's code, on the other hand, is compiled straight into react-dom: react-dom-client.production.js in react-dom 19.3.1 defines beginWork and performUnitOfWork itself, and the only things it requires are react, react-dom, and scheduler.

react-reconciler is also published as its own npm package for people writing their own renderer. ink 8.0.0 lists it as a dependency, and react-three-fiber 9.8.2 ships a bundled copy of react-reconciler inside its own package. React Native's renderer is compiled from the same reconciler source too. Swap out react-dom, and the same reconciler can draw components into a 3D scene (react-three-fiber) or a terminal (ink).

How the APIs you use connect to the four steps

Most of these four steps happen in places you never import. Compared with the packages you do touch:

PackageDo you import it?Role
reactyes, every daythe component API: useState, useMemo, startTransition
react-domyesthe entry point and DOM output: createRoot, flushSync; the reconciler is compiled in here too
react-reconcilernothe reconciler, used only when writing your own renderer
schedulernowhen that work runs, and for how long at a time

startTransition sends the render through renderRootConcurrent, which pauses every 5 ms, so one long transition render does not freeze the tab; a long render triggered by a click or setTimeout goes through renderRootSync and still freezes it. React.memo lets beginWork in step 3 skip that component.
