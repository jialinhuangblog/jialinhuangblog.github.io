你登入了 bank.com，接著在另一個分頁打開 evil.com。那一頁裡有這一行：

瀏覽器會對 bank.com 發出一個 request。過去好幾年，不管是哪一頁發起的，只要 request 是送往 bank.com，瀏覽器就會把 bank.com 的 session cookie 一起帶上。session cookie 是登入時 bank.com 存在瀏覽器裡的一小段值，server 讀到它，就知道這個 request 是你送的。於是這筆轉帳成立了。

這就是 CSRF（Cross-Site Request Forgery，跨站請求偽造）。你什麼都沒點，攻擊者只是騙瀏覽器送出一個 request，就借用了你已經登入的 session。

那這個 <img> 現在還有用嗎？大多沒有了。在本機用 HTTPS server 扮演 bank.test 跟 evil.test 測試的話，Chrome for Testing 156 只送出標了 SameSite=None 的 cookie，因為從 Chrome 80（2020 年陸續上線）開始，沒寫 SameSite 的 cookie 會被當成 SameSite=Lax，別的網站的圖片發出的 request 就不會帶它。Firefox 159 一個 cookie 都沒送，因為它的 Total Cookie Protection（2022 年 6 月起預設開啟）會在 evil.test 裡另外給 bank.test 一個空的 cookie jar。Safari 則是從 13.1（2020 年 3 月，WebKit 的公告）起，預設就不在這種跨站 request 上帶 cookie。

不過，要是把 <img> 換成一個會自己送出 POST 到 bank.test/transfer 的 form，有兩種情況 cookie 又會被帶上。Firefox 會送出沒寫 SameSite 的 cookie，因為 Firefox 沒有把預設值改成 Lax。Chrome 也會送，但只限 cookie 設下之後的兩分鐘內，這是 Chromium 的 SameSite 更新紀錄裡稱為「Lax + POST」的暫時例外。登入 130 秒後再送一次，Chrome 就沒帶了。標了 SameSite=Lax 或 Strict 的 cookie，上面這幾種情況都沒被送出。所以 CSRF 能用的路比以前少，但沒寫 SameSite 的 cookie 還是有風險。

再看另一個情境。你逛到 forum.com，讀到某人的留言，留言內容是：

如果 forum.com 把留言原封不動當成 HTML 放進頁面，沒做 escape（把 < 換成 &lt;，讓它顯示成文字），這段 script 就會在 forum.com 的 origin 裡執行。origin 是 scheme、host 跟 port 三者合起來，這裡就是 https://forum.com。瀏覽器把每個 origin 的資料分開放，而在某個 origin 裡跑的程式，那個 origin 擁有的東西它都碰得到。所以這段 script 能讀到頁面的 DOM、cookie（標了 HttpOnly 的除外）跟 localStorage，攻擊者就拿到了你的 session。

這就是 XSS（Cross-Site Scripting，跨站腳本攻擊）。攻擊者塞進來的程式，執行起來就像是 forum.com 自己寫的。

把你登入的網站想成一棟大樓吧。server 是大樓的管理員，你在裡面有一戶。瀏覽器是幫你跑腿的人，身上帶著你那一戶的鑰匙，也就是 session cookie。每張單子就是一個 request。跑腿的人把單子送進大樓時會亮出鑰匙，管理員看到鑰匙，就照單子上寫的辦。

兩個攻擊者站的位置不一樣。CSRF 的攻擊者在外面。他沒有鑰匙，只能從別的網站的頁面遞一張假單子給跑腿的人，而跑腿的人照樣亮出你的鑰匙，管理員也就照辦了。XSS 的攻擊者則是把單子混進你自己的頁面裡。網站把別人寫的留言直接當成 HTML 放進你的頁面，就等於在你的單子本上留了一個欄位給陌生人填。從那個欄位寫出去的單子，跑腿的人跟管理員都分不出是不是你寫的，而且填那個欄位的人，還看得見你單子本上的每一頁。

兩種攻擊，兩種威脅模型

XSS：不是我寫的程式碼，在我的 origin 裡執行。攻擊者把 payload 放進會被存起來的內容（留言、個人資料欄位）、會被反射回頁面的 URL 參數，或是透過 DOM 操作塞進來。一旦執行，它就有這個 origin 的全部權限，能讀沒標 HttpOnly 的 cookie、localStorage 跟頁面狀態，也能用使用者的身分送 request。它利用了頁面對使用者內容的信任。

CSRF：我的瀏覽器送出了一個我沒打算送的 request。攻擊者掌握另一個 origin，在頁面上嵌入某個東西（圖片、form、fetch），觸發一個送往目標網站的 request。只要 cookie 的設定允許，瀏覽器就會自動帶上目標網站的 cookie，而 server 光看 cookie，分不出這個 request 是不是你本來就想送的。它利用了瀏覽器會自動帶 cookie 這件事。

登入方式決定了你要面對哪一種威脅

app 怎麼驗證使用者，決定了哪一種威脅比較嚴重。

Cookie session（server 設一個 session cookie，之後瀏覽器送 request 到這個 server，都自動帶上它）：

  • 會被 CSRF 攻擊。別的網站發起的 request 可能會帶著你的 cookie，除非 SameSite（後面會講）把它攔下來。
  • XSS 一樣危險。它能讀沒標 HttpOnly 的 cookie，也能用完整的 session 送 same-origin request。

Token 驗證（JWT，也就是 JSON Web Token，或類似的字串，由你自己的 JavaScript 放進每個 request 的 Authorization header）：

  • CSRF 大致上就不成問題了。沒有 cookie 會被自動帶上，偽造的 request 不會帶著憑證。
  • XSS 變成最主要的威脅。要是 token 放在 localStorage，XSS 的 payload 讀出來之後，就能在任何裝置上冒充這個使用者，直到 token 過期。

現代的 SPA 常用 token，server 產生頁面的 app 通常用 cookie。

CSP 的 nonce 是只用一次的隨機值。設了 script-src 'self' 'nonce-abc123' 之後，server 會在每個正當的 <script> tag 上加 nonce="abc123"，瀏覽器只執行帶著這個值的 inline script，另外加上從自己 origin 載入的 script 檔，這是 'self' 允許的。攻擊者塞進來的 script 沒有這個值，而且 server 每次回應都換一個新的 nonce，所以在舊頁面上看到的值，到了下一頁就沒用了。

深入：XSS 為什麼偽造不了 nonce

攻擊者如果只能塞 markup 進來，例如一則留言，他得在頁面送出之前就把 nonce 寫進自己的 <script>。可是 nonce 是 server 每次回應時才產生的，他沒辦法事先知道。

那從頁面上讀出來呢？CSP 用 response header 送的話，瀏覽器會把每個 nonce attribute 清成空字串，只有已經在執行的 script 能從 .nonce 這個 property 讀到原本的值：

清掉 attribute，是為了不讓塞進來的 CSS 讀到 nonce。攻擊者的 CSS 可以替每個可能的字元各寫一條規則，script[nonce^="a"]、script[nonce^="b"]……，每條載入一張網址不同的背景圖。nonce 如果是 a 開頭，script[nonce^="a"] 就會生效，攻擊者的 server 就會收到 a 對應的背景圖 request。只要頁面沒有重新載入，nonce 就不會變。塞進來的 CSS 會用 @import 再向攻擊者的 server 要下一份 CSS，server 先不回，等收到圖的 request、知道第一個字元之後，才回一份猜第二個字元的規則，例如 script[nonce^="ab"]。這樣一直往下猜，就能拼出整個 nonce。attribute 清成空字串之後，這些規則都不會生效。Chrome for Testing 156 跟 Firefox 159 都會清掉。不過如果 CSP 是用 <meta> 送的，attribute 會留著，這招就還有機會。

如果 nonce 寫死或亂數太短，攻擊者就可能猜中。

沒有 'unsafe-eval' 的話，CSP 會封鎖 eval。加了它之後，如果頁面原本就有一段 script 會把網址參數丟進 eval，攻擊者只要在網址參數裡放自己的程式碼，再騙使用者打開這個網址，他的程式碼就會被執行。

另外，用了 'strict-dynamic' 的話，有 nonce 的 script 去載入別的 script 時，被載入的 script 不用 nonce 也能執行。所以如果其中有一支 loader 會照網址參數去載入 script，攻擊者就能透過它載入自己的程式。'unsafe-inline' 跟 nonce 寫在一起倒是沒關係，因為有 nonce 的時候，瀏覽器會忽略 'unsafe-inline'。

深入：nosniff 是在回傳檔案時決定的，不是上傳時

X-Content-Type-Options 跟它要保護的 Content-Type，都是 server 把存起來的檔案回傳時才設的，跟上傳那一次無關。這是兩趟不同的傳輸：

  • 上傳（使用者把檔案傳給你）。這個 request 上的 Content-Type 是上傳的人自己填的，所以攻擊者可以任意設定。不要把它存起來之後拿來用。
  • 回傳（server 把檔案傳給來看的人）。這時 Content-Type 由你的 server 自己設，通常依副檔名決定（.png 對應 image/png），再加上 nosniff。瀏覽器怎麼處理這個檔案，看的是這個 response。

nosniff 叫看檔案那個人的瀏覽器相信回傳時的 Content-Type，不要再從位元組去猜。所以前提是這個 Content-Type 本身是對的。如果你照抄上傳者填的值，回傳成 text/html，nosniff 也會照單全收，把它當網頁顯示出來。這個 header 只負責讓瀏覽器照你的標籤走，標籤要先標對。

那瀏覽器到底在什麼時候會猜？在 Chrome for Testing 156 跟 Firefox 159 上測試：準備一個存起來的檔案，內容是一個帶 <script> 的 HTML 頁面，用不同的標籤回傳，直接在分頁裡打開。

受害的是第三個人：攻擊者上傳一個藏了 script 的檔案，你的 server 把它存起來，另一個使用者打開它的網址。同一個檔案要是透過 <img> 載入，瀏覽器只會把它當圖片的位元組解碼，不會執行。

HttpOnly 只能減少損害，不能防止 XSS

HttpOnly 讓 XSS 讀不到 cookie 的值，但沒辦法讓 XSS 不去使用這個 session。 XSS 還是可以在 origin 裡面執行 fetch('/transfer', ...)，瀏覽器照樣自動帶上 HttpOnly cookie，server 也照常通過驗證。在 Chrome for Testing 156 跟 Firefox 159 上，document.cookie 列出了 HttpOnly cookie 以外的所有 cookie，而 same-origin 的 fetch POST 還是帶著它。

能做到的事沒有 HttpOnly有 HttpOnly
XSS 讀 document.cookie✅❌
XSS 把 cookie 傳到攻擊者的 server✅❌
XSS 在受害者的瀏覽器裡送出已驗證的 request✅✅
受害者關掉分頁之後，攻擊還能繼續✅❌
從另一台裝置重放這個 cookie✅❌

第二列跟第三列看起來都是 XSS 發出一個 request，結果卻不一樣，因為瀏覽器只會把 cookie 帶給設它的那個網站。XSS 對 evil.com 發 request 的話，瀏覽器帶的是 evil.com 的 cookie，不會帶 bank.com 的。所以 script 要把 session 交給攻擊者，得先從 document.cookie 讀出它的值，再放進網址或 body 裡送出去。設了 HttpOnly，document.cookie 裡就沒有它，script 讀不到值，也就送不出去。XSS 對 bank.com 發的 request 倒是會帶上 cookie，只是 cookie 的值一直留在瀏覽器裡，攻擊者拿不到，只能趁分頁開著的時候借用。

還是要設 HttpOnly。沒設的話，攻擊者能把 cookie 帶走，在自己的電腦上一直用到 server 結束這個 session 為止；設了之後，他只能透過受害者開著的那個分頁操作，分頁關了就沒了。但不要把它當成 XSS 的防線，防 XSS 要靠 output encoding 加上 CSP。

深入：放在記憶體裡的 token，XSS 一樣讀得到

把 JWT 或 access token 放在記憶體裡（Zustand、React context、普通的 module 變數），比放 localStorage 好，但 XSS 還是讀得到。XSS 在你的 origin 裡執行，JS 碰得到的狀態，它都碰得到：

它比 localStorage 好的地方有兩個，都是在減少損害：

  • 通用的 XSS payload 比較難得手。 localStorage.getItem('token') 在每個網站上寫法都一樣。要讀 Zustand store，得先拿到那個 app 的 store，而每個 app 都不一樣。所以一支同時瞄準很多網站的 payload，很容易拿到 localStorage 裡的 token，要拿記憶體裡的就得針對個別 app 下工夫。
  • 分頁一關，token 就跟著消失。 payload 必須在 token 還在記憶體裡的時候執行。localStorage 的 token 存在磁碟上，重新整理、重開瀏覽器都還在，所以之後才執行的 XSS，就算隔了好幾天，還是找得到它。

不過這比 HttpOnly 弱。HttpOnly cookie 完全讀不到；記憶體裡的 token 一旦被 payload 讀到，就能傳到攻擊者的 server，在任何裝置上重放，直到過期。這時只剩 token 的有效期限能限制損害，所以才會用短效的 access token（5 到 15 分鐘），再把長效的 refresh token 放在 HttpOnly cookie 裡，這樣偷到的 access token 只能用幾分鐘。不過只要 payload 還在執行，它就能自己呼叫 /auth/refresh。瀏覽器會自動帶上 refresh cookie，所以 payload 每呼叫一次，就拿到一個新的 access token 可以傳出去。要等 payload 停下來，最後傳出去的那個 token 才會在幾分鐘內失效。受害者關掉分頁之後，攻擊者就換不到新的 access token 了。因為 refresh token 在 HttpOnly cookie 裡，他讀不到，只能透過受害者開著的分頁去呼叫 /auth/refresh。反過來，如果 refresh token 放在 JS 讀得到的地方，被偷走之後，攻擊者可以一直自己換新的 access token，直到 refresh token 過期，受害者關不關分頁都一樣。

CSRF 的防線，一層一層看

讀這整張表時，先假設 XSS 已經防住了。 這裡幾乎每一道 CSRF 防線，在攻擊者能做 XSS 之後都會失效，因為 XSS 是以你自己的 origin 身分執行，能直接讀 token、DOM 跟頁面狀態。最後一欄「XSS 進來之後還有用嗎？」就是把這層依賴寫出來。

SameSite cookieBrowser + ServerSet-Cookie: ...; SameSite=Lax。單子如果是從別的網站遞來的，跑腿的人就不亮鑰匙。例外是你在別的網站點了連結，整個分頁換成你的網站，而且用的是 GET。跨站的 sub-resource request 跟跨站的 form POST 都不會帶 cookie。Chrome 從 Chrome 80（2020 年）起把沒寫 SameSite 的 cookie 當成 Lax，Firefox 跟 Safari 沒有，所以要明確寫出來。沒用。XSS 在同一個 site 裡執行，cookie 照常帶上。

敏感操作前重新驗證 / MFAServer + Client + 使用者開保險箱之前，管理員先打電話問你本人。在重要操作前重新輸入密碼、輸入驗證器的一次性密碼（TOTP），或按一下安全金鑰（WebAuthn）。部分有用。 XSS 自己變不出你的密碼，也沒辦法替你按金鑰。但頁面在它手上，它可以跳出一個看起來很正常的提示，等你自己填。這時它得先騙到你配合，沒辦法再悄悄完成。

為什麼 XSS 比較要緊

XSS 一進來，所有常見的 CSRF 防線都會失效，上面那張表的最後一欄就是這個結果。OWASP 的 CSRF cheat sheet 用一句話講完：「Cross-Site Scripting (XSS) can defeat all CSRF mitigation techniques!」重新驗證是 XSS 進來之後唯一還有作用的一層，因為 XSS 沒有你的密碼跟金鑰，得想辦法讓你自己交出來。

實際的優先順序：

  1. 先防 XSS。 框架的自動 escape、CSP、存進來的內容先清過、nosniff，再用 HttpOnly 限制損害。
  2. 再疊上 CSRF 的防線。 SameSite、token、Origin 檢查。這些只有在 XSS 已經防住的前提下才有意義。
  3. 高風險的操作，加上重新驗證或 MFA。 XSS 成功之後它還有點用，攻擊者得騙你按下確認，沒辦法自己動手。

依架構一步步補強

一樣的防線，依架構組合起來。每一條路線都從最陽春的版本開始，一次加一層。

一步步補強 cookie session 的 app

防 XSS 的三樣東西要先做，後面稱為地基：CSP nonce、框架的自動 escape、nosniff。XSS 一進來，SameSite、CSRF token、Origin 檢查都會失效，HttpOnly 也只能限制損害。

既有的 app 要補強，可以照下面第 0 步到第 6 步的順序。CSP nonce 要改每個 template、檢查每支第三方 script，是最花工夫的一步，所以排到第 4 步，讓便宜的先做。下表列出每一層的成本跟防禦價值：

層成本價值
HttpOnly + Secure各一行限制損害，但不會阻止攻擊
nosniff一行擋掉一條 XSS 路徑：上傳的檔案回傳時的 Content-Type 如果不是 JavaScript，用 <script src> 載入也不會執行。從其他地方進來的 XSS 不受影響
SameSite一行攔下其他網站發起的典型 CSRF；從你自己的 subdomain 發起的攔不下來，其他攻擊也沒用
CSRF token每個 form 都要接XSS 一進來就失效
CSP nonce真正要排時程的工作：server 每個 request 產生一個 nonce，每個 template 都要放進去，每支第三方 script 都要檢查過。漏掉一個，頁面就壞了整組裡價值最高的。它讓塞進來的 script 根本不會執行，而 XSS 正是能穿過其他每一層的那種攻擊

既有的 app 這樣排，是為了補強時不把東西弄壞。昂貴但價值高的 CSP，等排得出時間再做。

0. 什麼都沒設的 cookie。 全部暴露在外：XSS 讀得到，CSRF 用得到，還用明文傳送。

Set-Cookie: session=abc123

1. 先把 cookie 鎖起來，順手加上那個免費的 header。 HttpOnly 讓 JS 讀不到它，Secure 讓它不走明文的 HTTP。nosniff 只要一行，放在這一批一起做，雖然它防的是第 4 步講的 script 執行那一層。

Set-Cookie: session=abc123; HttpOnly; Secure; Path=/
X-Content-Type-Options: nosniff

XSS 沒辦法再把 cookie 傳出去了。但它還是可以在頁面裡使用這個 session，所以這一步只是減少損害，問題還在。

2. 用 SameSite 攔下典型的 CSRF。 跨站的 sub-resource request（就是 <img src="bank.com/transfer"> 那一招）跟跨站的 form POST，都不會再帶 cookie。Chrome 本來就把沒寫的 cookie 當成 Lax，但明確寫出來，也能關掉 Chrome 那兩分鐘的 POST 例外，而且 Firefox 跟 Safari 也會照一樣的規則走。

Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/

管理後台跟跟錢有關的 endpoint 用 SameSite=Strict。

3. 在會改變狀態的 request 上加 CSRF token，因為 SameSite 有漏洞。「site」指的是 scheme 加上可註冊網域（registrable domain），所以 https://evil.bank.com 跟 https://bank.com 是同一個 site。如果有一個 subdomain 落在別人手上（被接管的廢棄 subdomain、放使用者內容的 host），它能通過每一種 SameSite 檢查。實測時，evil.bank.test 上的 <img> 跟 form POST，在 Chrome 跟 Firefox 都帶上了 bank.test 標成 Strict 的 cookie。不過 Origin header 寫的還是 https://evil.bank.test，所以第 5 步在這裡用得上。另外，別的網站連到你的某個 GET 網址時，Lax 還是會帶 cookie，所以會改變狀態的 GET 一樣有風險。

4. 把地基寫出來。 CSP nonce 跟框架的自動 escape（nosniff 第 1 步已經加了）。這就是開頭講的地基。如果你是新專案，做到這裡時這一項早就完成了，前面幾步是之後才補上的便宜基本功。

Content-Security-Policy: script-src 'self' 'nonce-RANDOM'

5. 拒絕外來的 Origin，用在會改變狀態的路由上。便宜的第二層。實測時，瀏覽器在每個 POST 上都送了 Origin，同 origin 的 form 跟 fetch 也一樣，而一般的 GET 沒有送，所以要在會改變狀態的 method 上檢查。POST 沒帶 Origin，不代表它就是你自己送的，這段檢查也會拒絕它。

6. 危險的操作要重新驗證。 轉帳、改 email、刪帳號，都要重新輸入密碼或按一下安全金鑰。XSS 進來之後，只剩這一層還需要你本人點頭。

補強 JWT 的 app，先打地基

動 token 之前，先把地基打好。token 放在哪裡（下面的 A、B、C）只能在 XSS 已經進來之後減少損害，只有一層能一開始就不讓 XSS 進來，所以它排第一。

D. 地基：讓 XSS 根本不會執行。 CSP nonce、框架的自動 escape、nosniff，敏感操作前重新驗證。一個把 token 放在 localStorage、但 CSP 設得很完整的 app，可能比 token 放得很講究、卻沒有 CSP 的 app 安全，因為後者還是讓塞進來的 script 執行。這是唯一能不讓攻擊者進來、而不只是減少損害的一層。

Content-Security-Policy: script-src 'self' 'nonce-RANDOM'
X-Content-Type-Options: nosniff

接著決定 token 放哪裡。這幾項用字母編號，不像前面 cookie 那條用數字，因為只能選一個，不是全部都做。A、B、C 都在回答「token 放在哪裡」這個問題，後一個取代前一個。能做到哪一個，就選最後面那個。

A. Token 放 localStorage。 最糟。XSS 一行就偷走，而且在過期前能從任何裝置重放。

B. Token 放記憶體。 一個 module 變數或 store，不寫進任何儲存空間。分頁一關它就消失，之後才執行的 XSS 什麼都找不到。但分頁開著的時候執行的 XSS 還是讀得到，也能把它傳出去，攻擊者拿到的 token 在過期前都能用。取代 A。

C. 短效的 access token 放記憶體，refresh token 放 HttpOnly cookie。 access token 在記憶體變數裡只用 5 到 15 分鐘；refresh token 放在 JS 永遠讀不到的地方。取代 B。

Set-Cookie: refresh=...; HttpOnly; Secure; SameSite=Strict; Path=/auth/refresh

XSS 讀不到 refresh token，但上面這兩行它也能照跑。實測時，頁面上的一段 script 呼叫了三次 /auth/refresh，瀏覽器每次都自動帶上 refresh cookie，script 也每次都讀到新的 access token，兩個瀏覽器都一樣。前面 HttpOnly 那節也是這樣，cookie 的值讀不到，request 照樣帶著它出去。所以只要分頁開著，payload 每幾分鐘就能拿一個新的 token 傳出去。分頁關掉以後 payload 就停了，最後傳出去的那個 access token 幾分鐘內就過期，refresh token 則從頭到尾沒離開過瀏覽器。

refresh cookie 會被自動帶上，所以 /auth/refresh 自己就有 CSRF 的問題。在這個 cookie 上設 SameSite=Strict，其他網站發起的 request 就不會帶它；但兄弟 subdomain 屬於同一個 site，還是會帶，所以這個 endpoint 也要檢查 Origin。Strict 不會打斷正常流程。實測時，使用者從別的網站點連結進來，頁面接著呼叫 /auth/refresh，這個 request 有帶上 Strict 的 cookie，因為它是從你自己的頁面發出的。這樣一來，CSRF 要處理的範圍就從整個 app 縮到一個 endpoint。

最穩的 JWT app 是 D 加 C：不讓 XSS 進來。萬一進來了，受害者的分頁開著多久，它就能透過 /auth/refresh 拿新的 token 拿多久。不過有了 C，分頁關掉幾分鐘後，它傳出去的 token 都會失效。只要驗證資訊放在 header 裡，就不需要 CSRF token，因為 JWT 不會被自動帶上。還在用 cookie 驗證的路由，就是 cookie app，照 cookie app 的方式防。
