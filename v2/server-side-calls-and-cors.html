Why only the browser gives you a CORS error, and why a call through your own server doesn't

2025/08/02
securitycorsnextjswebcsrf

You wire up an API call. Postman returns 200. curl returns 200. The backend engineer checks the logs and says "works fine on my end." The same call in the browser fails, and Chrome's console shows:

Access to fetch at 'https://api.example.test:8443/none' from origin 'https://app.example.test:8443'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the
requested resource.

So you go back to the backend: "can you add my origin to the CORS headers?" They do. Next week a new endpoint shows the same error, and you have to ask again.

Why does only the browser fail?

Only the browser checks CORS

The same endpoint, which sends no CORS headers, called two ways:

CallerRequest reached the serverCaller got the body
curlyesyes
JavaScript in a page on another origin (Chrome 156, Firefox 159)yesno, fetch throws a TypeError

The server received the request and answered both times. CORS is a rule the browser applies to JavaScript running in a web page. Postman, curl, and your backend calling another backend don't apply it. So "works in Postman, fails in the browser" is not a contradiction: of these clients, only the browser has the rule.

Origin, SOP, and CORS

An origin is scheme + host + port. Two URLs have the same origin only when all three match:

PageRequest toSame origin?
https://app.example.comhttps://app.example.com/apiyes
https://app.example.comhttps://api.example.comno, the host differs
http://localhost:5173http://localhost:8080no, the port differs
http://app.example.comhttps://app.example.comno, the scheme differs

Same-Origin Policy (SOP) is the browser's default: JavaScript in a page cannot read a response from another origin. Nobody has to switch it on. A frontend at app.example.com reading from api.example.com crosses origins, so the read fails by default.

CORS (Cross-Origin Resource Sharing) is how a server lifts that default for the origins it names. The browser adds an Origin header to the request, and the server answers with Access-Control-Allow-Origin:

The value matches the page's origin, so the browser hands the response to the JavaScript. Without that header, the browser does not hand it over.

Which requests go straight to the server

A simple request goes out directly. It has to meet all three conditions (Fetch Standard, MDN):

  1. The method is GET, HEAD, or POST.
  2. Your code sets no headers other than Accept, Accept-Language, Content-Language, and Content-Type, each value at most 128 bytes. (The spec also allows a simple Range header.)
  3. If Content-Type is set, it is application/x-www-form-urlencoded, multipart/form-data, or text/plain.

These are roughly the requests an HTML form can send. Headers the browser adds on its own, like Origin, Cookie, and User-Agent, don't count.

Any other request makes the browser send an OPTIONS request first, the preflight, asking the server whether the real request is allowed:

Requests from a page to an endpoint with no CORS headers (Chrome 156 and Firefox 159 gave the same results):

RequestPreflightServer receivedJavaScript read the response
GETnoGETno
POST, Content-Type: text/plainnoPOSTno
POST, Content-Type: application/jsonyesOPTIONS onlyno
GET with an Authorization headeryesOPTIONS onlyno
PUTyesOPTIONS onlyno

For a simple request, the server has already processed it, and CORS only decides whether the JavaScript can read the response. For a preflighted request, if the server does not approve the preflight, the real request is never sent.

Send the call through your own origin

The error appears because the browser's request goes to a different origin. If the page calls a server on its own origin, and that server calls the API, the browser's request is same-origin. SOP does not apply to same-origin requests, so there is no CORS header to ask the backend for. The call to the API goes from server to server; it does not pass through the browser, so CORS is never checked.

browser  →  https://app.example.com/api/charge     same origin, no preflight
server   →  https://api.payments.com/charge        server to server, no CORS

A same-origin POST with Content-Type: application/json and an Authorization header went out as one request, with no preflight, in both browsers.

In development, Vite's dev server proxy does this:

The browser calls /api/charge on the dev server's origin, and Vite forwards it to https://api.payments.com/charge. Without rewrite, Vite keeps the path as it is and the request goes to https://api.payments.com/api/charge (measured on Vite 7.3.7). changeOrigin: true sets the Host header to the target's host. Vite forwards the browser's Origin header unchanged, so an API that checks Origin itself still sees http://localhost:5173.

server.proxy is part of the dev server, so it is gone in production. In production a real server has to be in the path. In the Next.js App Router (13.2 and later), that can be a Route Handler:

The browser calls /api/charge on its own origin, and your server calls the payment API. Without the Content-Type line, fetch on the server sends the JSON string as text/plain;charset=UTF-8 (measured on Next.js 16.4.3), and an API that expects JSON may reject it.

In Server Actions ("use server") and Server Components, the fetch also runs on the server, during the action and during the render. On Next.js 16.4.3, pages using a Route Handler, a Server Action, and a Server Component each sent requests only to their own origin, and the payment API was called from the server.

The same setup keeps the API key out of the browser

In the Route Handler, the line Authorization: Bearer ${process.env.PAYMENTS_KEY} runs on the server. Next.js puts an environment variable into the browser's JavaScript only when its name starts with NEXT_PUBLIC_; PAYMENTS_KEY is available only on the server (Next.js docs). The Route Handler, Server Action, and Server Component pages each used the key only to call the payment API, and the key appeared in none of the requests the browser sent and none of the responses it received.

If the component had called the payment API directly, the key would be in the request the browser makes, in plain text in the DevTools Network tab for anyone who opens it. Routed through your server, the browser's request carries no key. The server adds the key on the server-to-server request, which the user never sees.

Even without an attacker, a key in the browser has already been handed to whoever uses the page: anything the browser sends shows up in DevTools, and any script running in the page can reach whatever your JavaScript can reach. Obscuring or "encrypting" the key on the client doesn't help, because the code that decrypts it ships to the browser too.

If a 'use client' component reads process.env.PAYMENTS_KEY, the browser's JavaScript gets undefined, but when Next.js renders that component on the server, it gets the real value. A test page rendered the variable, and the key ended up in the HTML (Next.js 16.4.3, next dev).

If a Server Component renders the key, the key reaches the browser too. On a client-side navigation (clicking a <Link>, for example), the browser does not reload the HTML; it downloads an RSC (React Server Components) payload, which holds what the Server Component rendered, including the props it passes to client components. The test used three Server Component pages (Next.js 16.4.3, next dev):

How the Server Component uses the keyKey in the HTMLKey in the RSC payload
Writes it into JSXyesyes
Passes it as a prop to a 'use client' component that shows only the string's lengthyesyes
Uses it only to call the payment API, and passes the API's result as a prop to the same 'use client' componentnono

Route Handlers, Server Actions, and Server Components can all read the key, as long as they don't render it and don't pass it as a prop to a 'use client' component.

After this change, /api/charge is an endpoint anyone can call, including your own users with DevTools open, so your server has to authenticate the user and rate-limit the route.

When routing through your origin isn't the answer

All of the above is about calling someone else's API. Two other situations work differently.

You own an API that browsers on other origins have to call. If your public API is meant to be called from other people's web apps, it can't go through your server. Set CORS on purpose and list specific origins. When the request carries cookies, the browser rejects Access-Control-Allow-Origin: * anyway (see the reference table below).

The request comes from an attacker. For a simple request, CORS only decides who can read the response, so it does not stop a forged request (CSRF) from reaching your server. The stories below show what it stops and what it doesn't.

Deeper: how CORS plays out against an attacker (three stories)

Measured in Chrome 156 and Firefox 159. SameSite is a cookie attribute that limits which cookies go along on requests started by another site (details in Why a localhost cookie never reaches thembase.localhost). In the test, the bank sets three cookies, whose SameSite is unset, Lax, and None; Secure.

Story 1: classic CSRF, where CORS plays no part. A user is logged in to bank.com and opens evil.com, whose page auto-submits a form:

A form POST is a simple request, so there is no preflight. It goes straight to bank.com/transfer. Both browsers attached the SameSite=None cookie and the cookie without SameSite, and neither sent the SameSite=Lax cookie. Chrome sent the cookie without SameSite only because it had been set a few seconds earlier; after two minutes Chrome stops sending it on cross-site POSTs (details in Why a localhost cookie never reaches thembase.localhost). If the session cookie goes along, the bank sees a logged-in user asking for a transfer and, with no other defense, carries it out. The bank's CORS settings play no part here; the defenses against this attack are SameSite=Lax cookies, a CSRF token, and an Origin check (see XSS and CSRF: which defense stops which attack).

Story 2: CSRF with fetch, where CORS helps part way. evil.com sends the POST with fetch, credentials: 'include' (which makes a cross-origin request carry cookies), and Content-Type: application/json, so a preflight goes first.

SituationChrome 156Firefox 159 (user opened evil.com directly)
The bank sends no CORS headersonly the OPTIONS arrivesonly the OPTIONS arrives
The bank's preflight approves any origin, but the actual response has no CORS headersthe POST arrives with the SameSite=None cookie; evil.com's JavaScript can't read the resultthe POST arrives with no cookies; the JavaScript can't read the result
The same JSON body sent as Content-Type: text/plain with mode: 'no-cors'no preflight; the POST arrives with the SameSite=None cookieno preflight; the POST arrives with no cookies

In the first row, CORS did stop the request. But if the bank parses the body as JSON without checking Content-Type, the attacker only has to drop the header as in the last row, and is back to story 1. Firefox's Total Cookie Protection stores cookies by the site that was in the address bar when they were set. bank.com's cookies were set while the address bar showed bank.com, so when the user opens evil.com directly, the fetch calls from evil.com don't get them, which is why the Firefox column above shows no cookies.

It changes when the user reaches evil.com by clicking a link on a bank.com page. Firefox has a heuristic: after the user clicks a link from A to B, requests from B's page to A can carry A's cookies. In the test, on an evil.com reached by a link from bank.com, the POSTs in the second and last rows carried the cookie without SameSite and the SameSite=None cookie. A few seconds after that click, the user opened evil.com directly, and Firefox still sent both cookies. How long Firefox keeps sending them was not measured. With privacy.restrict3rdpartystorage.heuristic.navigation set to false in Firefox's about:config, a rerun sent no cookies after the link click. Chrome 156 sent the same cookies as the Chrome column above whether the user opened evil.com directly or clicked through to it (details on SameSite and Total Cookie Protection in Why a localhost cookie never reaches thembase.localhost).

Story 3: supply chain, where someone else's script runs inside an allowed origin. Because trusted-site.com is a partner, your CORS settings allow it, and allow its requests to carry cookies. trusted-site.com loads an ad script from ad-scripts.com, and that script runs in trusted-site.com's origin. Its requests carry Origin: https://trusted-site.com, which is on your allow list, so the browser lets the script read your responses. In the test, the ad script read the response and sent it to the ad server, in both browsers. Chrome also sent the SameSite=None cookie; Firefox sent no cookies (the user opened trusted-site.com directly). CORS checks only the origin, not which script inside the origin made the request. The defenses:

  • Subresource Integrity (integrity="sha384-..."): the browser refuses to run a script whose content has changed.
  • CSP: limits where scripts can be loaded from.
  • Allow as few origins as possible.
Reference: CORS headers (sent by the browser and by the server)

The browser fills in these headers itself; you don't write them in your fetch.

HeaderWhat it carries
OriginThe calling page's scheme + host + port
Access-Control-Request-MethodPreflight only. The method the real request will use.
Access-Control-Request-HeadersPreflight only. The headers the real request will set that are not on the simple list.

You write the server headers in your CORS middleware.

HeaderWhat it controls
Access-Control-Allow-OriginThe allowed origin: one origin that matches Origin, or * for any. With credentials: 'include', * fails.
Access-Control-Allow-MethodsMethods the server accepts from a preflighted request.
Access-Control-Allow-HeadersHeaders outside the simple list that the server accepts.
Access-Control-Allow-CredentialsWith true, JavaScript may read the response to a request sent with credentials: 'include'. On a preflight, without it the real request is not sent. It does not decide whether cookies are sent: in the test, a request with credentials: 'include' carried cookies even though the response had no such header, and only the read failed.
Access-Control-Max-AgeSeconds the browser may reuse the preflight result. Cached per URL, query string included. Without it, 5 seconds. Firefox caps it at 86400, Chrome at 7200 (MDN).

To send cookies on a cross-origin call, the client opts in with fetch(url, { credentials: 'include' }) or the older xhr.withCredentials = true.

API keys, read access, and CSRF: what handles each

JobWhat does itWhat it stops
Keep secrets out of the clientRoute the call through your own serverYour API key showing up in the browser
Control who can read your responsesSOP by default, CORS to open it upJavaScript on other origins reading sensitive responses
Block forged cross-site requestsSameSite cookie + CSRF token + Origin checkClassic CSRF on simple requests

If you are the one calling an API, route the call through your own origin. You skip the CORS setup and keep the key on the server at the same time. Configure CORS only when you own an endpoint that really has to be read from other origins. Don't count CORS as a CSRF defense, because a simple request reaches your server either way.

For the CSRF side in full, see XSS and CSRF: which defense stops which attack.
