Skill、Agent、Tool、Hook：誰呼叫誰

claude-codeagentskillhookmcp

skill 能不能叫另一個 skill？hook 能不能開 subagent？Claude Code 自己能設定的有 skill、agent、tool、hook 四種，我把它們兩兩配成十六種，每種都跑過一次。

model（API 那頭的語言模型）跟 engine（本機的 claude binary）會發出呼叫，tool 不會。

下面常說的「欄位」，指的是定義檔開頭那塊設定（frontmatter），或 settings.json 裡的設定。

如果欄位裡寫死了要叫誰，engine 就一定會照做。比如 skill 寫了 context: fork，每次被叫起來，engine 都會開一個 subagent 去跑它。

如果沒有欄位可以寫，像 skill 要叫另一個 skill，那就只能在內文用文字請 model 去叫。model 可以不理，所以這種串接不保證會發生。

  • allowed-tools 不是白名單。 skill 寫了 allowed-tools: Read，載入之後內文叫 Bash，Bash 還是照跑。它只決定哪些 tool 跑之前不用問使用者。如果要禁止 Bash，得寫在 disallowed-tools。
  • skill 跑完之後，它的 hooks: 還會留著。 只要這次啟動的 claude 還沒結束，之後每一次呼叫 tool 都會經過它。所以如果在 skill 裡寫一條拒絕 Bash 的 hook，等 skill 結束了，Bash 也還是會被拒。
  • hook 的事件名拼錯，不會報錯。 比如 PreToolUse 多打一個 e 變成 PreToolUsee，hook 就不會跑，正常輸出也沒有任何提示，只有 --debug 裡會印一行錯誤訊息。

環境：

  • CLI 2.1.302（mcp_tool、prompt 兩種 hook action 是在 2.1.257 測的）
  • Agent SDK 0.3.257
  • 實驗都用 claude -p 跑：給一句 prompt、印出結果就結束，不開互動介面

model 跟 engine

在 Claude Code 裡打一句「幫我看一下 git 的狀態」，終端機最後會印出 git status 的結果。

這句話先送到 model，也就是 Opus、Fable 這類跑在 API 那頭的語言模型。它自己沒辦法執行指令，能做的只有在回覆裡寫一段「我要呼叫 Bash，參數是 git status」。這段叫 tool_use，長這樣：

到這一步 git status 還沒有跑，這段只是 model 回傳的文字。

接著輪到 engine，也就是本機那支 claude binary。它收到這段 tool_use，才真的把 git status 交給 shell 執行，再把輸出包成一段 tool_result 送回給 model。整段來回是這樣：

使用者：幫我看一下 git 的狀態
→ engine 把這句話跟工具清單一起送給 model
→ model 回一段 tool_use：name 是 Bash，command 是 git status
→ engine 把 git status 交給 shell 執行，輸出包成 tool_result 送回 model
→ model 讀完輸出，寫一段回覆給使用者

engine 在執行 tool 之前跟之後，還會去看 settings.json 有沒有設定 hook 要跑。

有時候 engine 會另外開一段對話給 model，不帶主線的對話紀錄，讓它專心做一件事，這段就叫 subagent。主線跟每個 subagent 各有一份自己的工具清單。

四個元件

skill 跟 agent 是磁碟上的 .md 檔，hook 寫在 settings.json 或 frontmatter，tool 沒有檔案。

tool

tool 是 model 能呼叫的函式，一個名字加一份參數 schema。上面那段 tool_use 裡，Bash 是 tool 的名字，git status 是傳給它的參數。所以工具清單上有 Bash，沒有 git status。

一個東西要能被呼叫，得先登記進這次對話的工具清單。沒登記的 tool，model 看不到也沒辦法呼叫。

內建 tool 的名字是一個詞，像 Read、Write、Edit、Bash。外接的 MCP（Model Context Protocol）server 也能提供 tool，名字是 mcp__<server>__<tool>，例如 GitHub MCP server 的 mcp__github__search_repositories。

寫了 skills，subagent 就能用 skill 嗎？

不能。寫 skills: [inner]，engine 會在開場把 inner 的內文貼進 subagent 的對話，但工具清單裡不會多出 Skill：

系統提示：You are a test agent. ...
inner 的 SKILL.md 全文     ← engine 貼進來
工具清單：Read             ← 沒有 Skill

也就是說，subagent 讀得到 inner 要它做什麼，手上卻沒有 Skill 這個 tool 可以去呼叫 inner。實測時它回報自己只有 Read，卻講得出 inner 要它做什麼。

要讓 subagent 能呼叫 skill，得把 Skill 寫進 tools，或整行不寫。偏偏 SDK 的型別檔 sdk.d.ts 把 tools: [..., Skill] 標成 deprecated，叫你改寫 skills 而不是宣告在 tools 欄位裡；照字面上解讀的話，subagent 就不能呼叫 skill 了。我覺得這裡蠻誤導的就是。

hook

hook 是 engine 在固定時機自動執行的規則，寫在 settings.json。例如每次 model 要呼叫 Write 或 Edit，engine 先跑一支檢查 script：

PreToolUse 是事件，在 tool 執行之前觸發，可以否決這個 tool 呼叫；官方文件一共列了 33 種事件。matcher 比對 tool 名字。內層的 hooks 是命中之後要跑的項目，下面叫它 action。

action 由 engine 執行，主線的 model 不參與。 type 有五種：

type寫法engine 做什麼
command{"type": "command", "command": "bash check.sh"}開一個 process，hook 的輸入從 stdin 進去
prompt{"type": "prompt", "prompt": "Is this safe? $ARGUMENTS"}另外叫一次小 model 判斷
agent{"type": "agent", "prompt": "... $ARGUMENTS"}開一個 subagent 判斷，不指定 model 就用 Haiku
mcp_tool{"type": "mcp_tool", "server": "marker", "tool": "record"}直接對那台 MCP server 發 tools/call
http沒測把 hook 的輸入 POST 到一個 URL

$ARGUMENTS 會換成 hook 的輸入。五種裡面只有 mcp_tool 真的去呼叫一個 tool（marker 是我自己架的測試用 MCP server），其他四種在 log 裡都不會出現 tool_use。

matcher 只有字母、數字、_、-、空格、,、| 時是完全比對，出現其他字元就當成 regex：

matcher比對方式命中哪些 tool
Bash完全比對只有 Bash
Write|Edit完全比對Write、Edit
Write, Edit完全比對Write、Edit
mcp__jira完全比對沒有
mcp__jira__.*regexjira 這台 server 的所有 tool
留空或 *全部所有 tool

regex 寫壞掉的話，例如 Bash( 少一個右括號，engine 不會停，只印一行 Invalid regex pattern in hook matcher，然後當作沒命中。開 subagent 就是呼叫 Agent，所以想在每次開 subagent 前做事，matcher 填 Agent 就好。

十六種組合

下表每一列是一種「誰呼叫誰」。中間那欄寫實際發出呼叫的是誰，箭頭後面是讓它成立的欄位。agent 那幾列指的是 .claude/agents/<name>.md 開出來的 subagent。

發出呼叫的分四類：

  • model（4 列）：model 寫出 tool_use，呼叫才發生。比如 subagent 的 tools: 裡有 Agent，model 手上才有 Agent 可以用，但叫不叫由 model 決定。「skill 呼叫 tool」那列也算 model，因為 Bash 是 model 照 skill 內文發出去的；allowed-tools: Read 沒有攔住它
  • engine（5 列）：欄位直接寫了要叫什麼，engine 照著做，model 沒參與。比如 skill 寫了 context: fork，engine 就開一個 subagent 跑它；hook 寫了 mcp_tool action，engine 就自己去呼叫那個 MCP tool。hooks: 出現在「subagent 呼叫 hook」跟「skill 呼叫 hook」兩列，所以四個欄位對到五列
  • 間接（3 列）：沒有欄位，只能把要求寫成文字放進對話，看 model 理不理
  • 不成立（4 列）：tool 沒有自己的設定檔，沒地方寫要叫誰

tool 能不能主動呼叫別的東西？

tool 呼叫 subagent、tool 呼叫 skill、tool 呼叫 tool，這三列都不成立。tool 被呼叫的時候只照參數做一件事，不會再去呼叫別的東西。

Agent 也一樣。它被呼叫之後開出來的 subagent 會去叫 tool、skill、下一層 subagent，這些呼叫都由 subagent 裡的 model 發出，Agent 只負責把 subagent 開起來。

自己寫的 MCP server 收到 tools/call 之後，可以在程式裡另外開一個 claude process，讓它開 subagent、跑 skill。但那是另一個 session，不算這個 session 裡的 tool 呼叫了誰。

tool 呼叫 hook 也不成立。hook 確實跑了，但它跑在 Bash 開始之前，由 engine 叫起來，Bash 從頭到尾沒參與：

model 寫出 tool_use，name=Bash，command=echo MAIN
→ engine 查 settings.json 的 hook 設定
→ matcher 命中，engine 執行 action，等它執行完
→ 回 deny  → 到此為止，shell 從頭到尾沒收到東西
→ 沒 deny  → engine 才把 echo MAIN 交給 shell

PostToolUse 也一樣，Bash 跑完之後，是 engine 去執行 hook。

hook 能不能觸發另一條 hook？

五種 action 沒有一種能填另一條 hook，所以設定檔裡沒地方寫「然後去觸發那條 hook」。

但 hook 觸發的條件是「有人呼叫 tool」。要是 hook 自己開出來的 subagent 也去呼叫 tool，會不會再觸發一次？

實驗的設定是一條 PreToolUse 規則，matcher 是 Bash，掛兩個 action：

  • command：把要跑的指令記進 ran.txt，用來數這條規則被觸發幾次
  • agent：開一個 subagent，要它自己去跑 echo FROMHOOKAGENT

寫成設定是這樣：

command 從 stdin 收到 hook 的輸入，用 jq 取出 tool_input.command，也就是這次要跑的那行指令，再接到 ran.txt 後面。

主線只叫一次 Bash，跑 echo MAIN。跑完 ran.txt 有兩行：

PreToolUse | echo MAIN
PreToolUse | echo FROMHOOKAGENT

第一行是主線那次觸發的。第二行是 hook 開出來的 subagent 自己呼叫 Bash 的時候，engine 查了同一份 settings.json，matcher: "Bash" 第二次命中。

對照組只改一個地方：把 agent 的 prompt 換成「回一個 OK 就好，不用跑任何指令」，ran.txt 就只剩一行。

兩組只差在 model 有沒有去呼叫 tool。所以 hook 要再觸發一次 hook，只能靠 hook 開出來的 subagent 自己去呼叫 tool。

那為什麼停在兩行，沒有一直觸發下去？

因為第二次命中時，engine 只跑了 command，沒有再跑 agent。--debug-file 的紀錄裡，Processing agent hook 只出現一次。hook 開出來的 subagent 呼叫 Bash 的時候，agent_id 是 hook-agent-…，這時 command 照常觸發，agent 就不再觸發了。同樣的實驗跑了兩次，結果一樣，官方文件沒有寫這件事。

engine 自己發的呼叫則不會觸發 hook。mcp_tool action 是 engine 直接呼叫 MCP server，server 收得到，但這個 tools/call 不會回頭觸發 PreToolUse。

為什麼回了 Execute skill:，skill 卻沒跑？

frontmatter 寫了 allowed-tools、disallowed-tools 或 hooks，model 呼叫 Skill 時，engine 會先要使用者核准。這篇的實驗都跑在 -p 底下，沒有人可以按同意，engine 就直接拒絕。五份 skill 各多一種欄位，在 -p 底下各叫一次：

frontmatter 多了tool_result 回什麼
（沒有）Launching skill: inner
context: forkSkill "forktest" completed (forked execution).
allowed-tools: ReadExecute skill: tooltest
disallowed-tools: BashExecute skill: dtest
hooks: PreToolUse …Execute skill: hooktest

Execute skill: <name> 是拒絕，SKILL.md 的內文沒有載入。

同一份 tooltest 拿到別的模式跑，就看得出這一步是在等核准：

  • manual mode（每次都問使用者）：跳出對話框「Use skill "tooltest"?」
  • auto mode（由分類器自動判斷）：直接放行
  • -p：沒有人可以回答，直接拒絕

所以下面三個實驗都加了 --dangerously-skip-permissions（所有權限一律放行），不加的話內文不會載入。
