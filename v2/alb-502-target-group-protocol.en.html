Why my load balancer returned 502 (the task was fine)

2025/03/23
awsecsload-balancingtarget-grouphttps

I had a Go server running on AWS ECS, and I wanted to put it behind a domain name with HTTPS. Getting the whole thing deployed, from Docker to ECR to task definitions to the load balancer, is its own story, and I wrote that part up in from docker push to HTTPS. This post is about one wall I hit near the end: a 502 error that made no sense.

For HTTPS, I put a load balancer (an ALB) in front of the service. Between the load balancer and my service sits a target group. The target group is how the load balancer knows where to send traffic. It holds a list of registered targets, here my running tasks.

My Go app was listening on port 80, plain HTTP.

When I configured the load balancer, I chose HTTPS on port 443. That is correct: users should reach me over HTTPS.

Then I created the target group, and I set it to HTTPS:443 as well, because that felt consistent. That was the mistake.

The part that made no sense

Here is what I saw:

  • The task's public IP worked. I opened it directly and the Go server responded.
  • The target group was pointing at the correct private IP of my task.
  • But every request through the load balancer returned 502 Bad Gateway.

Each piece looked right, and it still failed. That is the worst kind of bug.

The fix

The target group's protocol has to match what your service speaks, not what the load balancer speaks.

My service speaks plain HTTP on port 80. So the target group must be HTTP:80, even though the load balancer is HTTPS:443.

wrong:  user → LB (HTTPS 443) → target group (HTTPS 443) → task (HTTP 80)
right:  user → LB (HTTPS 443) → target group (HTTP 80)   → task (HTTP 80)

I changed the target group to HTTP:80, and the 502 was gone.

Why it happens

The thing I had wrong: HTTPS stops at the load balancer.

The load balancer terminates TLS. It receives the encrypted request from the user, decrypts it, and then makes a separate, fresh request to the task, using the protocol set in the target group. That second request travels inside the VPC, a private network.

So when the target group was HTTPS:443, the load balancer tried to start a TLS handshake with my Go app on port 80. The 443 was only a default: ECS's load balancer config ties each task to its container port, here 80. But my Go app only speaks plain HTTP there. No certificate, no TLS on its side. The handshake failed, the load balancer got nothing usable back, and it reported 502 Bad Gateway to the user. AWS's ALB troubleshooting page lists an SSL handshake error with the target as one cause of 502.

My wrong picture was "the whole path is HTTPS." It is not. HTTPS covers only the first hop, from the user to the load balancer. The second hop, from the load balancer to the task, uses whatever the target group says. For most apps, that is plain HTTP.

So what is a target group, really

A target group is not a server or a machine. It is a logical pointer. It tells the load balancer two things: where the tasks are, and how to reach them, meaning the protocol and the port. Set that protocol wrong, and the load balancer ends up speaking a language your service does not understand.

What if you want it encrypted all the way?

The fix above is the default: TLS ends at the ALB, and the LB-to-task hop runs plain HTTP. That hop is inside your VPC, so plain HTTP there is fine for most apps.

If a compliance rule wants that hop encrypted too, two ways to go further:

  • Re-encryption (target group on HTTPS): your Go server listens on TLS with its own certificate (self-signed is fine, the ALB doesn't validate it). The ALB still decrypts to route the request, then re-encrypts to the server. You keep the ALB's L7 routing; the cost is a certificate on the task and two handshakes.
  • NLB passthrough (L4 TCP): swap the ALB for a Network Load Balancer. With a TCP listener it forwards bytes without decrypting, so your Go server terminates TLS itself. One TLS session the balancer never touches; the cost is losing L7 routing (no path or header rules).

Where the certificate goes in each setup

A certificate is really two files, kept on whichever end of a TLS connection acts as the server:

  • certificate (say fullchain.pem): public. It holds the domain name (say api.example.com), an expiry date, and the signature of the CA that issued it (Let's Encrypt, ACM and the like).
  • private key (say privkey.pem): stays on the server only, and proves the certificate belongs to it.

When a browser connects, the server hands over the certificate, and the browser checks that a trusted CA signed it, that the domain matches, and that it hasn't expired. If any check fails, the browser shows a "connection not secure" warning.

The certificate goes on the end that terminates TLS. In the three setups below, that is the ALB, the ALB and the task, and the task:

Re-encryption: a self-signed certificate on the task is enough

Re-encryption has two TLS hops, so it has two certificates:

  • Browser to ALB: the ALB presents the ACM certificate on its listener, same as the default setup. This is the only one the browser checks.
  • ALB to task: the task is the server on this hop, so it needs its own certificate.

Only the ALB reads the second one, and the ALB target group docs say the ALB doesn't validate target certificates, so self-signed or expired ones work. The docs' reason: the ALB and its targets are in a VPC, where AWS authenticates traffic at the packet level, so an invalid certificate still doesn't open the door to man-in-the-middle attacks.

NLB passthrough: the task needs a real certificate

With passthrough, the browser does TLS directly with the task and checks the certificate the task presents, so self-signed won't do. A real certificate can come from two places:

  • Let's Encrypt: free. Go's official golang.org/x/crypto/acme/autocert requests and renews certificates automatically. It isn't in the standard library, so go get it: With several tasks behind the NLB, DirCache keeps a separate copy per task, so each task requests its own. To share one certificate, point DirCache at an EFS directory every task mounts, or implement the autocert.Cache interface (Get, Put, Delete) and store certificates in S3.
  • ACM exportable public certificate: a regular ACM certificate can only be attached to AWS services such as an ALB or CloudFront, and its private key can't be taken out. In June 2025 AWS launched an exportable version: mark it exportable when you request it, then download the certificate and private key and put them on the task. Per the ACM docs:
    • it is valid for 198 days, and ACM renews it 45 days before it expires;
    • after renewal you deploy the new certificate to the task yourself; ACM only sends a notification;
    • it costs extra; see the ACM pricing page for the amount.
