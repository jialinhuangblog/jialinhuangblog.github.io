assumeRole 跟 trust policy：為什麼只有 IAM user 不夠

2025/11/05

IAM（Identity and Access Management）user 身上掛 policy，policy 寫明能對哪些資源做哪些動作。到這裡都很單純。

接著出現了 assumeRole 跟 trust policy。文件一開始就教怎麼設定，卻沒先講為什麼需要它們。

role 是 IAM 裡的一種身分，有自己的權限，但沒有密碼或永久 key。sts:AssumeRole 是 STS（Security Token Service）的一個 API action。service 或 user 呼叫它，換到某個 role 的臨時憑證。Trust policy 是掛在那個 role 上的 policy，規定誰可以對它呼叫 sts:AssumeRole。

為什麼不直接用 IAM user

IAM user 拿的是永久憑證，一組 access key 加 secret key。除非有人手動撤銷，不然會一直有效。

這在三種情況下會出問題：

  • key 不小心被 commit 進 git。在有人發現之前，它都還能用。
  • 另一個 AWS 帳號的合作團隊需要存取權限。你就得替別人管一個永久身分。
  • AWS 的 service 需要權限，例如 ECS（Elastic Container Service，用來跑 container）或 Lambda。service 不會登入，如果要給它永久 key，只能貼進它的設定裡，那就跟第一種一樣可能外洩。

這三種情況要的都是有期限、只涵蓋特定資源的權限。

assumeRole 給的臨時憑證時間到了自己就失效，不用事後清理。

沒有 assumeRole 的話

如果用 Fargate（機器由 AWS 管，不用自己開 server），task 沒有 role 就拿不到任何 AWS 憑證。它發給 S3 的請求沒有簽章，會被當成匿名請求，bucket 直接拒絕。

在 bucket policy（直接掛在 S3 bucket 上的 policy）裡把權限開給 ecs.amazonaws.com，task 一樣讀不到 bucket，因為 task 送出的請求不是用這個身分簽的。

ecs.amazonaws.com 跟 ecs-tasks.amazonaws.com 只差幾個字，卻是兩個不同的身分，寫在不同 role 的 trust policy 裡：

  • ecs-tasks.amazonaws.com 寫在 task role（這裡是 s3-reader-role）的 trust policy 裡。ECS 用這個身分替 task 拿 s3-reader-role 的憑證，交給 task 裡的程式碼。
  • ecs.amazonaws.com 寫在 AWSServiceRoleForECS 的 trust policy 裡。這個 role 是第一次建 ECS cluster 或 service 時 AWS 自動建的。ECS 文件說 ECS 用它管理 cluster，例如替 task 建 ENI（elastic network interface）、把 task 註冊到 load balancer。

兩個身分都只有 ECS 在用，task 裡的程式碼一個也沒用到。程式碼送請求給 S3 時，簽名用的是 ECS 交給它的 s3-reader-role 憑證。所以 S3 看到的身分是 s3-reader-role，不是 bucket policy 裡寫的 ecs.amazonaws.com，這條 policy 就不會套用到 task 身上。

想改成在 service principal 裡指定某一個 task，也沒辦法。AWS 的 Principal 文件把 service principal 定義成「an identifier for a service」，格式是 service-name.amazonaws.com，只到 service 這一層，沒有欄位可以填 task。

填了之後，只要 task definition 掛的是 s3-reader-role，它跑出來的 task 都符合這個 Principal，都讀得到 bucket。要讓不同的 task 有不同的權限，就讓它們的 task definition 各掛不同的 role。

完全不用 role 的話，剩下的辦法就是 IAM user：每個要讀 S3 的 service 各建一個 user、各產一組 access key，再貼進 task 的環境變數。十個 service 要讀 S3，就有十把永久 key 存在十份設定裡，其中任何一把外洩了，在有人撤銷之前都還能用。

用 assumeRole 的話，哪裡都不用存永久的東西。權限掛在 role 上，ECS 每次替 task 拿新的憑證。新的 service 加進 trust policy，就拿到一樣的 S3 權限。同一個帳號裡，bucket policy 完全不用動，role 的 permission policy 就夠了。

AWS service 不需要這一步，人（或人寫的 script）才需要，因為對方帳號得先允許這個 user 去 assume 這個 role。

兩邊都要允許。 role 的 trust policy 要列出對方帳號，user 自己的 policy 也要允許對這個 role 呼叫 sts:AssumeRole。只要有一邊沒允許，就是 access denied。

如果是同一個帳號，規則寬一點。trust policy 直接寫了 user 的 ARN（Amazon Resource Name，AWS 資源的完整 ID），那個 user 自己就不用掛任何 policy；trust policy 寫的是整個帳號（:root），user 還是要有第三步那份 policy。

跑起來的流程跟前面一樣：user 呼叫 sts:AssumeRole，STS 兩邊都檢查過，回傳臨時憑證（預設一小時）。

怎麼記

帶永久 key 的 IAM user 像家裡的鑰匙，換鎖之前永遠能開。

assumeRole 像飯店的房卡，只開一間房、只用一晚，退房就失效。

Trust policy = 飯店的住客名單（誰可以入住） User policy = 訂房紀錄（證明這位客人有資格來要房間） 臨時憑證 = 房卡（有期限，時間到就不能用）
