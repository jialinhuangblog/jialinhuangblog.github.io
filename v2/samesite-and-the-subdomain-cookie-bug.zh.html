為什麼 localhost 設的 cookie 不會送到 thembase.localhost

2024/09/19
networkhttpcookiesamesitesecurity

在 localhost:3000 登入，server 設了一個 session cookie。接著打開 thembase.localhost:3000，同一台機器、同一個瀏覽器、同一個 port，cookie 卻不見了，server 說你沒登入。

第一個懷疑的通常是 SameSite，可是把它改成 Lax、Strict、None，結果都一樣。那 cookie 到底是怎麼不見的呢？

瀏覽器怎麼決定要不要帶 cookie

整篇用同一個場景：一棟辦公大樓，裡面有很多家公司。

大樓瀏覽器
某個部門的櫃台host，例如 www.example.com
擁有好幾個櫃台的公司site，例如 example.com
櫃台發給你的門禁卡cookie
大樓的名冊，列出哪些名字是大樓本身、不是公司Public Suffix List
印在卡上的規則：別家公司帶你過來的時候，要不要出示這張卡SameSite

瀏覽器替你保管這些卡。你每次走到一個櫃台，它就從口袋裡挑出這個櫃台認得的卡出示。下面一個一個看，它是怎麼挑的。

host

host 是網址裡 :// 後面、port 前面的名字。

  • http://localhost:3000 的 host 是 localhost。
  • http://thembase.localhost:3000 的 host 是 thembase.localhost。

port 一樣、機器一樣都沒有用，對瀏覽器來說，這是兩個不同的 host，也就是大樓裡兩個不同的櫃台。

cookie 會送給哪些 host

server 用 Set-Cookie 設 cookie 的時候，瀏覽器會一起記下這個 cookie 屬於哪些 host。之後每發一個請求，只帶上屬於那個 host 的 cookie。

假設 myapp.test 的 server 回了下面兩種 header，瀏覽器接著對兩個 host 發請求：

myapp.test 回的 header送到 myapp.test送到 sub.myapp.test
Set-Cookie: id=1帶不帶
Set-Cookie: id=1; Domain=myapp.test帶帶

沒寫 Domain 的 cookie 叫 host-only，它只屬於設它的 host，subdomain 也收不到。換成大樓的說法，櫃台發的卡只能在這個櫃台用。加了 Domain=myapp.test，這張卡就變成整家公司的櫃台都能用。

Domain 不能寫太大：Public Suffix List

Domain 只能寫 host 本身或它上層的名字，所以 sub.myapp.test 可以寫 Domain=myapp.test。可是如果上層的名字是大家共用的呢？

youraccount.github.io 跟 myaccount.github.io 是兩個不同人的網站。如果 youraccount.github.io 可以設一個 Domain=github.io 的 cookie，瀏覽器就會把它送給每一個 *.github.io，連我的網站也收得到。

Public Suffix List（PSL）就是用來防這件事的名冊。它列出大家都能在底下註冊名字的網域，像 com、co.uk、github.io、vercel.app，這些叫 public suffix，也就是大樓本身，不是一家公司。RFC 6265bis §5.7 第 9 步規定瀏覽器碰到 Domain 是 public suffix 的時候：

  • 跟 host 一模一樣的話，忽略 Domain，cookie 變成 host-only。
  • 跟 host 不一樣的話，整個 cookie 丟掉。

所以 youraccount.github.io 設的 Domain=github.io 會被丟掉，誰都不能發一張整棟大樓通用的卡。

瀏覽器拿 host 的結尾去名冊上查，查到的部分叫 eTLD（effective top-level domain）。以 www.example.com 來說：

  • com：名冊上有，所以是 eTLD，大樓本身
  • example.com：eTLD 往左多接一個名字 example，叫 eTLD+1。這就是 site，也就是大樓裡的那家公司
  • www.example.com：完整的 host，那家公司的某一個櫃台

名冊上查不到的話，瀏覽器就把用點隔開的最右邊那個名字當成 eTLD。所以 eTLD 不一定在名冊上，shop.unknowntld 的 eTLD 就是名冊上沒有的 unknowntld。

網域名冊上查到eTLDeTLD+1（site）
www.example.comcomcomexample.com
blog.example.co.ukco.ukco.ukexample.co.uk

SameSite：別的網站發起的請求要不要帶

host、Domain 跟 PSL 一起決定 cookie 屬於哪些 host。假設 cookie 已經屬於請求要去的那個 host，可是這個請求是從別的 site 的頁面發起的，這時瀏覽器會再讀 cookie 上的 SameSite。比如 server 設 cookie 時寫了 SameSite=Strict，這個請求就不會帶它。

所以瀏覽器要先判斷發起請求的頁面跟請求要去的網址是不是同站。同站跟同源（same origin）不一樣：

同站（Same Site）同源（Same Origin）
誰在用SameSite cookie 屬性、Sec-Fetch-Site headerSame-Origin Policy（storage、fetch、postMessage）
比較什麼eTLD+1，Chrome 91 起再加上 schemescheme、host、port 三個都要一樣
www.example.com 對 blog.example.com同站不同源
http://x.com 對 https://x.com舊定義算同站，Chrome 91 起算跨站不同源
example.com:80 對 example.com:8080同站不同源

用大樓來講，同源是同一個櫃台、從同一個門進來；同站是同一家公司。

回到 localhost：cookie 為什麼帶不過去

當時設的 cookie 長這樣：

這裡沒有 Domain，所以它是 host-only，只屬於 localhost。thembase.localhost 是另一個 host，瀏覽器對它發請求時當然不會帶。

那加上 Domain=localhost 呢？

也不行。localhost 是 RFC 6761 §6.3 保留的名字，不在 PSL 上。它沒有點，最右邊的名字就是 localhost 本身，所以 eTLD 是 localhost。eTLD+1 要在 eTLD 左邊多接一個名字，localhost 左邊沒有名字可接，因此沒有 eTLD+1：

www.example.com      eTLD = com          eTLD+1 = example.com
shop.unknowntld      eTLD = unknowntld   eTLD+1 = shop.unknowntld
thembase.localhost   eTLD = localhost    eTLD+1 = thembase.localhost
localhost            eTLD = localhost    eTLD+1 = （沒有）

只要 host 沒有 eTLD+1，Domain 就只能寫跟 host 一樣的值，cookie 也只能是 host-only。IP 位址跟 co.uk 本身也沒有 eTLD+1，所以也走這條規則。兩個瀏覽器的程式碼裡，都沒有專門判斷 localhost 的規則：

  • Chrome 找不到 localhost 的 eTLD+1（net/cookies/cookie_util.cc）。
  • Firefox 要 localhost 左邊再接一個名字才有 eTLD+1，例如 thembase.localhost。單獨的 localhost 會回傳 NS_ERROR_INSUFFICIENT_DOMAIN_LEVELS，cookie 的程式碰到這個錯誤，就只接受跟 host 一模一樣的 Domain（netwerk/cookie/CookieCommons.cpp）。

所以 Domain=localhost 會被忽略，cookie 還是 host-only。換成大樓的說法，localhost 是大樓的大廳，大廳有櫃台，可是它不是一家公司；thembase.localhost 才是大樓裡的一家公司。

Domain=localhost 跟 Domain=.localhost 不會報錯。瀏覽器留下 cookie、忽略 Domain，所以在 localhost 上一切正常，換到別的 host 才發現 cookie 不見了。

為什麼改 SameSite 沒用

SameSite 只決定已經屬於這個 host 的 cookie 要不要帶。這個 cookie 從一開始就不屬於 thembase.localhost，SameSite 設成什麼都改變不了。實測時 Lax、Strict、None; Secure 跟不寫，localhost 的 cookie 都沒有送到 thembase.localhost。

不過 localhost 跟 thembase.localhost 確實是兩個不同的站。從其中一個點連結到另一個，Chrome 跟 Firefox 送出的都是 Sec-Fetch-Site: cross-site。在 Chrome 裡，從 thembase.localhost 對 localhost 發 fetch()，也只會帶上 SameSite=None 的 cookie。所以 SameSite 在它們之間是有作用的，只是 cookie 不見不是它造成的。

修好 localhost 的開發環境

單獨一個 localhost 是大廳，沒辦法發整家公司通用的卡。換成一個有 eTLD+1 的名字就可以，例如 myapp.test，下面兩種都行。

1. 用 /etc/hosts 設 myapp.test。 RFC 6761 保留 .test 就是為了這種用途，它也不像 .local 會跟 macOS 的 mDNS 撞名。把名字指到 loopback：

# /etc/hosts
127.0.0.1   myapp.test
127.0.0.1   sub.myapp.test

或是一行加進去：

開發時用 http://myapp.test:3000，cookie 加上 Domain=myapp.test，兩個 host 就都收得到。myapp.test 的行為跟正式環境的 myapp.com 一樣。

要留意的是，走純 HTTP 的 myapp.test 不是 secure context，帶 Secure 的 cookie 在這裡會被丟掉。在 http://myapp.test 設的 Secure、Secure; SameSite=Lax、SameSite=None; Secure 三種 cookie，Chrome 156 跟 Firefox 155 都丟了；同樣的 cookie 改在 https://myapp.test 設，兩邊都收下。如果正式環境的 cookie 有 Secure，開發用的 server 就要用本機憑證跑 HTTPS。

2. 用 myapp.localhost 跟 sub.myapp.localhost，不必改 /etc/hosts。 Chrome 跟 Firefox 都會自己把 *.localhost 解析到 loopback。myapp.localhost 是大樓裡的一家公司，所以在它上面設 cookie、加上 Domain=myapp.localhost，sub.myapp.localhost 就收得到。上面表格的 thembase.localhost 就是同樣的結構，在 Chrome 156、Firefox 151 跟 155 都送到了 a.thembase.localhost。Safari 沒有測。

另外有兩種做法看起來像解法，其實沒用：

  • Domain=.localhost 或 Domain=localhost。 瀏覽器會忽略這個屬性，subdomain 還是收不到。
  • SameSite=None; Secure。 SameSite 不會讓 cookie 屬於更多 host。

SameSite 的細節

三個值

Set-Cookie: id=abc; SameSite=Strict
Set-Cookie: id=abc; SameSite=Lax
Set-Cookie: id=abc; SameSite=None; Secure
值跨站的 subresource 請求（<img>、<iframe>、fetch）跨站的 top-level navigation
Strict不送不送。 從別的網站點連結到你的網站，第一個請求也不帶 cookie
Lax不送GET 會送（例如點連結）。跨站的 POST 表單不送
None送，但 Firefox 會照 top-level site 分開存（見下方）送。必須加 Secure

top-level navigation 會改變網址列上的網址，例如點連結、跟著 redirect、送出表單。<img src>、<iframe>、<script>、fetch()、XHR 都不會改網址列，這些是 subresource 請求。

銀行網站的 session cookie 設成 Lax 時：

  • 會送。 使用者在 email 裡點了銀行的連結。這是 top-level navigation，方法是 GET，所以打開銀行網站時還是登入狀態。
  • 不送。 攻擊者在自己的頁面放一個 <img src="https://yourbank.com/transfer?to=evil">，這是 subresource 請求，送出去時沒有 session cookie，CSRF 就失敗了。藏起來的表單用 POST 送到你的網站，雖然算 top-level navigation，可是方法不是 GET，Lax 一樣不送。

Strict 最保守，連 email 連結點進去都是登出狀態，留給管理後台或銀行的轉帳確認這種風險高的操作。

沒寫 SameSite 的時候

只有 Chrome 會把沒寫 SameSite 的 cookie 當成 Lax（Chrome 80 開始），Firefox 跟 Safari 當成 None（MDN 相容性資料）。把 Firefox 的 Total Cookie Protection 關掉（network.cookie.cookieBehavior=0）的話，Firefox 151 跟 155 會在跨站的 <img> 請求帶上沒寫 SameSite 的 cookie，Chrome 156 不會。所以 SameSite=Lax 要明寫出來。

Chrome 對沒寫的 cookie 還有一個例外：設下去之後的前兩分鐘，跨站的 top-level POST 還是會送（RFC 6265bis 叫它 Lax-allowing-unsafe）。在 Chrome 156 上，cookie 設下去 16 秒後，跨站 POST 有帶它，147 秒後就沒帶了。明寫 SameSite=Lax 的 cookie 兩次都沒帶。

Firefox 會把 None 的 cookie 分開存

廣告商靠 SameSite=None 的 cookie 認出同一個人。news.test 跟 shop.test 都放了 ads.test 的廣告，使用者逛 news.test 時，ads.test 設了一個 cookie id=42。之後使用者逛 shop.test，瀏覽器又把 id=42 送回 ads.test，ads.test 就知道這兩個網站是同一個人逛的。

Firefox 的宣傳片 It's time to come back to Firefox 找回一群早期的網路紅人一起跳舞，講的是以前的網路有多美好。廣告打的是情懷，不過 Firefox 在設定上也真的有動作：從 2022 年 6 月起，所有桌面版使用者預設都開著 Total Cookie Protection。照 Mozilla 的說明，追蹤者原本能把同一個人在好幾個網站上的行為串起來。開了這個功能之後，ads.test 就會把 news.test 上跟 shop.test 上的使用者當成兩個不相關的人（Mozilla）。

Chrome 原本也打算停用第三方 cookie，可是拖了幾年之後，Google 在 2025 年 4 月宣布維持現狀。第三方 cookie 照樣送出，使用者想關掉的話，得自己去設定裡關（Privacy Sandbox）。

Firefox 的做法是把 cookie 照「使用者當時在哪個網站上」分開放。ads.test 在 news.test 上設的 cookie，只有使用者在 news.test 上時才會送出去：

登入 cookie 是使用者逛 myapp.test 的時候拿到的，所以 Firefox 只在使用者逛 myapp.test 時才送它。如果小工具靠這個 cookie 判斷登入，嵌在 other.test 上的時候，在 Firefox 裡就會顯示未登入。

不過使用者如果是點連結過去的，Firefox 會多送一些 cookie。實測時，使用者在 localhost 的頁面點了連結，進到 thembase.localhost，接著 thembase.localhost 的頁面對 localhost 發請求。照上面的規則，使用者這時在逛 thembase.localhost，不該帶 localhost 的 cookie，可是 Firefox 155 帶了。沒寫 SameSite 跟 SameSite=None 的 cookie 都帶上了，Lax 跟 Strict 的還是沒帶，因為這個請求仍然算跨站。這個例外只在 *.localhost 上測過。

Firefox 這樣做，應該是為了「用 A 網站的帳號登入 B 網站」這種流程。使用者從 A 點連結到 B，B 的頁面要向 A 問這個人有沒有登入，如果請求沒帶 A 的 cookie，A 只會回答未登入。

http 跟 https 算不算同站：Schemeful same-site

網址列：http://myapp.test
GET https://myapp.test/api
→ Cookie: id=abc     Firefox 155（cookie 是 SameSite=Lax）
→ （沒有 Cookie）     Chrome 156

網域一樣，只有頁面是 http、請求是 https。判斷兩邊是不是同站的時候，Chrome 從 91 版開始連 scheme（http 還是 https）也一起比，所以這個請求在 Chrome 算跨站，Lax 跟 Strict 的 cookie 都不帶。Firefox 只比 eTLD+1，算同站。這個改動叫 Schemeful Same-Site。如果整個網站都走 HTTPS，就不會碰到這種情況。

為什麼 SameSite=None 一定要加 Secure

SameSite=None 的 cookie 在跨站請求也會送，送出去的次數多很多。如果沒有 Secure，它也會走純 HTTP，同一個咖啡店 Wi-Fi 上的人就能直接從網路上讀到它。所以有執行這條規則的瀏覽器，會直接拒收這種 cookie：

Set-Cookie: id=abc; SameSite=None             拒收，沒有 Secure
Set-Cookie: id=abc; SameSite=None; Secure     收下，只在 HTTPS 送出

Chrome 從 Chrome 80 開始執行，Firefox 到 Firefox 131 才跟上，Safari 沒有執行（MDN 相容性資料）。實測 Chrome 156、Firefox 151 跟 155 都拒收沒有 Secure 的 SameSite=None。

目前最佳組合

Set-Cookie: session=...; HttpOnly; Secure; SameSite=Lax; Path=/
  • HttpOnly：頁面上的 JavaScript 從 document.cookie 讀不到它，XSS payload 就沒辦法把 session ID 抄出去。不過 XSS 還是能從頁面發請求，瀏覽器照樣會幫這些請求帶上 cookie。
  • Secure：只走 HTTPS。Chrome 跟 Firefox 在 http://localhost 上也收。
  • SameSite=Lax：明寫出來，因為只有 Chrome 預設是它。
  • Path=/：整個 app。

只有 subdomain 真的需要共用 cookie 時才加 Domain。加了之後每一個 subdomain 都收得到，別的團隊、別的程式跑的 subdomain 也一樣。
