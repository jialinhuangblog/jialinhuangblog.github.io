為什麼只有瀏覽器會出現 CORS 錯誤，改從自己的 server 呼叫又為什麼不會

2025/08/02
securitycorsnextjswebcsrf

串好一個 API 呼叫，Postman 回 200，curl 也回 200，後端工程師看了 log 說「我這邊正常」。同一個呼叫放到瀏覽器裡就失敗，Chrome 的 console 印出：

Access to fetch at 'https://api.example.test:8443/none' from origin 'https://app.example.test:8443'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the
requested resource.

於是回頭去找後端：「可以把我的 origin 加進 CORS header 嗎？」後端加了。下個禮拜接新的 endpoint，同一個錯誤又出現，只好再去問一次。

為什麼只有瀏覽器會失敗呢？

只有瀏覽器會檢查 CORS

同一個 endpoint，不送任何 CORS header，用兩種方式呼叫：

呼叫的一方請求有沒有到 server有沒有拿到 body
curl有有
另一個 origin 的頁面裡的 JavaScript（Chrome 156、Firefox 159）有沒有，fetch 丟出 TypeError

兩次 server 都收到了請求，也都回應了。CORS 是瀏覽器對網頁裡的 JavaScript 執行的規則，Postman、curl、後端呼叫另一個後端，都不會執行它。所以「Postman 可以、瀏覽器不行」並不矛盾，這幾個 client 裡只有瀏覽器有這條規則。

Origin、SOP 跟 CORS

origin 由 scheme、host、port 組成，三個都一樣才算同一個 origin：

頁面請求送到同一個 origin 嗎
https://app.example.comhttps://app.example.com/api是
https://app.example.comhttps://api.example.com不是，host 不同
http://localhost:5173http://localhost:8080不是，port 不同
http://app.example.comhttps://app.example.com不是，scheme 不同

Same-Origin Policy（SOP，同源政策） 是瀏覽器的預設：頁面裡的 JavaScript 不能讀另一個 origin 的 response。這條規則不用誰去打開，本來就在。app.example.com 上的前端去讀 api.example.com，跨了 origin，所以預設是讀不到的。

CORS（Cross-Origin Resource Sharing） 是 server 替它指定的 origin 解除這個預設的方法。瀏覽器在請求裡加上 Origin header，server 用 Access-Control-Allow-Origin 回應：

這個值跟頁面的 origin 一樣，瀏覽器就把 response 交給 JavaScript；少了這個 header，瀏覽器就不交。

哪些請求會直接送到 server

simple request 會直接送出，下面三個條件都要符合（Fetch Standard、MDN）：

  1. method 是 GET、HEAD 或 POST。
  2. 程式自己設的 header 只有 Accept、Accept-Language、Content-Language、Content-Type，每個值不超過 128 bytes。（規格另外也允許簡單的 Range header。）
  3. 如果有設 Content-Type，值是 application/x-www-form-urlencoded、multipart/form-data 或 text/plain。

大致上就是 HTML 表單能送出的請求。瀏覽器自己加的 header，像 Origin、Cookie、User-Agent，不算在內。

其他的請求，瀏覽器會先送一個 OPTIONS 請求，叫 preflight，問 server 允不允許真正的請求：

頁面對一個沒有 CORS header 的 endpoint 發請求，Chrome 156 跟 Firefox 159 的結果一樣：

請求preflightserver 收到JavaScript 讀到 response
GET沒有GET沒有
POST，Content-Type: text/plain沒有POST沒有
POST，Content-Type: application/json有只有 OPTIONS沒有
帶 Authorization header 的 GET有只有 OPTIONS沒有
PUT有只有 OPTIONS沒有

simple request 照常送到 server，server 也處理完了，CORS 只決定 JavaScript 能不能讀 response。需要 preflight 的請求，如果 server 沒有同意 preflight，真正的請求就不會送出。

改從自己的 origin 呼叫

錯誤會出現，是因為瀏覽器的請求送到了另一個 origin。如果頁面呼叫的是自己 origin 上的 server，再由這個 server 去呼叫 API，瀏覽器發出的就是同源請求。SOP 不管同源請求，所以也沒有 CORS header 要找後端加。呼叫 API 的請求變成 server 對 server，不經過瀏覽器，也就不會檢查 CORS。

瀏覽器  →  https://app.example.com/api/charge     同源，沒有 preflight
server  →  https://api.payments.com/charge        server 對 server，沒有 CORS

同源的 POST 帶著 Content-Type: application/json 跟 Authorization header，在兩個瀏覽器都只送出一個請求，沒有 preflight。

開發時可以用 Vite dev server 的 proxy：

瀏覽器呼叫 dev server 這個 origin 上的 /api/charge，Vite 把它轉送到 https://api.payments.com/charge。如果沒寫 rewrite，Vite 會保留原本的路徑，請求就送到 https://api.payments.com/api/charge（Vite 7.3.7 實測）。changeOrigin: true 會把 Host header 改成 target 的 host。瀏覽器送來的 Origin header，Vite 原封不動轉過去，所以如果 API 自己會檢查 Origin，它收到的還是 http://localhost:5173。

server.proxy 屬於 dev server，所以上線之後就沒有了。正式環境要有一個真的 server 在中間。Next.js 的 App Router（13.2 起）可以用 Route Handler：

瀏覽器呼叫自己 origin 上的 /api/charge，再由自己的 server 呼叫付款 API。如果少了 Content-Type 這一行，server 上的 fetch 會把 JSON 字串當成 text/plain;charset=UTF-8 送出（Next.js 16.4.3 實測），等著收 JSON 的 API 可能會拒絕。

Server Actions（"use server"）跟 Server Components 裡的 fetch 也跑在 server 上，分別在 action 執行跟 render 的時候。在 Next.js 16.4.3 上，分別用 Route Handler、Server Action、Server Component 的三個頁面，瀏覽器都只對自己的 origin 發請求，付款 API 是 server 去呼叫的。

API key 也因此留在 server 上

Route Handler 裡 Authorization: Bearer ${process.env.PAYMENTS_KEY} 這一行是在 server 上執行的。Next.js 只會把名字以 NEXT_PUBLIC_ 開頭的環境變數放進瀏覽器的 JavaScript，PAYMENTS_KEY 只有 server 上的程式能讀取（Next.js 文件）。Route Handler、Server Action、Server Component 三個頁面都只拿 key 去呼叫付款 API，瀏覽器送出的請求跟收到的 response 裡，都沒有出現這個 key。

如果元件直接呼叫付款 API，key 就會出現在瀏覽器發出的請求裡，任何人打開 DevTools 的 Network 分頁，都能讀到明文。改經過自己的 server 之後，瀏覽器的請求裡沒有 key，key 是 server 對 server 的請求才加上去的，使用者碰不到這個請求。

就算沒有攻擊者，key 放在瀏覽器裡，也等於已經交給每一個用這個頁面的人。瀏覽器送出的每個請求都會出現在 DevTools 裡，頁面上執行的任何 script，能讀取的東西也跟頁面自己的 JavaScript 一樣多。在 client 端把 key 混淆或「加密」也沒用，因為解密的程式碼一樣會送到瀏覽器。

如果在 'use client' 元件裡讀 process.env.PAYMENTS_KEY，瀏覽器的 JavaScript 拿到的是 undefined，可是 Next.js 在 server 上 render 這個元件時，拿到的是真正的值。測試頁面把這個變數 render 出來，key 就跟著寫進了 HTML（Next.js 16.4.3，next dev）。

Server Component 把 key render 出來，key 一樣會送到瀏覽器。client 端換頁（例如點 <Link>）的時候，瀏覽器不重新載入 HTML，而是下載一份 RSC（React Server Components）payload，裡面是 Server Component render 的結果，也包含傳給 client 元件的 prop。測試用了三個 Server Component 頁面（Next.js 16.4.3，next dev）：

Server Component 怎麼用 keyHTML 裡有 keyRSC payload 裡有 key
寫進 JSX有有
當 prop 傳給一個只顯示字串長度的 'use client' 元件有有
只拿 key 呼叫付款 API，把 API 回的結果當 prop 傳給同一個 'use client' 元件沒有沒有

Route Handler、Server Action、Server Component 都可以讀 key，只是不能把它 render 出來，也不能把它當 prop 傳給 'use client' 元件。

這樣改了之後，/api/charge 是任何人都能呼叫的 endpoint，包括打開 DevTools 的使用者，所以自己的 server 要負責驗證使用者，也要替這個 route 加上 rate limit。

什麼時候不能改從自己的 origin 呼叫

上面講的都是自己去呼叫別人的 API，下面兩種情況不適用。

自己的 API 要讓其他 origin 的瀏覽器呼叫。 如果公開的 API 本來就是給別人的網頁呼叫，請求沒辦法經過自己的 server。這時要刻意設定 CORS，列出明確的 origin。請求帶 cookie 的時候，瀏覽器本來就不接受 Access-Control-Allow-Origin: *（見下面的 header 對照表）。

發請求的是攻擊者。 對 simple request 來說，CORS 只決定誰能讀 response，所以偽造的請求（CSRF）照樣會送到 server。下面三個情境寫出 CORS 能防什麼、不能防什麼。

深入：CORS 碰上攻擊者的三個情境

在 Chrome 156 跟 Firefox 159 實測。SameSite 是 cookie 的屬性，限制別的網站發起的請求能帶哪些 cookie（細節見〈為什麼 localhost 設的 cookie 不會送到 thembase.localhost〉）。測試裡銀行設了三個 cookie，SameSite 分別是沒寫、Lax、None; Secure。

情境 1：一般的 CSRF，CORS 完全沒參與。 使用者登入了 bank.com，接著打開 evil.com，這個頁面會自動送出一個表單：

表單 POST 是 simple request，沒有 preflight，直接送到 bank.com/transfer。兩個瀏覽器都帶上了 SameSite=None 跟沒寫 SameSite 的 cookie，SameSite=Lax 的 cookie 都沒帶。Chrome 會帶沒寫 SameSite 的 cookie，只是因為它剛設下去幾秒；過了兩分鐘，Chrome 就不會在跨站的 POST 帶它（細節見〈為什麼 localhost 設的 cookie 不會送到 thembase.localhost〉）。如果 session cookie 跟著送出，銀行看到的就是一個已登入的使用者要求轉帳，沒有其他防線的話就會照做。銀行的 CORS 設定在這裡完全沒作用，要防這種攻擊，得用 SameSite=Lax cookie、CSRF token 跟 Origin 檢查（見〈XSS 跟 CSRF 各要怎麼防，為什麼先處理 XSS〉）。

情境 2：用 fetch 發的 CSRF，CORS 幫了一部分。 evil.com 用 fetch 送 POST，帶 credentials: 'include'（讓跨 origin 的請求也帶上 cookie）跟 Content-Type: application/json，所以會先送 preflight。

情況Chrome 156Firefox 159（使用者直接打開 evil.com）
銀行沒送任何 CORS header只收到 OPTIONS只收到 OPTIONS
銀行的 preflight 同意任何 origin，但真正的 response 沒有 CORS headerPOST 送到了，帶著 SameSite=None 的 cookie；evil.com 的 JavaScript 讀不到結果POST 送到了，沒帶 cookie；JavaScript 讀不到結果
同樣的 JSON body 改用 Content-Type: text/plain、mode: 'no-cors' 送出沒有 preflight；POST 送到了，帶著 SameSite=None 的 cookie沒有 preflight；POST 送到了，沒帶 cookie

第一列的情況，CORS 確實攔下了請求。可是如果銀行不檢查 Content-Type 就把 body 當 JSON 解析，攻擊者只要像最後一列那樣拿掉這個 header，就回到情境 1。Firefox 的 Total Cookie Protection 會照「設 cookie 時網址列上是哪個網站」分開存 cookie。bank.com 的 cookie 是在網址列為 bank.com 的時候設的，所以使用者直接打開 evil.com 時，evil.com 發出的 fetch 拿不到這些 cookie，上表 Firefox 那欄才會都沒帶。

使用者如果是在 bank.com 的頁面點連結進到 evil.com，結果就不同了。Firefox 有一條 heuristic：使用者從 A 點連結到 B 之後，B 的頁面發給 A 的請求可以帶 A 的 cookie。實測時，從 bank.com 點連結進來的 evil.com，第二列跟最後一列的 POST 都帶上了沒寫 SameSite 跟 SameSite=None 的 cookie。點過那次連結，幾秒後使用者再直接打開 evil.com，Firefox 還是帶了這兩個 cookie。要隔多久 Firefox 才不再帶，這次沒有測。在 Firefox 的 about:config 把 privacy.restrict3rdpartystorage.heuristic.navigation 設成 false 再跑一次，點連結進來就不帶了。Chrome 156 不管使用者是直接打開還是點連結進到 evil.com，帶的 cookie 都跟上表 Chrome 那欄一樣（SameSite 跟 Total Cookie Protection 的細節見〈為什麼 localhost 設的 cookie 不會送到 thembase.localhost〉）。

情境 3：供應鏈，允許清單上的 origin 裡跑著別人的 script。 因為 trusted-site.com 是合作夥伴，所以 CORS 設定允許它，也允許它的請求帶 cookie。trusted-site.com 從 ad-scripts.com 載入一支廣告 script，這支 script 在 trusted-site.com 的 origin 裡執行。它發出的請求帶著 Origin: https://trusted-site.com，這個 origin 在允許清單上，所以瀏覽器讓它讀 response。實測時兩個瀏覽器裡，廣告 script 都讀到了 response，並把內容送到廣告的 server。Chrome 還帶上了 SameSite=None 的 cookie，Firefox 沒帶 cookie（使用者是直接打開 trusted-site.com 的）。CORS 只檢查 origin，不管是 origin 裡的哪個 script 發的請求。防線有這幾種：

  • Subresource Integrity（integrity="sha384-..."）：script 的內容被改過，瀏覽器就拒絕執行。
  • CSP：限制 script 能從哪些地方載入。
  • 允許的 origin 越少越好。
對照表：CORS 的 header（瀏覽器送的跟 server 送的）

下面這些 header 由瀏覽器自己填，不用寫在 fetch 裡。

Header內容
Origin發出請求的頁面的 scheme + host + port
Access-Control-Request-Method只在 preflight 出現。真正的請求要用的 method。
Access-Control-Request-Headers只在 preflight 出現。真正的請求會設、而且不在 simple 清單上的 header。

server 的 header 寫在 CORS middleware 裡。

Header控制什麼
Access-Control-Allow-Origin允許的 origin：一個跟 Origin 相同的 origin，或 * 代表全部。請求帶 credentials: 'include' 時，* 會失敗。
Access-Control-Allow-Methods需要 preflight 的請求，server 接受哪些 method。
Access-Control-Allow-Headers不在 simple 清單上的 header，server 接受哪些。
Access-Control-Allow-Credentials設成 true，JavaScript 才能讀帶 credentials: 'include' 的請求的 response。preflight 的 response 沒有它，真正的請求就不會送出。它不決定 cookie 送不送：實測時，帶 credentials: 'include' 的請求在 response 沒有這個 header 的情況下照樣帶了 cookie，只有讀取失敗。
Access-Control-Max-Agepreflight 的結果可以重複使用幾秒。照 URL 分開快取，query string 也算在內。沒有這個 header 時是 5 秒。Firefox 上限 86400，Chrome 上限 7200（MDN）。

跨 origin 的呼叫要帶 cookie，client 得自己開：fetch(url, { credentials: 'include' })，或舊的 xhr.withCredentials = true。

API key、讀取權限跟 CSRF，各用什麼處理

要做的事怎麼做防的是什麼
不讓 secret 進到 client呼叫經過自己的 serverAPI key 出現在瀏覽器裡
控制誰能讀自己 server 的 response預設靠 SOP，要開放就用 CORS其他 origin 的 JavaScript 讀到敏感的 response
攔下偽造的跨站請求SameSite cookie + CSRF token + Origin 檢查simple request 的一般 CSRF

如果是自己要呼叫 API，就讓呼叫經過自己的 origin。 這樣不用處理 CORS 設定，key 也留在 server 上。自己的 endpoint 真的要讓其他 origin 讀的時候，才需要設定 CORS。也不要把 CORS 當成 CSRF 的防線，因為 simple request 不管怎樣都會送到 server。

CSRF 完整的防法見〈XSS 跟 CSRF 各要怎麼防，為什麼先處理 XSS〉。
