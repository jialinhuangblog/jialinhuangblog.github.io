<p>This object follows the W3C spec <a href="https://www.w3.org/TR/navigation-timing-2/">Navigation Timing Level 2</a> (Working Draft, this revision dated 2026-09-01); the API is <a href="https://developer.mozilla.org/en-US/docs/Web/API/PerformanceNavigationTiming"><code>PerformanceNavigationTiming</code></a>. The Navigation Timing diagram redrawn in the iframe below comes from the first version, <a href="https://www.w3.org/TR/navigation-timing/">Level 1</a> (W3C Recommendation, 2012-12-17), in its <a href="https://www.w3.org/TR/navigation-timing/#processing-model">Processing Model</a> section; its API is <a href="https://developer.mozilla.org/en-US/docs/Web/API/Performance/timing"><code>performance.timing</code></a>, now marked deprecated on MDN. Most field names are the same in both. The differences are where the clock starts and a few fields Level 2 dropped, listed at the end.</p>
<p><code>domainLookupEnd − domainLookupStart</code> = 74.2 − 0.9 = 73 ms, the time DNS took. Every other stage is the same kind of subtraction between its two ends. <h2>Each stage's blocking issue</h2>
<ul>
<li><strong>unload, redirect, App cache</strong>: always 0 on this site. unload is set only when the previous page was on the same origin, <a href="https://developer.mozilla.org/en-US/docs/Web/API/PerformanceNavigationTiming/unloadEventStart">0 otherwise</a>. redirect is 0 because <a href="https://groups.google.com/a/chromium.org/g/blink-dev/c/cAS525en8XE">since Chrome 115</a> the browser upgrades <code>http://</code> to <code>https://</code> before sending the request, so the server's 301 for <code>http://</code> is never followed.</li>
<li><strong>DNS</strong>: the first lookup took 73 ms. After that the answer stays in the operating system's resolver cache, which a fresh browser profile does not clear, so only the first of five cold starts was not 0.</li>
<li><strong>TCP</strong>: a handshake needs at least one round trip, and ping from this machine to the server is 42 to 54 ms. No code removes that; only a CDN moves the endpoint closer. The 152 ms in the table is an exception: halfway through TLS on that load, Chrome swapped its certificate verifier and reopened the connection, so it measured two connections. In a Chrome netlog recorded separately (a log of the connection steps), each single handshake took 46 to 68 ms. Only starting a new Chrome for every measurement runs into this.</li>
<li><strong>TLS</strong>: a TLS 1.2 handshake takes two round trips and TLS 1.3 takes one; a connection that is not reused is also slow. <a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Connection_management_in_HTTP_1.x">HTTP/1.1 keeps connections open by default</a> and HTTP/2 and HTTP/3 multiplex one connection, so TLS usually happens once per origin.</li>
<li><strong>Request</strong>: the server handling the request. For a static file, a long TTFB usually means the CDN had no cached copy; for server rendering, the time mostly goes to the render function. <a href="/v2/spa-is-not-csr-rendering-strategies">Rendering strategy</a> mainly affects this stage.</li>
<li><strong>Response</strong>: the HTML is large, or not compressed. Compare <code>encodedBodySize</code> with <code>decodedBodySize</code> (<code>transferSize</code> includes headers, so it does not work for this). Here <code>encodedBodySize</code> is 3772 and it decodes to 14187, so compression is on.</li>
<li><strong>Parse</strong>: the same HTML takes 5 to 10 ms on reload and 198 to 424 ms on a cold start; the difference is all waiting for stylesheets. <code>&#x3C;body></code> has inline <code>&#x3C;script></code> elements, and <a href="https://html.spec.whatwg.org/multipage/scripting.html#script-processing-model">the HTML spec makes them wait for stylesheets in <code>&#x3C;head></code> that are still loading</a>, so the parser stops too. Five more cold starts with a script that also records each resource's timing put <code>domInteractive</code> 1 to 29 ms after the last stylesheet finished, every time. One of the three stylesheets is cross-site, <code>fonts.googleapis.com</code>, and it alone costs an extra DNS lookup plus a new connection, 57 to 138 ms. So a faster Parse on this site means inlining the stylesheets, preloading them, or dropping the cross-site origin.</li>
<li><strong>Deferred scripts</strong>: <code>&#x3C;script defer></code> runs after parsing and before <code>DOMContentLoaded</code>, and <a href="https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/script#defer"><code>DOMContentLoaded</code> waits for it</a>. This site loads its chunks with <code>async</code>, which does not delay <code>DOMContentLoaded</code>, so this is 0 here. If a page loads <code>&#x3C;script defer src="app.js"></code> and <code>app.js</code> takes 300 ms to run, those 300 ms show up in Deferred scripts.</li>
<li><strong>Subresources</strong>: <a href="https://developer.mozilla.org/en-US/docs/Web/API/Window/load_event"><code>load</code> waits for images, scripts and iframes</a>. MDN does not list fonts, but they count: on a test page whose only slow resource is a 2 s font, <code>load</code> came 2 s later. The article page <a href="/v2/from-setstate-to-pixels">from-setstate-to-pixels</a> embeds a cross-site iframe. Across five runs of the script that records resource timing this stage took 487 to 596 ms, nearly all of it waiting for that iframe: <code>domComplete</code> came 0.2 to 1.7 ms after the iframe finished.</li>
</ul>
<h2>Five cold starts, and one reload</h2>

<h2>Which Level 1 timestamps did Level 2 drop</h2>
<ul>
<li><strong>navigationStart</strong>: Level 2 changed clocks. Level 1's values are absolute milliseconds since 1970; Level 2 uses <code>DOMHighResTimeStamp</code> counted from the time origin, so <a href="https://www.w3.org/TR/navigation-timing-2/#dom-performancetiming-navigationstart">the start is always 0</a>. The reasons are that <a href="https://www.w3.org/TR/hr-time-3/">an absolute clock can go backwards when the system clock is adjusted and only resolves to a millisecond</a>. navigationStart became the 0 of <code>startTime</code>.</li>
<li><strong>domLoading</strong>: browsers create the Document at different moments, Chrome before the response begins, IE when it starts, Firefox after buffering some of it, so the value measured an implementation detail. <a href="https://github.com/w3c/navigation-timing/issues/13">Issue #13</a> proposed removing it in 2015 and <a href="https://www.w3.org/TR/navigation-timing-2/#obsolete-heading">the spec added a deprecation note</a>. The closest value is <code>responseEnd</code>.</li>
<li><strong>Prompt for unload</strong>: happens before <code>navigationStart</code>, since <a href="https://www.w3.org/TR/navigation-timing/#sec-navigation-timing-interface">Level 1 defines the start as the moment right after prompting to unload the previous document</a>, so neither version has a timestamp for it; the diagram draws the box only to show what precedes the start.</li>
</ul>
<p>The gap between <code>startTime</code> and <code>fetchStart</code> has no name. unload and redirect would fall in that span if they happened, and both were 0 here; a <code>redirectStart</code> of 0 means there was no redirect, not that a redirect took 0 ms.</p>

## Each stage's blocking issue

- **unload, redirect, App cache**: always 0 on this site. unload is set only when the previous page was on the same origin, [0 otherwise](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceNavigationTiming/unloadEventStart). redirect is 0 because [since Chrome 115](https://groups.google.com/a/chromium.org/g/blink-dev/c/cAS525en8XE) the browser upgrades `http://` to `https://` before sending the request, so the server's 301 for `http://` is never followed.
- **DNS**: the first lookup took 73 ms. After that the answer stays in the operating system's resolver cache, which a fresh browser profile does not clear, so only the first of five cold starts was not 0.
- **TCP**: a handshake needs at least one round trip, and ping from this machine to the server is 42 to 54 ms. No code removes that; only a CDN moves the endpoint closer. The 152 ms in the table is an exception: halfway through TLS on that load, Chrome swapped its certificate verifier and reopened the connection, so it measured two connections. In a Chrome netlog recorded separately (a log of the connection steps), each single handshake took 46 to 68 ms. Only starting a new Chrome for every measurement runs into this.
- **TLS**: a TLS 1.2 handshake takes two round trips and TLS 1.3 takes one; a connection that is not reused is also slow. [HTTP/1.1 keeps connections open by default](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Connection_management_in_HTTP_1.x) and HTTP/2 and HTTP/3 multiplex one connection, so TLS usually happens once per origin.
- **Request**: the server handling the request. For a static file, a long TTFB usually means the CDN had no cached copy; for server rendering, the time mostly goes to the render function. [Rendering strategy](/v2/spa-is-not-csr-rendering-strategies) mainly affects this stage.
- **Response**: the HTML is large, or not compressed. Compare `encodedBodySize` with `decodedBodySize` (`transferSize` includes headers, so it does not work for this). Here `encodedBodySize` is 3772 and it decodes to 14187, so compression is on.
- **Parse**: the same HTML takes 5 to 10 ms on reload and 198 to 424 ms on a cold start; the difference is all waiting for stylesheets. `<body>` has inline `<script>` elements, and [the HTML spec makes them wait for stylesheets in `<head>` that are still loading](https://html.spec.whatwg.org/multipage/scripting.html#script-processing-model), so the parser stops too. Five more cold starts with a script that also records each resource's timing put `domInteractive` 1 to 29 ms after the last stylesheet finished, every time. One of the three stylesheets is cross-site, `fonts.googleapis.com`, and it alone costs an extra DNS lookup plus a new connection, 57 to 138 ms. So a faster Parse on this site means inlining the stylesheets, preloading them, or dropping the cross-site origin.
- **Deferred scripts**: `<script defer>` runs after parsing and before `DOMContentLoaded`, and [`DOMContentLoaded` waits for it](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/script#defer). This site loads its chunks with `async`, which does not delay `DOMContentLoaded`, so this is 0 here. If a page loads `<script defer src="app.js">` and `app.js` takes 300 ms to run, those 300 ms show up in Deferred scripts.
- **Subresources**: [`load` waits for images, scripts and iframes](https://developer.mozilla.org/en-US/docs/Web/API/Window/load_event). MDN does not list fonts, but they count: on a test page whose only slow resource is a 2 s font, `load` came 2 s later. The article page [from-setstate-to-pixels](/v2/from-setstate-to-pixels) embeds a cross-site iframe. Across five runs of the script that records resource timing this stage took 487 to 596 ms, nearly all of it waiting for that iframe: `domComplete` came 0.2 to 1.7 ms after the iframe finished.

<summary>The measurement script</summary>

The reload column uses the same script plus one step: after the first `load`, send `Page.reload` and read the entry again. import { spawn } from 'node:child_process'
import { mkdtempSync } from 'node:fs'
import { tmpdir } from 'node:os'
import { join } from 'node:path'

const [url, runsArg] = process.argv.slice(2)
const sleep = ms => new Promise(r => setTimeout(r, ms))

async function once(port) {
  const profile = mkdtempSync(join(tmpdir(), 'chrome-prof-'))
  const cache = mkdtempSync(join(tmpdir(), 'chrome-cache-'))
  const chrome = spawn('/Applications/Google Chrome.app/Contents/MacOS/Google Chrome', [
    '--headless=new', `--remote-debugging-port=${port}`,
    `--user-data-dir=${profile}`, `--disk-cache-dir=${cache}`,
    '--no-first-run', 'about:blank',
  ], { stdio: 'ignore' })

  let targets
  for (let i = 0; i < 40; i++) {
    await sleep(250)
    try { targets = await (await fetch(`http://127.0.0.1:${port}/json`)).json(); break } catch {}
  }
  const ws = new WebSocket(targets.find(t => t.type === 'page').webSocketDebuggerUrl)
  await new Promise(r => ws.onopen = r)
  let id = 0
  const pending = new Map()
  ws.onmessage = e => { const m = JSON.parse(e.data); if (pending.has(m.id)) { pending.get(m.id)(m); pending.delete(m.id) } }
  const send = (method, params = {}) => new Promise(r => { pending.set(++id, r); ws.send(JSON.stringify({ id, method, params })) })

  await send('Page.enable')
  await send('Page.navigate', { url })
  let entry
  for (let i = 0; i < 120; i++) {
    await sleep(250)
    const r = await send('Runtime.evaluate', { returnByValue: true,
      expression: `JSON.stringify(performance.getEntriesByType('navigation')[0]?.toJSON() ?? null)` })
    entry = JSON.parse(r.result.result.value)
    if (entry && entry.loadEventEnd > 0) break
  }
  ws.close()
  chrome.kill()
  return entry
}

const all = []
for (let i = 0; i < Number(runsArg || 5); i++) all.push(await once(9400 + i))
console.log(JSON.stringify(all))

## Which Level 1 timestamps did Level 2 drop

- **navigationStart**: Level 2 changed clocks. Level 1's values are absolute milliseconds since 1970; Level 2 uses `DOMHighResTimeStamp` counted from the time origin, so [the start is always 0](https://www.w3.org/TR/navigation-timing-2/#dom-performancetiming-navigationstart). The reasons are that [an absolute clock can go backwards when the system clock is adjusted and only resolves to a millisecond](https://www.w3.org/TR/hr-time-3/). navigationStart became the 0 of `startTime`.
- **domLoading**: browsers create the Document at different moments, Chrome before the response begins, IE when it starts, Firefox after buffering some of it, so the value measured an implementation detail. [Issue #13](https://github.com/w3c/navigation-timing/issues/13) proposed removing it in 2015 and [the spec added a deprecation note](https://www.w3.org/TR/navigation-timing-2/#obsolete-heading). The closest value is `responseEnd`.
- **Prompt for unload**: happens before `navigationStart`, since [Level 1 defines the start as the moment right after prompting to unload the previous document](https://www.w3.org/TR/navigation-timing/#sec-navigation-timing-interface), so neither version has a timestamp for it; the diagram draws the box only to show what precedes the start.

The gap between `startTime` and `fetchStart` has no name. unload and redirect would fall in that span if they happened, and both were 0 here; a `redirectStart` of 0 means there was no redirect, not that a redirect took 0 ms.

<h2>每個階段的 blocking issue</h2>
<ul>
<li><strong>unload、redirect、App cache</strong>：這個站上一直是 0。unload 只有上一頁同源才有值，<a href="https://developer.mozilla.org/en-US/docs/Web/API/PerformanceNavigationTiming/unloadEventStart">不同源是 0</a>。redirect 是 0，因為 <a href="https://groups.google.com/a/chromium.org/g/blink-dev/c/cAS525en8XE">Chrome 115 起</a>會在送出請求之前自己把 <code>http://</code> 升成 <code>https://</code>，伺服器對 <code>http://</code> 回的 301 沒被走到。</li>
<li><strong>DNS</strong>：第一次查詢要 73 ms，之後答案留在作業系統的 resolver cache，換瀏覽器 profile 也清不掉，所以五次 cold start 只有第一次不是 0。</li>
<li><strong>TCP</strong>：握手至少要一個 round trip，這台機器到伺服器 ping 是 42 到 54 ms，程式碼省不掉，只能用 CDN 讓端點近一點。表格裡的 152 ms 是例外：那次 TLS 做到一半，Chrome 換了憑證驗證器，把連線關掉重開，所以量到的是兩條連線。另外記下的 Chrome netlog（連線過程的紀錄）裡，單次握手是 46 到 68 ms。只有每次都開一個新的 Chrome 來量，才會遇到。</li>
<li><strong>TLS</strong>：TLS 1.2 握手要兩個 round trip，1.3 只要一個；連線沒被重用也會慢。<a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Connection_management_in_HTTP_1.x">HTTP/1.1 預設會把連線留著</a>，HTTP/2 和 HTTP/3 一條連線多工，所以 TLS 通常每個 origin 只做一次。</li>
<li><strong>Request</strong>：伺服器在處理請求。靜態檔的話，TTFB 長通常是 CDN 沒有 cache；server render 的話，時間多半花在 render function。<a href="/v2/spa-is-not-csr-rendering-strategies">rendering strategy</a> 影響的主要是這一段。</li>
<li><strong>Response</strong>：HTML 太大，或沒壓縮。拿 <code>encodedBodySize</code> 跟 <code>decodedBodySize</code> 比就知道（<code>transferSize</code> 含 header，不能拿來比）。這裡 <code>encodedBodySize</code> 是 3772，解開是 14187，壓縮有開。</li>
<li><strong>Parse</strong>：同一份 HTML，reload 只要 5 到 10 ms，cold start 卻要 198 到 424 ms，差的時間都在等 stylesheet。<code>&#x3C;body></code> 裡有 inline <code>&#x3C;script></code>，<a href="https://html.spec.whatwg.org/multipage/scripting.html#script-processing-model">HTML spec 規定它要等 <code>&#x3C;head></code> 裡還沒載完的 stylesheet</a>，parser 也跟著停。另外用一支會記下每個資源載入時間的腳本再跑五次 cold start，五次的 <code>domInteractive</code> 都在最後一個 stylesheet 載完之後 1 到 29 ms 出現。三個 stylesheet 裡有一個是跨站的 <code>fonts.googleapis.com</code>，光它就要多一次 DNS 加一條新連線，57 到 138 ms。所以這個站的 Parse 要變快，得把 stylesheet inline、preload，或拿掉跨站那個來源。</li>
<li><strong>Deferred scripts</strong>：<code>&#x3C;script defer></code> 在 parse 完、<code>DOMContentLoaded</code> 之前執行，<a href="https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/script#defer"><code>DOMContentLoaded</code> 會等它</a>。這個站的 chunk 用 <code>async</code>，不會讓 <code>DOMContentLoaded</code> 延後，所以這裡是 0。要是頁面寫的是 <code>&#x3C;script defer src="app.js"></code>，而 <code>app.js</code> 執行要 300 ms，這 300 ms 就會出現在 Deferred scripts。</li>
<li><strong>Subresources</strong>：<a href="https://developer.mozilla.org/en-US/docs/Web/API/Window/load_event"><code>load</code> 要等圖片、script、iframe 到齊</a>。字型 MDN 沒列，但也算：一個只有字型慢 2 秒的測試頁，<code>load</code> 晚了 2 秒。文章頁 <a href="/v2/from-setstate-to-pixels">from-setstate-to-pixels</a> 嵌了一個跨站 iframe，用記錄 resource timing 的那支腳本跑五次，這一段是 487 到 596 ms，幾乎都在等那個 iframe：它載完之後 0.2 到 1.7 ms，<code>domComplete</code> 就到了。</li>
</ul>
<h2>五次 cold start，加一次 reload</h2>
<p>每次 cold start 都是新開的 headless Chrome 153，新 profile、新 disk cache，導航一次，台北時間下午 12 點到 3 點。reload 是同一個瀏覽器載完首頁後用 DevTools protocol 的 <code>Page.reload</code> 再載一次，entry 的 <code>type</code> 是 <code>reload</code>。文章頁是 <code>/v2/from-setstate-to-pixels</code>。</p>

<h2>Level 2 拿掉了哪些 Level 1 的時間戳</h2>
<ul>
<li><strong>navigationStart</strong>：Level 2 換了時鐘。Level 1 的值是從 1970 年起算的絕對毫秒，Level 2 改用從 time origin 起算的 <code>DOMHighResTimeStamp</code>，<a href="https://www.w3.org/TR/navigation-timing-2/#dom-performancetiming-navigationstart">起點恆為 0</a>，理由是<a href="https://www.w3.org/TR/hr-time-3/">絕對時鐘會被系統調整倒退、精度只到毫秒</a>。navigationStart 變成 <code>startTime</code> 的 0。</li>
<li><strong>domLoading</strong>：各家瀏覽器建立 Document 的時間點不同，Chrome 在 response 開始前，IE 在 response 開始時，Firefox 要先 buffer 一段，量到的是實作細節。2015 年 <a href="https://github.com/w3c/navigation-timing/issues/13">issue #13</a> 提出移除，<a href="https://www.w3.org/TR/navigation-timing-2/#obsolete-heading">spec 加了 deprecation note</a>。最接近的值是 <code>responseEnd</code>。</li>
<li><strong>Prompt for unload</strong>：發生在 <code>navigationStart</code> 之前，<a href="https://www.w3.org/TR/navigation-timing/#sec-navigation-timing-interface">Level 1 把起點定義在「問完要不要離開上一頁之後」</a>，兩版都沒有它的時間戳，圖上畫它只是標出起點前面的動作。</li>
</ul>
<p><code>startTime</code> 到 <code>fetchStart</code> 那段空檔沒有名字。unload 跟 redirect 有發生的話會落在這段，這次都是 0；<code>redirectStart</code> 是 0 表示沒有 redirect，不是 redirect 花了 0 ms。</p>
