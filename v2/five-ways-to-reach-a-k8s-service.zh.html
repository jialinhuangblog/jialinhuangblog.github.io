連到 Kubernetes service 的五種方法，平常該用哪一種

2025/09/07
kubernetesnetworkingdevops

要確認 cluster 裡某個 API 有沒有通，常見的做法是 kubectl exec 進一個 pod，再用 wget 或 curl 去打它。

pod 一重建 IP 就會換。為了讓呼叫的一方不必追著 IP 跑，Kubernetes 在一組 pod 前面放一個 service。service 有固定的 DNS 名稱跟 virtual IP；如果是 NodePort 類型，每個 node 上還會多開一個 port。所以同一個 API 有好幾個位址可以打，下面依序試：

  1. 在 node 裡連 localhost 加 node port
  2. 從 pod 連 service 的 DNS 名稱
  3. 從 pod 連 service 的 virtual IP
  4. 從 pod 連 node 的 IP 加 node port
  5. 跳過 service，直接連 pod 的 IP

環境

我用的是 Kind，它的每個 K8s node 都是一個 Docker container。pod 是一個或幾個共用同一個 IP 的 container。noah 這個 namespace（把資源分組用的名字）裡有兩個很小的 Node.js API，都跑在 pod 裡，service 分別是：

  • joke-service → type: ClusterIP
  • number-service → type: NodePort

ClusterIP 的 service 會拿到一個 virtual IP，只有在 cluster 裡面才連得到。NodePort 的 service 一樣有這種 IP，另外每個 node 還會替它開一個 30000 到 32767 之間的 port。

兩份 YAML 除了名字，只差 type 這一行。可是下面五種方法，NodePort 的 service 五種都能用，ClusterIP 的只剩三種。從 joke-service 改成 number-service，差異如下：

$ kubectl get svc -n noah
NAME             TYPE        CLUSTER-IP      PORT(S)
joke-service     ClusterIP   10.96.236.182   80/TCP
number-service   NodePort    10.96.183.131   80:30405/TCP

下面的指令有的用 wget、有的用 curl，因為 Alpine 的 pod 裡只有 wget，Kind 的 node 是 Debian，裝了 curl。

2026 年 11 月在 Kind v0.30.0（Kubernetes v1.34.0）重跑過，每種方法的結果都跟文中一樣。下面的 IP 跟 port 是原本那次的。

連 NodePort service：五種都能用

NodePort 的 service 限制最少，每一種方法都能用。

1. docker exec 進 node（只有 Kind 能這樣做）。 Kind 的 node 是 container，所以可以直接進去連 localhost：

30405 是 kubectl get svc 列出來的 node port。這樣能連，是因為在 node 裡面，NodePort 就只是一個本機的 port。真的 cluster 上沒辦法 docker exec 進 node，要改成 SSH 進去（或用 kubectl debug node/<name>），再連 127.0.0.1:30405。

不要寫 localhost，因為用 Alpine image 開的 kubectl debug pod 會把 localhost 解析成 IPv6 的 ::1，而 kube-proxy（每個 node 上把 service 的位址轉成封包規則的元件）不會在 ::1 上處理 NodePort，所以連線被拒絕。127.0.0.1 也只有在 kube-proxy 跑 iptables 模式時才能連，Kind 預設就是這個模式。照 kube-proxy 的設定文件，另外兩種模式不在 loopback 位址上處理 NodePort（IPVS 一律不處理，nftables 預設不處理），所以要改連 node 自己的 IP。這兩種模式沒有實測過。

第 2 到第 5 種方法沒有用到 Kind 特有的東西，不過也只在 Kind 上跑過。

2. Service DNS（平常該用的就是這個）。 寫 service 的名稱，讓 K8s 去解析：

有兩種情況，這個名稱會連不到：

  • 從別的 namespace 連，名稱要加上 namespace：number-service.noah，或寫完整的 number-service.noah.svc.cluster.local。只寫 number-service 的話，會拿到 bad address，因為 DNS 只會幫 pod 補上它自己的 namespace。
  • CoreDNS（cluster 裡的 DNS server，本身也是幾個 pod）停掉的時候，五種方法裡只有這一種連不到，下面幾種直接用 IP 的照樣能連。

這樣連很可靠，只是要先用 kubectl get svc 查出 IP。

組出這個網址要查兩次：先用 kubectl get nodes -o wide 查 node IP，再用 kubectl get svc 查那個隨機分配的 port。平常幾乎不會這樣連。

5. 直接連 pod IP（完全繞過 service）。 對某一個 pod 的 container port 發請求：

pod 的 IP 可以用 kubectl get pods -o wide 查，也可以從 service 的 endpoints 讀出來：

$ kubectl describe svc number-service -n noah
Endpoints: 10.244.1.18:3000,10.244.2.23:3000

這樣請求不會經過 load balancing，一定送到指定的那個 pod，所以可以單獨測某一個行為怪怪的 pod。

ClusterIP service 少了兩種

把 joke-service 設成 type: ClusterIP，需要 node port 的方法就都不能用了。五種並排比較：

#方法NodePortClusterIP
1docker exec → localhost:NodePort✅❌ 沒有 node port
2Service DNS✅✅
3直接連 ClusterIP✅✅
4NodeIP + NodePort✅❌ 沒有 node port
5直接連 pod IP✅✅

ClusterIP 留下 2、3、5，少了 1 跟 4。這兩種都要經過 node port，而 ClusterIP 的 service 沒有 node port。

平常該用哪一種

實際寫程式就用 service DNS（service-name:port）。它好讀，而且這套命名是 Kubernetes 的 DNS 規格定的，跟 Kind 無關。

pod IP、ClusterIP、node port 都可能變，service 的名稱不會變。 pod 只要被換掉，不管是因為 rollout（部署新版本）還是有人刪掉 pod，新的 pod 就會拿到新的 IP；只有同一個 pod 裡的 container 重啟，IP 才會留著。ClusterIP 跟 node port 只要 Service 物件還在就不會變。不過這份 YAML 沒寫 spec.clusterIP，也沒寫 nodePort，所以 Service 刪掉重建後，兩個都由 Kubernetes 重新分配。重跑時拿到的 ClusterIP 是 10.96.54.49、node port 是 31738，把 Service 刪掉重建之後變成 10.96.209.100 跟 30236，但用 number-service 這個名稱照樣能連。另外四種方法最後都是連到其中某個位址，所以拿來查某一層的問題很好用（是 DNS 的問題嗎？還是某一個 pod 的問題？），但不適合寫進真正要上線的程式。
