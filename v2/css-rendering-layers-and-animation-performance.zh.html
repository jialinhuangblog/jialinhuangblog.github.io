CSS 動畫為什麼用 transform 比用 width 順：layer、thread 跟渲染流程

2025/09/21
frontendbrowsercssperformance

當你要做側選單從左邊 slide 出來，有兩種畫法：讓 width 從 0 變到 240px，或是讓側選單一直維持 240px 寬，再用 transform 把它從畫面外移進來。兩種做法在畫面上看起來一模一樣，用 width 的卻可能會卡，用 transform 的就很順，為什麼差這麼多呢？

下面左邊用 width、右邊用 transform 做同一個滑動。只按「滑出側欄」，兩邊看起來一樣。按「滑出側欄，同時讓 JavaScript 跑 600ms」的話，滑動開始後 JavaScript 會一口氣佔住 Main Thread 600ms。這段時間整頁都會停住，連捲動都不行，只有右邊的側欄繼續滑。

渲染的流程

瀏覽器把 CSS 變成畫面上的像素，要經過幾個階段，前一個階段的結果會交給下一個。所以只要觸發了前面的階段，後面的每一個都得重跑。

Style → Layout → Paint → Composite

  • Style：算出每個元素套用了哪些 CSS 規則。
  • Layout：算出每個元素的大小跟位置。
  • Paint：算出每個 layer 上的像素。layer 是頁面上單獨畫成一張圖的部分。
  • Composite：把各個 layer 疊成最後的畫面。

Style、Layout、Paint 在 Main Thread 上跑，JavaScript 也是在這條 thread 上跑。Composite 則在另一條 Compositor Thread 上跑，最後由 GPU 畫出來。

螢幕一秒更新 60 次，等於每 16.7ms（1000 ÷ 60）就要交出一張新畫面。如果 Main Thread 上的 JavaScript、Style、Layout、Paint 加起來超過 16.7ms，這次更新就趕不上，螢幕只能繼續顯示上一張，看起來就是卡了一下。Compositor Thread 一樣每 16.7ms 要交一張畫面，但它不跑 JavaScript，所以 Main Thread 被 JavaScript 佔住的時候，只靠 Compositor Thread 就做得完的動畫還是會繼續動。

改 width 的話，瀏覽器要重算 Layout、重新 paint、再重新 composite。Layout 跟 Paint 都在 Main Thread 上，所以每個 frame 都要跟 JavaScript 分那 16.7ms。

改 color 的話，Layout 不用重算，但還是要重新 paint。Paint 也在 Main Thread 上，所以 JavaScript 一卡，color 的動畫一樣會停。

改 transform 的話，Layout 跟 Paint 都不用重跑，只要重新 composite，整件事在 Compositor Thread 上就做完了，不用跟 JavaScript 分時間。2026 年 11 月在 Chrome 153 上測試時，用一個 busy loop 佔住 Main Thread 600ms，這段時間裡 transform 的 transition 照樣畫了 36 個 frame，width 的是 0 個。

哪些屬性會觸發哪個階段

觸發屬性會發生什麼
Layoutwidth、height、margin、padding、top、left、font-size周圍元素的位置都要重算，很花時間。
Paintcolor、background、border-color、box-shadow、outline重新算像素，位置不變。
Compositetransform、opacity、filter（blur() 跟 drop-shadow() 除外）在 GPU 上重新疊 layer，開銷很小。

blur() 跟 drop-shadow() 會讓像素超出元素原本的範圍，所以 Chrome 把這兩種動畫放在 Main Thread 上跑。另外，background 雖然列在 Paint 那一列，Chrome 153 的 background-color 動畫卻是在 Compositor Thread 上跑的。

Compositor layer

transform 動畫能跳過 Paint，是因為動畫期間元素會被提升成一張獨立的 layer：像素畫好一次，之後每個 frame 只要移動這張圖。每個 layer 都要佔 GPU 記憶體，例如一個 500x500 的元素，它的 layer 大約佔 1MB（每個像素 4 bytes）。所以瀏覽器要有理由，才會把元素提升成獨立的 compositor layer。

會建立 layer 的：

  • 3D transform。 寫上 translateZ(0) 或 translate3d()，元素馬上就會提升成 layer。translateX(50px) 這種 2D transform 通常不會，除非它正在動畫裡。
  • will-change: transform。 讓瀏覽器提前建好 layer。用在確定會動的元素上，動完就拿掉，因為 layer 一直留著會浪費記憶體。
  • position: fixed。 fixed 的元素會有自己的 layer。
  • 正在跑的 transform 或 opacity 動畫。 就算是 2D transform，動畫期間也會暫時有一個 layer，瀏覽器在動畫開始時提升它，結束後再降回來。

不會建立 layer 的：

  • hover 狀態。 hover 本身跟 layer 無關，hover 時改 color 還是在 Main Thread 上做。只有 hover 觸發的動畫才可能建立 layer。
  • 靜態的 transform。 沒有動畫、也沒有 will-change 的 transform: translateX(50px)，會跟頁面其他部分一起 paint，不會提升成 layer。

用 DevTools 的 Performance 分頁把這段動畫錄下來，可以看到每個 frame 都有 Layout 跟 Paint。如果頁面上有一張資料表，每次 Layout 還會連帶重算表格的欄寬。2026 年 11 月在 Chrome 153 上測試時，在側欄旁邊放了一張 125 列的表格，CPU 全速時 Main Thread 每個 frame 大約要花 2.7ms，把 DevTools 的 CPU throttling 設成慢 6 倍時大約要花 13.1ms。這已經是 16.7ms 的八成，不過不管是全速還是 6 倍，每一次測試都還維持一秒 61 或 62 個 frame。所以在這個測試裡，width 動畫每個 frame 在 Main Thread 上的工作還沒超過 16.7ms。如果同時還有 JavaScript 在跑，兩邊加起來就可能超過。最上面的 embed 讓一段 JavaScript 連續跑 600ms，這段時間裡 Main Thread 一個 frame 都畫不出來，width 的側欄就整個停住。

Performance 分頁裡完全沒有 Layout，transition 期間側欄有自己的 layer。Main Thread 只處理開頭跟結尾那幾個 frame，中間的都由 Compositor Thread 畫。

側欄一直都是 240px 寬，只是一開始在畫面外，再滑進來。畫面上的結果一樣，但不用重新排版。

檢查清單

  1. 動畫用 transform 跟 opacity。 這兩個在 Compositor Thread 上跑。
  2. will-change 只用在一兩個元素上，不要全域加。 動畫結束就拿掉。
  3. 用 DevTools 的 Performance 分頁錄下動畫。 如果 Main 那條 track（Main Thread 那一列）每個 frame 都有工作，動畫就不是在 Compositor Thread 上跑，就算裡面沒有 Layout 或 Paint 也一樣。
  4. 在慢的裝置上測，或開 DevTools 的 CPU throttling。 在快的筆電上看不太出 Layout 的開銷。
