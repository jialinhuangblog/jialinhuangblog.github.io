14:Tbab6,<p>Writing React means meeting four names every day: <code>ReactNode</code>, <code>ReactElement</code>, <code>Component</code>, and HTML tag names like <code>div</code>. Early on it is easy to treat them as the same thing, since they all seem to be a piece of the screen. Yet returning <code>&#x3C;Comp /></code> renders, while returning <code>Comp</code> shows nothing; assigning a string to a variable typed <code>ReactElement</code> is a TypeScript error, while assigning it to <code>ReactNode</code> is fine.</p>
<p>So what is each of these names? Which ones exist only in JavaScript memory, and which one ends up as a DOM node in the browser?</p>
<h2>render and commit</h2>
<p>Every time React updates the screen, it works in two steps:</p>
<ol>
<li><strong>render</strong>: React calls your component functions and works out what the screen should become. This step only handles JavaScript objects; the DOM on the page does not change.</li>
<li><strong>commit</strong>: React writes the changes that render worked out into the DOM on the page.</li>
</ol>
<p>After commit, the browser still has to compute styles, lay out, and paint pixels. Those steps are in <a href="/v2/from-setstate-to-pixels">from setState to pixels</a>.</p>
<h2>What each name is</h2>






























<table><thead><tr><th>Name</th><th>What it is</th><th>Where it exists</th></tr></thead><tbody><tr><td><strong>ReactNode</strong></td><td>A TypeScript type, the widest one: any value React can render</td><td>Only during type checking; gone once compiled to JavaScript</td></tr><tr><td><strong>ReactElement</strong></td><td>A plain object made by JSX or <code>createElement</code>; main fields are <code>type</code>, <code>props</code>, <code>key</code></td><td>JavaScript memory</td></tr><tr><td><strong>Component</strong></td><td>A function or class that takes props and returns what to render</td><td>A function in JavaScript memory</td></tr><tr><td><strong><code>div</code></strong></td><td>A string, the name of an HTML tag</td><td>The string is in JavaScript memory; React creates an <code>HTMLDivElement</code> for it during render and puts it on the page at commit</td></tr></tbody></table>
<p>Of the four names, only <code>div</code> ends up matched to a DOM element on the page. Strings and numbers are ReactNodes too, though, and they become Text nodes. After <code>&#x3C;b>{42}&#x3C;/b></code> commits, the <code>&#x3C;b></code> on the page holds one Text node whose content is <code>"42"</code>. <code>null</code> and <code>false</code> produce no DOM.</p>
<h2>How the four relate</h2>
<h3>ReactNode contains ReactElement</h3>
<p><code>ReactNode</code> is the widest type. Any value React can render counts, and ReactElement is just one kind:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="tsx" data-theme="github-dark github-light"><code data-language="tsx" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">&#x3C;</span><span style="--shiki-dark:#85E89D;--shiki-light:#22863A">div</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> />                          </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// ReactElement</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">&#x3C;>hi&#x3C;/>                          </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// also a ReactElement, type is React.Fragment</span></span>
<span data-line=""><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'hello'</span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">                          // string</span></span>
<span data-line=""><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">42</span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">                               // number</span></span>
<span data-line=""><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">null</span></span>
<span data-line=""><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">false</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">[&#x3C;</span><span style="--shiki-dark:#85E89D;--shiki-light:#22863A">a</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1"> key</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">=</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">"a"</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> />, &#x3C;</span><span style="--shiki-dark:#85E89D;--shiki-light:#22863A">b</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1"> key</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">=</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">"b"</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> />]   </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// array</span></span></code></pre></figure>
<p>Checked with TypeScript 5.9.3 and <code>@types/react</code> 19.3.0, every line above is assignable to <code>ReactNode</code>. <code>&#x3C;>hi&#x3C;/></code> is also assignable to <code>ReactElement</code>, because JSX compiles it to <code>jsx(Fragment, { children: 'hi' })</code>, which produces an element whose <code>type</code> is <code>React.Fragment</code>.</p>
<h3>Component and <code>'div'</code> sit in the same field</h3>
<p>A ReactElement produced by the React 19.3.1 production build looks like this:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="js" data-theme="github-dark github-light"><code data-language="js" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">{ </span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">$$typeof</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">: </span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">Symbol</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(react.transitional.element), type, key, ref, props }</span></span></code></pre></figure>
<p><code>$$typeof</code> is the marker React uses to confirm "this is an element"; <code>React.isValidElement</code> checks it.</p>
<p>The <code>type</code> field can hold a string such as <code>'div'</code>, which makes the element a host component, or it can hold a Component, meaning a function or a class. The two kinds of value share one field and neither contains the other:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="jsx" data-theme="github-dark github-light"><code data-language="jsx" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">&#x3C;</span><span style="--shiki-dark:#85E89D;--shiki-light:#22863A">div</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">>hi&#x3C;/</span><span style="--shiki-dark:#85E89D;--shiki-light:#22863A">div</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">>        </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// type: 'div'      string, host component</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">&#x3C;</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">Button</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">>hi&#x3C;/</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">Button</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">>  </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// type: Button     function, your own component</span></span></code></pre></figure>
<p>During render, React looks at <code>type</code> to decide what to do:</p>
<ul>
<li>String: create a DOM node for it, and put it on the page at commit.</li>
<li>Function or class: call it, and keep going with whatever it returns.</li>
</ul>
<h3>Component produces ReactElements</h3>
<p>When you write <code>&#x3C;Button label="OK" /></code>, <code>Button</code> has not been called yet. The line only produces an element with <code>type: Button</code>. React calls <code>Button</code> when render reaches that element. What it returns is usually a ReactElement, but it can also be a string or <code>null</code>; in any case it is a ReactNode.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="jsx" data-theme="github-dark github-light"><code data-language="jsx" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">function</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1"> Button</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">({ </span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">label</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> }) {</span></span>
<span data-line=""><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">  return</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> &#x3C;</span><span style="--shiki-dark:#85E89D;--shiki-light:#22863A">span</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">>{label}&#x3C;/</span><span style="--shiki-dark:#85E89D;--shiki-light:#22863A">span</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">>   </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// returns a ReactElement</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">}</span></span></code></pre></figure>
<p>There is no <code>Button</code> on the page. Only the <code>&#x3C;span></code> it returns becomes a <code>&#x3C;span></code> node on the page, at commit.</p>

<p>At this point <code>Greeting</code> has not been called.</p>
<p>During render, React creates a <strong>fiber</strong> for each element. A fiber is React's own record object: what kind of component this is, what its props are, where its state lives, which children it has, which DOM node it maps to. No field on the fiber points at the element object; React copies only the element's <code>type</code>, <code>key</code> and <code>props</code> onto the fiber. In React 19 <code>ref</code> lives inside <code>props</code>, so it is copied too. The code is <code>createFiberFromElement</code> in <a href="https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiber.js"><code>ReactFiber.js</code></a>. Elements are made fresh every render, while fibers stay for the next render.</p>
<p>The fiber for <code>Greeting</code> is created first. React sees that <code>type</code> is a function, calls it with the props, and gets another element:</p>

<h3>When the DOM node is created, and when it enters the page</h3>
<p>Wrap <code>document.createElement</code> and <code>appendChild</code> with logging, then mount an <code>App</code> with the React 19.3.1 production build. <code>App</code> has two children: <code>A</code> renders <code>&#x3C;section>&#x3C;p>a&#x3C;/p>&#x3C;/section></code>, and <code>B</code> renders <code>&#x3C;div>b&#x3C;/div></code>. The logged order is:</p>
<ol>
<li>render <code>App</code></li>
<li>render <code>A</code></li>
<li><code>document.createElement('p')</code></li>
<li><code>document.createElement('section')</code></li>
<li><code>&#x3C;p></code> appended under <code>&#x3C;section></code>; <code>&#x3C;section></code> is not on the page yet</li>
<li>render <code>B</code></li>
<li><code>document.createElement('div')</code></li>
<li><code>&#x3C;section></code> appended under <code>#root</code>; only now is it on the page</li>
<li><code>&#x3C;div></code> appended under <code>#root</code></li>
<li><code>useLayoutEffect</code></li>
</ol>
<p><code>&#x3C;section></code> and <code>&#x3C;p></code> exist before <code>B</code> renders, which means they were created during render. As React walks the fibers, it passes each fiber twice: on the way down it calls the component, and on the way back up it finishes the fiber, a step called <code>completeWork</code>. A host component fiber creates its DOM node in <code>completeWork</code> and appends its children's DOM nodes to it; none of this is on the page yet. In <a href="https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiberCompleteWork.js"><code>ReactFiberCompleteWork.js</code></a>, the <code>HostComponent</code> branch calls <code>createInstance</code> and <code>appendAllChildren</code>. At commit, React puts the assembled DOM into <code>#root</code>. The way down and the way back up are covered in <a href="/v2/inside-react-fiberworkloop">Inside React's work loop</a>.</p>
<p>The whole path, in order:</p>
<ol>
<li><code>Greeting</code> is a function in your source code; it is always there.</li>
<li>JSX produces the element <code>{ type: Greeting }</code>; the next render produces a new element.</li>
<li>React creates a fiber for it. Hook values live on this fiber, which stays for the next render.</li>
<li>React calls <code>Greeting</code> and gets the element <code>{ type: 'div' }</code>. Once React copies its <code>type</code>, <code>key</code> and <code>props</code> onto the fiber, no fiber references it.</li>
<li>React creates a fiber for it, which also stays for the next render.</li>
<li><code>completeWork</code> creates an <code>HTMLDivElement</code> for that fiber and stores it in <code>stateNode</code>; it is not on the page yet.</li>
<li>Commit puts the <code>HTMLDivElement</code> on the page.</li>
</ol>
<h2>Why each fiber has two copies</h2>
<p>React keeps two fiber trees at the same time: <code>current</code> is the version on screen, and <code>workInProgress</code> is the version this render is building. The fibers on both sides for the same <code>&#x3C;div></code> point their <code>stateNode</code> at the same <code>HTMLDivElement</code>: when <a href="https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiber.js"><code>createWorkInProgress</code></a> builds a workInProgress fiber, it copies <code>stateNode</code> from current.</p>
<p>So when React changes things on workInProgress, does it change the DOM on screen?</p>
<p>No. <code>stateNode</code> is only a reference to the DOM node. Changing the DOM takes calls like <code>setAttribute</code>, <code>appendChild</code>, <code>removeChild</code>, and React only makes them in commit's mutation step, in <code>commitMutationEffectsOnFiber</code> in <a href="https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiberCommitWork.js"><code>ReactFiberCommitWork.js</code></a>. What render changes are the fiber's own fields:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="js" data-theme="github-dark github-light"><code data-language="js" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">wipFiber.memoizedProps </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">=</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> { children: </span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'new text'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> }  </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// the fiber's own field</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">wipFiber.flags </span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49">|=</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> Update                           </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// the fiber's own field</span></span>

<p>The only DOM render creates is for nodes added in this update, like the <code>&#x3C;section></code> in the previous section, and those are not attached to the page when they are created.</p>
<p>React does not prepare two copies of every fiber, though. At mount each fiber has one copy. Only when the first update comes and render reaches it does React create a second copy, and from then on the two take turns as current. So "this component's fiber" is not one fixed object; it switches to the other copy every render. The DOM node behind <code>&#x3C;div></code>, on the other hand, is the same one throughout.</p>
<p>If a component is wrapped in <code>React.memo</code> and its props did not change, React skips its whole subtree. A fiber in that subtree stays a single copy for as long as render never reaches it. Because there is only one copy, its <code>alternate</code> is <code>null</code>, and the current and workInProgress trees use the same fiber object. The comment in <code>createWorkInProgress</code> says the same: the second fiber is created only when needed, "to avoid allocating extra objects for things that are never updated". As long as the component's type and key stay the same, React keeps alternating between these two objects and never creates a third.</p>
<h3>What commit swaps</h3>
<p>Three things in commit, in this order, involve the two fiber trees:</p>
<ol>
<li><strong>mutation</strong>: change the real DOM, such as <code>setAttribute</code>, <code>appendChild</code>, <code>removeChild</code>. Every change the user will see happens here.</li>
<li><strong>swap current</strong>: <code>root.current = finishedWork</code>; workInProgress becomes current.</li>
<li><strong>layout</strong>: run <code>useLayoutEffect</code> and <code>componentDidMount</code>.</li>
</ol>
<p>There are two copies of each fiber but only one DOM, so mutation has no second DOM to prepare and swap in. It changes the nodes on the page directly, for example changing an attribute, or adding and removing a few nodes. By the time current is swapped, the DOM is already updated, so this line changes nothing on screen. What it affects is the next render: React uses the version just finished as current and compares its props with the new ones, and the old version swapped out becomes the next workInProgress.</p>
<p>The line sits at the end of <code>flushMutationEffects</code> in <a href="https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiberWorkLoop.js"><code>ReactFiberWorkLoop.js</code></a>, which <code>commitRoot</code> calls:</p>

<h3>alternate on mount, update, delete</h3>






























<table><thead><tr><th>Case</th><th>Where this fiber is</th><th><code>alternate</code></th></tr></thead><tbody><tr><td>mount</td><td>only in workInProgress</td><td><code>null</code></td></tr><tr><td>update, and this render reached it</td><td>one copy each in current and workInProgress</td><td>the two point at each other</td></tr><tr><td>update, and its whole subtree was skipped</td><td>current and workInProgress share one object</td><td>stays <code>null</code> if it was never reached</td></tr><tr><td>delete</td><td>only in current</td><td>React builds no workInProgress fiber for it</td></tr></tbody></table>
<p>React does not mark a deletion by setting <code>alternate</code> to <code>null</code>. A node being removed gets no workInProgress fiber; React puts the old fiber into the parent's <code>deletions</code> array and adds the <code>ChildDeletion</code> flag to the parent. Commit reads that array and calls <code>removeChild</code>. The code is <code>deleteChild</code> in <a href="https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactChildFiber.js"><code>ReactChildFiber.js</code></a>; it changes only the parent's <code>deletions</code> and <code>flags</code>, and nothing touches the removed child's <code>alternate</code>.</p>
<h2>Where useState keeps its value</h2>
<p>A function component is just a function. It runs, returns, and its local variables are gone. Write <code>let count = 0</code> inside a component and it goes back to 0 every render. So how does a <code>useState</code> value survive until the next render?</p>
<p>It lives on the component's fiber, in the <code>memoizedState</code> field. That field points to a linked list, with one node for every call to <code>useState</code>, <code>useRef</code>, <code>useEffect</code>. For a component that calls <code>useState</code>, <code>useRef</code>, <code>useEffect</code> in that order, <code>fiber.memoizedState</code> points to the first node (the <code>useState</code> one), its <code>next</code> points to the <code>useRef</code> node, and the one after that is the <code>useEffect</code> node.</p>
<p>As the previous section showed, a component's fiber has two copies that take turns. On each render, <code>updateWorkInProgressHook</code> in <a href="https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiberHooks.js"><code>ReactFiberHooks.js</code></a> copies the hook nodes from the current fiber to the workInProgress fiber one by one, in order, so the values carry over. Each time render reaches a <code>useState</code>, React moves to the next node in the list and hands back what is stored there.</p>
<p>How does React know which node belongs to which <code>useState</code>? It does not know your variable names, so it cannot tell which <code>useState</code> is <code>name</code> and which is <code>age</code>. It can only count: the first call gets the first node, the second call gets the second, and so on.</p>
<p>The hook node has no place for a name either. React creates hook nodes in <code>mountWorkInProgressHook</code> in <code>ReactFiberHooks.js</code>:</p>

<h3>Why can a component return <code>null</code> but not a Component?</h3>
<p>What a component returns has to be a ReactNode. <code>null</code> is a ReactNode, meaning "render nothing here". A Component is a function, and a function is not a ReactNode. You need <code>&#x3C;Comp /></code>, not just <code>Comp</code>.</p>
<p>In React 19.3.1, <code>return Comp</code> puts nothing on screen. The development build logs "Functions are not valid as a React child. This may happen if you return Comp instead of <comp> from render. Or maybe you meant to call this function rather than return it." The production build logs nothing. In TypeScript, assigning a function to a variable typed <code>ReactNode</code> is an error.</comp></p>
<h3>Why does changing a list item's <code>key</code> reset its state?</h3>
<p>During render, React matches new elements to existing fibers by <code>key</code>:</p>
<ul>
<li><strong>Same key and type</strong>: reuse the fiber; its <code>memoizedState</code> and DOM node stay.</li>
<li><strong>Different key</strong>: drop the old fiber and create a new one with empty state.</li>
</ul>
<p>Using the array index as the key causes trouble: insert a row at the top, every index shifts by one, and React pairs the wrong fiber with the wrong row. Below, every row has a <code>useState('note for ' + label)</code>, and A is inserted in front of B and C:</p>

<h2>Summary</h2>
<ol>
<li>JSX produces a <strong>ReactElement</strong>, whose <code>type</code> is a string or a Component.</li>
<li>During render, React creates a fiber for each element, or reuses the one from last time. If <code>type</code> is a Component, React calls it and gets more elements.</li>
<li>React walks the fibers one at a time through <code>child</code>, <code>sibling</code> and <code>return</code>, without recursive calls.</li>
<li>A fiber whose <code>type</code> is a string creates its DOM node in <code>completeWork</code> and attaches its children; it is not on the page yet.</li>
<li>Commit puts those DOM nodes on the page, then swaps <code>root.current</code> to the new version.</li>
</ol>

Writing React means meeting four names every day: `ReactNode`, `ReactElement`, `Component`, and HTML tag names like `div`. Early on it is easy to treat them as the same thing, since they all seem to be a piece of the screen. Yet returning `<Comp />` renders, while returning `Comp` shows nothing; assigning a string to a variable typed `ReactElement` is a TypeScript error, while assigning it to `ReactNode` is fine.

So what is each of these names? Which ones exist only in JavaScript memory, and which one ends up as a DOM node in the browser?

## render and commit

Every time React updates the screen, it works in two steps:

1. **render**: React calls your component functions and works out what the screen should become. This step only handles JavaScript objects; the DOM on the page does not change.
2. **commit**: React writes the changes that render worked out into the DOM on the page.

After commit, the browser still has to compute styles, lay out, and paint pixels. Those steps are in [from setState to pixels](/v2/from-setstate-to-pixels).

## What each name is

| Name | What it is | Where it exists |
|---|---|---|
| **ReactNode** | A TypeScript type, the widest one: any value React can render | Only during type checking; gone once compiled to JavaScript |
| **ReactElement** | A plain object made by JSX or `createElement`; main fields are `type`, `props`, `key` | JavaScript memory |
| **Component** | A function or class that takes props and returns what to render | A function in JavaScript memory |
| **`div`** | A string, the name of an HTML tag | The string is in JavaScript memory; React creates an `HTMLDivElement` for it during render and puts it on the page at commit |

Of the four names, only `div` ends up matched to a DOM element on the page. Strings and numbers are ReactNodes too, though, and they become Text nodes. After `<b>{42}</b>` commits, the `<b>` on the page holds one Text node whose content is `"42"`. `null` and `false` produce no DOM.

## How the four relate

### ReactNode contains ReactElement

`ReactNode` is the widest type. Any value React can render counts, and ReactElement is just one kind:

```tsx
<div />                          // ReactElement
<>hi</>                          // also a ReactElement, type is React.Fragment
'hello'                          // string
42                               // number
null
false
[<a key="a" />, <b key="b" />]   // array
```

Checked with TypeScript 5.9.3 and `@types/react` 19.3.0, every line above is assignable to `ReactNode`. `<>hi</>` is also assignable to `ReactElement`, because JSX compiles it to `jsx(Fragment, { children: 'hi' })`, which produces an element whose `type` is `React.Fragment`.

### Component and `'div'` sit in the same field

A ReactElement produced by the React 19.3.1 production build looks like this:

```js
{ $$typeof: Symbol(react.transitional.element), type, key, ref, props }
```

`$$typeof` is the marker React uses to confirm "this is an element"; `React.isValidElement` checks it.

The `type` field can hold a string such as `'div'`, which makes the element a host component, or it can hold a Component, meaning a function or a class. The two kinds of value share one field and neither contains the other:

```jsx
<div>hi</div>        // type: 'div'      string, host component
<Button>hi</Button>  // type: Button     function, your own component
```

During render, React looks at `type` to decide what to do:

- String: create a DOM node for it, and put it on the page at commit.
- Function or class: call it, and keep going with whatever it returns.

### Component produces ReactElements

When you write `<Button label="OK" />`, `Button` has not been called yet. The line only produces an element with `type: Button`. React calls `Button` when render reaches that element. What it returns is usually a ReactElement, but it can also be a string or `null`; in any case it is a ReactNode.

```jsx
function Button({ label }) {
  return <span>{label}</span>   // returns a ReactElement
}
```

There is no `Button` on the page. Only the `<span>` it returns becomes a `<span>` node on the page, at commit.

## From `<Greeting />` to HTMLDivElement

```jsx
function Greeting({ name }) {
  return <div>Hello, {name}</div>
}

const tree = <Greeting name="Jialin" />
```

`tree` is a ReactElement, and its `type` field holds the `Greeting` function itself:

```js
{
  $$typeof: Symbol(react.transitional.element),
  type: Greeting,
  key: null,
  ref: null,
  props: { name: 'Jialin' }
}
```

At this point `Greeting` has not been called.

During render, React creates a **fiber** for each element. A fiber is React's own record object: what kind of component this is, what its props are, where its state lives, which children it has, which DOM node it maps to. No field on the fiber points at the element object; React copies only the element's `type`, `key` and `props` onto the fiber. In React 19 `ref` lives inside `props`, so it is copied too. The code is `createFiberFromElement` in [`ReactFiber.js`](https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiber.js). Elements are made fresh every render, while fibers stay for the next render.

The fiber for `Greeting` is created first. React sees that `type` is a function, calls it with the props, and gets another element:

```js
{
  $$typeof: Symbol(react.transitional.element),
  type: 'div',
  key: null,
  ref: null,
  props: { children: ['Hello, ', 'Jialin'] }
}
```

This time `type` is the string `'div'`, and React creates a host component fiber for it. The two strings in `children` get a fiber each as well. Rendering `<Greeting name="Jialin" />` with React 19.3.1 in Chrome 156 and then walking every fiber down from the root prints:

```
HostRoot
  FunctionComponent  Greeting    stateNode = null
    HostComponent    div         stateNode = HTMLDivElement
      HostText       "Hello, "   stateNode = Text
      HostText       "Jialin"    stateNode = Text
```

The full fiber definition lives in [`ReactInternalTypes.js`](https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactInternalTypes.js). The `div` fiber, with most fields removed, looks roughly like this:

```js
{
  tag: HostComponent,
  type: 'div',                    // same as the element's type
  stateNode: HTMLDivElement,      // DOM node created during render
  child: Fiber,                   // first child, here the "Hello, " fiber
  sibling: null,                  // next sibling
  return: Fiber,                  // parent, here the Greeting fiber
  alternate: Fiber | null,        // matching fiber in the other fiber tree, next section
  memoizedProps: { children: ['Hello, ', 'Jialin'] },
  memoizedState: null,            // a function component's fiber keeps its hook list here
  lanes: 0,                       // pending updates on this fiber, and their priorities
  flags: 0,                       // what commit must do: Placement, Update, ChildDeletion, etc.
}
```

### When the DOM node is created, and when it enters the page

Wrap `document.createElement` and `appendChild` with logging, then mount an `App` with the React 19.3.1 production build. `App` has two children: `A` renders `<section><p>a</p></section>`, and `B` renders `<div>b</div>`. The logged order is:

1. render `App`
2. render `A`
3. `document.createElement('p')`
4. `document.createElement('section')`
5. `<p>` appended under `<section>`; `<section>` is not on the page yet
6. render `B`
7. `document.createElement('div')`
8. `<section>` appended under `#root`; only now is it on the page
9. `<div>` appended under `#root`
10. `useLayoutEffect`

`<section>` and `<p>` exist before `B` renders, which means they were created during render. As React walks the fibers, it passes each fiber twice: on the way down it calls the component, and on the way back up it finishes the fiber, a step called `completeWork`. A host component fiber creates its DOM node in `completeWork` and appends its children's DOM nodes to it; none of this is on the page yet. In [`ReactFiberCompleteWork.js`](https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiberCompleteWork.js), the `HostComponent` branch calls `createInstance` and `appendAllChildren`. At commit, React puts the assembled DOM into `#root`. The way down and the way back up are covered in [Inside React's work loop](/v2/inside-react-fiberworkloop).

The whole path, in order:

1. `Greeting` is a function in your source code; it is always there.
2. JSX produces the element `{ type: Greeting }`; the next render produces a new element.
3. React creates a fiber for it. Hook values live on this fiber, which stays for the next render.
4. React calls `Greeting` and gets the element `{ type: 'div' }`. Once React copies its `type`, `key` and `props` onto the fiber, no fiber references it.
5. React creates a fiber for it, which also stays for the next render.
6. `completeWork` creates an `HTMLDivElement` for that fiber and stores it in `stateNode`; it is not on the page yet.
7. Commit puts the `HTMLDivElement` on the page.

## Why each fiber has two copies

React keeps two fiber trees at the same time: `current` is the version on screen, and `workInProgress` is the version this render is building. The fibers on both sides for the same `<div>` point their `stateNode` at the same `HTMLDivElement`: when [`createWorkInProgress`](https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiber.js) builds a workInProgress fiber, it copies `stateNode` from current.

So when React changes things on workInProgress, does it change the DOM on screen?

No. `stateNode` is only a reference to the DOM node. Changing the DOM takes calls like `setAttribute`, `appendChild`, `removeChild`, and React only makes them in commit's mutation step, in `commitMutationEffectsOnFiber` in [`ReactFiberCommitWork.js`](https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiberCommitWork.js). What render changes are the fiber's own fields:

```js
wipFiber.memoizedProps = { children: 'new text' }  // the fiber's own field
wipFiber.flags |= Update                           // the fiber's own field
wipFiber.child = newChildFiber                     // a pointer between fibers
```

The only DOM render creates is for nodes added in this update, like the `<section>` in the previous section, and those are not attached to the page when they are created.

React does not prepare two copies of every fiber, though. At mount each fiber has one copy. Only when the first update comes and render reaches it does React create a second copy, and from then on the two take turns as current. So "this component's fiber" is not one fixed object; it switches to the other copy every render. The DOM node behind `<div>`, on the other hand, is the same one throughout.

If a component is wrapped in `React.memo` and its props did not change, React skips its whole subtree. A fiber in that subtree stays a single copy for as long as render never reaches it. Because there is only one copy, its `alternate` is `null`, and the current and workInProgress trees use the same fiber object. The comment in `createWorkInProgress` says the same: the second fiber is created only when needed, "to avoid allocating extra objects for things that are never updated". As long as the component's type and key stay the same, React keeps alternating between these two objects and never creates a third.

### What commit swaps

Three things in commit, in this order, involve the two fiber trees:

1. **mutation**: change the real DOM, such as `setAttribute`, `appendChild`, `removeChild`. Every change the user will see happens here.
2. **swap current**: `root.current = finishedWork`; workInProgress becomes current.
3. **layout**: run `useLayoutEffect` and `componentDidMount`.

There are two copies of each fiber but only one DOM, so mutation has no second DOM to prepare and swap in. It changes the nodes on the page directly, for example changing an attribute, or adding and removing a few nodes. By the time current is swapped, the DOM is already updated, so this line changes nothing on screen. What it affects is the next render: React uses the version just finished as current and compares its props with the new ones, and the old version swapped out becomes the next workInProgress.

The line sits at the end of `flushMutationEffects` in [`ReactFiberWorkLoop.js`](https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiberWorkLoop.js), which `commitRoot` calls:

```js
  // The work-in-progress tree is now the current tree. This must come after
  // the mutation phase, so that the previous tree is still current during
  // componentWillUnmount, but before the layout phase, so that the finished
  // work is current during componentDidMount/Update.
  root.current = finishedWork;
  pendingEffectsStatus = PENDING_LAYOUT_PHASE;
```

`finishedWork` is the workInProgress version. The line runs after mutation and before layout, so `componentWillUnmount` still sees the old version as current, while `useLayoutEffect` and `componentDidMount` already see the new one.

### alternate on mount, update, delete

| Case | Where this fiber is | `alternate` |
|---|---|---|
| mount | only in workInProgress | `null` |
| update, and this render reached it | one copy each in current and workInProgress | the two point at each other |
| update, and its whole subtree was skipped | current and workInProgress share one object | stays `null` if it was never reached |
| delete | only in current | React builds no workInProgress fiber for it |

React does not mark a deletion by setting `alternate` to `null`. A node being removed gets no workInProgress fiber; React puts the old fiber into the parent's `deletions` array and adds the `ChildDeletion` flag to the parent. Commit reads that array and calls `removeChild`. The code is `deleteChild` in [`ReactChildFiber.js`](https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactChildFiber.js); it changes only the parent's `deletions` and `flags`, and nothing touches the removed child's `alternate`.

## Where useState keeps its value

A function component is just a function. It runs, returns, and its local variables are gone. Write `let count = 0` inside a component and it goes back to 0 every render. So how does a `useState` value survive until the next render?

It lives on the component's fiber, in the `memoizedState` field. That field points to a linked list, with one node for every call to `useState`, `useRef`, `useEffect`. For a component that calls `useState`, `useRef`, `useEffect` in that order, `fiber.memoizedState` points to the first node (the `useState` one), its `next` points to the `useRef` node, and the one after that is the `useEffect` node.

As the previous section showed, a component's fiber has two copies that take turns. On each render, `updateWorkInProgressHook` in [`ReactFiberHooks.js`](https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiberHooks.js) copies the hook nodes from the current fiber to the workInProgress fiber one by one, in order, so the values carry over. Each time render reaches a `useState`, React moves to the next node in the list and hands back what is stored there.

How does React know which node belongs to which `useState`? It does not know your variable names, so it cannot tell which `useState` is `name` and which is `age`. It can only count: the first call gets the first node, the second call gets the second, and so on.

The hook node has no place for a name either. React creates hook nodes in `mountWorkInProgressHook` in `ReactFiberHooks.js`:

```js
const hook = {
  memoizedState: null,
  baseState: null,
  baseQueue: null,
  queue: null,
  next: null,
};
```

No name, no key, no id; the only link from one hook to the next is `next`.

So the order of hook calls has to be the same on every render. Try putting a hook inside an `if`:

```jsx
function Profile({ show }) {
  if (show) {
    const [name] = useState('Ann')   // sometimes called, sometimes skipped
  }
  const [age] = useState(20)
}
```

First render, `show` is `true`. Two calls, two nodes:

| Call | Node it gets | Value |
|---|---|---|
| 1st (`name`) | node 1 | `'Ann'` |
| 2nd (`age`) | node 2 | `20` |

Next render, `show` is `false`, and the `if` skips the first call. One call is left, and React still counts from the top:

| Call | Node it gets | Value |
|---|---|---|
| 1st (`age`) | node 1 | `'Ann'` |

`age` gets the first node and reads `name`'s value. Every hook after the skipped one moves up a position and reads the wrong value. React expected two hooks and saw one, so it throws. Running this with the React 19.3.1 development build, `age` on the second render is indeed `'Ann'`, followed by "Rendered fewer hooks than expected. This may be caused by an accidental early return statement." That is why the [Rules of Hooks](https://react.dev/reference/rules/rules-of-hooks) put hooks at the top level of a component: not inside `if` or `for`, and not after an early `return`.

## A few more questions

### Why does `<MyComponent />` render, but lowercase `<myComponent />` does not?

The JSX compiler looks at the first letter to decide what goes into `type`: uppercase means a variable, lowercase means a string. Compiled with esbuild 0.25.10:

```js
<div />          →  createElement("div", null)          // lowercase: a string
<MyComponent />  →  createElement(MyComponent, null)    // uppercase: a variable
<myComponent />  →  createElement("myComponent", null)  // lowercase: still a string
```

`<myComponent />` looks like a component, but its first letter is lowercase, so the compiler emits the string `"myComponent"`. React gets `type: "myComponent"`, treats it as an HTML tag, and creates a `<mycomponent>`. The function named `myComponent` is never called.

As [JSX In Depth](https://legacy.reactjs.org/docs/jsx-in-depth.html#user-defined-components-must-be-capitalized) also notes, casing is the JSX compiler's rule; React only receives the `type` the compiler already decided.

### Why can a component return `null` but not a Component?

What a component returns has to be a ReactNode. `null` is a ReactNode, meaning "render nothing here". A Component is a function, and a function is not a ReactNode. You need `<Comp />`, not just `Comp`.

In React 19.3.1, `return Comp` puts nothing on screen. The development build logs "Functions are not valid as a React child. This may happen if you return Comp instead of <Comp /> from render. Or maybe you meant to call this function rather than return it." The production build logs nothing. In TypeScript, assigning a function to a variable typed `ReactNode` is an error.

### Why does changing a list item's `key` reset its state?

During render, React matches new elements to existing fibers by `key`:

- **Same key and type**: reuse the fiber; its `memoizedState` and DOM node stay.
- **Different key**: drop the old fiber and create a new one with empty state.

Using the array index as the key causes trouble: insert a row at the top, every index shifts by one, and React pairs the wrong fiber with the wrong row. Below, every row has a `useState('note for ' + label)`, and A is inserted in front of B and C:

| Key | Before | After inserting A at the top |
|---|---|---|
| index | `B / note for B`, `C / note for C` | `A / note for B`, `B / note for C`, `C / note for C` |
| each row's own id | `B / note for B`, `C / note for C` | `A / note for A`, `B / note for B`, `C / note for C` |

With index keys, A got B's old state, B got C's, and C is a newly created fiber.

## Summary

1. JSX produces a **ReactElement**, whose `type` is a string or a Component.
2. During render, React creates a fiber for each element, or reuses the one from last time. If `type` is a Component, React calls it and gets more elements.
3. React walks the fibers one at a time through `child`, `sibling` and `return`, without recursive calls.
4. A fiber whose `type` is a string creates its DOM node in `completeWork` and attaches its children; it is not on the page yet.
5. Commit puts those DOM nodes on the page, then swaps `root.current` to the new version.

React 天天會碰到四個名字：<code>ReactNode</code>、<code>ReactElement</code>、<code>Component</code>，還有 <code>div</code> 這種 HTML tag 的名字。剛開始寫的時候，很容易把它們當成同一種東西，反正都是畫面上的一塊。可是回傳 <code>&#x3C;Comp /></code> 會 render，回傳 <code>Comp</code> 卻什麼都不顯示；把字串指定給 <code>ReactElement</code> 型別的變數，TypeScript 會報錯，指定給 <code>ReactNode</code> 就沒事。</p>
<p>這四個名字各是什麼呢？哪些只存在 JavaScript 的記憶體裡，哪一個最後會變成瀏覽器裡的 DOM 節點？</p>
<h2>render 跟 commit</h2>
<p>React 每次更新畫面，都分成兩步：</p>
<ol>
<li><strong>render</strong>：React 呼叫元件的 function，算出畫面應該變成什麼樣子。這一步只處理 JavaScript 物件，頁面上的 DOM 不會變。</li>
<li><strong>commit</strong>：React 把 render 算出來的變更寫進頁面上的 DOM。</li>
</ol>
<p>commit 之後瀏覽器還要算 style、排版、畫出像素，那些步驟寫在<a href="/v2/from-setstate-to-pixels">從 setState 到畫面上的像素</a>。</p>
<h2>四個名字各是什麼</h2>






























<table><thead><tr><th>名字</th><th>是什麼</th><th>存在哪裡</th></tr></thead><tbody><tr><td><strong>ReactNode</strong></td><td>TypeScript 的型別，範圍最大，React 能 render 的值都算</td><td>只在型別檢查時存在，編譯成 JavaScript 之後就沒了</td></tr><tr><td><strong>ReactElement</strong></td><td>JSX 或 <code>createElement</code> 產生的普通物件，主要欄位是 <code>type</code>、<code>props</code>、<code>key</code></td><td>JavaScript 記憶體</td></tr><tr><td><strong>Component</strong></td><td>一個 function 或 class，收 props，回傳要 render 的東西</td><td>JavaScript 記憶體裡的一個 function</td></tr><tr><td><strong><code>div</code></strong></td><td>一個字串，HTML tag 的名字</td><td>字串本身在 JavaScript 記憶體裡；React 在 render 時替它建一個 <code>HTMLDivElement</code>，commit 時放進頁面</td></tr></tbody></table>
<p>這四個名字裡，只有 <code>div</code> 會在頁面上對應到一個 DOM 元素。不過字串跟數字也算 ReactNode，它們會變成 Text 節點。<code>&#x3C;b>{42}&#x3C;/b></code> commit 之後，頁面上的 <code>&#x3C;b></code> 底下有一個內容是 <code>"42"</code> 的 Text 節點。<code>null</code> 跟 <code>false</code> 不會產生 DOM。</p>
<h2>四個名字之間是什麼關係</h2>
<h3>ReactNode 包含 ReactElement</h3>
<p><code>ReactNode</code> 是最寬的型別，React 能 render 的值都算，ReactElement 只是其中一種：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="tsx" data-theme="github-dark github-light"><code data-language="tsx" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">&#x3C;</span><span style="--shiki-dark:#85E89D;--shiki-light:#22863A">div</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> />                          </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// ReactElement</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">&#x3C;>hi&#x3C;/>                          </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// 也是 ReactElement，type 是 React.Fragment</span></span>
<span data-line=""><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'hello'</span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">                          // string</span></span>
<span data-line=""><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">42</span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">                               // number</span></span>
<span data-line=""><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">null</span></span>
<span data-line=""><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">false</span></span>

<p>用 TypeScript 5.9.3 跟 <code>@types/react</code> 19.3.0 檢查，上面每一行都能指定給 <code>ReactNode</code>。<code>&#x3C;>hi&#x3C;/></code> 也能指定給 <code>ReactElement</code>，因為 JSX 會把它編譯成 <code>jsx(Fragment, { children: 'hi' })</code>，產生的是 <code>type</code> 為 <code>React.Fragment</code> 的 element。</p>
<h3>Component 跟 <code>'div'</code> 放在同一個欄位</h3>
<p>React 19.3.1 的 production build 產生的 ReactElement 長這樣：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="js" data-theme="github-dark github-light"><code data-language="js" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">{ </span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">$$typeof</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">: </span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">Symbol</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(react.transitional.element), type, key, ref, props }</span></span></code></pre></figure>
<p><code>$$typeof</code> 是 React 用來確認「這是一個 element」的標記，<code>React.isValidElement</code> 檢查的就是它。</p>
<p><code>type</code> 欄位可以放字串，例如 <code>'div'</code>，這種 element 叫 host component；也可以放一個 Component，也就是一個 function 或 class。這兩種值放在同一個欄位，彼此沒有包含關係：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="jsx" data-theme="github-dark github-light"><code data-language="jsx" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">&#x3C;</span><span style="--shiki-dark:#85E89D;--shiki-light:#22863A">div</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">>hi&#x3C;/</span><span style="--shiki-dark:#85E89D;--shiki-light:#22863A">div</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">>        </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// type: 'div'      字串，host component</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">&#x3C;</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">Button</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">>hi&#x3C;/</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">Button</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">>  </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// type: Button     function，自己寫的元件</span></span></code></pre></figure>
<p>render 的時候，React 看 <code>type</code> 決定怎麼處理：</p>
<ul>
<li>字串：替它建一個 DOM 節點，commit 時放進頁面。</li>
<li>function 或 class：呼叫它，拿它回傳的東西繼續往下處理。</li>
</ul>
<h3>Component 產生 ReactElement</h3>
<p>寫 <code>&#x3C;Button label="OK" /></code> 的時候，<code>Button</code> 還沒被呼叫，這一行只產生一個 <code>type: Button</code> 的 element。等 React render 到這個 element，才會呼叫 <code>Button</code>。它回傳的通常是 ReactElement，也可以是字串或 <code>null</code>，總之是一個 ReactNode。</p>

<p>React render 的時候，會替每個 element 建一個 <strong>fiber</strong>。fiber 是 React 自己的記錄物件，這個元件是什麼類型、props 是什麼、state 放在哪裡、底下有哪些 child、對應哪個 DOM 節點，都記在 fiber 上。fiber 上沒有任何欄位指向 element 物件，React 只把 element 的 <code>type</code>、<code>key</code>、<code>props</code> 抄到 fiber 上。React 19 的 <code>ref</code> 放在 <code>props</code> 裡，也跟著抄過去。程式碼在 <a href="https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiber.js"><code>ReactFiber.js</code></a> 的 <code>createFiberFromElement</code>。element 每次 render 都重新產生，fiber 則會留到下一次 render。</p>

<h3>DOM 節點什麼時候建好、什麼時候進頁面</h3>
<p>把 <code>document.createElement</code> 跟 <code>appendChild</code> 包一層記錄，再用 React 19.3.1 的 production build mount 一個 <code>App</code>。<code>App</code> 底下有兩個元件：<code>A</code> render 出 <code>&#x3C;section>&#x3C;p>a&#x3C;/p>&#x3C;/section></code>，<code>B</code> render 出 <code>&#x3C;div>b&#x3C;/div></code>。記錄下來的順序是：</p>
<ol>
<li>render <code>App</code></li>
<li>render <code>A</code></li>
<li><code>document.createElement('p')</code></li>
<li><code>document.createElement('section')</code></li>
<li>把 <code>&#x3C;p></code> 接到 <code>&#x3C;section></code> 底下，<code>&#x3C;section></code> 還不在頁面上</li>
<li>render <code>B</code></li>
<li><code>document.createElement('div')</code></li>
<li>把 <code>&#x3C;section></code> 接到 <code>#root</code> 底下，這時才進頁面</li>
<li>把 <code>&#x3C;div></code> 接到 <code>#root</code> 底下</li>
<li><code>useLayoutEffect</code></li>
</ol>
<p><code>&#x3C;section></code> 跟 <code>&#x3C;p></code> 在 render <code>B</code> 之前就建好了，也就是還在 render 的時候。React 走 fiber 時，每個 fiber 會經過兩次：往下走時呼叫元件，往回走時收尾，收尾那一步叫 <code>completeWork</code>。host component 的 fiber 在 <code>completeWork</code> 裡建出 DOM 節點，再把 child 的 DOM 節點接上去，這時接好的 DOM 都還不在頁面上。對應的程式碼是 <a href="https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiberCompleteWork.js"><code>ReactFiberCompleteWork.js</code></a> 的 <code>HostComponent</code> 分支，它呼叫 <code>createInstance</code> 跟 <code>appendAllChildren</code>。到了 commit，React 才把接好的 DOM 放進 <code>#root</code>。往下走、往回走的細節在 <a href="/v2/inside-react-fiberworkloop">React 的 work loop 裡發生了什麼</a>。</p>
<p>把整條路照順序排起來：</p>
<ol>
<li><code>Greeting</code> 是原始碼裡的 function，一直都在。</li>
<li>JSX 產生 <code>{ type: Greeting }</code> 這個 element，下一次 render 會產生新的 element。</li>
<li>React 替它建 fiber，hook 的值存在這個 fiber 上，會留到下一次 render。</li>
<li>React 呼叫 <code>Greeting</code>，拿到 <code>{ type: 'div' }</code> 這個 element。React 把它的 <code>type</code>、<code>key</code>、<code>props</code> 抄到 fiber 上之後，就沒有 fiber reference 著它。</li>
<li>React 替它建 fiber，也會留到下一次 render。</li>
<li><code>completeWork</code> 替這個 fiber 建出 <code>HTMLDivElement</code>，記在 <code>stateNode</code> 上，這時還不在頁面上。</li>
<li>commit 把 <code>HTMLDivElement</code> 放進頁面。</li>
</ol>
<h2>為什麼 fiber 有兩份</h2>
<p>React 同時留著兩份 fiber 樹：<code>current</code> 是現在畫面上的版本，<code>workInProgress</code> 是這次 render 正在建的版本。兩邊對應同一個 <code>&#x3C;div></code> 的 fiber，<code>stateNode</code> 都指向同一個 <code>HTMLDivElement</code>：<a href="https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiber.js"><code>createWorkInProgress</code></a> 建 workInProgress 的 fiber 時，會把 current 的 <code>stateNode</code> 抄過去。</p>
<p>那 React 在 workInProgress 上改東西，會不會改到畫面上的 DOM 呢？</p>
<p>不會。<code>stateNode</code> 只是指向 DOM 節點的參照，要改 DOM，得呼叫 <code>setAttribute</code>、<code>appendChild</code>、<code>removeChild</code> 這類 method，而 React 只在 commit 的 mutation 階段，也就是 <a href="https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiberCommitWork.js"><code>ReactFiberCommitWork.js</code></a> 裡的 <code>commitMutationEffectsOnFiber</code>，呼叫它們。render 時修改的都是 fiber 自己的欄位：</p>

<p>render 時唯一會新建的 DOM，是這次新加進來的節點，像上一節的 <code>&#x3C;section></code>，而它們建好的時候還沒接到頁面上。</p>
<p>不過 React 也不是每個 fiber 都準備兩份。mount 的時候每個 fiber 只有一份，等到第一次更新、render 走到它，React 才替它建第二份，之後兩份輪流當 current。所以「這個元件的 fiber」不是固定一個物件，每次 render 都會換成另一份。<code>&#x3C;div></code> 對應的 DOM 節點倒是從頭到尾都是同一個。</p>
<p>如果元件用 <code>React.memo</code> 包起來，而且 props 沒變，React 會跳過它底下整個 subtree。subtree 裡的 fiber 只要一直沒被 render 走到，就始終只有一份。因為只有一份，它的 <code>alternate</code> 是 <code>null</code>，current 跟 workInProgress 兩棵樹用的也是同一個 fiber 物件。<code>createWorkInProgress</code> 的註解也寫了，第二份 fiber 是等到需要才建，「to avoid allocating extra objects for things that are never updated」。元件的 type 跟 key 沒變的話，React 就一直拿這兩個物件輪流用，不會建第三個。</p>
<h3>commit 時換掉的是什麼</h3>
<p>commit 裡依序有三件事跟這兩份 fiber 樹有關：</p>
<ol>
<li><strong>mutation</strong>：改真的 DOM，像 <code>setAttribute</code>、<code>appendChild</code>、<code>removeChild</code>。使用者會看到的變化都在這一步。</li>
<li><strong>換 current</strong>：<code>root.current = finishedWork</code>，workInProgress 變成 current。</li>
<li><strong>layout</strong>：執行 <code>useLayoutEffect</code>、<code>componentDidMount</code>。</li>
</ol>
<p>fiber 有兩份，DOM 卻只有一份，所以 mutation 沒有另一份 DOM 可以先改好再換上去，只能直接改頁面上的節點，例如改一個屬性，或加入、移除幾個節點。換 current 的時候 DOM 已經改好了，所以這一行不會讓畫面有任何變化。它影響的是下一次 render：React 會拿這次完成的版本當 current，用它上面的 props 跟新的 props 比較，而這次被換下來的舊版本，就成了下一次的 workInProgress。</p>
<p>這一行在 <a href="https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiberWorkLoop.js"><code>ReactFiberWorkLoop.js</code></a> 的 <code>flushMutationEffects</code> 最後面，<code>commitRoot</code> 會呼叫 <code>flushMutationEffects</code>：</p>

<p><code>finishedWork</code> 就是 workInProgress 那份。這一行排在 mutation 之後、layout 之前，所以 <code>componentWillUnmount</code> 讀到的 current 還是舊的版本，<code>useLayoutEffect</code> 跟 <code>componentDidMount</code> 讀到的 current 已經是新的版本。</p>
<h3>mount、update、delete 時的 alternate</h3>






























<table><thead><tr><th>情況</th><th>這個 fiber 在哪邊</th><th><code>alternate</code></th></tr></thead><tbody><tr><td>mount</td><td>只在 workInProgress</td><td><code>null</code></td></tr><tr><td>update，這次 render 有走到它</td><td>current 跟 workInProgress 各一份</td><td>兩份互指</td></tr><tr><td>update，它所在的 subtree 整個被跳過</td><td>current 跟 workInProgress 共用同一個物件</td><td>從沒走到過的話，一直是 <code>null</code></td></tr><tr><td>delete</td><td>只在 current</td><td>React 不替它建 workInProgress 的 fiber</td></tr></tbody></table>
<p>React 不是用把 <code>alternate</code> 設成 <code>null</code> 來表示刪除。要刪的節點不會有 workInProgress 的 fiber，React 把舊的 fiber 放進 parent 的 <code>deletions</code> 陣列，再替 parent 加上 <code>ChildDeletion</code> 這個 flag。commit 讀到這個陣列，就呼叫 <code>removeChild</code>。程式碼在 <a href="https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactChildFiber.js"><code>ReactChildFiber.js</code></a> 的 <code>deleteChild</code>，它只動了 parent 的 <code>deletions</code> 跟 <code>flags</code>，被刪的 child 的 <code>alternate</code> 沒有人碰。</p>
<h2>useState 的值存在哪裡</h2>
<p>function component 只是一個 function，跑完就回傳，裡面的區域變數也跟著消失。在元件裡寫 <code>let count = 0</code>，每次 render 都會重新變回 0。那 <code>useState</code> 的值是怎麼留到下一次 render 的？</p>
<p>它存在元件的 fiber 上，也就是 <code>memoizedState</code> 欄位。這個欄位指向一個 linked list，每呼叫一次 <code>useState</code>、<code>useRef</code>、<code>useEffect</code>，list 上就有一個節點。例如一個元件依序呼叫 <code>useState</code>、<code>useRef</code>、<code>useEffect</code>，<code>fiber.memoizedState</code> 就指向第一個節點（<code>useState</code> 的），它的 <code>next</code> 指向 <code>useRef</code> 的節點，再下一個是 <code>useEffect</code> 的。</p>
<p>上一節說過，元件的 fiber 有兩份輪流用。每次 render，<a href="https://github.com/react/react/blob/v19.3.1/packages/react-reconciler/src/ReactFiberHooks.js"><code>ReactFiberHooks.js</code></a> 的 <code>updateWorkInProgressHook</code> 會從 current 那份 fiber 照順序把 hook 節點一個一個複製到 workInProgress 那份，所以值會一直留下來。render 時每遇到一個 <code>useState</code>，React 就往 list 的下一個節點走，把裡面存的值交回來。</p>
<p>React 怎麼知道哪個節點屬於哪個 <code>useState</code> 呢？它不知道變數名稱，也就不知道哪個 <code>useState</code> 是 <code>name</code>、哪個是 <code>age</code>，只能數：第一次呼叫拿第一個節點，第二次呼叫拿第二個，依此類推。</p>
<p>hook 節點本身也沒有地方放名字。React 建 hook 節點的程式碼在 <code>ReactFiberHooks.js</code> 的 <code>mountWorkInProgressHook</code>：</p>

<h2>還有幾個問題</h2>
<h3>為什麼 <code>&#x3C;MyComponent /></code> 會 render，小寫的 <code>&#x3C;myComponent /></code> 不會？</h3>
<p>JSX 編譯器看第一個字母決定 <code>type</code> 放什麼：大寫開頭是一個變數，小寫開頭是一個字串。用 esbuild 0.25.10 編譯：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="js" data-theme="github-dark github-light"><code data-language="js" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">&#x3C;</span><span style="--shiki-dark:#85E89D;--shiki-light:#22863A">div</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> />          →  </span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">createElement</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">"div"</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">null</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">)          </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// 小寫：字串</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">&#x3C;</span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">MyComponent</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> />  →  </span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">createElement</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(MyComponent, </span><span style="--shiki-dark:#79B8FF;--shiki-light:#005CC5">null</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">)    </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// 大寫：變數</span></span>

<p><code>&#x3C;myComponent /></code> 看起來像元件，可是第一個字母小寫，編譯器就輸出字串 <code>"myComponent"</code>。React 收到 <code>type: "myComponent"</code>，把它當成 HTML tag，建出一個 <code>&#x3C;mycomponent></code>。叫做 <code>myComponent</code> 的 function 完全沒被呼叫。</p>
<p><a href="https://legacy.reactjs.org/docs/jsx-in-depth.html#user-defined-components-must-be-capitalized">JSX In Depth</a> 也寫到，大小寫是 JSX 編譯器的規則，React 只會收到編譯器已經決定好的 <code>type</code>。</p>
<h3>為什麼可以回傳 <code>null</code>，卻不能回傳一個 Component？</h3>
<p>元件回傳的東西要是 ReactNode。<code>null</code> 是 ReactNode，意思是這裡什麼都不 render。Component 是一個 function，function 不是 ReactNode，要寫成 <code>&#x3C;Comp /></code>，不能只寫 <code>Comp</code>。</p>
<p>在 React 19.3.1 裡寫 <code>return Comp</code>，畫面上什麼都沒有。development build 會印出「Functions are not valid as a React child. This may happen if you return Comp instead of <comp> from render. Or maybe you meant to call this function rather than return it.」，production build 什麼都不印。在 TypeScript 裡，把 function 指定給 <code>ReactNode</code> 型別的變數會報錯。</comp></p>
<h3>為什麼清單項目的 <code>key</code> 一換，state 就重設？</h3>
<p>render 時，React 用 <code>key</code> 把新的 element 對到現有的 fiber：</p>
<ul>
<li><strong>key 跟 type 都一樣</strong>：重用這個 fiber，它的 <code>memoizedState</code> 跟 DOM 節點都留著。</li>
<li><strong>key 不一樣</strong>：丟掉舊的 fiber，建一個 state 是空的新 fiber。</li>
</ul>
<p>拿陣列的 index 當 key 就會出問題：在最前面插入一列，每一列的 index 都往後移一位，React 會把錯的 fiber 配給錯的列。下面每一列都有一個 <code>useState('note for ' + label)</code>，在 B、C 前面插入 A：</p>




















<table><thead><tr><th>key 用什麼</th><th>插入前</th><th>在最前面插入 A 之後</th></tr></thead><tbody><tr><td>index</td><td><code>B / note for B</code>、<code>C / note for C</code></td><td><code>A / note for B</code>、<code>B / note for C</code>、<code>C / note for C</code></td></tr><tr><td>每列自己的 id</td><td><code>B / note for B</code>、<code>C / note for C</code></td><td><code>A / note for A</code>、<code>B / note for B</code>、<code>C / note for C</code></td></tr></tbody></table>
<p>用 index 當 key，A 拿到了 B 原本的 state，B 拿到 C 的，C 是新建的 fiber。</p>
<h2>整理</h2>
<ol>
<li>JSX 產生 <strong>ReactElement</strong>，它的 <code>type</code> 是字串，或是一個 Component。</li>
<li>render 時，React 替每個 element 建一個 fiber，或重用上一次的 fiber。<code>type</code> 是 Component 的話就呼叫它，拿到更多 element。</li>
<li>React 沿著 fiber 的 <code>child</code>、<code>sibling</code>、<code>return</code> 一個一個走，不用遞迴呼叫。</li>
<li><code>type</code> 是字串的 fiber，在 <code>completeWork</code> 裡建出 DOM 節點，接好 child，這時還不在頁面上。</li>
<li>commit 把這些 DOM 節點放進頁面，再把 <code>root.current</code> 換成新的版本。</li>
</ol>
