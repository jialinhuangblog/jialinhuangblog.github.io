ReactNode, ReactElement, Component, div: which live only in memory, and which becomes DOM

2026/04/21
reactinternalstypes

Writing React means meeting four names every day: ReactNode, ReactElement, Component, and HTML tag names like div. Early on it is easy to treat them as the same thing, since they all seem to be a piece of the screen. Yet returning <Comp /> renders, while returning Comp shows nothing; assigning a string to a variable typed ReactElement is a TypeScript error, while assigning it to ReactNode is fine.

So what is each of these names? Which ones exist only in JavaScript memory, and which one ends up as a DOM node in the browser?

render and commit

Every time React updates the screen, it works in two steps:

  1. render: React calls your component functions and works out what the screen should become. This step only handles JavaScript objects; the DOM on the page does not change.
  2. commit: React writes the changes that render worked out into the DOM on the page.

After commit, the browser still has to compute styles, lay out, and paint pixels. Those steps are in from setState to pixels.

What each name is

NameWhat it isWhere it exists
ReactNodeA TypeScript type, the widest one: any value React can renderOnly during type checking; gone once compiled to JavaScript
ReactElementA plain object made by JSX or createElement; main fields are type, props, keyJavaScript memory
ComponentA function or class that takes props and returns what to renderA function in JavaScript memory
divA string, the name of an HTML tagThe string is in JavaScript memory; React creates an HTMLDivElement for it during render and puts it on the page at commit

Of the four names, only div ends up matched to a DOM element on the page. Strings and numbers are ReactNodes too, though, and they become Text nodes. After <b>{42}</b> commits, the <b> on the page holds one Text node whose content is "42". null and false produce no DOM.

Component produces ReactElements

When you write <Button label="OK" />, Button has not been called yet. The line only produces an element with type: Button. React calls Button when render reaches that element. What it returns is usually a ReactElement, but it can also be a string or null; in any case it is a ReactNode.

There is no Button on the page. Only the <span> it returns becomes a <span> node on the page, at commit.

During render, React creates a fiber for each element. A fiber is React's own record object: what kind of component this is, what its props are, where its state lives, which children it has, which DOM node it maps to. No field on the fiber points at the element object; React copies only the element's type, key and props onto the fiber. In React 19 ref lives inside props, so it is copied too. The code is createFiberFromElement in ReactFiber.js. Elements are made fresh every render, while fibers stay for the next render.

Is the element garbage collected right after the copy?

After the copy, the element is not necessarily garbage collected right away, because a fiber may still reference it indirectly. Take <main><Greeting /></main>: the <Greeting /> element sits in the main element's props.children, and the main fiber stores the whole props object in memoizedProps. As long as some fiber's memoizedProps points at those props, <Greeting /> is not collected. The <div> that Greeting returns is different: it is not in any element's props, and the Greeting fiber has no field that stores the component's return value, so no fiber references it. If the tree above is passed straight to root.render, React stores it in memoizedState.element of the topmost fiber of the tree (the HostRoot printed below), so it stays too.

In the development build the fiber has a few more fields: React copies the element's _owner, _debugStack and _debugTask to the fiber's _debugOwner, _debugStack and _debugTask. Fibers in the production build have none of these fields.

When the DOM node is created, and when it enters the page

Wrap document.createElement and appendChild with logging, then mount an App with the React 19.3.1 production build. App has two children: A renders <section><p>a</p></section>, and B renders <div>b</div>. The logged order is:

  1. render App
  2. render A
  3. document.createElement('p')
  4. document.createElement('section')
  5. <p> appended under <section>; <section> is not on the page yet
  6. render B
  7. document.createElement('div')
  8. <section> appended under #root; only now is it on the page
  9. <div> appended under #root
  10. useLayoutEffect

<section> and <p> exist before B renders, which means they were created during render. As React walks the fibers, it passes each fiber twice: on the way down it calls the component, and on the way back up it finishes the fiber, a step called completeWork. A host component fiber creates its DOM node in completeWork and appends its children's DOM nodes to it; none of this is on the page yet (ReactFiberCompleteWork.js, the HostComponent branch calls createInstance and appendAllChildren). At commit, React puts the assembled DOM into #root. The way down and the way back up are covered in Inside React's work loop.

The whole path, in order:

  1. Greeting is a function in your source code; it is always there.
  2. JSX produces the element { type: Greeting }; the next render produces a new element.
  3. React creates a fiber for it. Hook values live on this fiber, which stays for the next render.
  4. React calls Greeting and gets the element { type: 'div' }. Once React copies its type, key and props onto the fiber, no fiber references it.
  5. React creates a fiber for it, which also stays for the next render.
  6. completeWork creates an HTMLDivElement for that fiber and stores it in stateNode; it is not on the page yet.
  7. Commit puts the HTMLDivElement on the page.

Why each fiber has two copies

React keeps two fiber trees at the same time: current is the version on screen, and workInProgress is the version this render is building. The fibers on both sides for the same <div> point their stateNode at the same HTMLDivElement: when createWorkInProgress builds a workInProgress fiber, it copies stateNode from current.

So when React changes things on workInProgress, does it change the DOM on screen?

No. stateNode is only a reference to the DOM node. Changing the DOM takes calls like setAttribute, appendChild, removeChild, and React only makes them in commit's mutation step (commitMutationEffectsOnFiber in ReactFiberCommitWork.js). What render changes are the fiber's own fields:

The only DOM render creates is for nodes added in this update, like the <section> in the previous section, and those are not attached to the page when they are created.

Then why not change the current fiber directly and save a copy? The React source does not give that reason. The comment in createWorkInProgress only says React needs at most two versions of the tree, so it keeps the other one around for reuse ("we know that we'll only ever need at most two versions of a tree").

The current code reads current in two places during render, and both treat it as the version left by the last commit:

  • beginWork calls current's memoizedProps oldProps and compares it with workInProgress's pendingProps. If oldProps and pendingProps are not the same object, it marks the fiber as updated (ReactFiberBeginWork.js).
  • An update wrapped in startTransition is called a transition, and its render can be dropped halfway because a more urgent update arrived. After dropping it, React calls createWorkInProgress(root.current, null) to copy a fresh workInProgress from current and starts over (prepareFreshStack in ReactFiberWorkLoop.js).

React does not prepare two copies of every fiber, though. An experiment in Chrome 156 with React 19.3.1: Counter updates its state each time; under it are a <b> showing the number and a Static wrapped in React.memo with no props, which renders an <i>. The comment in createWorkInProgress says the same: the second fiber is created only when needed, "to avoid allocating extra objects for things that are never updated".

What commit swaps

Three things in commit, in this order, involve the two fiber trees:

  1. mutation: change the real DOM, such as setAttribute, appendChild, removeChild. Every change the user will see happens here.
  2. swap current: root.current = finishedWork; workInProgress becomes current.
  3. layout: run useLayoutEffect and componentDidMount.

There are two copies of each fiber but only one DOM, so mutation has no second DOM to prepare and swap in. It changes the nodes on the page directly, for example changing an attribute, or adding and removing a few nodes. By the time current is swapped, the DOM is already updated, so this line changes nothing on screen. What it affects is the next render: React uses the version just finished as current and compares its props with the new ones, and the old version swapped out becomes the next workInProgress.

Where useState keeps its value

A function component is just a function. It runs, returns, and its local variables are gone. Write let count = 0 inside a component and it goes back to 0 every render. So how does a useState value survive until the next render?

It lives on the component's fiber, in the memoizedState field. That field points to a linked list, with one node for every call to useState, useRef, useEffect. For a component that calls useState, useRef, useEffect in that order, fiber.memoizedState points to the first node (the useState one), its next points to the useRef node, and the one after that is the useEffect node.

As the previous section showed, a component's fiber has two copies that take turns. On each render, the workInProgress fiber copies the hook nodes from the current fiber one by one, in order (updateWorkInProgressHook in ReactFiberHooks.js), so the values carry over. Each time render reaches a useState, React moves to the next node in the list and hands back what is stored there.

How does React know which node belongs to which useState? It does not know your variable names, so it cannot tell which useState is name and which is age. It can only count: the first call gets the first node, the second call gets the second, and so on.

The hook node has no place for a name either. React creates hook nodes in mountWorkInProgressHook in ReactFiberHooks.js:

No name, no key, no id; the only link from one hook to the next is next. Reading a component in React 19.3.1 that calls useState('Ann'), useRef, useEffect in order, all three nodes have exactly these five fields, and their memoizedState values are 'Ann', { current }, and an effect object.

So the order of hook calls has to be the same on every render. Try putting a hook inside an if:

First render, show is true. Two calls, two nodes:

CallNode it getsValue

2nd (age)node 220

Next render, show is false, and the if skips the first call. One call is left, and React still counts from the top:

age gets the first node and reads name's value. Every hook after the skipped one moves up a position and reads the wrong value. React expected two hooks and saw one, so it throws. Running this with the React 19.3.1 development build, age on the second render is indeed 'Ann', followed by "Rendered fewer hooks than expected. This may be caused by an accidental early return statement." That is why hooks go at the top level of a component: not inside if or for, and not after an early return (Rules of Hooks).

This also explains why changing key resets state. When a component's key changes, React creates a new fiber for it, with an empty memoizedState. Measured: a component whose count was raised to 2 stays at 2 when re-rendered with the same key, and goes back to 0 when the key changes from a to b.

A few more questions

Why does <MyComponent /> render, but lowercase <myComponent /> does not?

The JSX compiler looks at the first letter to decide what goes into type: uppercase means a variable, lowercase means a string. Compiled with esbuild 0.25.10:

<myComponent /> looks like a component, but its first letter is lowercase, so the compiler emits the string "myComponent". React gets type: "myComponent", treats it as an HTML tag, and creates a <mycomponent>. The function named myComponent is never called.

The browser does not recognize the tag, but it does not drop it either. Rendering <myComponent>child text</myComponent> with React 19.3.1 in Chrome 156 leaves an HTMLUnknownElement on the page, with display: inline, and the text inside still shows. The development build logs two errors in the console: one says the casing is wrong, the other says the browser does not recognize the <myComponent> tag and that a component name must start with an uppercase letter. The production build logs nothing.

Casing is the JSX compiler's rule; React only receives the type the compiler already decided (JSX In Depth).

Why can a component return null but not a Component?

What a component returns has to be a ReactNode. null is a ReactNode, meaning "render nothing here". A Component is a function, and a function is not a ReactNode. You need <Comp />, not just Comp.

In React 19.3.1, return Comp puts nothing on screen. The development build logs "Functions are not valid as a React child. This may happen if you return Comp instead of from render. Or maybe you meant to call this function rather than return it." The production build logs nothing. In TypeScript, assigning a function to a variable typed ReactNode is an error.

Why does changing a list item's key reset its state?

During render, React matches new elements to existing fibers by key:

  • Same key and type: reuse the fiber; its memoizedState and DOM node stay.
  • Different key: drop the old fiber and create a new one with empty state.

Using the array index as the key causes trouble: insert a row at the top, every index shifts by one, and React pairs the wrong fiber with the wrong row. Below, every row has a useState('note for ' + label), and A is inserted in front of B and C:

KeyBeforeAfter inserting A at the top

each row's own idB / note for B, C / note for CA / note for A, B / note for B, C / note for C

With index keys, A got B's old state, B got C's, and C is a newly created fiber.

Summary

  1. JSX produces a ReactElement, whose type is a string or a Component.
  2. During render, React creates a fiber for each element, or reuses the one from last time. If type is a Component, React calls it and gets more elements.
  3. React walks the fibers one at a time through child, sibling and return, without recursive calls.
  4. A fiber whose type is a string creates its DOM node in completeWork and attaches its children; it is not on the page yet.
  5. Commit puts those DOM nodes on the page, then swaps root.current to the new version.
