這個物件的格式來自 W3C 的 Navigation Timing Level 2（Working Draft，2026-09-01 這版），API 名字是 PerformanceNavigationTiming。下面 iframe 重畫的那張 Navigation Timing 原圖來自第一版 Level 1（W3C Recommendation，2012-12-17），圖檔在 spec 的 Processing Model 那節，API 是 performance.timing，MDN 已經標 deprecated。兩版的欄位名字大多一樣，差在起點怎麼算，還有 Level 2 少了幾個欄位，文末有對照。

domainLookupEnd − domainLookupStart = 74.2 − 0.9 = 73 ms，這是 DNS 花的時間。其他欄位也是這樣兩兩相減，每一對是一個階段的頭和尾。原圖的每個格子都在下面，包括這次是 0 的：

每個階段的 blocking issue

  • unload、redirect、App cache：這個站上一直是 0。unload 只有上一頁同源才有值，不同源是 0。redirect 是 0，因為 Chrome 115 起會在送出請求之前自己把 http:// 升成 https://，伺服器對 http:// 回的 301 沒被走到。
  • DNS：第一次查詢要 73 ms，之後答案留在作業系統的 resolver cache，換瀏覽器 profile 也清不掉，所以五次 cold start 只有第一次不是 0。
  • TCP：握手至少要一個 round trip，這台機器到伺服器 ping 是 42 到 54 ms，程式碼省不掉，只能用 CDN 讓端點近一點。表格裡的 152 ms 是例外：那次 TLS 做到一半，Chrome 換了憑證驗證器，把連線關掉重開，所以量到的是兩條連線。另外記下的 Chrome netlog（連線過程的紀錄）裡，單次握手是 46 到 68 ms。只有每次都開一個新的 Chrome 來量，才會遇到。
  • TLS：TLS 1.2 握手要兩個 round trip，1.3 只要一個；連線沒被重用也會慢。HTTP/1.1 預設會把連線留著，HTTP/2 和 HTTP/3 一條連線多工，所以 TLS 通常每個 origin 只做一次。
  • Request：伺服器在處理請求。靜態檔的話，TTFB 長通常是 CDN 沒有 cache；server render 的話，時間多半花在 render function。rendering strategy 影響的主要是這一段。
  • Response：HTML 太大，或沒壓縮。拿 encodedBodySize 跟 decodedBodySize 比就知道（transferSize 含 header，不能拿來比）。這裡 encodedBodySize 是 3772，解開是 14187，壓縮有開。
  • Parse：同一份 HTML，reload 只要 5 到 10 ms，cold start 卻要 198 到 424 ms，差的時間都在等 stylesheet。<body> 裡有 inline <script>，HTML spec 規定它要等 <head> 裡還沒載完的 stylesheet，parser 也跟著停。另外用一支會記下每個資源載入時間的腳本再跑五次 cold start，五次的 domInteractive 都在最後一個 stylesheet 載完之後 1 到 29 ms 出現。三個 stylesheet 裡有一個是跨站的 fonts.googleapis.com，光它就要多一次 DNS 加一條新連線，57 到 138 ms。所以這個站的 Parse 要變快，得把 stylesheet inline、preload，或拿掉跨站那個來源。
  • Deferred scripts：<script defer> 在 parse 完、DOMContentLoaded 之前執行，DOMContentLoaded 會等它。這個站的 chunk 用 async，不會讓 DOMContentLoaded 延後，所以這裡是 0。要是頁面寫的是 <script defer src="app.js">，而 app.js 執行要 300 ms，這 300 ms 就會出現在 Deferred scripts。
  • Subresources：load 要等圖片、script、iframe 到齊。字型 MDN 沒列，但也算：一個只有字型慢 2 秒的測試頁，load 晚了 2 秒。文章頁 from-setstate-to-pixels 嵌了一個跨站 iframe，用記錄 resource timing 的那支腳本跑五次，這一段是 487 到 596 ms，幾乎都在等那個 iframe：它載完之後 0.2 到 1.7 ms，domComplete 就到了。

五次 cold start，加一次 reload

每次 cold start 都是新開的 headless Chrome 153，新 profile、新 disk cache，導航一次，台北時間下午 12 點到 3 點。reload 是同一個瀏覽器載完首頁後用 DevTools protocol 的 Page.reload 再載一次，entry 的 type 是 reload。文章頁是 /v2/from-setstate-to-pixels。

量測腳本

Node 22、macOS、Chrome 裝在預設路徑。腳本在 load 之後把 entry 讀出來。reload 那欄用的是同一支腳本加一段：第一次 load 之後送 Page.reload，再讀一次 entry。stylesheet 的時間是另一支同型的腳本，多 dump 一份 performance.getEntriesByType('resource')。字型的測試是一個本機頁面，唯一慢的資源是一個延遲 2 秒的字型檔。

Level 2 拿掉了哪些 Level 1 的時間戳

  • navigationStart：Level 2 換了時鐘。Level 1 的值是從 1970 年起算的絕對毫秒，Level 2 改用從 time origin 起算的 DOMHighResTimeStamp，起點恆為 0，理由是絕對時鐘會被系統調整倒退、精度只到毫秒。navigationStart 變成 startTime 的 0。
  • domLoading：各家瀏覽器建立 Document 的時間點不同，Chrome 在 response 開始前，IE 在 response 開始時，Firefox 要先 buffer 一段，量到的是實作細節。2015 年 issue #13 提出移除，spec 加了 deprecation note。最接近的值是 responseEnd。
  • Prompt for unload：發生在 navigationStart 之前，Level 1 把起點定義在「問完要不要離開上一頁之後」，兩版都沒有它的時間戳，圖上畫它只是標出起點前面的動作。

startTime 到 fetchStart 那段空檔沒有名字。unload 跟 redirect 有發生的話會落在這段，這次都是 0；redirectStart 是 0 表示沒有 redirect，不是 redirect 花了 0 ms。
