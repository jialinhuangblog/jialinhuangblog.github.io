從 setState 到畫面上的像素：React 跟瀏覽器各做了哪幾步

2026/04/14
frontendreactbrowserrendering

呼叫 setState 的那一行，螢幕上什麼都還沒變。這一行只是排了一次重新 render。React 會在之後跑這次 render、把結果寫進 DOM，接著瀏覽器還要把 DOM 變成像素，畫面才會變。

拿一個搜尋框當例子吧。使用者打了一個「a」，輸入框要顯示「a」，下面的結果清單也要跟著篩選。從按下按鍵到這些像素出現，中間有九個步驟。前三個跟最後一個是 React 的，中間五個是瀏覽器的；就算不用任何框架，瀏覽器也一樣要做這五步。

setState
  → render           ┐
  → commit           │  React
  → useLayoutEffect  ┘
  → Style Recalc     ┐
  → Render Tree      │
  → Layout           │  瀏覽器
  → Paint            │
  → Composite        ┘
  → useEffect           React（通常在這裡，例外寫在第九節）

一、render 階段

React 重新呼叫一次元件的 function。這個 function 回傳一棵由普通 JavaScript 物件組成的新樹，一般叫它 Virtual DOM。瀏覽器碰不到這棵樹，它只是記憶體裡的資料。

React 拿新樹跟上一次的樹比對，比對時照兩條規則：

  • 同一個位置的元素類型變了，例如 <div> 變成 <section>，就把舊的整棵子樹拆掉，重新建一棵。
  • 清單裡的項目，React 靠 key 這個 prop 認出前後兩次 render 裡哪個項目是哪個。

React 18 開始，這個階段可以暫停、也可以重來。用 startTransition 包起來的更新，priority 會被標低。照 react.dev 的說明，如果這次 render 做到一半，來了一個比較急的更新，React 會丟掉做到一半的結果，先處理急的那個，之後再從頭跑一次 priority 低的那個 render。因為這時候 DOM 一個字都還沒動，丟掉做到一半的結果也不會出事。

沒有 startTransition 的話，按鍵觸發的更新會一口氣同步 render 完，清單 render 完之前，輸入框都會卡著。

二、commit 階段

比對的結果出來了。以搜尋框為例，輸入框的值要改成「a」，清單要拿掉十幾個項目。React 把這些變更寫進真正的 DOM。

這個階段不能中斷。DOM 一旦開始改，中途停下來的話，畫面上就會出現改到一半的頁面，所以 React 會一口氣做完。

在 ReactFiberCommitWork.js 裡，React 把 commit 分成三段：

  • Before mutation：在 DOM 改動之前，先記下現在的狀態。class 元件的 getSnapshotBeforeUpdate 在這裡跑，常拿來記下捲動位置。
  • Mutation：真的寫 DOM，insertBefore、removeChild、setAttribute 都在這段。舊的 ref 在這段解除，上一次 useLayoutEffect 的 cleanup 也在這段跑。
  • Layout：接上新的 ref，然後執行 useLayoutEffect。所以常聽到的「useLayoutEffect 在 commit 之後執行」，實際上是在這三段的最後一段裡執行。

三、useLayoutEffect

瀏覽器畫出任何東西之前，React 會同步執行 useLayoutEffect。

拿 tooltip 來看為什麼需要這一步。tooltip 平常放在按鈕下方，如果下方空間不夠，就要改放到上方。可是 tooltip 要先放進 DOM、量過高度，才知道下方夠不夠放。要量尺寸（getBoundingClientRect、offsetHeight、捲動位置）、再趕在使用者看到之前把 DOM 改對，useLayoutEffect 是最後的機會。react.dev 提到，如果改在 useEffect 裡量，再用 setState 把 tooltip 移過去，瀏覽器可能已經把放錯位置的 tooltip 畫出來了，使用者會看到它跳一下。

點一下才打開的 tooltip 也會跳。在 headless Chrome 156 上用一個 tooltip 測試：點按鈕打開，先畫在按鈕下方，useEffect 量完高度再 setState 把它翻到上方。React 18.3.1 跟 19.3.1 各跑 10 次，10 次都是先在下方畫出一個 frame，才跳到上方。改用 useLayoutEffect，10 次都直接畫在上方。

點擊觸發的更新，useEffect 其實會在 paint 之前執行，第九節有實測。那 tooltip 為什麼還會跳？effect 在 paint 之前跑完，不代表 effect 裡 setState 排的那次 render 也會在 paint 之前做完。React 的更新分 priority，點擊觸發的更新 priority 最高，React 會馬上 render。effect 執行時排的更新就不一樣了。照 React 18.3.1 跟 19.3.1 的原始碼，點擊之後在 effect 裡排的更新，priority 是 default（DefaultEventPriority），比點擊低。default priority 的更新 React 不馬上做，而是交給它的 Scheduler，在另一個 task 裡跑。React 沒有保證這個 task 會排在瀏覽器下一次 paint 之前。上面的測試 10 次都是 paint 先，所以 tooltip 第一個畫出來的 frame 還在下方。

讀 layout 是同步的，會卡住 main thread，會強制 layout 的屬性清單裡的每一個都是這樣。getBoundingClientRect() 執行的那一行，瀏覽器就在算 style 跟 layout，沒有 Promise，也沒有 await 提醒。不過只有 layout 是 dirty（過期、需要重算）的時候，讀取才會觸發重算，而寫入會讓它變成 dirty。讀一次就是算一輪：

讀取 → style recalc → layout

讀跟寫交錯的話，每寫一次 layout 就又過期，於是同樣這一輪會一直重跑，這叫 layout thrashing：

讀取 → style recalc → layout → 寫入 → style recalc → layout → 寫入 → style recalc → layout

解法是先把要讀的全部讀完，再一次寫。如果只是要量尺寸，ResizeObserver、IntersectionObserver 會非同步回報結果，不會強制 layout。

commit 剛寫過 DOM，所以 useLayoutEffect 開始的時候 layout 一定是 dirty 的。effect 裡第一次讀 layout，例如呼叫 getBoundingClientRect()，瀏覽器就當場把第四到第六節的事做完，也就是 Style Recalc、Render Tree、Layout。三步都做完，這個呼叫才回傳，effect 才接著往下跑。在 headless Chrome 156 錄的 trace 裡，寫完 DOM 之後呼叫一次 getBoundingClientRect()，從呼叫到回傳之間有 16 個事件，一層包一層，跑三次都是同樣這 16 個。最外層是 Document::UpdateStyleAndLayout，它底下依序出現 Document::recalcStyle、Document::rebuildLayoutTree 跟 Layout，正好對到這三步。剩下的事件是這三步外面再包的一層，或是它們裡面更細的步驟，例如 Layout 裡面的 LocalFrameView::performLayout。effect 之後如果沒有再寫 DOM，等到要 paint 的時候，瀏覽器不用再算一次 style 跟 layout，直接用 effect 裡算好的。

useLayoutEffect 會卡住 paint，所以裡面的程式要快。

接下來的步驟由瀏覽器做。

嚴格說起來的 CRP。 從 Style Recalc 到 Composite 這一整段，很常被叫成 Critical Rendering Path（關鍵渲染路徑）。不過照 web.dev 的定義，CRP 指的是頁面第一次 render 之前的那段路。之後每次 setState 也走同樣這幾步，只是那已經不叫 CRP 了，因為 CRP 關心的是第一次 render 要等哪些資源（HTML、CSS、會卡住 parser 的 script）。

四、Style Recalc

DOM 變了，瀏覽器就要重新算出受影響的每個元素長什麼樣子。照 CSS 規格 CSS Cascade 5 §4 的講法，一個元素上的一個屬性值，從寫在 CSS 裡到出現在螢幕上，要經過六種形式：

declared → cascaded → specified → computed → used → actual

Style Recalc 負責前四種，也就是下面這幾步。used 跟 actual 要到 Layout 跟 Paint 才會算完。

收集。 瀏覽器從三個地方收集 style：瀏覽器自己內建的預設值（User Agent）、使用者在瀏覽器裡設定的偏好（User），還有網站自己的 stylesheet（Author）。

cascade。 收集到的宣告會互相競爭。發生衝突時，瀏覽器照 CSS Cascade 5 §6.1 列的順序決定誰贏，越上面越優先：

  1. Transitions
  2. User Agent + !important
  3. User + !important
  4. Author + !important
  5. Animations
  6. Author
  7. User
  8. User Agent

來源跟 !important 都一樣的時候，寫在 style attribute 裡的宣告會贏過任何 stylesheet 裡的規則。接著比 cascade layer（@layer），再來才比 specificity：ID 贏過 class，class 贏過元素名稱。specificity 也一樣的話，寫在後面的宣告贏。下面這張參考表列了一些 selector 的分數。它把 style attribute 跟 !important 也放在同一套分數上，寫成 1-0-0-0 跟 1-0-0-0-0；這只是幫忙記的寫法，規格裡這兩個都不算 specificity。

補預設值。 沒有任何宣告的屬性還是需要一個值，補法有兩種。
跟文字有關的屬性從 parent 繼承，例如 color、font-size、font-family。
跟盒子有關的屬性用規格寫好的初始值，例如 border-style 是 none、margin 是 0。
這兩條路都可以用 inherit、initial、unset 或 revert 改掉。

換算（不需要尺寸的那一半）。 換算分兩次，這是第一次，另一次在第六節。不需要知道幾何尺寸的值，在這裡都換成具體的值。em 照元素自己的字級換算，例如字級 20px 的元素寫 padding: 1em，就是 20px；只有寫在 font-size 裡的 em 才照 parent 的字級算。rem 照根元素的字級算，bold 變成 700，相對路徑變成完整的 URL。至於要知道盒子多大才算得出來的值，像 50%、auto、min-content，這時還沒辦法算，要等 Layout。

這一步的產出是每個節點的 computed style。這裡說的是 computed，width: 50% 這時還是 50%，還不是像素。從 JavaScript 也能確認這一點。一個元素設成 display: none，沒有盒子、也不做 layout，getComputedStyle(el).width 回傳的是 50%。把它顯示出來，同一個呼叫就回傳 400px，因為元素有做 layout 的時候，這個 API 回報的是 Layout 之後的值。

五、Render Tree

DOM 跟 computed style 合起來，就是 Render Tree（Chrome 叫它 layout tree）。它大致就是掛上 style 的 DOM，不過拿掉了完全不佔空間的節點，又多了幾個 DOM 裡沒有的節點。

display: none：不放進來。樹裡沒有這個節點，layout 也不留位置。
visibility: hidden：放進來。位置照留，只是不畫像素。
<title>、<head>、<script>：不放進來，因為瀏覽器內建的 stylesheet 把它們設成 display: none。
有 content 的 ::before、::after：放進來。Inside look, part 3 提到，它們雖然不是 DOM 節點，也會放進 layout tree。

六、Layout / Reflow

瀏覽器走過 Render Tree，算出每個元素的幾何資訊：位置、寬、高。這一步也叫 Reflow。回到搜尋框，清單少了十幾個項目，高度變矮，清單下面的東西全部往上移，這些新位置都在這一步算出來。CSS 有兩步在這裡完成：

排版。 瀏覽器把元素分進不同的 formatting context，像 block、inline、flex、grid。每一種 context 都有自己的規則，決定裡面的子元素怎麼堆、怎麼流動。

換算（需要尺寸的那一半）。 第二次換算。50%、auto、min-content 要有一個盒子當基準才能算，現在盒子有了，就可以算出來。Style Recalc 給的是 computed value（50%），Layout 把它變成 used value（在 800px 寬的 parent 裡就是 400px）。

Layout 很花時間。插入一個 DOM 節點會觸發它，改 font-size 會觸發它，調整視窗大小也會觸發它。動畫進行中去讀 getBoundingClientRect，可能會讓它一再重跑。

所以 useLayoutEffect 才排在第三節那個位置：DOM 剛寫完、還沒 paint。在那裡讀尺寸，頂多強制一次 layout，而且在那裡做的修正，會趕在使用者看到第一個畫面之前生效。

七、Paint

Paint 這一步其實還沒填像素。Inside look, part 3 寫到，在 Chrome 裡，main thread 走過 layout tree，寫下一份份繪製指令，叫 paint record，內容像是「先畫背景，再畫文字，再畫邊框」。之後 raster thread 才照這些指令，一塊一塊（tile）把像素畫出來。

瀏覽器會把頁面分成幾個 layer，可以想成分開畫、最後再疊起來的幾張圖層。大部分元素都跟周圍的元素共用一個 layer，元素的 background、color、box-shadow、border 也都畫在那個 layer 上。只有少數元素會獨立成一個 layer，例如設了 will-change: transform 的元素。

used → actual。 六種形式的最後一種。有些 used value 沒辦法照原樣畫出來。CSS Cascade 5 §4.6 舉的例子是：裝置可能只能畫整數像素寬的邊框，遇到帶小數的邊框寬度，瀏覽器就取一個近似值。（這跟 CSS 的 transform: translate() 無關，那個在下一節。）

paint record 是在 main thread 上產生的，跟執行 JavaScript 的是同一條 thread。

八、Composite

compositor thread 把這些 layer 排好位置，組成一個 frame 交給 GPU，由 GPU 畫到螢幕上。

transform 跟 opacity 就是在這一步處理的。在 headless Chrome 156 上錄一秒的 trace，量三次：CSS 動畫只改 transform 的時候，main thread 上一次 style recalc、layout 或 paint 都沒有。同樣的動畫改成動 left 或 width，每個 frame 都要跑一次 layout 跟 paint，一秒下來大約 60 次（57 到 61 次）。改用 JavaScript 每個 frame 去設 transform，style recalc 還是每個 frame 都跑，但 layout 跟 paint 都沒有跑。

Inside look, part 3 提到，compositor thread 不用等 JavaScript 或 style 計算，所以 main thread 在忙的時候，transform 跟 opacity 的 CSS 動畫還是會繼續動。left、top、width 的動畫就不一樣了，每個 frame 都要在 main thread 上跑 layout 跟 paint；JavaScript 一直佔著 main thread 的話，frame 就會掉，動畫看起來一頓一頓的。

九、useEffect

useEffect 通常在瀏覽器 paint 之後才執行。React 文件的用詞是「generally」，例外有三種：

  • click、keydown 這類離散的使用者輸入。 React 18 升級指南寫到，React 18 起，這類更新的 useEffect 會在 paint 之前執行。在 headless Chrome 156 上點一下按鈕之後，React 18.3.1 跟 19.3.1 都在那個 frame paint 之前就跑了 useEffect。effect 本身是在 paint 之前跑沒錯，可是它裡面 setState 再排的 render，在第三節的 tooltip 測試裡 10 次都落到 paint 之後。
  • 其他來源，像 timer 或網路回應。 React 一般會先讓瀏覽器 paint，但沒有保證。同樣在 Chrome 156 上，setTimeout 觸發的更新，React 19.3.1 在 paint 之後才跑 useEffect；React 18.3.1 則是三次都在下一個 frame 之前就跑了。
  • 在 useLayoutEffect 裡 setState。 照 react.dev 的說明，這時 React 會立刻把還沒跑的 effect 全部跑完，useEffect 也包括在內。

所以 useEffect 在 paint 之前或之後跑都有可能，就算在 paint 之前跑，它裡面 setState 改的畫面也可能趕不上這次 paint。它適合放早一點、晚一點都沒差的事：抓資料、訂閱、掛 event listener。以搜尋框來說，就是向 server 要搜尋結果的那個請求。一定要在 paint 之前做的事放 useLayoutEffect。react.dev 寫到，一定要等 paint 之後才做的事，例如 alert()，要再包一層 setTimeout。假設搜尋框旁邊有一個「清除」按鈕，按下去會清空結果，再跳一個 alert 說已清除。這是 click 觸發的更新，所以 useEffect 可能在 paint 之前就跑。如果在裡面直接呼叫 alert()，舊的清單還留在畫面上，對話框就先跳出來了。而且 alert 會停住 main thread，使用者按下確定之前，清單都不會從畫面上消失：

setTimeout 把 alert 排到下一個 task，瀏覽器通常會先把這個 frame 畫完再執行它。

「render」這個字的兩個意思

前端講「render」有兩個意思，混在一起用的話，討論效能時很容易各講各的。

名詞意思
React 的 render 階段執行元件的 function，產生 Virtual DOM。瀏覽器沒有參與。
瀏覽器的 Render TreeDOM 加上 CSSOM 合起來的結果，從 React 在 commit 階段寫好的真實 DOM 建出來。

React 的 render 階段產生的是 JavaScript 物件，瀏覽器的 Render Tree 是從真的 DOM 節點建出來的，兩者沒有重疊。同一次更新裡，React 會先做完 render 跟 commit，瀏覽器才用新的 DOM 建 Render Tree。transition 的 render 可能做到一半就暫停，這段期間瀏覽器照樣畫出 frame，畫的是舊的 DOM。

從開啟頁面到 app 跑起來

CSS 慢，React 會不會也跟著晚開始呢？React 的 bundle 用 defer 或 type="module" 載入的話會，CSS 晚 1.5 秒到，React 就晚 1.5 秒才開始跑。用 async 載入的話不會，script 下載完就執行，不等 CSS。Vite 7.3.7 vite build 出來的 index.html 用的是 type="module"，這個網站用 Next.js 15.5.12 App Router build 出來的頁面則是 async。

在 headless Chrome 156 上可以這樣驗證：讓 server 故意晚 1.5 秒才回 stylesheet，script 檔則馬上回，然後記下 script 在第幾 ms 開始執行，以及第一個畫面（first contentful paint）在第幾 ms 畫出來。script 早就下載好了，如果它還是拖到 1.5 秒才執行，就代表它在等 CSS。每種頁面各跑三次，defer 跟 type="module" 另外把 script 移到 <link> 前面，再跑三次：

defer 跟 type="module" 的 script 寫在 <link> 前面或後面，結果都一樣。照 HTML 規格的 "The end" 這一節，parse 完之後，只要文件裡還有 stylesheet 沒下載完，defer 的 script 就先等，等 stylesheet 都到了才執行。就算 stylesheet 寫在 script 後面，只要 parser 讀到了，defer 的 script 也一樣要等它。async 的 script 不走這段流程，所以不用等。

不過 async 只讓 React 的程式早一點開始跑。script 在 8 到 11 ms 就執行了，可是 stylesheet 還沒到，瀏覽器就不會把畫面畫出來。表格最後一欄是實測結果：用 async 的頁面，第一個畫面也要到 1520 到 1532 ms 才出現，跟 defer 差不多。

      │  Style Recalc     cascade、specificity、換算     │
      │  Render Tree      DOM + computed style           │
      │  Layout / Reflow  幾何：位置、尺寸               │
      │  Paint            每個 layer 的 paint record     │
      │  Composite        layer → GPU → 螢幕             │
      │  useEffect        side effect（點擊觸發的更新    │
      │                   會在 paint 之前跑）            │
      └────────────────────────┬─────────────────────────┘
                               │ 任何 setState
                               └──► 回到 render 階段

三個 paint 指標。 上面頁面載入那段路的終點是 FCP（First Contentful Paint），也就是 DOM 裡的文字或圖片第一次畫出來的時間。旁邊還有兩個相關的指標。Paint Timing 定義的 FP（First Paint）是任何像素第一次畫出來的時間，畫了一個非預設的背景色也算。照 web.dev 的說明，LCP（Largest Contentful Paint）是視窗裡最大的那張圖片、那段文字或那支影片畫出來的時間。如果最大的元素是圖片，LCP 就要等那張圖下載完。

只要 app 還開著，這個迴圈就會一直跑。下面這張時間軸把同一個迴圈攤開，可以對照這九個步驟分別落在哪些 process 跟 thread 上：

  • Houdini APIs，MDN。Houdini 讓網頁開發者能介入 CSS 引擎內部的步驟。Paint、Layout、Animation 三種 Worklet 原本設計成各自接進上面 pipeline 的其中一步，不過正式上線的只有 Paint Worklet，而且只有 Chrome 跟 Edge 支援。Houdini 的其他部分，例如 @property，Firefox 跟 Safari 也能用。
