kernel 有漏洞的時候，container 之間靠什麼隔開

k8scontainersecurity

同一台 node 上的 container，用的是同一個 host kernel。kernel 有漏洞的時候，任何一個 container 都可能利用它控制整台機器，連帶碰到其他 Pod。

2022 年的 CVE-2022-0185 就是這種漏洞。在 kernel 修好之前，有三種做法：

做法做了什麼碰到 kernel 漏洞時
seccomp限制 container 能呼叫哪些 syscall漏洞剛好在被禁止的 syscall 裡才有用
gVisorcontainer 的 syscall 交給 gVisor 自己的 kernel 處理syscall 進不到 host 的 kernel
Kata Containers每個 Pod 跑在自己的小 VM 裡syscall 進的是 VM 自己的 kernel

所以如果 node 上跑的是不完全信任的程式，例如好幾個客戶共用一台機器，光靠 seccomp 不夠。要讓 container 碰不到 host 的 kernel，就得用 gVisor 或 Kata。

另外，把 host 的 user.max_user_namespaces 設成 0，container 就開不了 user namespace，CVE-2022-0185 這種要先開 user namespace 的攻擊會在第一步失敗（下面 CVE 那節有說明）。但下一個漏洞不一定需要 user namespace，所以這個設定跟 seccomp 一樣，只對某一類攻擊有效。

程式讀一個檔案時，kernel 做了什麼

kernel 是作業系統最底層的程式。它管理硬碟、記憶體、網路，也決定每個程式能做什麼。一般程式不能直接碰硬體，要做事都得請 kernel 代勞，這個動作叫 syscall（system call）。

在 CLI 下 cat notes.txt，kernel 分解步驟做了：

  1. openat：打開 notes.txt
  2. read：讀出檔案內容
  3. write：把內容印到螢幕上

這些 syscall 由 cat 發出，每一個都由 kernel 執行。所以 kernel 的程式碼有 bug 的話，任何能發出對應 syscall 的程式都可能觸發它。

container 沒有自己的 kernel

VM 是用軟體模擬出一整台電腦，有自己的 kernel。container 不一樣。runc 是實際建立 container 的程式，也是 Kubernetes 最常見的預設。用 runc 跑的 container 只是 host 上的一般 process，用的就是 host 的 kernel。

container 看起來像一台獨立的機器，是因為 host 的 kernel 決定了它的邊界：

  • namespace 決定它能看到什麼。在 container 裡跑 ps，只會列出這個 container 自己的 process。
  • cgroup 決定它能用多少 CPU 跟記憶體。

邊界是 kernel 決定的，而所有 container 的 syscall 都進同一個 kernel。kernel 本身有漏洞的話，container 裡的程式就可能透過 syscall 把邊界整個繞過去。

CVE-2022-0185

CVE-2022-0185 是 2022 年 1 月公開的 Linux kernel 漏洞，影響 5.1 起的 kernel，5.4.173、5.10.93、5.15.16、5.16.2 這幾版修掉了。kernel 裡處理掛載參數的 legacy_parse_param 收到 4095 bytes 以上的參數時，會寫到記憶體裡不該寫的地方，攻擊者能靠它變成 root（CrowdStrike 的分析）。

從 container 裡攻擊分三步：

  1. 呼叫 unshare 開一個新的 user namespace。kernel 會把程式當成這個 namespace 裡的 root，給它 CAP_SYS_ADMIN，也就是掛載檔案系統需要的權限。一般的 container 本來沒有這個權限。
  2. 有了 CAP_SYS_ADMIN，就能呼叫 fsconfig，塞進 4095 bytes 以上的參數，觸發漏洞。
  3. 改寫 kernel 的記憶體，取得整台 host 的 root。

如果 Pod 套了 seccomp（Kubernetes 預設沒套）、runc 從預設的 pivot_root 改用 chroot 切換根目錄，或 host 把 user.max_user_namespaces 設成 0，第 1 步就會失敗。

最直接的解法是升級 kernel。但下一個漏洞還會出現，修好之前要靠下面三種做法。

seccomp：限制能呼叫的 syscall

seccomp 是 kernel 的功能，替程式設一份 syscall 允許清單，清單外的一律拒絕。Kubernetes 在 node 上請 containerd 或 CRI-O 建立 container，兩者都附了預設清單，Pod 用 RuntimeDefault 指定：

CrowdStrike 加上這段再試一次，第 1 步的 unshare 直接失敗，回的是「Operation not permitted」，攻擊停在第一步。

但 Kubernetes 不會自動套用這份清單。Pod 沒寫 seccompProfile 的話就是 Unconfined，什麼都不擋。要讓所有 Pod 預設套用，得在每個 node 的 kubelet（node 上負責啟動 Pod 的 Kubernetes 程式）加上 --seccomp-default 這個 flag，它從 Kubernetes 1.27 起是 stable（Kubernetes seccomp 文件）。

seccomp 也有極限。清單一定會放行 read 這類每個程式都要用的 syscall。下一個漏洞要是出在這種 syscall 裡，seccomp 就沒用，因為放行的 syscall 照樣進 host 的 kernel。

gVisor：在中間多放一個 kernel

gVisor 是 Google 的專案，它在 container 跟 host kernel 之間多放了一個 kernel，叫 Sentry。Sentry 用 Go 寫，在 host 上就是一個普通的 process。container 裡的程式發出的 syscall 會送到 Sentry，由 Sentry 自己的程式碼處理。gVisor 的文件寫的是「gVisor never passes through any system call to the host」（gVisor architecture）。

一般 container：程式 → host kernel
gVisor：        程式 → Sentry → host kernel（只有 Sentry 自己要用的少數呼叫）

套回 CVE-2022-0185，unshare 跟 fsconfig 都由 Sentry 處理，Sentry 沒實作的就回錯誤。兩種情況都不會進到 host 的 kernel，有漏洞的 legacy_parse_param 也就不會被執行。

Sentry 自己也是 process，還是得請 host 的 kernel 做一些事，例如計時、處理 signal。但這些請求是 Sentry 為了自己的工作發的，container 裡的程式沒辦法決定它要呼叫哪個 syscall、帶什麼參數（gVisor security）。

讀寫檔案原本要經過另一個叫 Gofer 的 process，Sentry 不能自己開 host 上的檔案，要請 Gofer 代開。2023 年 6 月起，gVisor 預設改用 directfs，讓 Sentry 直接開 container 裡的檔案，讀寫比較快。不過這樣 Sentry 在 host 上需要的權限也變大了，gVisor 在設定說明裡也寫著「Sentry runs with higher privileges」（gVisor 公告）。

gVisor 的限制：

  • Sentry 沒實作的 kernel 功能，程式就用不到。
  • syscall 都要先經過 Sentry，所以 syscall 很頻繁、每次只做一點事的程式會明顯變慢，官方舉的例子是 Redis 的小操作。網路跟檔案 I/O 目前也偏慢，官方說主要是實作還需要改進（gVisor performance）。

Kata Containers：每個 Pod 一台小 VM

Kata Containers 替每個 Pod 開一台輕量的 VM，Pod 裡的 container 都在裡面跑。VM 有自己的 kernel，叫 guest kernel。在 host 上負責開 VM 的程式叫 hypervisor，Kata 支援 QEMU、Cloud Hypervisor 等好幾種（Kata architecture）。

一般 container：程式 → host kernel
Kata：          程式 → guest kernel（這個 Pod 自己的）→ hypervisor → host kernel

套回 CVE-2022-0185，unshare 跟 fsconfig 進的是這個 Pod 自己的 guest kernel。就算 guest kernel 也有這個漏洞，攻擊者拿到的也只是這台 VM，host 跟其他 Pod 還在 VM 外面。要再往外，得另外找到 hypervisor 的漏洞。Kata 的文件把 VM 這一層稱為「second layer of defence」，也就是第二道防線。

Kata 的限制是每個 Pod 都要多跑一個 kernel，node 上也得裝好 hypervisor。

三種做法比一比

程式的 syscall 由誰處理想利用 host kernel 的漏洞，攻擊者得先過哪一關
runc（預設）host kernel沒有
runc 加 seccomphost kernel，只放行清單裡的 syscall漏洞得剛好在清單放行的 syscall 裡
gVisorSentry先攻破 Sentry，再利用 Sentry 能用的那一小組 host syscall（預設開了 directfs，所以也包括開啟 container 裡的檔案）
Kata這個 Pod 的 guest kernel先控制 guest kernel，再突破 hypervisor

我沒找到在相同條件下比較這幾種做法安全性的資料，所以這張表不排名次。gVisor 的文件提到，VM 一樣有可以攻擊的地方。VM 裡的程式用到網卡、硬碟時，是 hypervisor 那一側的程式在模擬這些裝置，這段程式有漏洞的話，攻擊者一樣能從 VM 碰到 host。gVisor 的文件據此提醒，改用 VM 不代表就比 gVisor 安全。

在 Kubernetes 裡改用 gVisor 或 Kata

containerd 不會直接呼叫 runc。它先啟動一個叫 shim 的小程式，一般 container 用的是 containerd-shim-runc-v2，由 shim 去呼叫 runc，之後 shim 會留下來回報 container 的狀態。細節寫在〈Inside containerd: How shim and runc Actually Work〉。

gVisor 跟 Kata 都附了自己的 shim：

  • gVisor 的是 containerd-shim-runsc-v1，它再去呼叫 runsc，也就是 gVisor 用來取代 runc、負責啟動 Sentry 的程式。
  • Kata 的是 containerd-shim-kata-v2，它本身就是 Kata 的 runtime，直接叫 hypervisor 開 VM。

所以 node 上要先裝好新的 shim，gVisor 還要另外裝 runsc。裝好之後，以 gVisor 為例，照它的 containerd quick start，設定分三步。

  1. 在 containerd 的設定檔加一個 runtime handler，也就是替「用 gVisor 跑」這個選項取一個名字，這裡叫 runsc。底下 runtime_type = "io.containerd.runsc.v1" 這一行指定要用的 shim，containerd 照命名規則把它對應到 containerd-shim-runsc-v1 這個執行檔。

  2. 建一個 RuntimeClass。RuntimeClass 是 Kubernetes 的一種設定，把一個名字（這裡叫 gvisor）對到 node 上的 handler（runsc）。

  3. 在 Pod spec 裡用 runtimeClassName 指定這個 RuntimeClass。

image 不用換，Pod spec 只多了 runtimeClassName 這一行。沒寫 runtimeClassName 的 Pod，Kubernetes 會用 node 預設的 handler，照原本的方式交給 runc 跑（K8s RuntimeClass）。
