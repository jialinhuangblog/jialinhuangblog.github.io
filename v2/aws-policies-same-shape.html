AWS has a dozen policies. They're all one shape.

in 4 hours
awsiamsecuritycloud

AWS keeps inventing policies. S3 bucket policy, SQS queue policy, SNS topic policy, Lambda function policy, KMS key policy, API Gateway resource policy, IAM role trust policy. It looks like a dozen things to learn.

It's one JSON shape, and two questions sort most of them.

The basic shape

Every one of them is this JSON (the comments are for reading; real policy JSON has none):

From one service to the next, two parts change:

  • the service prefix on the action: s3:, sqs:, kms:
  • the format of the ARN (Amazon Resource Name, the full ID of an AWS resource) in Resource

Principal is sometimes there and sometimes not.

How do a dozen policies sort?

The IAM policy types page lists 9 policy types: identity-based, resource-based, VPC endpoint policy, permissions boundary, SCP, RCP, ACL, RAM (Resource Access Manager) resource share, session policy.

Eight of them sort with two questions. Is the policy attached to an identity or to a resource? Does it grant access, or only cap it?

Grants accessOnly caps access
Attached to an identity (no Principal)identity-based policy (including a role's permission policy)permissions boundary, session policy, SCP
Attached to a resource (needs Principal)resource-based policy (bucket policy, a role's trust policy, KMS key policy, ..., and the policy a RAM resource share generates)RCP, VPC endpoint policy

RAM generates a resource-based policy for you, to share resources like subnets with other accounts, so it counts as resource-based too (see the RAM managed permissions page).

SCP and RCP don't actually attach to an identity or a resource; they attach to an AWS Organizations organization root, OU (organizational unit) or account. The table places them by what they govern:

  • An SCP directly limits what the users and roles in the account can do. Its target is already fixed, so it has no Principal; the effect is the same as attaching a copy to each identity.
  • An RCP limits who can access the resources in the account. A rule written against resources has to say who is accessing them, so an RCP has a Principal. It can only be *, though; narrowing it takes a Condition, for example to deny only accounts outside the organization.

Two exceptions sit outside the table:

  • An ACL grants access but doesn't use JSON.
  • A CloudFormation stack policy uses the same JSON but has nothing to do with access, so it isn't one of AWS's 9.

A KMS key policy belongs with "attached to a resource, grants access," but identity-based policies on a KMS key follow one rule that S3 doesn't have; the example is further down.

Question one: attached to an identity, or to a resource?

Say you created a role called Reader (an example name, used throughout), and it should be able to read files in the bucket reports. There are two places to write that.

Identity-based policy: on the role

The first place is the role Reader. A policy attached to an identity is an identity-based policy (shortened to "identity policy" in the boolean expressions later, and sometimes called an "IAM policy"; all three mean the same thing):

Writing the policy isn't enough; it has to be attached. Save it as read-reports.json (wrapped in "Version" and "Statement", like the JSON at the top of the article) and attach it to the role:

aws iam put-role-policy \
  --role-name Reader \
  --policy-name read-reports \
  --policy-document file://read-reports.json

Why only the bucket policy needs a Principal

A bucket policy says who may read the bucket, so Principal names them. The one on Reader doesn't need it, because the one reading is Reader itself. The IAM Principal element page states both rules. Checked in November 2026 with aws accessanalyzer validate-policy: the second policy, checked as an identity-based policy, returns UNSUPPORTED_PRINCIPAL; the first, checked as a bucket policy, returns MISSING_PRINCIPAL.

Every policy listed at the top of the article sits on a resource like this. When unsure, ask: can I attach a policy directly to this thing? If yes, it's resource-based and wants a Principal. The "Resource-based policies" column in the IAM services table has the full list.

Which kind is an IAM role's policy?

What people call an "IAM role policy" is really one of two: the permission policy or the trust policy. The first is identity-based, the second resource-based. Both are set in IAM.

Say a Lambda function uses Reader to read reports.

Trust policy: who may assume Reader

A trust policy's Action depends on how whoever assumes the role signed in (see the IAM OIDC role page):

  • An AWS user, role or service: sts:AssumeRole
  • Signed in through OIDC (OpenID Connect), such as GitHub Actions: sts:AssumeRoleWithWebIdentity
  • Signed in through SAML (Security Assertion Markup Language): sts:AssumeRoleWithSAML

This one lets a Lambda assume Reader:

Permission policy: what Reader may do once assumed

The permission policy is the one from question one, attached to Reader and allowing reads of reports.

How AWS checks the two when the Lambda reads a file

  1. The Lambda asks to assume Reader.
  2. AWS checks the trust policy: lambda.amazonaws.com is in Principal, so this is allowed.
  3. The Lambda gets Reader's temporary credentials.
  4. The Lambda calls s3:GetObject with them.
  5. AWS checks the permission policy: reports/* is allowed, so this is allowed.

Why only the trust policy needs a Principal

A trust policy says who may assume Reader, so Principal names them. The permission policy doesn't need one, because it sits on Reader and the one acting is Reader itself. The IAM services table calls it the only resource-based policy IAM supports.

A trust policy has no Resource, because the resource is the role itself. validate-policy rejects a trust policy that includes one with ROLE_TRUST_POLICY_SYNTAX_ERROR_RESOURCE.

How trust policies work is covered in assumeRole and trust policy.

Question two: does it grant access, or only cap it?

Every policy so far grants access. A few others use the same shape but only set a ceiling and grant nothing themselves. Some attach to identities and some to resources.

Permissions boundary

A permissions boundary attaches to an IAM user or role and has no Principal. Say Reader's identity-based policy allows every S3 action:

Reader also has a permissions boundary, s3-read-only, that allows only s3:GetObject:

Both are the same kind of JSON, attached with different commands:

  • Attached with put-role-policy, it's an identity-based policy and grants access. If Reader has several, they combine with ||: one allow is enough.
  • Attached with put-role-permissions-boundary below, it's a permissions boundary and only caps.
  • Identity-based policy and permissions boundary combine with &&, which the IAM evaluation page calls an intersection: identity-based policy && permissions boundary.

So Reader can do only s3:GetObject, which both allow; an s3:PutObject call is denied.

The other way round, if the boundary allows s3:* and the identity-based policy allows no S3 action, Reader has no S3 access.

A boundary has to exist as a managed policy first, then gets attached by its ARN:

aws iam create-policy \
  --policy-name s3-read-only \
  --policy-document file://s3-read-only.json

aws iam put-role-permissions-boundary \
  --role-name Reader \
  --permissions-boundary arn:aws:iam::111122223333:policy/s3-read-only

Session policy

A session policy also only caps. It and the trust policy both come up when a role is assumed, so they're easy to mix up. Say the session policy only-q3.json allows reading only reports/q3.pdf:

A caller assumes Reader with this command, gets a temporary session, and passes the session policy with --policy:

aws sts assume-role \
  --role-arn arn:aws:iam::111122223333:role/Reader \
  --role-session-name read-q3 \
  --policy file://only-q3.json
  1. AWS checks Reader's trust policy first. A caller not in its Principal can't assume the role.
  2. After that, the session can do only what both Reader's permission policy and only-q3.json allow.
  • Reader's permission policy allows reading all of reports/*.
  • only-q3.json allows reading only reports/q3.pdf.
  • The session's permissions are permission policy && session policy, so it can read only q3.pdf.

A session policy isn't attached anywhere; it's passed on each assume-role call and affects only that session. The example above has the session policy narrowing access to q3.pdf. A session policy can't widen access, though: even if only-q3.json were s3:*, the session still couldn't do anything Reader's permission policy doesn't allow.

The IAM policy types page says permissions boundaries and session policies "do not grant permissions." In the expressions identity-based policy && permissions boundary and permission policy && session policy above, they only appear to the right of &&: when the left side is false, nothing on the right can make the result true.

SCP

An SCP (service control policy) is an AWS Organizations policy. It attaches to the organization root, an OU or an account, and limits the IAM users and roles underneath. An organization looks roughly like this:

organization root
├── management account   ← created the organization, pays the whole organization's bill
├── OU: prod
│   ├── account A
│   └── account B
└── OU: dev
    └── account C

Say this SCP is attached to the organization root:

  • A user in account A, B or C who calls s3:DeleteBucket is denied, even if their identity-based policy allows s3:*.
  • The management account is under the root too, but its users and roles can still call s3:DeleteBucket. The SCP page says SCPs don't affect users or roles in the management account, or service-linked roles.

Attach the same SCP to OU: prod instead, and only accounts A and B are limited.

Because SCPs can't limit the management account, the Organizations best practices for the management account recommend keeping resources in other accounts. Use the management account only to manage the organization itself, such as creating accounts, creating and attaching SCPs, and viewing the organization's bill.

The same page says that organizations created in the console after July 10, 2026 get an SCP at the root automatically. It denies organizations:LeaveOrganization and account:CloseAccount, so users and roles in a member account can't take their account out of the organization or close it; those two steps are handled from the management account instead.

An SCP can't have a Principal: the SCP syntax page lists Principal and NotPrincipal as unsupported.

RCP

An RCP (Resource Control Policy) is an Organizations policy added in November 2024. It attaches to the account that owns the bucket and limits who may access that account's resources. It and an SCP limit different things:

  • SCP: what users and roles inside the organization may do.
  • RCP: who may access resources in the organization, including accounts outside it.

An RCP's Principal accepts only *, and an RCP you write can only use Deny. The RCP syntax page says Allow is supported only in RCPFullAWSAccess. When you enable RCPs, AWS attaches that policy to every root, OU and account, and you can't detach it. It lets every request pass the RCP check, so with no Deny written, RCPs refuse nothing. An RCP refuses a request only when someone writes a Deny and the request matches it. For example, if the bucket policy allows an outside account s3:GetObject and an RCP has a Deny for accounts outside the organization, that account still can't read the object. Like SCPs, RCPs don't affect resources in the management account (see the RCP page).

VPC endpoint policy

A VPC endpoint policy attaches to a VPC endpoint and limits what requests through that endpoint can reach. An endpoint created without a policy gets a default endpoint policy that lets requests through it reach any resource.

One kind of S3 endpoint is the gateway endpoint: EC2 instances in the VPC reach S3 through it without an internet gateway or NAT (see the S3 gateway endpoint page). Principal has a negated form, NotPrincipal. This bucket policy denies everyone except Admin access to reports:

NotPrincipal still names a who, so for question one it counts the same as Principal.

The IAM NotPrincipal page allows NotPrincipal only with Deny, and never in an identity-based policy or a trust policy. It also recommends against NotPrincipal in new policies, in favour of "Principal": "*" with an ArnNotEquals condition on aws:PrincipalArn.

Action and Resource have negated forms too, NotAction and NotResource. "NotAction": "iam:*" means every action outside IAM (see the NotAction page).

Which policies have rules of their own?

KMS key policy

Usually, if Reader's identity-based policy allows s3:GetObject and kms:Decrypt, it can read KMS-encrypted files (see the S3 SSE-KMS page).

That's because the default key policy has a statement whose Principal is the account itself (:root). Once the key policy allows the account, KMS looks at the account's identity-based policies, and Reader's kms:Decrypt counts (see the KMS default key policy page). If someone writes their own key policy and leaves this statement out, KMS ignores identity-based policies, and Reader is denied even with kms:Decrypt in its identity-based policy.

The + lines below are that statement:

S3:  identity policy || bucket policy
KMS: key policy names Reader || (key policy names :root && identity policy)

For S3, the identity-based policy sits inside || and is enough on its own; for KMS, it sits to the right of &&, so the key policy must allow :root first (see the IAM evaluation page).

What does Reader need to read reports/q3.pdf?

For Reader reading q3.pdf in the same account, the rules on the IAM policy evaluation page come out as a boolean expression, where any layer that isn't attached counts as true:

no Deny matches
&& (identity policy 1 || identity policy 2 || bucket policy)
&& permissions boundary
&& session policy
&& SCP && RCP && VPC endpoint policy
&& kms:Decrypt   (if q3.pdf is encrypted with a KMS key)

Every Deny counts on the first line, whether it sits in the bucket policy, an identity policy or an SCP. The other lines look only at whether that policy has an Allow: the bucket policy in the parentheses, for example, asks whether the bucket policy has an Allow statement that permits this request.

There is no ACL in this expression, because the IAM policy types page says "ACLs cannot grant permissions to entities within the same account". ACLs can only grant to other accounts and to anonymous requests, so the ACL term appears only in the cross-account expression below.

In the words of the IAM evaluation page:

  • || is a union: one allow among the identity-based and resource-based policies is enough.
  • && is an intersection: the || in parentheses being true isn't enough; every other line must be true too, including "no Deny matches" on the first line, the caps in the middle, and kms:Decrypt on the last.

Across accounts, the expression changes. Say Reader is in account A and reports in account B:

same account:   identity policy 1 || identity policy 2 || bucket policy
cross-account:  (identity policy 1 || identity policy 2) && (bucket policy || ACL)
  • Same account: one allow among the three is enough.
  • Cross-account: accounts A and B each check their own side, and both must allow it (see the IAM cross-account evaluation page).
    • Account A checks the policies on Reader: is Reader allowed to read someone else's bucket? identity policy 1 || identity policy 2, one allow is enough.
    • Account B checks the policies on reports: does reports let account A's Reader in? bucket policy || ACL, one allow is enough.
    • The two groups are joined by &&: only when A says yes and B says yes can Reader read the file.

With ACLs on, an Allow-only bucket policy is undone however precise it is

Besides policies, S3 has an older access system, the ACL (access control list): the ACL in bucket policy || ACL in the cross-account expression above; anonymous requests are checked against it too. The IAM policy types page calls ACLs the only policy type that doesn't use JSON.

Say the bucket policy on reports lets in only Reader, and ACLs are still enabled. Someone uploads q3.pdf with --acl public-read:

aws s3 cp q3.pdf s3://reports/ --acl public-read
  1. q3.pdf's ACL gains a grant: AllUsers may READ.
  2. The bucket policy still names only Reader.
  3. Anyone can GET the file's URL, unsigned, and read it.

Block Public Access: do public ACLs and bucket policies count?

The left side of the embed below holds the switches: Object Ownership (a three-way choice, one option of which disables ACLs), the four Block Public Access switches, and how q3.pdf was encrypted when uploaded, with the KMS key policy below that.   • Set Object Ownership to Bucket owner enforced, which disables ACLs, and q3.pdf's object ACL and the BlockPublicAcls and IgnorePublicAcls switches turn grey, because S3 no longer counts ACLs when checking access.
  • The four lines at the top right are the results. Their text never changes; only the colour gives the answer: normal ink means yes, faded means no.

Block Public Access isn't a single switch but a set of four. Each can be on or off on its own; the S3 Block Public Access page says "These settings are independent and can be used in any combination." They deal with public ACLs and bucket policies. A public ACL is a grant to AllUsers like the one above; a public bucket policy is one like the Principal: "*" statement in the embed, with no limiting Condition, so anyone can read.

In the console's wording, two of the four act on new ones and two on any:

  • BlockPublicAcls, BlockPublicPolicy (new): S3 rejects any attempt to write a public ACL or bucket policy. Existing ones are untouched; q3.pdf's ACL stays in force.
  • IgnorePublicAcls, RestrictPublicBuckets (any): existing ones aren't deleted, but stop working for outsiders. A public ACL doesn't count, so anonymous requests can't read q3.pdf; a public bucket policy works only for users in the bucket owner's account and AWS services. Reader still reads through policies in its own account.

If the account, organization or an access point also sets these switches, S3 compares them one switch at a time: a switch on in any of those places counts as on for reports. If the account has IgnorePublicAcls on, public ACLs in reports don't count even though the bucket itself has it off. The organization is the exception: the Block Public Access page says that at the organization level all four settings apply together, and you can't turn on just one.

The 2023 defaults

Since April 2023, new buckets have all four on and ACLs disabled ("Bucket owner enforced"). With ACLs disabled:

  • the --acl public-read upload above fails with a 400 AccessControlListNotSupported;
  • existing ACLs no longer take part in access evaluation; the ACL term in the expression is never true, and only the policies decide.

The takeaway

Next time AWS hands you a new "X policy," ask two questions:

  1. Does it name a who, with Principal or NotPrincipal? If yes, it sits on a resource; if no, on an identity. SCP and RCP are the exception: they attach to an Organizations root, OU or account.
  2. Does it grant access, or only cap it? If the docs say it does "not grant permissions," it only caps.

Then find its cell in the table above. For a KMS key, the key policy must first allow the key's account to use identity-based policies before any identity-based policy takes effect.
