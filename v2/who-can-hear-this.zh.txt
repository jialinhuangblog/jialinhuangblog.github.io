14:Tf13d,<p>瀏覽器裡送訊息的方法有好幾種：<code>window.postMessage</code>、<code>worker.postMessage</code>、<code>MessageChannel</code>、<code>BroadcastChannel</code>，還有 service worker 跟它底下的頁面互傳。要從裡面挑一個，可以先問自己：</p>
<ol>
<li>這則訊息實際上誰會收到？</li>
<li>能不能只讓指定的對象收到？</li>
</ol>
<p>每一種 messaging API 對這兩個問題的答案都不一樣。</p>
<h2><code>postMessage</code> 其實是好幾個 method</h2>
<p><code>postMessage</code> 是好幾個不同 method 共用的名字，分別掛在不同的物件上：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="js" data-theme="github-dark github-light"><code data-language="js" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">someWindow.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">postMessage</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(msg, targetOrigin)  </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// 在 Window 上（iframe、popup、parent、opener）</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">worker.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">postMessage</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(msg)                     </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// 在 Worker 上</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">port.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">postMessage</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(msg)                       </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// 在 MessagePort 上</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">client.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">postMessage</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(msg)                     </span><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// 在 service worker 的 Client 上</span></span></code></pre></figure>
<p>看 <code>targetOrigin</code> 就分得出來。只有 <strong>Window</strong> 的版本要填 <code>targetOrigin</code>，因為另一端的 window 可能是別的 origin，瀏覽器要求寫明信任哪個 origin。worker 跟 client 的版本沒有 <code>targetOrigin</code>，因為它們本來就只在同一個 origin 裡（<code>Client</code> 是 service worker 手上代表某一個頁面的物件）。port（<code>MessageChannel</code> 的其中一端）也不用填，因為建立 channel 的人交出 <code>port2</code> 的時候，就已經選好收件人了。之後從 <code>port1</code> 送出的訊息只會到 <code>port2</code>，不必再檢查 origin。</p>
<h2>有哪些角色</h2>
<p>會收發訊息的有分頁（window）、分頁裡的 iframe 或 popup，以及三種 worker。它們各自跑在自己的 JavaScript 環境裡，下面把每一個都叫做一個 context。</p>
<ul>
<li><strong>Dedicated worker</strong>：一個頁面專用的執行緒，用 <code>new Worker('a.js')</code> 建立。頁面以外，dedicated worker 跟 shared worker 裡也能呼叫 <code>new Worker()</code>。</li>
<li><strong>Shared worker</strong>：同一個 origin 的好幾個分頁共用一個 worker。就算每個分頁都呼叫一次 <code>new SharedWorker('hub.js')</code>，瀏覽器也只啟動一個 <code>hub.js</code>。<code>new SharedWorker()</code> 只能在頁面裡呼叫，worker 裡不行。</li>
<li><strong>Service worker</strong>：像 proxy 一樣夾在一組頁面跟網路之間，用來做離線、cache、推播。不用 <code>new</code>，而是頁面呼叫 <code>navigator.serviceWorker.register('sw.js')</code> 向瀏覽器註冊。</li>
</ul>
<h2>預設是每個 listener 都收到</h2>
<p>對 iframe 呼叫 <code>postMessage</code> 的時候，第一個反應通常是以為送了一則訊息給一個收件人：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="js" data-theme="github-dark github-light"><code data-language="js" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">iframe.contentWindow.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">postMessage</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'hello'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, </span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'https://trusted.com'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">);</span></span></code></pre></figure>
<p>可是訊息其實是送進接收端 window 的 <code>message</code> event，那個 window 裡的<strong>每一個</strong> listener 都會拿到一份：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="js" data-theme="github-dark github-light"><code data-language="js" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// 接收端頁面的任何地方，例如第三方的分析 script：</span></span>
<span data-line=""><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">window.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">addEventListener</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'message'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, </span><span style="--shiki-dark:#FFAB70;--shiki-light:#E36209">e</span><span style="--shiki-dark:#F97583;--shiki-light:#D73A49"> =></span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E"> console.</span><span style="--shiki-dark:#B392F0;--shiki-light:#6F42C1">log</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">(</span><span style="--shiki-dark:#9ECBFF;--shiki-light:#032F62">'I got it too:'</span><span style="--shiki-dark:#E1E4E8;--shiki-light:#24292E">, e.data));</span></span></code></pre></figure>
<p>同 origin 不代表 code 都是自己寫的。被注入的 script、廣告 SDK、那個頁面載入的套件，都跑在同一個 context 裡，也都能加 listener。<code>BroadcastChannel</code> 也一樣，而且是刻意這樣設計的：任何加入同一個 channel 名稱的 context 都會收到所有訊息。</p>
<p>那要怎樣才能只送給一個對象呢？</p>
<h2>只送給一方：把 port 交出去</h2>
<p>上一節的問題出在訊息走 <code>message</code> event，誰在上面掛了 listener 誰就收得到。要避開它，就改走一條只有兩端的線，也就是 <code>MessageChannel</code>。</p>
<p>例如頁面要跟它建立的 worker 講私話：</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="js" data-theme="github-dark github-light"><code data-language="js" data-theme="github-dark github-light" style="display: grid;"><span data-line=""><span style="--shiki-dark:#6A737D;--shiki-light:#6A737D">// 頁面的程式</span></span>

<p><code>worker.postMessage</code> 的第二個參數是 transfer 清單。<code>port2</code> 交出去之後，頁面手上就沒有它了，只剩 worker 握著。之後頁面從 <code>port1</code> 送出的訊息只會到 <code>port2</code>，不經過任何 window 的 <code>message</code> event，所以頁面上其他 script 掛的 listener 都收不到。</p>
<p>交出 port 的那一步本身還是走 <code>message</code> event。因為 port 是夾在一則 <code>postMessage</code> 裡送過去的，對方那邊每個 <code>message</code> listener 都會拿到 <code>e.ports[0]</code>，也能在上面掛自己的 listener。worker 裡通常只有自己寫的 script，不太會有別的 listener 一起拿到 port。iframe 裡的頁面卻常常載了廣告、分析這類第三方 script，它們也能拿到這個 port。</p>
<h2>從誰傳給誰</h2>
<p><code>postMessage</code> 要先拿到對方的 handle 才能傳，<code>BroadcastChannel</code> 只要兩邊開同一個名稱。照「從哪裡傳到哪裡」列出來：</p>
<ul>
<li><strong>頁面 → iframe / popup</strong>：<code>window.postMessage</code>。handle 是 <code>iframe.contentWindow</code>，或 <code>window.open()</code> 的回傳值。對方 window 上每個 listener 都收到。</li>
<li><strong>頁面 ↔ dedicated worker</strong>：頁面用 <code>worker.postMessage</code>，worker 用 <code>self.postMessage</code>。handle 是 <code>new Worker()</code> 的回傳值。只有這兩方收到。</li>
<li><strong>頁面 ↔ shared worker</strong>：兩邊都用 <code>port.postMessage</code>。頁面的 port 是 <code>new SharedWorker().port</code>，worker 的 port 在 <code>onconnect</code> 拿到。每個分頁一個 port，worker 對哪個 port 送，就只有那個分頁收到。</li>
<li><strong>頁面 → service worker</strong>：<code>registration.active.postMessage</code>。registration 從 <code>await navigator.serviceWorker.ready</code> 拿到。</li>
<li><strong>service worker → 頁面</strong>：<code>client.postMessage</code>，一次送一個 client。client 是 <code>e.source</code>，或 <code>clients.matchAll()</code> 的結果。頁面在 <code>navigator.serviceWorker</code> 上收，不是在 <code>window</code> 上。</li>
<li><strong>worker ↔ 它自己建立的 dedicated worker</strong>：寫法跟頁面 ↔ dedicated worker 一樣。dedicated worker 跟 shared worker 裡都能呼叫 <code>new Worker()</code>。</li>
<li><strong>兩個 worker，誰都不是對方建立的</strong>：例如同一個頁面建的兩個 dedicated worker、dedicated worker 跟 shared worker、任何一種 worker 跟 service worker。兩邊都沒有對方的 handle，要由頁面建一條 <code>MessageChannel</code> 交給兩邊，或用 <code>BroadcastChannel</code>。</li>
<li><strong>不相干的同 origin 分頁</strong>：<code>BroadcastChannel</code>，不需要 handle，名稱相同就好。開了同一個名稱的每個 context 都收到。</li>
</ul>
<p><code>MessageChannel</code> 不算另一條路。它要借上面某一條路線的 <code>postMessage</code> 把 port 交出去，交過去之後，兩端之間就是一條別人收不到的專線。三種 worker 裡都能 <code>new MessageChannel()</code> 跟 <code>new BroadcastChannel()</code>，寫法跟在頁面裡一樣。</p>
<p><strong>三種送法</strong></p>
<details>
<summary>postMessage：window 傳給 window（iframe、popup、opener）</summary>
<p>這裡有三個角色。<code>https://parent.example</code> 上的頁面（下面叫 parent）嵌了一個 <code>https://child.example</code> 的 iframe，又用 <code>window.open</code> 開了一個同網址的 popup。iframe 跟 popup 都是 parent 產生的，所以 parent 手上有它們的 handle：iframe 的 <code>contentWindow</code>，跟 <code>window.open</code> 的回傳值。反過來，iframe 用 <code>window.parent</code>、popup 用 <code>window.opener</code> 拿到 parent 的 handle。</p>
<p>送訊息的一方要先握著對方的 handle 才能送。</p>
<p>parent 剛嵌好 iframe、剛開好 popup 時，它們的頁面可能還沒載入完，這時 parent 送出的訊息，iframe 跟 popup 都收不到。所以下面讓 iframe 跟 popup 載入完先送一則 <code>ready</code>，parent 收到之後，對 <code>e.source</code>（送來的那個 window）呼叫 <code>postMessage</code> 回覆。</p>

<details>
<summary>MessageChannel：任意兩個 context 之間的專線</summary>
<p>想像一條線綁著兩個鐵罐（<code>port1</code>、<code>port2</code>）。<code>new MessageChannel()</code> 之後，自己留一個罐子、另一個交出去，只有拿著罐子的兩方聽得到。一條線上固定就這兩個罐子，要再接第三方，得再建一個 <code>MessageChannel</code>。</p>
<p>正文「只送給一方」示範了頁面怎麼跟自己的 worker 拉一條線。同樣的做法也能讓兩個 worker 直接互傳。這個例子有三個角色：頁面、workerA、workerB。兩個 worker 都是頁面建立的，所以只有頁面同時握著兩邊的 handle，workerA 跟 workerB 彼此沒有對方的 handle。頁面建一個 channel，<code>port1</code> 交給 workerA、<code>port2</code> 交給 workerB，之後兩個 worker 直接互傳，資料不經過頁面。</p>

瀏覽器裡送訊息的方法有好幾種：`window.postMessage`、`worker.postMessage`、`MessageChannel`、`BroadcastChannel`，還有 service worker 跟它底下的頁面互傳。要從裡面挑一個，可以先問自己：

1. 這則訊息實際上誰會收到？
2. 能不能只讓指定的對象收到？

每一種 messaging API 對這兩個問題的答案都不一樣。

## `postMessage` 其實是好幾個 method

`postMessage` 是好幾個不同 method 共用的名字，分別掛在不同的物件上：

```js
someWindow.postMessage(msg, targetOrigin)  // 在 Window 上（iframe、popup、parent、opener）
worker.postMessage(msg)                     // 在 Worker 上
port.postMessage(msg)                       // 在 MessagePort 上
client.postMessage(msg)                     // 在 service worker 的 Client 上
```

看 `targetOrigin` 就分得出來。只有 **Window** 的版本要填 `targetOrigin`，因為另一端的 window 可能是別的 origin，瀏覽器要求寫明信任哪個 origin。worker 跟 client 的版本沒有 `targetOrigin`，因為它們本來就只在同一個 origin 裡（`Client` 是 service worker 手上代表某一個頁面的物件）。port（`MessageChannel` 的其中一端）也不用填，因為建立 channel 的人交出 `port2` 的時候，就已經選好收件人了。之後從 `port1` 送出的訊息只會到 `port2`，不必再檢查 origin。

## 有哪些角色

會收發訊息的有分頁（window）、分頁裡的 iframe 或 popup，以及三種 worker。它們各自跑在自己的 JavaScript 環境裡，下面把每一個都叫做一個 context。

- **Dedicated worker**：一個頁面專用的執行緒，用 `new Worker('a.js')` 建立。頁面以外，dedicated worker 跟 shared worker 裡也能呼叫 `new Worker()`。
- **Shared worker**：同一個 origin 的好幾個分頁共用一個 worker。就算每個分頁都呼叫一次 `new SharedWorker('hub.js')`，瀏覽器也只啟動一個 `hub.js`。`new SharedWorker()` 只能在頁面裡呼叫，worker 裡不行。
- **Service worker**：像 proxy 一樣夾在一組頁面跟網路之間，用來做離線、cache、推播。不用 `new`，而是頁面呼叫 `navigator.serviceWorker.register('sw.js')` 向瀏覽器註冊。

## 預設是每個 listener 都收到

對 iframe 呼叫 `postMessage` 的時候，第一個反應通常是以為送了一則訊息給一個收件人：

```js
iframe.contentWindow.postMessage('hello', 'https://trusted.com');
```

可是訊息其實是送進接收端 window 的 `message` event，那個 window 裡的**每一個** listener 都會拿到一份：

```js
// 接收端頁面的任何地方，例如第三方的分析 script：
window.addEventListener('message', e => console.log('I got it too:', e.data));
```

同 origin 不代表 code 都是自己寫的。被注入的 script、廣告 SDK、那個頁面載入的套件，都跑在同一個 context 裡，也都能加 listener。`BroadcastChannel` 也一樣，而且是刻意這樣設計的：任何加入同一個 channel 名稱的 context 都會收到所有訊息。

那要怎樣才能只送給一個對象呢？

## 只送給一方：把 port 交出去

上一節的問題出在訊息走 `message` event，誰在上面掛了 listener 誰就收得到。要避開它，就改走一條只有兩端的線，也就是 `MessageChannel`。

例如頁面要跟它建立的 worker 講私話：

```js
// 頁面的程式
const worker = new Worker('worker.js');
const channel = new MessageChannel();            // 一條線，兩端是 port1、port2
worker.postMessage('setup', [channel.port2]);    // 把 port2 交給 worker
channel.port1.postMessage('only the worker hears this');

// worker.js
self.onmessage = (e) => {
  const port = e.ports[0];                       // 頁面交過來的 port2
  port.onmessage = (ev) => console.log(ev.data);
};
```

`worker.postMessage` 的第二個參數是 transfer 清單。`port2` 交出去之後，頁面手上就沒有它了，只剩 worker 握著。之後頁面從 `port1` 送出的訊息只會到 `port2`，不經過任何 window 的 `message` event，所以頁面上其他 script 掛的 listener 都收不到。

交出 port 的那一步本身還是走 `message` event。因為 port 是夾在一則 `postMessage` 裡送過去的，對方那邊每個 `message` listener 都會拿到 `e.ports[0]`，也能在上面掛自己的 listener。worker 裡通常只有自己寫的 script，不太會有別的 listener 一起拿到 port。iframe 裡的頁面卻常常載了廣告、分析這類第三方 script，它們也能拿到這個 port。

## 從誰傳給誰

`postMessage` 要先拿到對方的 handle 才能傳，`BroadcastChannel` 只要兩邊開同一個名稱。照「從哪裡傳到哪裡」列出來：

- **頁面 → iframe / popup**：`window.postMessage`。handle 是 `iframe.contentWindow`，或 `window.open()` 的回傳值。對方 window 上每個 listener 都收到。
- **頁面 ↔ dedicated worker**：頁面用 `worker.postMessage`，worker 用 `self.postMessage`。handle 是 `new Worker()` 的回傳值。只有這兩方收到。
- **頁面 ↔ shared worker**：兩邊都用 `port.postMessage`。頁面的 port 是 `new SharedWorker().port`，worker 的 port 在 `onconnect` 拿到。每個分頁一個 port，worker 對哪個 port 送，就只有那個分頁收到。
- **頁面 → service worker**：`registration.active.postMessage`。registration 從 `await navigator.serviceWorker.ready` 拿到。
- **service worker → 頁面**：`client.postMessage`，一次送一個 client。client 是 `e.source`，或 `clients.matchAll()` 的結果。頁面在 `navigator.serviceWorker` 上收，不是在 `window` 上。
- **worker ↔ 它自己建立的 dedicated worker**：寫法跟頁面 ↔ dedicated worker 一樣。dedicated worker 跟 shared worker 裡都能呼叫 `new Worker()`。
- **兩個 worker，誰都不是對方建立的**：例如同一個頁面建的兩個 dedicated worker、dedicated worker 跟 shared worker、任何一種 worker 跟 service worker。兩邊都沒有對方的 handle，要由頁面建一條 `MessageChannel` 交給兩邊，或用 `BroadcastChannel`。
- **不相干的同 origin 分頁**：`BroadcastChannel`，不需要 handle，名稱相同就好。開了同一個名稱的每個 context 都收到。

`MessageChannel` 不算另一條路。它要借上面某一條路線的 `postMessage` 把 port 交出去，交過去之後，兩端之間就是一條別人收不到的專線。三種 worker 裡都能 `new MessageChannel()` 跟 `new BroadcastChannel()`，寫法跟在頁面裡一樣。

**三種送法**

<details>
<summary>postMessage：window 傳給 window（iframe、popup、opener）</summary>

這裡有三個角色。`https://parent.example` 上的頁面（下面叫 parent）嵌了一個 `https://child.example` 的 iframe，又用 `window.open` 開了一個同網址的 popup。iframe 跟 popup 都是 parent 產生的，所以 parent 手上有它們的 handle：iframe 的 `contentWindow`，跟 `window.open` 的回傳值。反過來，iframe 用 `window.parent`、popup 用 `window.opener` 拿到 parent 的 handle。

送訊息的一方要先握著對方的 handle 才能送。

parent 剛嵌好 iframe、剛開好 popup 時，它們的頁面可能還沒載入完，這時 parent 送出的訊息，iframe 跟 popup 都收不到。所以下面讓 iframe 跟 popup 載入完先送一則 `ready`，parent 收到之後，對 `e.source`（送來的那個 window）呼叫 `postMessage` 回覆。

```js
// parent 的頁面程式（https://parent.example）
const popup = window.open('https://child.example');   // parent 開的 popup
window.addEventListener('message', (e) => {
  if (e.origin !== 'https://child.example') return;
  console.log('parent got:', e.data);                 // 'iframe ready' 或 'popup ready'
  e.source.postMessage('hi', 'https://child.example'); // e.source 就是送來的那個 window
});

// iframe 裡的程式（https://child.example）
window.parent.postMessage('iframe ready', 'https://parent.example');

// popup 裡的程式（https://child.example）
window.opener.postMessage('popup ready', 'https://parent.example');
```

跟自己沒有關係的分頁，因為手上沒有它的 handle，所以不能用這個方法傳，要改用 BroadcastChannel。

<details>
<summary>MessageChannel：任意兩個 context 之間的專線</summary>

想像一條線綁著兩個鐵罐（`port1`、`port2`）。`new MessageChannel()` 之後，自己留一個罐子、另一個交出去，只有拿著罐子的兩方聽得到。一條線上固定就這兩個罐子，要再接第三方，得再建一個 `MessageChannel`。

正文「只送給一方」示範了頁面怎麼跟自己的 worker 拉一條線。同樣的做法也能讓兩個 worker 直接互傳。這個例子有三個角色：頁面、workerA、workerB。兩個 worker 都是頁面建立的，所以只有頁面同時握著兩邊的 handle，workerA 跟 workerB 彼此沒有對方的 handle。頁面建一個 channel，`port1` 交給 workerA、`port2` 交給 workerB，之後兩個 worker 直接互傳，資料不經過頁面。

```js
// 頁面的程式
const workerA = new Worker('workerA.js');
const workerB = new Worker('workerB.js');
const ch = new MessageChannel();
workerA.postMessage('connect', [ch.port1]);
workerB.postMessage('connect', [ch.port2]);

// workerA.js（workerB.js 是對稱的）
self.onmessage = (e) => {
  // e.ports 是這則訊息夾帶的 port 清單。頁面給 workerA 只夾了 port1，所以 [0] 就是 port1；
  // workerB 那邊寫法一樣，拿到的是 port2
  const peer = e.ports[0];
  peer.onmessage = (ev) => console.log('A got from B:', ev.data);
  peer.postMessage('hi B, straight to you');   // 不會經過頁面
};
```

牽線的頁面不一定要是建立這兩個 worker 的那個，只要同時握著兩邊的 handle 就行。例如一個分頁同時連著 `hub.js` 跟 `hub2.js` 兩個 shared worker，就能用同樣的方式讓兩個 hub 直接互傳，只是交 port 要走各自的 `.port.postMessage`：

```js
// 同時連著兩個 hub 的分頁
const hub1 = new SharedWorker('hub.js');
const hub2 = new SharedWorker('hub2.js');
const ch = new MessageChannel();
hub1.port.postMessage('peer', [ch.port1]);
hub2.port.postMessage('peer', [ch.port2]);

// hub.js（hub2.js 寫法一樣）
onconnect = (e) => {
  const tabPort = e.ports[0];            // 這個分頁連進來的 port
  tabPort.onmessage = (ev) => {
    if (ev.data !== 'peer') return;
    const peer = ev.ports[0];            // hub.js 拿到 ch.port1，hub2.js 拿到 ch.port2
    peer.onmessage = (m) => console.log('hub got:', m.data);
    peer.postMessage('hi from hub');     // 直接送到另一個 hub，不經過分頁
  };
};
```

</details>

<details>
<summary>BroadcastChannel：廣播給同一個名稱上的所有人</summary>

這裡有四個角色，都在同一個 origin 底下：

- tab1、tab2：同一個網站開的兩個分頁。
- sw：這個網站註冊的 service worker，程式在 `sw.js`。
- `logout.js`：tab1 用 `new Worker('logout.js')` 建立的 dedicated worker。

它們彼此不需要任何 handle，只要都 `new BroadcastChannel('app')`，就連上同一個 channel。

```js
// tab1 的頁面程式
const bc = new BroadcastChannel('app');
bc.onmessage = (e) => console.log('tab1 heard:', e.data);
const worker = new Worker('logout.js');

// tab2 的頁面程式（同一個網站的另一個分頁）
const bc = new BroadcastChannel('app');
bc.onmessage = (e) => console.log('tab2 heard:', e.data);

// sw.js
const bc = new BroadcastChannel('app');
bc.onmessage = (e) => console.log('sw heard:', e.data);

// logout.js（tab1 建立的 dedicated worker），由它發出訊息
const bc = new BroadcastChannel('app');
bc.postMessage({ type: 'logout' });
```

`logout.js` 呼叫一次 `postMessage`，tab1、tab2 跟 sw 都會收到 `logout`。發出訊息的 worker 自己那個 `bc` 收不到；如果同一個 worker 裡再 `new BroadcastChannel('app')` 一個，新的那個會收到。

service worker 閒置一段時間會被瀏覽器停掉，停掉期間送出的 BroadcastChannel 訊息它收不到，之後啟動也補不回來（Chrome 153 實測）。一定要它收到的訊息，就從頁面用 `(await navigator.serviceWorker.ready).active.postMessage(msg)` 送，這樣會把它喚醒。

</details>

**三種 worker**

<details>
<summary>Dedicated worker：一個頁面專用的執行緒</summary>

兩個角色：頁面，跟頁面用 `new Worker('crunch.js')` 建立的 worker。worker 只跟建立它的頁面溝通，頁面握著 `worker`，worker 裡用 `self` 回給頁面。

```js
// 頁面的程式
const worker = new Worker('crunch.js');
worker.postMessage({ rows: bigArray });
worker.onmessage = (e) => render(e.data);

// crunch.js（worker）
self.onmessage = (e) => self.postMessage(heavyWork(e.data.rows));
```

</details>

<details>
<summary>Shared worker：很多分頁共用一個 worker</summary>

假設同一個網站開了三個分頁：tabA、tabB、tabC。三個分頁的程式都呼叫 `new SharedWorker('hub.js')`，瀏覽器只會啟動一個 `hub.js`，三個分頁連到的都是它。這裡的 `hub.js` 就是 shared worker 本身的程式檔。

每個分頁連進來，`hub.js` 就拿到一個新的 port 物件。port 身上沒有名字也沒有 id，`hub.js` 分不出哪個 port 是哪個分頁的。下面的寫法是讓分頁一連上就報自己的 id，`hub.js` 用這個 id 當 key，把 port 存進 Map。

```js
// tabA 的頁面程式（tabB、tabC 一樣，只是把 'tabA' 換成自己的名字）
const sw = new SharedWorker('hub.js');
sw.port.start();
sw.port.postMessage({ register: 'tabA' });
sw.port.onmessage = (e) => console.log('tabA got:', e.data);

// hub.js（shared worker）：三個分頁各一個 port，用 id 存起來
const tabs = new Map();
onconnect = (e) => {
  // connect event 的 ports 不是分頁夾帶的，是瀏覽器替這個新連進來的分頁建的 port，固定只有一個
  const port = e.ports[0];
  port.onmessage = (ev) => { if (ev.data.register) tabs.set(ev.data.register, port); };
  port.start();
};

// 三個分頁都註冊過之後，hub.js 要送的時候再呼叫：
function sendToC() { tabs.get('tabC').postMessage('just for C'); }            // 只有 tabC 收到
function sendToAll() { tabs.forEach((port) => port.postMessage('hi all')); } // tabA、tabB、tabC 都收到
```

</details>

<details>
<summary>Service worker：夾在頁面跟網路之間的 proxy</summary>

假設同一個網站開了兩個分頁 tabA、tabB，網站在頁面裡用 `navigator.serviceWorker.register('sw.js')` 註冊了 service worker。兩個分頁都受同一個 `sw.js` 控制，對 `sw.js` 來說它們各是一個 client。如果 tabA 先送訊息給 `sw.js`（寫法在這一段最後），`sw.js` 可以只回給 tabA；`sw.js` 也可以不等誰先送，主動送給 tabA 跟 tabB。

```js
// sw.js
self.addEventListener('message', (e) => {
  e.source.postMessage('reply, just to the tab that asked');  // 只回給送訊息來的分頁，例如 tabA
});

// 主動送，不用等分頁先送訊息來：
async function announce(msg) {
  const clients = await self.clients.matchAll({ type: 'window' });
  clients.forEach((c) => c.postMessage(msg));                 // tabA、tabB 都收到
}
```

tabA 要主動傳給 `sw.js`，或交一個 `MessageChannel` 的 port 給它，都是對 `registration.active` 呼叫 `postMessage`：

```js
// tabA 的頁面程式
const reg = await navigator.serviceWorker.ready;
const ch = new MessageChannel();
reg.active.postMessage('line', [ch.port2]);
ch.port1.onmessage = (e) => console.log('from sw:', e.data);

// sw.js 的 message listener 裡，tabA 只夾了 ch.port2，所以 e.ports[0] 就是它
e.ports[0]?.postMessage('reply on the private line');
```

</details>

<h2>First trap: "postMessage" is not one method</h2>
<p><code>postMessage</code> is a <em>name</em> shared by several different methods, each living on a different object:</p>

<p>The tell is <code>targetOrigin</code>. Only the <strong>Window</strong> version takes one, because the window on the other end might be a different origin and the browser wants you to name who you trust. The worker and client versions have no <code>targetOrigin</code> because they are same-origin by nature (a <code>Client</code> is the service worker's handle to one of its pages). A port (one end of a <code>MessageChannel</code>) takes none either, because whoever created the channel already chose the recipient when handing over <code>port2</code>. From then on, a message sent from <code>port1</code> reaches only <code>port2</code>, so there is no origin left to check.</p>
<h2>The cast</h2>
<p>Who can send and receive: a tab (window), an iframe or popup inside it, and the three workers. Each one runs its own JavaScript environment, and the rest of this article calls each of them a context.</p>
<ul>
<li><strong>Dedicated worker</strong> is a thread for one page, created with <code>new Worker('a.js')</code>. Besides pages, dedicated workers and shared workers can also call <code>new Worker()</code>.</li>
<li><strong>Shared worker</strong> is one worker shared by several tabs from the same origin. Even though every tab calls <code>new SharedWorker('hub.js')</code>, the browser starts only one <code>hub.js</code>. <code>new SharedWorker()</code> can only be called from a page, not from a worker.</li>
<li><strong>Service worker</strong> sits between a set of pages and the network, like a proxy (offline, caching, push). It isn't created with <code>new</code>; a page calls <code>navigator.serviceWorker.register('sw.js')</code> to register it with the browser.</li>
</ul>
<h2>The default is louder than you think</h2>
<p>You call <code>postMessage</code> on an iframe and assume you sent one message to one recipient:</p>

<p>Same origin does not mean "your code." An injected script, an ad SDK, a dependency that page loaded are all in the same context, all able to listen. <code>BroadcastChannel</code> is the same story on purpose: anyone who joins the channel name hears everything.</p>
<p>So broadcast is the default. The real question is how you opt out of it.</p>
<h2>Private means handing over a port</h2>
<p>The problem in the previous section is that the message travels on the <code>message</code> event, and anyone with a listener there receives it. To avoid it, use a line with only two ends: a <code>MessageChannel</code>.</p>

<p>The second argument of <code>worker.postMessage</code> is the transfer list. Once <code>port2</code> is handed over, the page no longer holds it; only the worker does. From then on, messages the page sends from <code>port1</code> reach only <code>port2</code> and never pass through any window's <code>message</code> event, so listeners other scripts attached on the page receive nothing.</p>
<p>The handover itself still travels on the <code>message</code> event. Because the port rides inside a <code>postMessage</code>, every <code>message</code> listener on the receiving side gets <code>e.ports[0]</code> and can attach its own listener to it. A worker usually runs only your own scripts, so other listeners rarely get the port. A page inside an iframe often loads third-party scripts such as ads and analytics, and they can get the port too.</p>
<h2>From whom to whom</h2>
<p><code>postMessage</code> needs a handle to the other side before you can send. <code>BroadcastChannel</code> only needs both sides to open the same name. Here is each route, by where the message starts and where it ends:</p>
<ul>
<li><strong>page → iframe / popup</strong>: <code>window.postMessage</code>. The handle is <code>iframe.contentWindow</code>, or the return value of <code>window.open()</code>. Every listener on the receiving window hears it.</li>
<li><strong>page ↔ dedicated worker</strong>: the page calls <code>worker.postMessage</code>, the worker calls <code>self.postMessage</code>. The handle is the return value of <code>new Worker()</code>. Only these two hear it.</li>
<li><strong>page ↔ shared worker</strong>: both sides call <code>port.postMessage</code>. The page's port is <code>new SharedWorker().port</code>; the worker gets its port in <code>onconnect</code>. Each tab has its own port, and only the tab whose port the worker sends on hears it.</li>
<li><strong>page → service worker</strong>: <code>registration.active.postMessage</code>. The registration comes from <code>await navigator.serviceWorker.ready</code>.</li>
<li><strong>service worker → page</strong>: <code>client.postMessage</code>, one client per call. The client is <code>e.source</code>, or one of the results of <code>clients.matchAll()</code>. The page receives it on <code>navigator.serviceWorker</code>, not on <code>window</code>.</li>
<li><strong>worker ↔ a dedicated worker it created</strong>: written the same way as page ↔ dedicated worker. Both dedicated and shared workers can call <code>new Worker()</code>.</li>
<li><strong>two workers, neither created by the other</strong>: for example two dedicated workers the same page created, a dedicated worker and a shared worker, or any worker and a service worker. Neither side holds a handle to the other, so the page creates a <code>MessageChannel</code> and gives one end to each, or they use <code>BroadcastChannel</code>.</li>
<li><strong>unrelated same-origin tabs</strong>: <code>BroadcastChannel</code>. No handle needed; the same name is enough. Every context that opened that name hears it.</li>
</ul>
<p><code>MessageChannel</code> is not a separate route. It uses the <code>postMessage</code> of one of the routes above to hand a port over, and after that the two ends have a private line no one else receives. All three kinds of worker can call <code>new MessageChannel()</code> and <code>new BroadcastChannel()</code>, written the same way as in a page.</p>

<summary>MessageChannel — a private 1:1 port between any two contexts</summary>
<p>Picture one string with two tin cans (<code>port1</code>, <code>port2</code>). You call <code>new MessageChannel()</code>, keep one can, hand the other over; only the two holders hear it. A channel always has exactly these two cans. To connect a third party, create another <code>MessageChannel</code>.</p>
<p>The section "Private means handing over a port" showed a page running a line to its own worker. The same approach lets two workers talk directly. This example has three roles: the page, workerA and workerB. The page created both workers, so only the page holds handles to both; workerA and workerB have no handle to each other. The page creates one channel, gives <code>port1</code> to workerA and <code>port2</code> to workerB, and from then on the two workers talk directly, without the data passing through the page.</p>

<summary>Service worker — a proxy between its pages and the network</summary>
<p>Say one site has two tabs open, tabA and tabB, and the site's page registered a service worker with <code>navigator.serviceWorker.register('sw.js')</code>. Both tabs are controlled by the same <code>sw.js</code>, and to <code>sw.js</code> each one is a client. If tabA sends a message to <code>sw.js</code> first (code at the end of this section), <code>sw.js</code> can reply to tabA alone; <code>sw.js</code> can also send to tabA and tabB on its own, without waiting for either to send first.</p>
