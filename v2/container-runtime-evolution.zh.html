Kubernetes 從離不開 Docker 到不需要 Docker

k8scontainerinfrastructure

Kubernetes 以前少不了 Docker，現在不用了。從 1.5（2016 年 12 月）到 1.24（2022 年 5 月），Docker 才完全離開 kubelet 的呼叫路徑。這段期間出現過兩個轉接層。

第一個是 dockershim，Kubernetes 把它寫在 kubelet 裡，讓 kubelet 能接上 Docker。1.20（2020 年 12 月）宣布 dockershim 要淘汰之後，Mirantis 在 2021 年 4 月宣布把這份程式碼搬到新的 repo，改名 cri-dockerd 繼續維護。到了 1.24 真的把 dockershim 從 Kubernetes 刪掉時，還要用 Docker 的 cluster 就改接 cri-dockerd。

第二個是 cri-containerd，讓 kubelet 能直接接上 containerd。到了 containerd 1.1 版，cri-containerd 的程式碼改成內建在 containerd 裡的 plugin，就是現在 kubelet 透過 CRI（Container Runtime Interface）呼叫的那一段。

CRI 出現之前，Docker 為什麼寫死在 kubelet 裡

Kubernetes 在 2014 年開源，那時候講 container，大多就是指 Docker。Kubernetes 團隊後來回顧時寫道：「當時其實沒有太多別的選擇，而 Docker 是操作 container 的主流工具。」所以 kubelet 直接呼叫 Docker API，中間沒有抽象層，也沒有 interface。kubelet 呼叫 Docker，就跟一般程式呼叫 console.log 一樣直接。

這樣做沒什麼問題，因為 Kubernetes 當時只支援 Docker 這一種 runtime。只有一種實作的話，何必先做一層抽象呢？

rkt 出現，Kubernetes 定義 CRI

2014 年 12 月，CoreOS 發表了 rkt（念作 rocket）。它是另一個 container runtime，架構跟 Docker 不一樣，1.0 在 2016 年 2 月釋出。CoreOS 希望它能跑在 Kubernetes 底下。

要支援 rkt，就得在 kubelet 裡再寫一套 runtime 呼叫，而 Kubernetes 1.3（2016 年 7 月）也真的這樣做了，這個專案的暱稱叫 rktnetes。於是 Docker 跟 rkt 都透過一個「內部的、隨時會變動的 interface」直接接進 kubelet，Kubernetes 團隊說這種整合方式「帶來很重的維護負擔」。要是再來第三個 runtime，就得再寫第三套。

有了兩種實作之後，Kubernetes 就定義了一個 interface。Kubernetes 1.5（2016 年 12 月）推出 CRI（Container Runtime Interface），狀態是 alpha，底層是 gRPC API。kubelet 只講 CRI，任何實作了 CRI 的 runtime 都能接上來，kubelet 裡不必再替每個 runtime 寫專屬的程式碼。

1.5 的公告列出當時正在實作 CRI 的專案，有 cri-o、rktlet（給 rkt 用的）、frakti（跑在 VM 上的 runtime），還有內建在 kubelet 裡的 Docker CRI shim。containerd 的 CRI 實作要到 2017 年才出現。

rkt 促成了 CRI，可是 rkt 本身後來沒落了。Red Hat 在 2018 年 1 月宣布收購 CoreOS，而 Red Hat 那時已經在做 CRI-O。CNCF 在 2019 年 8 月把 rkt 封存。

Docker Engine 一直沒有支援 CRI

Docker 自己也有 orchestrator，叫 Swarm，做的事跟 Kubernetes 一樣，介面比較簡單。下 docker swarm init 就有一個 cluster，下 docker service scale web=5 就有五個 replica，不用寫 CRD，也不用 etcd。

Docker Engine 從來沒有實作 CRI，到 2026 年 10 月也還是只講 Docker 自己的 API。Kubernetes 團隊 2022 年的回顧寫道：「Docker Engine 被當成 container runtime 使用的歷史比 CRI 還早，而且 Docker Engine 跟 CRI 不相容。」找不到第一手的資料說明 Docker 一直沒加上 CRI endpoint 的原因。

不過 Kubernetes 推出 CRI 的同一版，就自己附上了 Docker 的 shim，所以 Docker 的使用者從來不必等 Docker 官方做一個。另外，2017 年替 containerd 做 CRI 支援的工程師裡，也有 Docker 的人（見下面的第一步）。

Kubernetes 自己寫了 dockershim

Kubernetes 不可能放掉 Docker，因為大部分 cluster 都跑在 Docker 上。

所以同樣在 1.5，kubelet 內建了一個給 Docker 用的 CRI shim，叫 dockershim，負責把 CRI 呼叫轉成 Docker API 呼叫。1.5 的公告把它叫做「第一步」，也就是「用 CRI 把 Docker 重新接回 kubelet」。dockershim 放在 Kubernetes 的程式碼裡，由 Kubernetes 維護，CRI 每改一次，dockershim 也得跟著改。

這篇說的 hop，是指一次跨 process 的呼叫。dockershim 編譯在 kubelet 裡，跟 kubelet 是同一個 process，所以 kubelet 呼叫 dockershim 不算一個 hop。

階段 0（2014–2016）：kubelet 裡直接寫 Docker 的呼叫（1.3 起還有 rkt 的）。沒有 interface。

階段 1（1.5，2016 年 12 月起）：有了 CRI，但 Docker Engine 不支援，Kubernetes 就在 kubelet 裡附上 dockershim。

kubelet（含 dockershim）→ Docker Engine → containerd → runc → container

從 kubelet 到 containerd 要兩個 hop：kubelet 呼叫 Docker Engine，Docker Engine 再呼叫 containerd。

Docker Engine 自己從 1.11（2016 年 4 月）起，就把執行 container 的工作拆給 containerd 跟 runc 這兩個獨立的 binary，containerd 管 container 的生命週期，runc 負責建立 container。所以 Kubernetes 呼叫 Docker 之後，Docker 還要再去呼叫 containerd。

Kubernetes 團隊在 2018 年的部落格裡比較過兩條完整的路徑。一台 node 上跑 105 個 Pod，一邊是內建 CRI plugin 的 containerd 1.1，另一邊是 Docker 18.03 CE 加 dockershim。containerd 這條路的 Pod 啟動延遲比較低，kubelet 的 CPU 用量少 30.89%，container runtime 的 CPU 用量少 68.13%，記憶體（RSS）則是 kubelet 少 11.30%、container runtime 少 12.78%。

這些百分比是兩條路徑整體的差距。Docker 那條路多了 dockershim 跟整個 Docker Engine，兩邊的軟體版本也不同，而那篇部落格沒有把各層分開量，所以這些差距不能全算在 dockershim 或 Docker Engine 其中一個頭上。原文也沒寫 Docker 那邊的「container runtime」算進哪些 process，可能只有 dockerd，也可能連底下的 containerd 一起算。

Kubernetes 2022 年的回顧說，這個 shim「從來就不打算當成永久的解法」，而且「替 kubelet 本身帶來很多不必要的複雜度」。它從 1.5（2016 年 12 月）一直留到 1.24（2022 年 5 月），大約五年半。

分三步把 Docker 拿掉

第一步：cri-containerd 跳過 Docker（2017，containerd 1.0）

既然 Docker Engine 只是把工作轉交給 containerd，kubelet 大可直接呼叫 containerd。

2017 年，Google、Docker、IBM、ZTE 跟浙江大學的工程師一起做了 cri-containerd。它是一個獨立的 daemon，負責把 CRI 呼叫轉成 containerd 的呼叫，功能完整的 alpha 版在 2017 年 9 月 25 日釋出，搭配 containerd 1.0（2017 年 12 月）使用。

階段 2：繞過了 Docker Engine，但多了一個 daemon。

kubelet → cri-containerd（獨立 daemon）→ containerd → runc → container

到 containerd 一樣是兩個 hop，只是中間那個 process 從 Docker Engine 換成了 cri-containerd。

Docker Engine 從路徑上消失，這算是進步。可是 cri-containerd 跟 containerd 還是兩個透過 gRPC 溝通的 daemon，部署跟維運都得多顧一個 process。

第二步：containerd 把轉接層併進自己（containerd 1.1，2018 年 4 月）

containerd 1.1 把 cri-containerd 的程式碼重構成一個 CRI plugin，直接內建在 containerd 裡，預設就開啟。plugin 用一般的函式呼叫操作 containerd，不再走 gRPC，那個獨立的 daemon 也就不需要了。

階段 3：CRI plugin 跟 containerd 是同一個 process。

kubelet → containerd（內建 CRI plugin）→ runc → container

kubelet 一個 hop 就到 containerd。

現在每一台用 containerd 的 node 都走這條路，路上的 CRI plugin 就是 cri-containerd 重構後的程式碼。containerd 收到呼叫之後，怎麼透過 shim 跟 runc 把 container 建出來，寫在〈Inside containerd: How shim and runc Actually Work〉。

第三步：Kubernetes 刪掉 dockershim（1.24，2022 年 5 月）

Kubernetes 1.20（2020 年 12 月）把 dockershim 標成 deprecated，1.24（2022 年 5 月）正式移除。kubelet 從此不能自己接 Docker Engine。還在用 Docker 的 cluster 要嘛換成 containerd 或 CRI-O，要嘛另外裝 cri-dockerd，讓 Docker 繼續當 runtime。

換掉 Docker 的 node 上，container 照常執行，但 node 上直接呼叫 Docker 的 script、設定跟工具都得跟著改。Kubernetes 的遷移文件〈Check whether dockershim removal affects you〉列了這些：

  • 在 privileged Pod 裡、node 的開機 script 裡，或是直接裝在 node 上的 monitoring、security agent 裡，執行 docker ps、systemctl restart docker.service 這類 Docker 指令
  • 寫在 /etc/docker/daemon.json 的 private registry、image mirror 設定，要搬到新 runtime 的設定檔
  • SSH 上 node 排錯時用的 docker ps、docker exec，換掉之後列不出 container
  • kubelet /metrics/cadvisor 的 container 名稱格式跟著 runtime 變了，檔案系統相關的 metrics 也少了一批
  • 把 node 上的 docker.sock mount 進 Pod，借 node 的 Docker 來 build image 的 CI

例子：CI mount 的 docker.sock

在用 Docker Engine 當 runtime 的 node 上，Docker Engine 會開一個 /var/run/docker.sock。有些 CI 會把 build job 當成 Pod 跑在 cluster 裡，再把這個 socket mount 進去，借 node 上的 Docker 來 build image。Kubernetes 的部落格把這種做法叫 Docker in Docker。

用 Docker 當 runtime 的 node 上有兩個 daemon：

  • Docker Engine → /var/run/docker.sock ← CI 的 Pod mount 的是這個
  • containerd → /run/containerd/containerd.sock ← Docker 內部用這個

node 改用 containerd 當 runtime、node image 也拿掉 Docker 之後，就只剩一個：

  • containerd → /run/containerd/containerd.sock ← kubelet 直接呼叫這個
  • Docker Engine → 沒了
  • docker.sock → 沒了

containerd 有自己的 socket，可是 docker build 不會講 containerd 的 API，它只認 Docker 的 socket。這是兩個不同的程式，協定也不一樣。

docker build → 找 /var/run/docker.sock → 檔案不存在 → 失敗

有兩種改法：

  1. node 上留著 Docker Engine，再用 cri-dockerd 把 kubelet 接到它 → docker.sock 還在 → pipeline 不用改
  2. 改用 buildah → 在 container 裡照著 Dockerfile build image → 不需要 Docker daemon，也不需要 socket

Kubernetes 的 dockershim FAQ 列了四個不用 Docker 就能 build image 的工具：img、buildah、kaniko 跟 buildkit-cli-for-kubectl。到 2026 年 10 月，kaniko 的 repo 在 2025 年 6 月封存了，buildkit-cli-for-kubectl 的 repo 也封存了，img 最後一次更新是 2024 年 5 月，四個裡還在持續更新的只有 buildah。

cri-dockerd 讓來不及改 pipeline 的團隊可以先繼續用下去，到 2026 年 10 月還在發新版（v0.4.9）。不過它的呼叫鏈比較長：

kubelet → cri-dockerd → Docker Engine → containerd → runc

從 kubelet 到 containerd 要三個 hop，直接用 containerd 只要一個。

同一段時間的另一條路：CRI-O

在 Docker 一步步被拿出路徑的同時，Red Hat 從零開始做了 CRI-O，1.0 在 2017 年 10 月釋出。CRI-O 專門為 Kubernetes 設計，沒有 Docker 的歷史包袱，不負責 build image，也沒有其他附加功能。它對上接 CRI，對下呼叫符合 OCI（Open Container Initiative）規格的 runtime，例如 runc。

kubelet → CRI-O → crun 或 runc → container

CRI-O 現在的設定檔預設用 crun，也可以改成 runc。

OpenShift 4 從 2019 年 6 月起就在 production 上跑 CRI-O。containerd 能做的事比較多，CRI-O 的主張是它本來就不需要做那麼多。

Docker 後來怎麼了

2019 年 11 月，Docker 把企業版業務賣給 Mirantis。11 月 13 日，Docker 宣布「Docker 故事的下一章，重心放在開發者身上」。重心移到 pipeline 的另一端，也就是 build image，跑 image 的事交給別人。

Docker 留下的Docker 失去的
Docker Desktop（開發者的本機環境）Kubernetes cluster 上的 runtime 位置
Docker Hub（image registry）Docker Enterprise（2019 年賣給 Mirantis；Swarm mode 本身還留在 Docker Engine 裡）
docker build（build image）大多數 Kubernetes cluster 所用 runtime 的身分
Docker Compose（本機多 container 開發）dockershim（Kubernetes 刪掉了，Mirantis 接手）

業界現在的樣子：

開發者的筆電：
  docker build → build image
  docker push → 推到 registry

Production Kubernetes cluster：
  kubelet → containerd → runc → container
  （這條路上完全沒有 Docker。）

Docker 把核心捐了出去

Docker 在 2015 年把 runc 捐給 OCI，2017 年把 containerd 捐給 CNCF，聽起來像是把最值錢的東西送人。2019 年 containerd 從 CNCF 畢業時，containerd 的 maintainer、同時也是 Docker 工程師的 Michael Crosby 說，目標是「分享一個穩固、可擴充的 runtime」。

現在 Kubernetes 的 node 直接跑 containerd，Docker Engine 也跑在 containerd 上，containerd 則由 CNCF 託管。
