這則訊息會送到誰手上？瀏覽器 messaging 整理

2025/08/02
browserweb-workerspostmessagemessagechannelfrontend

瀏覽器裡送訊息的方法有好幾種：window.postMessage、worker.postMessage、MessageChannel、BroadcastChannel，還有 service worker 跟它底下的頁面互傳。要從裡面挑一個，可以先問自己：

  1. 這則訊息實際上誰會收到？
  2. 能不能只讓指定的對象收到？

每一種 messaging API 對這兩個問題的答案都不一樣。

postMessage 其實是好幾個 method

postMessage 是好幾個不同 method 共用的名字，分別掛在不同的物件上：

看 targetOrigin 就分得出來。只有 Window 的版本要填 targetOrigin，因為另一端的 window 可能是別的 origin，瀏覽器要求寫明信任哪個 origin。worker 跟 client 的版本沒有 targetOrigin，因為它們本來就只在同一個 origin 裡（Client 是 service worker 手上代表某一個頁面的物件）。port（MessageChannel 的其中一端）也不用填，因為建立 channel 的人交出 port2 的時候，就已經選好收件人了。之後從 port1 送出的訊息只會到 port2，不必再檢查 origin。

有哪些角色

會收發訊息的有分頁（window）、分頁裡的 iframe 或 popup，以及三種 worker。它們各自跑在自己的 JavaScript 環境裡，下面把每一個都叫做一個 context。

  • Dedicated worker：一個頁面專用的執行緒，用 new Worker('a.js') 建立。頁面以外，dedicated worker 跟 shared worker 裡也能呼叫 new Worker()。
  • Shared worker：同一個 origin 的好幾個分頁共用一個 worker。就算每個分頁都呼叫一次 new SharedWorker('hub.js')，瀏覽器也只啟動一個 hub.js。new SharedWorker() 只能在頁面裡呼叫，worker 裡不行。
  • Service worker：像 proxy 一樣夾在一組頁面跟網路之間，用來做離線、cache、推播。不用 new，而是頁面呼叫 navigator.serviceWorker.register('sw.js') 向瀏覽器註冊。

那要怎樣才能只送給一個對象呢？

只送給一方：把 port 交出去

上一節的問題出在訊息走 message event，誰在上面掛了 listener 誰就收得到。要避開它，就改走一條只有兩端的線，也就是 MessageChannel。

worker.postMessage 的第二個參數是 transfer 清單。port2 交出去之後，頁面手上就沒有它了，只剩 worker 握著。之後頁面從 port1 送出的訊息只會到 port2，不經過任何 window 的 message event，所以頁面上其他 script 掛的 listener 都收不到。

交出 port 的那一步本身還是走 message event。因為 port 是夾在一則 postMessage 裡送過去的，對方那邊每個 message listener 都會拿到 e.ports[0]，也能在上面掛自己的 listener。worker 裡通常只有自己寫的 script，不太會有別的 listener 一起拿到 port。iframe 裡的頁面卻常常載了廣告、分析這類第三方 script，它們也能拿到這個 port。

從誰傳給誰

postMessage 要先拿到對方的 handle 才能傳，BroadcastChannel 只要兩邊開同一個名稱。照「從哪裡傳到哪裡」列出來：

  • 頁面 → iframe / popup：window.postMessage。handle 是 iframe.contentWindow，或 window.open() 的回傳值。對方 window 上每個 listener 都收到。
  • 頁面 ↔ dedicated worker：頁面用 worker.postMessage，worker 用 self.postMessage。handle 是 new Worker() 的回傳值。只有這兩方收到。
  • 頁面 ↔ shared worker：兩邊都用 port.postMessage。頁面的 port 是 new SharedWorker().port，worker 的 port 在 onconnect 拿到。每個分頁一個 port，worker 對哪個 port 送，就只有那個分頁收到。
  • 頁面 → service worker：registration.active.postMessage。registration 從 await navigator.serviceWorker.ready 拿到。
  • service worker → 頁面：client.postMessage，一次送一個 client。client 是 e.source，或 clients.matchAll() 的結果。頁面在 navigator.serviceWorker 上收，不是在 window 上。
  • worker ↔ 它自己建立的 dedicated worker：寫法跟頁面 ↔ dedicated worker 一樣。dedicated worker 跟 shared worker 裡都能呼叫 new Worker()。
  • 兩個 worker，誰都不是對方建立的：例如同一個頁面建的兩個 dedicated worker、dedicated worker 跟 shared worker、任何一種 worker 跟 service worker。兩邊都沒有對方的 handle，要由頁面建一條 MessageChannel 交給兩邊，或用 BroadcastChannel。
  • 不相干的同 origin 分頁：BroadcastChannel，不需要 handle，名稱相同就好。開了同一個名稱的每個 context 都收到。

MessageChannel 不算另一條路。它要借上面某一條路線的 postMessage 把 port 交出去，交過去之後，兩端之間就是一條別人收不到的專線。三種 worker 裡都能 new MessageChannel() 跟 new BroadcastChannel()，寫法跟在頁面裡一樣。

三種送法

postMessage：window 傳給 window（iframe、popup、opener）

這裡有三個角色。https://parent.example 上的頁面（下面叫 parent）嵌了一個 https://child.example 的 iframe，又用 window.open 開了一個同網址的 popup。iframe 跟 popup 都是 parent 產生的，所以 parent 手上有它們的 handle：iframe 的 contentWindow，跟 window.open 的回傳值。反過來，iframe 用 window.parent、popup 用 window.opener 拿到 parent 的 handle。

送訊息的一方要先握著對方的 handle 才能送。

parent 剛嵌好 iframe、剛開好 popup 時，它們的頁面可能還沒載入完，這時 parent 送出的訊息，iframe 跟 popup 都收不到。所以下面讓 iframe 跟 popup 載入完先送一則 ready，parent 收到之後，對 e.source（送來的那個 window）呼叫 postMessage 回覆。

跟自己沒有關係的分頁，因為手上沒有它的 handle，所以不能用這個方法傳，要改用 BroadcastChannel。

MessageChannel：任意兩個 context 之間的專線

想像一條線綁著兩個鐵罐（port1、port2）。new MessageChannel() 之後，自己留一個罐子、另一個交出去，只有拿著罐子的兩方聽得到。一條線上固定就這兩個罐子，要再接第三方，得再建一個 MessageChannel。

正文「只送給一方」示範了頁面怎麼跟自己的 worker 拉一條線。同樣的做法也能讓兩個 worker 直接互傳。這個例子有三個角色：頁面、workerA、workerB。兩個 worker 都是頁面建立的，所以只有頁面同時握著兩邊的 handle，workerA 跟 workerB 彼此沒有對方的 handle。頁面建一個 channel，port1 交給 workerA、port2 交給 workerB，之後兩個 worker 直接互傳，資料不經過頁面。

牽線的頁面不一定要是建立這兩個 worker 的那個，只要同時握著兩邊的 handle 就行。例如一個分頁同時連著 hub.js 跟 hub2.js 兩個 shared worker，就能用同樣的方式讓兩個 hub 直接互傳，只是交 port 要走各自的 .port.postMessage：

BroadcastChannel：廣播給同一個名稱上的所有人

這裡有四個角色，都在同一個 origin 底下：

  • tab1、tab2：同一個網站開的兩個分頁。
  • sw：這個網站註冊的 service worker，程式在 sw.js。
  • logout.js：tab1 用 new Worker('logout.js') 建立的 dedicated worker。

它們彼此不需要任何 handle，只要都 new BroadcastChannel('app')，就連上同一個 channel。

logout.js 呼叫一次 postMessage，tab1、tab2 跟 sw 都會收到 logout。發出訊息的 worker 自己那個 bc 收不到；如果同一個 worker 裡再 new BroadcastChannel('app') 一個，新的那個會收到。

service worker 閒置一段時間會被瀏覽器停掉，停掉期間送出的 BroadcastChannel 訊息它收不到，之後啟動也補不回來（Chrome 153 實測）。一定要它收到的訊息，就從頁面用 (await navigator.serviceWorker.ready).active.postMessage(msg) 送，這樣會把它喚醒。

三種 worker

Dedicated worker：一個頁面專用的執行緒

兩個角色：頁面，跟頁面用 new Worker('crunch.js') 建立的 worker。worker 只跟建立它的頁面溝通，頁面握著 worker，worker 裡用 self 回給頁面。

Shared worker：很多分頁共用一個 worker

假設同一個網站開了三個分頁：tabA、tabB、tabC。三個分頁的程式都呼叫 new SharedWorker('hub.js')，瀏覽器只會啟動一個 hub.js，三個分頁連到的都是它。這裡的 hub.js 就是 shared worker 本身的程式檔。

每個分頁連進來，hub.js 就拿到一個新的 port 物件。port 身上沒有名字也沒有 id，hub.js 分不出哪個 port 是哪個分頁的。下面的寫法是讓分頁一連上就報自己的 id，hub.js 用這個 id 當 key，把 port 存進 Map。

Service worker：夾在頁面跟網路之間的 proxy
