把 Go server 部署到 ECS Fargate，從 docker push 一路到 HTTPS

2024/09/29
awsfargateecsecrgolangelbroute53

我要在 AWS 上部署一個用 Go 寫的 HTTP server，用的是 ECS（Elastic Container Service）加 Fargate。用 Fargate 的話，跑 container 的機器由 AWS 準備，我只要指定 image，再寫明 CPU 跟 memory 的大小。在自己的電腦上，docker build、push、run 三個指令就好。到了 AWS，這三個指令變成 Task Definition、Capacity Provider、Service 跟 Target Group，每一個都要自己設定，也要知道它們之間的關係。

Docker 的部分很簡單

會用 Docker 的話，這部分大多已經會了。一樣是 build、tag、push，只是 registry 的網址換成 ECR 的。ECR 是 Elastic Container Registry，AWS 自己的 image registry。

接著再兩步就能跑起來：

  1. 在 ECS 建一個 Task Definition，image 指向 123456789.dkr.ecr.us-west-2.amazonaws.com/my-app:latest
  2. 啟動一個 Service 或 Task，選這個 task definition 然後執行

Task Definition 之於 ECS，就像 AMI（Amazon Machine Image）之於 EC2，兩個都是藍圖，不過 Task Definition 簡單得多。AMI 是一份磁碟映像，裡面有整個作業系統、裝好的軟體跟設定。Task Definition 只描述 container、資源上限跟環境變數。每台 EC2 都是從某個 AMI 開機的，只是 AWS 有現成的 AMI，很少需要自己做。Task Definition 就沒有現成的，建 Service 或 Task 之前一定要自己先寫好。

build 成功，跑起來才壞掉的 Go binary

一個常見的 multi-stage Dockerfile：

CGO_ENABLED 跟 GOARCH 只要有一個設錯，build 照樣成功，binary 卻沒辦法在 Fargate 上執行。

CGO_ENABLED=0

Go 的標準函式庫大多是用 Go 寫的，只有兩個地方可能改去呼叫系統的 C library，一個是 net 的 DNS 查詢，另一個是 os/user 查詢使用者跟群組。設了 CGO_ENABLED=0，compiler 就會用純 Go 的版本，不去 link 系統的 C library。

如果沒設，在 golang:1.22 裡 build 的時候（這是一個內建 gcc 的 Debian image），只要目標架構跟 build 機器相同（例如在 amd64 的 CI 上 build），cgo 預設就是開的，所以 binary 會用 dynamic link 的方式依賴 glibc。而 Alpine 用的是 musl，沒有 glibc，所以 container 一啟動就結束了，錯誤訊息也沒提到 library：

exec ./main: no such file or directory

./main 其實就在那裡，但 binary 要求的 glibc loader 不在（我在 arm64 的 Mac 上重現時，它要的是 /lib/ld-linux-aarch64.so.1）。

如果程式真的需要呼叫 C，例如透過 mattn/go-sqlite3 使用 SQLite，或是某些繪圖 library，那就設成 1，而且執行用的 base image 要跟 build image 用同一種 C library。

GOARCH=amd64

ECS Fargate 只支援 X86_64 跟 ARM64 兩種架構，預設是 X86_64。

沒設 GOARCH 的話，Go 會照執行 build 的那台機器的架構來編譯。在 M1/M2 的 Mac 上，docker build 是在一台 arm64 的 Linux VM 裡跑的，所以編譯出來的 binary 是 arm64。當時 image 推上 ECR 沒問題，Fargate 也把 image 拉下來了，啟動時才出現：

exec ./main: exec format error

binary 是 arm64，Fargate 的環境卻是 X86_64，兩邊的架構不同。所以要指定 GOARCH=amd64；如果 Task Definition 選的是 ARM64，就指定 arm64。

"When you register a task definition, you specify the CPU architecture. The valid values are X86_64 and ARM64." Default: X86_64 — Amazon ECS task definition parameters

GOARCH 只會改變 binary 的架構。在 Mac 上 build 出來的 image，標示的平台還是 linux/arm64，裡面 Alpine 那一層也是 arm64。要讓整個 image 都是 amd64，就用 docker build --platform linux/amd64。

Service 跟 Task 有什麼不同

Task 是真正在跑的單位。 在 ECS 上跑的每個 container，都屬於某一個 Task。

Service 是疊在 Task 上面的管理層。 Service 負責「維持 N 個 task 在跑」，另外還有 auto scaling、load balancing 跟 rolling deployment。

我建了一個 3 個 replica 的 Service，畫面上除了這個 Service，還多了三個 Task。Service 沒有取代 Task，那三個 Task 就是 Service 開出來的。

TaskPod
ServiceDeployment + Service

長時間跑的 HTTP server 用 Service；一次性的 batch job、CI/CD 的某個步驟或 cron，用 Task。

在 console 裡，Service 跟 Task 的設定畫面幾乎一樣。選「Run new Task」，再把設定改得跟 Service 差不多，也是可以的。Service 有一個 Task 沒有的 scheduler，它會維持 task 的數量、補上停掉的 task，還會把 task 註冊到 load balancer。

Capacity Provider：為什麼「選 Fargate」有兩種選法

建 Service 的時候，ECS 會問要用 Launch Type 還是 Capacity Provider Strategy。

Launch Type 很單純，選 FARGATE 或 EC2 就好，要跑在自己的機器上則選 EXTERNAL。Fargate Spot 不在這份清單上，只能透過 capacity provider strategy 使用。

Task Definition 本身也有 launch type 的設定。我把自己那份 Task Definition 的 launch type 設成 EC2，改用 Fargate 啟動還是跑起來了。照 AWS 文件的說法，ECS 在註冊 task definition 時會照這個設定（requiresCompatibilities）檢查參數，但文件沒提到 task 啟動時還會再檢查一次。我的 definition 能在 Fargate 上跑，大概是因為它本來就符合 Fargate 的要求，用的是 awsvpc network mode，也設了 task 層級的 CPU 跟 memory。

Capacity Provider Strategy 是為了在正式環境省錢。它可以把 Fargate（穩定、比較貴）跟 Fargate Spot（便宜、可能被中斷）混著用，比例由兩個參數控制：

  • base：某一個 provider 至少要跑幾個 task。一個 strategy 裡只有一個 provider 能設 base，其他的預設是 0。
  • weight：base 分完之後，剩下的 task 照這個比例分配。

舉個例子，總共 12 個 task，Fargate 的 base=3、Spot 的 base=0，weight 是 1:2。

FargateFargate Spot
base30
weight12
結果6（3 + 3）6（0 + 6）

Fargate 先拿到 base 的 3 個，還剩 9 個。照 1:2 分成 3 個跟 6 個，所以 Fargate 總共 6 個，Spot 也是 6 個。

單獨執行的 Task 只在啟動那一次用到 strategy，Service 則會一直照著它來。Fargate Spot 中斷某個 task 之後，service 會再開一個補上，而且還是開在 Fargate Spot 上，不會改用一般的 Fargate。

只有一台 server，為什麼也要用 ALB

沒有 ALB（Application Load Balancer）的話，使用者要透過 task 的 public IP 連進來。可是 task 每次重啟，IP 都會變，使用者沒辦法把它存成書籤。要上 HTTPS，就得把憑證放進 container，自己負責更新。

ALB 靠 target group 解決這些問題。ECS 把 task 註冊進 target group，ALB 再把流量轉給 target group，對外就只有一個固定的 DNS 名稱。

多個 service 也可以共用同一個 ALB：

  • domain.app/api → target group backend
  • domain.app/ → target group landing-page

建 Service 時，Load Balancing 那一區可以指定 target group。指定之後，ECS 會把這個 service 的 task 註冊進去，ALB 就會把流量送給這些 task。

從 ALB 到自訂網域的 HTTPS

  1. 在 port 443 加一個 HTTPS listener，選用這個網域在 ACM（AWS Certificate Manager）的憑證。
  2. 把 port 80 的 HTTP listener 設成 redirect 到 HTTPS。
  3. 在 Route 53 建一筆 A record alias，把網域指到 ALB 的 DNS 名稱。

做完就有自訂網域跟 HTTPS，server 上也不用管理任何憑證。

如果 task 本身正常，load balancer 卻回 502，原因幾乎都出在 target group 的 protocol。這部分另外寫在〈為什麼我的 load balancer 回 502〉。

一開始就該做的設定

要是再來一次：

  1. 一開始就用 Capacity Provider Strategy，不要用 Launch Type。就算現在只用 Fargate，之後要加 Spot，改 strategy 就好。
  2. 一定要指定 GOARCH。少了它，build 跟 push 都會成功，要到 Fargate 上才會出錯。
  3. 第一天就把 ALB 放在前面。AWS 的 ELB 價目頁列的 us-east-1 價格是一小時 0.0225 美元，一個月大約 16 美元，另外每個 LCU（Load Balancer Capacity Unit，照流量跟連線數計算的用量單位）一小時 0.008 美元。之後才補 HTTPS 跟固定的 DNS 名稱會很麻煩。
  4. 要一直跑的東西用 Service，不要用 Task。單獨執行的 Task 停掉就停了，Service 會再開一個補上。
