搬 DNS，網站會跟著搬走嗎

不會，你原本在 Squarespace DNS 大部分指向 GitHub，你現在從 Squarespace 搬到 Cloudflare，但也都指向 GitHub，根本還是跟原來一樣，網站檔案都是放在 GitHub！

搬家前  訪客 → 問 Google 的 nameserver     → 185.199.108.153（GitHub） → GitHub 回網頁
搬家後  訪客 → 問 Cloudflare 的 nameserver → 185.199.108.153（GitHub） → GitHub 回網頁

怎麼把 record 搬到 Cloudflare

把 Squarespace DNS Settings 頁上的 record 全部照 Berkeley Internet Name Domain（BIND）格式寫成一個 txt 檔，在 Cloudflare 的 DNS → Records 用 Import DNS Records 上傳：

$ORIGIN whateveryoucall.com.
$TTL 3600
alpha        IN CNAME <user>.github.io.
bravo        IN CNAME <user>.github.io.
...
delta        IN NS    ns-2048.awsdns-64.com.
...

（<user> 是放網頁的 GitHub 帳號。）

匯入之後，Cloudflare 上的 record 就跟 Squarespace 上的一樣。

匯入的 record 預設會打開 Proxied

Cloudflare 每一筆 A、AAAA、CNAME 都有一個雲朵開關。Import 對話框裡的 Proxy imported DNS records 預設是勾的，所以匯入的 record 全部是橘色的 Proxied，取消勾選就會匯入成 DNS only：

訪客查 alreadyhascert.whateveryoucall.com 得到網頁流量經過
GitHub 的 IP訪客 → GitHub
Cloudflare 的 IP訪客 → Cloudflare → GitHub

Proxied 的時候，Cloudflare 就是 GitHub 前面的 reverse proxy。 訪客查 DNS 只拿到 Cloudflare 的 IP，連到 Cloudflare 之後，Cloudflare 再照 CNAME <user>.github.io 把請求轉給 GitHub，這筆 CNAME 只留在 Cloudflare 內部用。因為 Cloudflare 站在中間，所以可以做快取、攔下攻擊。它轉送的只有網頁流量，所以雲朵開關只出現在瀏覽器找網站時會查的 record 上：

  • A、AAAA： 瀏覽器用它拿到網站的 IP。
  • CNAME： 瀏覽器先拿到另一個名字（例如 <user>.github.io），再去查這個名字的 IP。

另外三種不是瀏覽器在查，所以沒有開關：

  • MX： 寄信過來的郵件伺服器用它找收信的主機。
  • NS： resolver 用它找這個網域歸哪台 nameserver 管。
  • TXT： Google、GitHub 這類服務用它讀驗證用的文字。

可是 GitHub Pages 的子網域開 Proxied 有個疑慮：GitHub 替 custom domain 申請 https 憑證之前會先查 DNS，開了 Proxied，查到的就是 Cloudflare 的 IP，GitHub 可能就不申請了。在 Squarespace 時這些 record 都相當於 DNS only，所以我把它們全部點回灰色，只留 alreadyhascert 一筆 Proxied 當實驗，GitHub 到底會不會申請，後面有實測。

匯入的 _domainconnect CNAME 要不要刪

匯入的 record 其中一條，它是 Squarespace 原本就有的：

CNAME  _domainconnect  _domainconnect.domains.squarespace.com

它給 Domain Connect 協定用，讓別的服務能自動幫你新增 record。例如在 Google Workspace 設定用 whateveryoucall.com 收信，Google 會先查這筆，知道 DNS 哦原來歸 Squarespace 管，再把你帶到那一家的授權頁。

搬到 Cloudflare 之後，這筆留著或刪掉都一樣。Cloudflare 對 _domainconnect 的 TXT 查詢一律回自己的值，Google 查的是 TXT，所以會走到 Cloudflare。我把它刪了，讓 Records 清單少一筆用不到的 record；Squarespace 上原本那筆沒有動。

兩家查 _domainconnect 的路徑分成兩組，同一個步驟用同一個編號，第 1 步兩家就不一樣：

① 搬家前，DNS 在 Squarespace

② 搬家後，DNS 在 Cloudflare

Google 在 TXT 的值後面接上 /v2/whateveryoucall.com/settings 去打，Cloudflare 回的授權頁是 https://dash.cloudflare.com/domainconnect，所以同樣的流程現在會走到 Cloudflare。

一般的 DNS，一個名字有了 CNAME，問什麼都先回 CNAME，① 的 Squarespace 就是這樣；Cloudflare 在 _domainconnect 這個名字上不照這條走。

HiNet 還是偶發性會回 Google，是因為 resolver 會把舊的答案快取，而同一個 resolver 位址背後有很多台機器，每台的快取過期時間不一樣。TLD 上這一行的 TTL 是兩天，所以這兩天裡 Squarespace 上的 record 要留著。要是提早刪掉，用 HiNet 的人就有小機率打不開網站。

DNSSEC 跟換 nameserver，誰先誰後

先在 Squarespace 關 DNSSEC，等一天；再換 nameserver，等兩天；最後在 Cloudflare 開 DNSSEC，把 DS 貼回 Squarespace。但其實我當時沒等這麼久，就沒問題的樣子就是。

resolver 查網址像在問路：

1. resolver 問窗口（.com）：whateveryoucall.com 要去問誰？
2. 窗口回：去問 ada.ns.cloudflare.com、bob.ns.cloudflare.com（NS）
3. resolver 問 NS：whateveryoucall.com 在哪？
4. NS 回：185.199.108.153

沒開 DNSSEC 的時候，第 4 步誰先回答 resolver 就信誰，攻擊者可以搶在 NS 前面回一個假 IP。開了 DNSSEC，多了兩樣東西：

  • 第 2 步，窗口除了指路，還登記了「NS 的回答要用哪把鑰匙簽名」，這筆叫 DS（Delegation Signer）。
  • 第 4 步，NS 回答時附上簽名，叫 RRSIG（Resource Record Signature）。

resolver 拿 DS 比對 RRSIG，比對成功才收下。

搬家時 NS 跟 DS 都一定會跟著調整，兩個都在 Squarespace 那邊改設定。可是 resolver 會把舊的存在快取裡，NS 最長兩天、DS 最長一天，這段時間它可能拿著舊的 DS 去問新的 NS，或拿著新的 DS 去問舊的 NS。問到的那台 NS 沒有 DS 指定的那把鑰匙，簽名就驗不過，resolver 回 SERVFAIL；.com 上沒有 DS，resolver 就不驗。下面可以切換 DS 跟 NS 的組合：

「開在 Google」配「Cloudflare 的 nameserver」，就是 DNSSEC 沒關就換了 NS：DS 要 Google 的鑰匙，Cloudflare 沒有，網站跟信都查不到。

步驟做什麼要等多久這次等了
1. 關 DNSSEC在 Squarespace 關掉，DS 跟 Google 的簽名會同時撤掉一天，等 DS 的快取過期三分鐘
2. 換 NS在 Squarespace 改成 Cloudflare 的 nameserver兩天，等 NS 的快取過期三小時
3. 開 DNSSEC在 Cloudflare 開，再把 DS 貼到 Squarespace不用等

步驟 1 那一天也有風險：DS 跟 Google 的簽名在同一分鐘消失，快取裡還留著舊 DS 的驗證型 resolver 一樣會 SERVFAIL。撤 DS 那一刻對 8.8.8.8、1.1.1.1、9.9.9.9 各查一次，快取裡都沒有舊 DS，之後也沒有發現哪個子網域打不開。HiNet 換 NS 半天後還有 4% 問到 Google，不過它剛好不驗證 DNSSEC。

DS、DNSKEY、RRSIG 實際長什麼樣子

resolver 從根開始一層一層驗：先確認 .com 的鑰匙，再用 .com 上的 DS 確認 Cloudflare 的 DNSKEY，最後用這把 DNSKEY 驗 A 旁邊的 RRSIG。

在 Cloudflare 按下 Enable DNSSEC 之後：

  1. Cloudflare 產生兩組鑰匙對，就是 257 跟 256。私鑰留在 Cloudflare，公鑰放進 zone，成為那兩筆 DNSKEY。
  2. Cloudflare 用 256 的私鑰替 A、CNAME、MX、TXT 簽名，用 257 的私鑰替 DNSKEY 那一組簽名，簽出來的就是 RRSIG。Cloudflare 是在回答的當下才簽名，每次查詢拿到的 RRSIG，有效期都是從查詢時間往前、往後各 25 小時。
  3. Cloudflare 把網域名稱跟 257 的公鑰一起做 SHA-256，算出 DS，顯示在 dashboard。DS 複製到 Squarespace 的 DNSSEC 頁之後，Squarespace 送給 .com，.com 再用自己的私鑰替它簽名，就是 RRSIG DS。

分成兩把，是為了方便換鑰匙。256 簽的東西多，可以常換，換了只要 257 重簽一次 DNSKEY；257 一換，DS 就要跟著換，又得到 Squarespace 貼一次，所以 257 盡量不動。

拿不到憑證，網站為什麼還能打開

瀏覽器拿到的是 Cloudflare 的憑證，Cloudflare 再自己去連 GitHub。這個網域的 SSL/TLS 模式是 Full，不檢查 origin 的憑證，所以就算 GitHub 那張過期了，網站還是能打開，瀏覽器的鎖頭顯示的也是 Cloudflare 的憑證。

要是變成 Full (strict)，過期的 origin 憑證會讓 Cloudflare 回 526。現在的 Full 是 Automatic SSL/TLS 自動選的，它只升不降。續約時 GitHub 會不會再跑一次 https_eligible?，文件沒寫，這次也沒等到續約；如果會，Proxied 的子網域就續不了約，到時又升成 Full (strict) 的話就會變成 526。

所以 GitHub Pages 的子網域全部維持 DNS only，alreadyhascert 也改回灰色，測試用的 brandnewnocert 的 repo 跟 record 都刪了。

換 NS 兩天後，舊的 Google nameserver 不會再被問到，到時把 Squarespace DNS Settings 上的 record 全部刪掉，搬家才算結束。

題外話：留在 DNS 上的 CNAME 被佔用？

搬家之後，某個 repo 刪了，CNAME 忘記跟著同步刪除，會有什麼風險？

oldpage.whateveryoucall.com  CNAME  <user>.github.io     ← repo oldpage 已經刪了

陌生人在他自己的 repo 填上 oldpage.whateveryoucall.com 當 custom domain，GitHub 檢查 DNS，發現這個名字確實指向 GitHub，就會放行。GitHub Pages 的 IP 是所有人共用的，GitHub 只看這個網址被哪個 repo 認領，所以訪客打開 oldpage.whateveryoucall.com，看到的就是陌生人的網頁。整個過程他不用碰我們的 Cloudflare，就這樣鳩佔鵲巢，這叫 domain takeover。

其實 GitHub 有提供機制擋這件事，就是驗證網域：在 GitHub 帳號的 Settings → Pages 加入 whateveryoucall.com，照它給的值在 DNS 新增一筆 TXT _github-pages-challenge-<user>.whateveryoucall.com，再按 Verify。能在 DNS 上放這筆 TXT 的，只有網域的主人，所以驗證之後，只有這個帳號底下的 repo 能用 whateveryoucall.com 跟它的第一層子網域，陌生人填了會被拒絕。這筆 TXT 要一直留著；另外，它只管 GitHub Pages，指向其他服務的 CNAME 還是要記得刪。
